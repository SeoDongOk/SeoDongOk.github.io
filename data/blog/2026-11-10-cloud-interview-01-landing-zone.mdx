## 이 글에서 답할 면접 질문

- 회사가 클라우드를 처음 본격적으로 쓴다면, 첫 3개월 동안 무엇부터 만들겠는가?
- 계정(프로젝트, 구독)은 어떤 기준으로 나누는가? 하나로 쓰면 왜 안 되는가?
- 개발자가 실수로 위험한 설정을 못 하게 하려면 어떻게 하는가? 막는 것과 찾아내는 것의 차이는?
- 사람의 로그인과 권한은 어디서 관리하는가? 클라우드마다 사용자를 따로 만드는가?
- 여러 팀의 네트워크를 어떻게 연결하고, 인터넷으로 나가는 길은 어떻게 통제하는가?
- 감사 로그는 어디에 모으고, 누가 지울 수 없게 하는가?
- 공통 기반 자체는 누가, 어떻게 바꾸는가? 콘솔 클릭으로 바꾸면 안 되는 이유는?
- 플랫폼 팀이 "통제하는 부서"가 아니라 "쓰고 싶은 서비스"가 되려면 무엇이 필요한가?

## 개념과 배경

### 왜 공통 기반이 필요한가

클라우드는 신용카드 한 장으로 계정을 만들고 바로 서버를 띄울 수 있다. 처음 한두 팀이 쓸 때는 이 속도가 장점이다. 문제는 팀이 열 개, 서른 개로 늘어날 때다.

- 팀마다 계정을 따로 만들고, 비밀번호와 권한을 따로 관리한다. 퇴사자의 접근을 끊으려면 계정 서른 개를 돌아다녀야 한다.
- 네트워크 대역을 팀마다 아무렇게나 잡는다. 나중에 서로 연결하려고 보니 `10.0.0.0/16`이 다섯 곳에서 겹친다.
- 어떤 팀은 감사 로그를 켜고 어떤 팀은 끈다. 사고가 나도 누가 무엇을 했는지 알 수 없다.
- 공개 버킷, 모든 IP에 열린 SSH 포트 같은 설정이 어딘가에 하나쯤은 반드시 생긴다.
- 청구서는 한 장으로 오는데, 어느 팀이 얼마를 썼는지 아무도 모른다.

이 문제를 팀마다 각자 풀게 두면 같은 일을 서른 번 하고, 그중 몇 번은 틀린다. 그래서 **모든 팀이 올라탈 공통 바닥**을 먼저 깐다. 이 바닥을 AWS와 Azure는 **랜딩 존**(landing zone)이라고 부르고, GCP는 비슷한 것을 **기반**(foundation)이라고 부른다. 이름은 달라도 내용은 같다.

### 랜딩 존이 담는 것

랜딩 존은 "새 팀이 클라우드에 도착했을 때 이미 갖춰져 있어야 하는 것들"의 묶음이다.

| 영역 | 무엇을 정하나 |
|---|---|
| 자원 계층 | 조직 아래 계정·프로젝트를 어떻게 나누고 묶나 |
| 신원과 접근 | 사람과 프로그램이 어떻게 로그인하고 어떤 권한을 받나 |
| 가드레일 | 절대 하면 안 되는 일을 어떻게 막고 찾아내나 |
| 네트워크 | 대역, 연결, 인터넷 출입구, DNS |
| 로그와 감사 | 무엇을 기록하고 어디에 모으나 |
| 보안 기준선 | 위협 탐지, 취약 설정 점검, 암호화 |
| 비용 | 태그, 예산, 비용 배분 |
| 자동화 | 이 모든 것을 코드로 만들고 새 계정을 자동으로 발급 |

면접에서 "공통 기반을 설계해 보라"는 질문을 받으면 이 표의 순서대로 말하면 빠지는 것이 없다. 핵심은 **기술 목록이 아니라 "왜 그 순서인가"**다. 신원과 계층이 먼저인 이유는, 그 위에 모든 권한과 정책이 붙기 때문이다. 네트워크가 그다음인 이유는, 대역을 한 번 잘못 잡으면 나중에 바꾸기가 가장 어렵기 때문이다.

## 깊게 1: 자원 계층

### 세 클라우드의 계층 구조

세 클라우드 모두 "조직 → 묶음 → 실제 자원을 담는 단위" 구조를 갖고 있다. 이 계층이 중요한 이유는, **정책과 권한이 위에서 아래로 상속**되기 때문이다. 위에 한 번 걸면 아래 전체에 적용된다.

```
AWS
Organization (관리 계정)
 └ 루트
    └ OU (조직 단위)
       └ 계정 ← 자원이 사는 곳
```

```
GCP
조직 (도메인에 연결)
 └ 폴더 (중첩 가능)
    └ 프로젝트 ← 자원이 사는 곳
```

```
Azure
Entra ID 테넌트
 └ 루트 관리 그룹
    └ 관리 그룹 (중첩 가능)
       └ 구독
          └ 리소스 그룹 ← 자원
```

| 역할 | AWS | GCP | Azure |
|---|---|---|---|
| 최상위 | Organization | 조직 | 테넌트·루트 관리 그룹 |
| 묶음 | OU | 폴더 | 관리 그룹 |
| 격리 단위 | 계정 | 프로젝트 | 구독 |
| 그 안의 묶음 | (태그로) | (라벨로) | 리소스 그룹 |

차이점도 알아 두자.

- **AWS**: 계정이 가장 강한 경계다. 계정 사이에는 기본적으로 아무 권한도 없고, 명시적으로 열어 줘야 한다. 그래서 AWS 설계는 "계정을 많이 만드는" 쪽으로 간다.
- **GCP**: 프로젝트가 격리 단위지만, IAM 권한이 조직·폴더에서 상속되기 때문에 **폴더 구조 = 권한 구조**가 된다. 프로젝트를 만드는 비용이 낮아서 서비스마다, 환경마다 프로젝트를 나누는 게 자연스럽다.
- **Azure**: 구독이 청구와 한도의 경계이고, 리소스 그룹은 "함께 만들고 함께 지우는 자원의 묶음"이다. 권한(RBAC)은 관리 그룹, 구독, 리소스 그룹, 개별 자원 어느 범위에나 줄 수 있다.

### 무엇을 기준으로 나누나

계정(프로젝트, 구독)을 나누는 기준은 대개 네 가지다.

1. **환경**: 운영, 스테이징, 개발. 가장 먼저, 가장 강하게 나눈다. 개발자가 개발 계정에서 마음껏 실험해도 운영에 닿을 수 없게 하는 것이 목적이다.
2. **워크로드(서비스)**: 결제, 회원, 검색처럼 서비스 단위. 한 서비스의 장애나 침해가 다른 서비스로 번지지 않게 한다.
3. **조직(팀·사업부)**: 비용 책임과 권한 관리 단위. 다만 조직 개편이 잦은 회사에서 팀 기준으로만 나누면 계정 이름과 실제 주인이 금방 어긋난다.
4. **공통 기능**: 로그 보관, 보안 도구, 네트워크 허브, 공용 서비스. 이것들은 서비스 계정과 분리해서 플랫폼 팀이 관리한다.

여기서 면접관이 듣고 싶은 단어는 **폭발 반경**(blast radius)이다. 계정을 나누는 이유는 결국 "사고가 났을 때 피해가 어디까지 번지는가"를 제한하는 것이다.

- 키 하나가 털렸을 때, 그 키로 접근할 수 있는 범위가 계정 하나에 갇힌다.
- 한 계정에서 실수로 한도(API 호출, 인스턴스 수)를 다 쓰더라도 다른 계정은 영향이 없다.
- 계정 단위로 청구가 나오므로 비용 책임이 자동으로 나뉜다.

반대로 너무 잘게 나누면 비용이 생긴다. 계정 사이 통신을 위해 네트워크 연결과 권한 위임이 늘고, 관리할 대상이 늘어난다. 그래서 "많이 나누되, **만들고 관리하는 일은 자동화**한다"가 정답에 가깝다.

### 전형적인 OU 구조 (AWS 예)

AWS가 권장하는 다중 계정 구조를 단순화하면 이렇다.

```
루트
├ Security OU
│  ├ 로그 보관 계정
│  └ 보안 도구 계정
├ Infrastructure OU
│  ├ 네트워크 허브 계정
│  └ 공용 서비스 계정
├ Workloads OU
│  ├ Prod OU → 서비스별 운영 계정
│  └ NonProd OU → 개발·스테이징
├ Sandbox OU → 개인 실험 계정
└ Suspended OU → 폐기 대기 계정
```

OU를 나누는 기준은 **"같은 정책을 받는가"**다. 운영 계정들은 강한 제약을, 샌드박스는 느슨한 제약과 예산 상한을 받는다. 그래서 OU는 조직도를 그대로 옮기는 것이 아니라 **정책 묶음**으로 설계한다. 이 점을 말할 수 있으면 "계층을 이해한다"는 신호가 된다.

관리 계정(Organization을 만든 계정)에는 서비스 자원을 두지 않는다. 관리 계정은 SCP의 영향을 받지 않고 조직 전체에 강한 권한을 가지므로, 여기에 업무 자원을 두면 가장 강한 계정이 가장 많이 노출된다.

## 깊게 2: 가드레일

### 막기와 찾아내기

가드레일은 "넘으면 안 되는 선"이다. 두 종류가 있다.

| 종류 | 언제 동작하나 | 예 |
|---|---|---|
| 예방형 | 요청하는 순간 거부 | 허용 리전 밖 자원 생성 금지 |
| 탐지형 | 만든 뒤 찾아서 알림·교정 | 공개된 버킷 찾기 |

예방형이 강하지만 모든 걸 예방형으로 걸 수는 없다. 조건이 복잡하거나 예외가 많은 규칙을 예방형으로 걸면 정당한 작업까지 막혀서, 결국 "가드레일을 끄는" 요청이 쏟아진다. 그래서 보통 이렇게 나눈다.

- **절대 깨지면 안 되는 몇 개**는 예방형으로: 감사 로그 끄기 금지, 허용 리전 제한, 루트 사용자 사용 금지, 조직 탈퇴 금지.
- **나머지 대부분**은 탐지형으로: 발견하면 알리고, 가능하면 자동으로 고친다.

### 클라우드별 도구

| 클라우드 | 예방형 | 탐지형 |
|---|---|---|
| AWS | SCP, RCP | Config 규칙, Security Hub |
| GCP | 조직 정책 | Security Command Center |
| Azure | Azure Policy (Deny) | Azure Policy (Audit), Defender |

- **AWS SCP**(서비스 제어 정책): OU나 계정에 붙여서 "이 범위에서는 이 API를 절대 못 쓴다"를 정한다. 중요한 점은 **SCP는 권한을 주지 않는다**는 것이다. 허용 상한선만 정한다. 실제 권한은 여전히 IAM 정책이 줘야 하고, 둘 다 허용해야 동작한다. 면접 단골 함정이다. 자원 쪽 상한을 정하는 RCP(자원 제어 정책)도 있다.
- **GCP 조직 정책**: 조직·폴더·프로젝트에 "외부 IP를 가진 VM 금지", "허용 리전", "서비스 계정 키 생성 금지" 같은 제약(constraint)을 건다. IAM과는 별개의 축이다. IAM은 "누가 무엇을 할 수 있나", 조직 정책은 "누가 하든 이 설정은 안 된다"다.
- **Azure Policy**: 관리 그룹·구독·리소스 그룹에 정책을 할당한다. 같은 정책 정의를 효과(effect)만 바꿔서 Deny(예방), Audit(탐지), DeployIfNotExists·Modify(자동 교정)로 쓸 수 있어서, 처음엔 Audit으로 걸어 위반 현황을 본 뒤 Deny로 올리는 단계적 도입이 쉽다.

### 단계적으로 거는 법

가드레일을 운영 중인 조직에 한 번에 걸면 기존 자원이 위반 상태가 되고, 배포가 갑자기 실패한다. 순서가 있다.

1. 탐지 모드로 먼저 건다. 위반이 몇 개, 어디에 있는지 본다.
2. 위반한 팀과 이야기해서 고치거나, 정당한 예외는 기록한다.
3. 새 자원부터 예방형으로 막는다.
4. 예외는 만료일을 붙여 관리한다. 영구 예외는 결국 구멍이 된다.

면접에서 "가드레일을 어떻게 도입하겠냐"고 물으면 이 순서를 말하는 것만으로도 운영 경험이 있는 사람처럼 들린다.

## 깊게 3: 신원과 접근

### 사람의 신원은 한 곳에서

가장 나쁜 구조는 클라우드 계정마다 IAM 사용자를 만들고, 각자 비밀번호와 장기 액세스 키를 갖게 하는 것이다. 퇴사자 처리, 비밀번호 정책, 다중 인증을 계정마다 따로 해야 한다.

좋은 구조는 **회사의 신원 공급자(IdP) 한 곳**에서 사람을 관리하고, 클라우드는 그 신원을 **연합**(federation)해서 받는 것이다.

```
회사 IdP (사람, 그룹, MFA)
   │ SAML / OIDC
   ▼
클라우드 SSO
   │ 그룹 → 역할 매핑
   ▼
계정마다 임시 권한
```

| 클라우드 | 연합·SSO의 중심 |
|---|---|
| AWS | IAM Identity Center |
| GCP | Cloud Identity / Google Workspace, 또는 외부 IdP 연합 |
| Azure | Microsoft Entra ID |

핵심 원칙은 세 가지다.

1. **그룹에 권한을 준다.** 사람 개인에게 주지 않는다. 입사·이동·퇴사는 IdP에서 그룹만 바꾸면 끝난다.
2. **임시 자격 증명만 쓴다.** 로그인하면 몇 시간짜리 권한을 받는다. 장기 액세스 키는 원칙적으로 없다.
3. **최소 권한 + 필요할 때만 올리기.** 평소엔 읽기 권한, 운영 작업이 필요할 때만 승인을 받아 일정 시간 관리자 권한을 받는다(Azure의 PIM이 대표적인 기능).

### 프로그램의 신원

사람보다 더 많은 것이 프로그램이다. CI/CD, 서버, 쿠버네티스 파드가 클라우드 API를 부른다.

- 클라우드 안에서 도는 프로그램은 **자원에 붙은 역할**을 쓴다. EC2 인스턴스 프로파일, GCP 서비스 계정을 붙인 VM, Azure 관리 ID. 키 파일이 없다.
- 클라우드 밖(다른 클라우드, GitHub Actions 같은 CI)에서 들어오는 프로그램은 **워크로드 신원 연합**으로 받는다. 외부가 발급한 OIDC 토큰을 클라우드가 검증하고 임시 권한으로 바꿔 준다. 장기 키를 CI 비밀값에 넣어 두는 방식은 이것으로 대체한다.
- 조직 정책으로 **서비스 계정 키 생성 자체를 금지**하는 것이 요즘 기준선이다.

### 비상 계정 (break-glass)

IdP가 장애로 죽으면 아무도 클라우드에 로그인할 수 없다. 그래서 **IdP를 거치지 않는 비상 계정**을 소수 준비한다.

- 하드웨어 MFA를 걸고, 자격 증명은 물리적으로 분리해 보관한다(금고, 두 사람이 나눠 갖기).
- 평소엔 절대 쓰지 않는다. **로그인하는 순간 경보**가 울리도록 탐지 규칙을 건다.
- 분기마다 실제로 로그인이 되는지 시험한다. 정작 필요할 때 안 되는 비상 계정이 가장 흔한 실패다.

## 깊게 4: 네트워크 기반

### 허브와 스포크

팀마다 VPC를 만들고 필요할 때마다 서로 피어링하면, 연결 수가 팀 수의 제곱으로 늘어난다. 게다가 AWS VPC 피어링은 전이되지 않아서(A-B, B-C가 연결돼도 A-C는 안 된다) 관리가 금방 불가능해진다.

그래서 가운데에 **허브**를 두고 각 팀의 네트워크(**스포크**)가 허브에만 붙게 한다.

```
   스포크A   스포크B
       \     /
        허브 ── 온프레(VPN/전용선)
       /  |  \
 스포크C  │  인터넷 출구
        검사(방화벽)
```

| 클라우드 | 허브 역할 |
|---|---|
| AWS | Transit Gateway (+ 네트워크 허브 계정) |
| GCP | 공유 VPC, 또는 Network Connectivity Center |
| Azure | 허브 VNet 피어링, 또는 Virtual WAN |

GCP는 결이 조금 다르다. **공유 VPC**는 호스트 프로젝트 하나가 VPC를 소유하고, 서비스 프로젝트들이 그 서브넷을 빌려 쓰는 방식이다. 네트워크는 네트워크 팀이 한 곳에서 관리하고, 서비스 팀은 자기 프로젝트에서 VM과 클러스터만 만든다. "네트워크 관리 권한"과 "서비스 운영 권한"을 프로젝트 경계로 깔끔하게 나눌 수 있다는 게 장점이다.

### 인터넷 출입구를 모은다

스포크마다 NAT 게이트웨이와 인터넷 게이트웨이를 두면, 인터넷으로 나가는 길이 서른 개가 된다. 어디로 무엇이 나가는지 통제할 수 없다.

- **중앙 집중 출구**(centralized egress): 스포크의 기본 경로(`0.0.0.0/0`)를 허브로 보내고, 허브에서만 NAT와 방화벽을 거쳐 나간다. 허용된 도메인만 나가게 하거나, 나가는 트래픽을 검사할 수 있다.
- **들어오는 쪽**은 보통 서비스마다 로드밸런서를 두되, 앞단에 WAF를 공통으로 붙인다.
- 비용과 병목의 트레이드오프가 있다. 모든 트래픽이 허브를 지나면 허브가 비싸지고, 허브가 장애 지점이 된다. 그래서 허브는 AZ마다 이중화하고, 같은 리전의 클라우드 서비스(오브젝트 스토리지 등)는 프라이빗 엔드포인트로 허브를 거치지 않게 한다.

### IP 계획과 DNS

- **IP 대역은 조직 전체에서 한 장의 표로** 관리한다. 리전별, 환경별로 큰 덩어리를 먼저 나누고 그 안에서 VPC를 할당한다. 온프레 대역과 겹치지 않게 처음부터 피한다. AWS VPC IPAM, Azure의 IPAM 기능처럼 대역 할당을 도구로 관리할 수 있다.
- 쿠버네티스는 노드·파드·서비스 대역을 따로 먹으므로 계획 단계에서 미리 넉넉히 떼어 둔다.
- **DNS**: 사설 영역을 허브에서 관리하고 스포크에 공유한다. 온프레와 클라우드가 서로의 이름을 풀어야 하면 조건부 전달(AWS Route 53 Resolver 엔드포인트, GCP Cloud DNS 전달 영역, Azure DNS Private Resolver)을 둔다.

## 깊게 5: 로그, 감사, 보안 기준선

### 감사 로그는 조직 단위로, 다른 계정에

"누가 언제 어떤 API를 불렀나"를 남기는 감사 로그는 모든 사고 조사의 출발점이다.

| 클라우드 | 감사 로그 |
|---|---|
| AWS | CloudTrail (조직 트레일) |
| GCP | Cloud Audit Logs (조직 싱크) |
| Azure | Activity Log, Entra 로그 (진단 설정) |

설계 원칙은 이렇다.

1. **조직 단위로 켠다.** 계정마다 켜는 게 아니라, 조직 트레일·조직 로그 싱크로 새 계정이 생겨도 자동으로 수집되게 한다.
2. **별도의 로그 보관 계정에 모은다.** 서비스 계정 관리자가 로그를 지울 수 없어야 한다. 침입자가 가장 먼저 하는 일이 흔적 지우기다.
3. **변경 불가로 보관한다.** 오브젝트 잠금(S3 Object Lock, GCS 보존 정책 잠금, Azure 변경 불가 Blob)으로 보존 기간 동안 아무도 못 지우게 한다.
4. **가드레일로 "로그 끄기"를 금지한다.** 앞의 예방형 가드레일이 여기에 걸린다.

감사 로그 외에도 네트워크 흐름 로그(VPC Flow Logs), 로드밸런서 접근 로그, DNS 쿼리 로그를 어디까지 모을지 정한다. 다 모으면 비용이 크므로 운영 환경과 보안상 중요한 구간부터 켠다.

### 보안 기준선

| 기능 | AWS | GCP | Azure |
|---|---|---|---|
| 위협 탐지 | GuardDuty | Security Command Center | Defender for Cloud |
| 설정 점검 모음 | Security Hub, Config | Security Command Center | Defender for Cloud |
| 키 관리 | KMS | Cloud KMS | Key Vault |

- 위협 탐지는 조직 전체에 켜고, **보안 도구 계정에 위임 관리자**를 둬서 한 곳에서 본다.
- 저장 데이터 암호화는 기본으로 켜고, 규제가 있는 데이터는 고객 관리 키(CMK)로 한다. 키를 누가 관리하고 누가 쓸 수 있는지 분리한다.
- 발견 사항은 사람이 보는 대시보드로 끝나면 안 된다. 심각도별로 담당 팀 티켓이나 알림으로 흘려야 실제로 고쳐진다.

## 깊게 6: 비용 배분

청구서 한 장을 팀별로 나누려면 두 가지가 필요하다.

1. **계정 구조로 나누기**: 계정을 서비스·팀 단위로 나눴다면 계정별 비용이 곧 팀별 비용이다. 가장 정확하다.
2. **태그·라벨로 나누기**: 같은 계정 안의 공용 자원은 `cost-center`, `service`, `env`, `owner` 같은 태그로 나눈다.

태그는 "붙이자"고 말하는 것만으로는 절대 붙지 않는다.

- 필수 태그 목록을 정하고, 가드레일로 **태그 없는 자원 생성을 막거나**(Azure Policy, AWS 태그 정책+SCP) 최소한 탐지한다.
- IaC 모듈에서 기본 태그를 자동으로 붙인다.
- 공용 자원(네트워크 허브, 공용 클러스터) 비용은 사용량 비율로 나누는 규칙을 미리 합의한다.

예산 알림은 계정마다 걸고, 샌드박스 계정은 예산을 넘으면 자원을 멈추는 자동화까지 둔다. 이 습관을 FinOps라고 부른다. "비용은 엔지니어링 지표"라는 관점이다.

## 깊게 7: 기반을 코드로, 계정을 자동으로

### 기반도 IaC로 관리한다

랜딩 존을 콘솔 클릭으로 만들면 세 가지 문제가 생긴다. 누가 왜 바꿨는지 기록이 없고, 같은 구성을 다른 리전·환경에 재현할 수 없고, 수동 변경이 쌓여 문서와 실제가 어긋난다.

그래서 기반 자체를 코드로 만들고, 바꿀 때는 코드 리뷰와 파이프라인을 거친다.

| 클라우드 | 공식 출발점 |
|---|---|
| AWS | Control Tower, Account Factory for Terraform(AFT), Landing Zone Accelerator |
| GCP | Cloud Foundation 가이드, Terraform 기반 Foundation 예제 |
| Azure | Cloud Adoption Framework의 Azure Landing Zones (Terraform·Bicep) |

공식 출발점을 그대로 쓰는 게 정답은 아니다. 하지만 면접에서는 "처음부터 다 만들기보다 검증된 참조 구조에서 출발해, 회사 규정에 맞게 고친다"는 답이 현실적이다.

### 계정 자동 발급 (account vending)

새 팀이 계정을 요청하면 다음이 자동으로 일어나야 한다.

1. 요청서(팀, 서비스, 환경, 비용 센터, 예산)를 받는다. 보통 PR이나 사내 포털 양식.
2. 승인되면 계정·프로젝트·구독을 만들고 알맞은 OU·폴더·관리 그룹에 넣는다. 그 순간 상위 가드레일이 자동 적용된다.
3. 기준선을 깐다: 감사 로그 연결, 보안 도구 등록, 기본 역할, 예산 알림, 필수 태그.
4. 네트워크가 필요하면 IP 대역을 할당하고 스포크 VPC를 만들어 허브에 붙인다.
5. 팀 그룹에 SSO 권한을 준다.

이게 30분 안에 끝나면 팀들은 "몰래 개인 카드로 계정 만들기"를 하지 않는다. **통제를 지키게 하는 가장 좋은 방법은 지키는 길을 가장 빠른 길로 만드는 것**이다.

### 드리프트

코드로 만들어도 누군가 콘솔에서 고치면 실제가 코드와 어긋난다(드리프트). 정기적으로 `plan`을 돌려 차이를 찾고, 탐지형 가드레일로 수동 변경을 알린다. 운영 환경은 사람의 쓰기 권한 자체를 줄이고, 변경은 파이프라인만 하게 하는 것이 근본 대책이다.

## 깊게 8: 플랫폼 팀 운영

공통 기반을 만드는 팀(플랫폼 팀, 클라우드 CoE)이 실패하는 가장 흔한 이유는 기술이 아니라 운영 방식이다.

- **통제만 하는 팀**이 되면, 서비스 팀은 플랫폼을 피해 다닌다. 결국 그림자 IT가 생긴다.
- **모든 요청을 손으로 처리하는 팀**이 되면, 플랫폼 팀이 병목이 된다.

그래서 요즘 표현으로 **플랫폼을 제품처럼** 운영한다.

- **사용자는 사내 개발자**다. 그들이 무엇에 시간을 쓰는지 묻고, 그걸 줄이는 기능을 만든다.
- **골든 패스**(golden path): "이 템플릿으로 시작하면 네트워크, 로그, 모니터링, 배포 파이프라인, 보안 설정이 다 된 서비스가 나온다"는 포장된 길을 준다. 강제가 아니라 가장 쉬운 길이다.
- **셀프서비스**: 계정 발급, 대역 할당, DNS 등록, 인증서 발급을 요청서나 API로 스스로 할 수 있게 한다.
- **문서와 지표**: 계정 발급 시간, 골든 패스 사용률, 가드레일 위반 수, 서비스 팀 만족도를 잰다.

면접에서 "공통 기반의 전략을 세운다"는 업무를 설명할 때, 이 운영 모델까지 말하면 단순히 "클라우드를 다룰 줄 아는 사람"이 아니라 "회사 전체의 클라우드 사용을 설계하는 사람"으로 들린다.

## 설계 예시: 가상의 통신 회사

조건을 정해 보자. 가상의 통신 회사가 고객 포털, 요금 계산, 사내 데이터 분석을 클라우드로 옮긴다. 온프레 데이터센터는 당분간 유지하고, 주력은 AWS, 분석은 GCP, 사내 업무 시스템은 Microsoft 365와 붙어 있어 Azure도 일부 쓴다. 개인정보가 있어서 데이터는 국내 리전에만 둬야 한다.

### 1단계: 신원과 계층 (첫 몇 주)

- 회사 IdP를 Entra ID로 정하고, AWS IAM Identity Center와 GCP에 연합한다. 사람의 신원은 여기 한 곳에만 있다.
- AWS Organization을 만들고 OU를 Security, Infrastructure, Workloads(Prod·NonProd), Sandbox, Suspended로 나눈다.
- GCP 조직 아래 폴더를 공통·운영·개발로 나눈다. Azure는 관리 그룹을 플랫폼·랜딩 존·샌드박스로 나눈다.
- 비상 계정을 클라우드마다 준비하고 로그인 경보를 건다.

### 2단계: 가드레일과 로그

- 예방형: 국내 리전 외 자원 생성 금지, 감사 로그 끄기 금지, 루트 사용자 사용 금지, 서비스 계정 키 생성 금지, 외부 IP를 가진 VM 금지(운영 폴더).
- 탐지형: 공개 버킷, 모든 IP에 열린 관리 포트, 암호화 안 된 디스크, 태그 누락.
- 감사 로그는 클라우드마다 조직 단위로 켜서 보안 계정의 변경 불가 저장소로 보낸다. 세 클라우드의 로그를 한 SIEM에서 같이 본다.

### 3단계: 네트워크

```
 [온프레 DC]
     │ 전용선(이중)
 [AWS 네트워크 허브]
  TGW ─ 출구 방화벽
   │
 ┌─┼──────┐
 포털 요금 공용
 (스포크 VPC들)
```

- IP 계획: 온프레가 쓰는 대역을 피해 클라우드에 큰 블록을 예약하고, 리전·환경별로 나눈다.
- AWS는 Transit Gateway 허브, GCP는 공유 VPC, Azure는 허브 VNet. 클라우드 간 연결은 꼭 필요한 흐름(분석용 데이터 전송)만 연다.
- 인터넷 출구는 허브에서만, 허용 도메인 목록으로 통제한다.

### 4단계: 자동화와 셀프서비스

- 기반 전체를 Terraform으로 관리하고, 변경은 PR 리뷰와 파이프라인으로만.
- 계정 발급은 PR 양식 하나로: 서비스 이름, 환경, 비용 센터, 예산, 필요한 대역 크기. 머지되면 계정, 기준선, 스포크 VPC, SSO 권한이 자동으로 생긴다.
- 골든 패스: "컨테이너 웹 서비스" 템플릿 하나를 먼저 만든다. 대부분의 신규 서비스가 이 모양이기 때문이다.

### 5단계: 운영

- 월간 리뷰: 비용(팀별), 가드레일 위반, 보안 발견 사항, 계정 발급 시간.
- 비상 계정 로그인 시험, 백업 복구 시험을 분기마다.

이 예시를 면접에서 2분으로 줄이면 이렇게 된다. "먼저 신원을 한 곳으로 모으고 계정 계층과 가드레일을 깝니다. 다음으로 IP 계획과 허브-스포크 네트워크를 만들고, 감사 로그를 변경 불가 저장소로 모읍니다. 이 모든 것을 코드로 관리하고, 새 팀은 요청서 하나로 기준선이 갖춰진 계정을 받습니다."

## 자주 하는 실수

1. **계정 하나에 다 넣고 시작한다.** 나중에 나누려면 자원 이전, 권한 재설계, 네트워크 재구성이 한꺼번에 필요하다. 처음부터 최소한 운영과 비운영은 나눈다.
2. **IP 대역을 팀마다 알아서 잡게 한다.** 겹친 대역은 연결 시점에 발견되고, 고치려면 재구축이 필요하다.
3. **관리 계정에서 업무를 돌린다.** 가장 강한 계정이 가장 많이 노출된다.
4. **가드레일을 예고 없이 Deny로 건다.** 기존 배포가 깨지고 플랫폼 팀이 신뢰를 잃는다. 탐지 → 협의 → 예방 순서로.
5. **SCP가 권한을 준다고 착각한다.** SCP는 상한선이다. "SCP에서 허용했는데 왜 안 되지?"의 답은 대개 IAM 정책이다.
6. **장기 액세스 키를 CI에 넣는다.** 워크로드 신원 연합으로 바꾼다.
7. **로그를 같은 계정에 둔다.** 침입자와 실수한 관리자가 함께 지울 수 있다.
8. **비상 계정을 만들고 시험하지 않는다.** 필요한 날 MFA 기기가 어디 있는지 아무도 모른다.
9. **태그를 권고로만 둔다.** 강제하지 않은 태그는 3개월 뒤 절반이 비어 있다.
10. **플랫폼 팀이 모든 요청을 손으로 처리한다.** 플랫폼이 병목이 되고 팀들은 우회로를 찾는다.

## 면접 질문 10개와 답

**Q1. 랜딩 존이란 무엇이고 왜 필요한가?**

여러 팀이 클라우드를 안전하고 일관되게 쓰도록 미리 깔아 두는 공통 기반입니다. 계정 구조, 신원과 접근, 가드레일, 네트워크, 로그와 보안 기준선, 비용 배분, 자동화를 포함합니다. 이게 없으면 팀마다 같은 일을 따로 하면서 설정이 제각각이 되고, 대역 충돌이나 감사 로그 누락 같은 문제가 나중에 비싸게 돌아옵니다. 랜딩 존은 그 비용을 처음에 한 번 치르는 것입니다.

> 日本語: ランディングゾーンは、複数のチームが安全かつ一貫してクラウドを使うための共通基盤です。

**Q2. 계정을 왜 여러 개로 나누는가?**

폭발 반경을 제한하기 위해서입니다. 자격 증명이 유출되거나 설정 실수가 나도 피해가 그 계정 안에 머뭅니다. 한도와 비용도 계정 단위로 나뉘어 책임이 분명해집니다. 대신 계정이 늘면 관리 부담이 커지므로, 발급과 기준선 적용을 자동화하는 것이 전제입니다.

**Q3. SCP와 IAM 정책의 차이는?**

IAM 정책은 주체에게 권한을 주고, SCP는 OU나 계정 단위로 허용 가능한 상한선을 정합니다. SCP는 권한을 주지 않기 때문에 실제 동작하려면 SCP와 IAM 정책 둘 다 허용해야 합니다. 그래서 SCP는 "절대 하면 안 되는 일"을 막는 데 쓰고, 일상적인 권한 설계는 IAM으로 합니다. 관리 계정은 SCP의 영향을 받지 않는다는 점도 설계 시 고려합니다.

**Q4. GCP에서 조직 정책과 IAM은 어떻게 다른가?**

IAM은 누가 어떤 자원에 무엇을 할 수 있는지를 정하고, 조직 정책은 누가 하든 허용되지 않는 설정을 정합니다. 예를 들어 IAM으로 VM 생성 권한이 있어도 조직 정책이 외부 IP를 금지하면 외부 IP를 가진 VM은 만들 수 없습니다. 둘 다 조직·폴더·프로젝트 계층을 따라 상속됩니다.

**Q5. 예방형과 탐지형 가드레일은 어떻게 나눠 쓰는가?**

감사 로그 끄기, 허용 리전 밖 생성처럼 절대 깨지면 안 되는 소수는 예방형으로 막습니다. 예외가 많거나 조건이 복잡한 규칙은 탐지형으로 걸어 알리고, 가능하면 자동 교정합니다. 새 규칙은 탐지 모드로 먼저 걸어 현황을 본 뒤, 팀과 협의해 예방형으로 올립니다.

> 日本語: 絶対に破ってはいけない少数のルールは予防的に、それ以外は発見的ガードレールで検知します。

**Q6. 사람과 프로그램의 신원은 어떻게 관리하는가?**

사람은 회사 IdP 한 곳에서 관리하고, 클라우드는 SAML이나 OIDC로 연합해서 그룹 단위로 임시 권한을 줍니다. 클라우드 안의 프로그램은 자원에 붙은 역할이나 관리 ID를 쓰고, 클라우드 밖의 CI나 다른 클라우드는 워크로드 신원 연합으로 임시 권한을 받습니다. 장기 키는 원칙적으로 만들지 않고, 조직 정책으로 키 생성을 금지합니다.

**Q7. 비상 계정은 어떻게 운영하는가?**

IdP 장애에 대비해 IdP를 거치지 않는 계정을 소수 둡니다. 하드웨어 MFA와 분리 보관을 하고, 로그인 즉시 경보가 울리게 합니다. 그리고 정기적으로 실제 로그인을 시험해서 필요할 때 쓸 수 있는지 확인합니다.

**Q8. 허브-스포크 네트워크의 장단점은?**

연결과 출입구를 허브 한 곳에 모아서 관리와 통제가 쉽고, 피어링이 제곱으로 늘어나는 문제를 없앱니다. 출구 트래픽 검사와 온프레 연결도 허브에서 한 번만 하면 됩니다. 대신 허브가 비용과 장애의 집중점이 되므로 이중화하고, 대용량 트래픽은 프라이빗 엔드포인트처럼 허브를 거치지 않는 길을 둡니다.

> 日本語: ハブアンドスポークは接続と出口を一か所に集めて管理しやすくしますが、ハブ自体を冗長化する必要があります。

**Q9. 감사 로그는 어떻게 보관하는가?**

조직 단위로 켜서 새 계정도 자동으로 수집되게 하고, 서비스 계정과 분리된 로그 보관 계정에 모읍니다. 오브젝트 잠금으로 보존 기간 동안 아무도 지울 수 없게 하고, 가드레일로 로그 끄기 자체를 막습니다. 이렇게 하면 침입자나 실수한 관리자가 흔적을 지울 수 없습니다.

**Q10. 플랫폼 팀이 성공하려면?**

통제보다 편의를 먼저 줘야 합니다. 계정 발급, 대역 할당, 배포 템플릿을 셀프서비스로 만들고, 기준을 지키는 길이 가장 빠른 길이 되게 합니다. 사내 개발자를 고객으로 보고 발급 시간, 템플릿 사용률, 만족도를 지표로 관리합니다. 그래야 우회하는 그림자 IT가 생기지 않습니다.

## 정답

1. 관리 계정은 SCP의 영향을 받지 않아 가드레일로 보호할 수 없고, 조직 전체에 강한 권한을 갖고 있어서 그 계정이 침해되면 조직 전체가 위험해진다.
2. 사용자 쪽 IAM 정책(그리고 버킷 정책). SCP는 상한선일 뿐 권한을 주지 않는다.
3. 호스트 프로젝트는 VPC와 서브넷, 방화벽 규칙을 소유한다. 서비스 프로젝트는 그 서브넷을 빌려 VM, GKE 클러스터 같은 자원을 만든다.
4. 탐지 모드로 걸어 현황 파악 → 위반 팀과 협의해 수정하거나 예외 기록 → 새 자원부터 예방형으로 차단 → 예외에 만료일을 붙여 관리.
5. 서비스 계정의 관리자나 그 계정에 침입한 공격자가 로그를 지우거나 고칠 수 없게 하기 위해서다. 사고 조사의 증거를 보존한다.
