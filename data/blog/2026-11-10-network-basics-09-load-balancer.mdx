## 질문

이벤트 때문에 트래픽이 평소의 10배로 뛴다. 서버를 늘리면 끝일까?

서버를 늘리는 건 시작일 뿐이다. 요청을 누가 어떻게 나눠 줄지, 서버 하나가 아플 때 어떻게 빼낼지, 실패한 요청을 다시 보내다가 오히려 전체를 쓰러뜨리지 않으려면 어떻게 할지, 그리고 애초에 서버까지 오는 요청을 어떻게 줄일지를 같이 풀어야 한다. 이 글은 그 순서대로 간다.

## 1. 왜 로드밸런서가 필요한가

### 스케일 업과 스케일 아웃

| | 스케일 업 | 스케일 아웃 |
|---|---|---|
| 방법 | 한 대를 더 크게 | 같은 서버를 여러 대로 |
| 한계 | 가장 큰 기계까지 | 거의 없음 |
| 장애 | 그 한 대가 단일 장애점 | 한 대가 죽어도 버팀 |
| 조건 | 앱 변경 없음 | 앱이 상태를 갖지 않아야 함 |

스케일 아웃의 조건이 중요하다. 로그인 세션을 서버 메모리에 두면, 다음 요청이 다른 서버로 갔을 때 로그인이 풀린다. 그래서 세션과 상태는 Redis나 DB 같은 **외부 저장소**로 빼고, 웹·앱 서버는 어느 것이 받아도 같은 결과를 내게 만든다(무상태). 이게 되면 서버를 몇 대든 늘릴 수 있다.

스케일 아웃을 하면 "요청을 여러 대에 나눠 주는" 장치가 필요하다. 그게 **로드밸런서**다. 로드밸런서가 하는 일은 크게 셋이다. **나누기**(분배), **빼기**(아픈 서버 제외), **가리기**(서버 목록이 바뀌어도 클라이언트는 같은 주소로 접속).

## 2. L4와 L7: 연결 단위냐 요청 단위냐

02편에서 L4는 IP와 포트까지, L7은 HTTP 내용까지 본다고 했다. 실무에서 더 중요한 차이는 **무엇을 단위로 나누느냐**다.

**L4 로드밸런서는 연결을 나눈다.** TCP 연결이 들어오면 출발지·목적지 IP와 포트, 프로토콜(이 다섯 가지를 5-튜플이라고 한다)을 보고 서버 하나를 고른다. 그 연결이 살아 있는 동안 그 연결로 오는 모든 데이터는 같은 서버로 간다. 연결 안의 내용은 열어 보지 않는다.

**L7 로드밸런서는 요청을 나눈다.** 클라이언트와의 연결을 **자기가 직접 받아서 끝낸다.** 그리고 HTTP 요청을 하나하나 읽고, 요청마다 서버를 고른다. 서버와는 별도의 연결(보통 미리 맺어 둔 연결 풀)로 보낸다.

| | L4 | L7 |
|---|---|---|
| 나누는 단위 | 연결 | 요청 |
| 라우팅 근거 | IP, 포트 | 경로, 헤더, 쿠키, 호스트 |
| TLS | 통과 가능 | 보통 여기서 종단 |
| 할 수 있는 일 | 빠른 전달 | 경로 분기, 재시도, 헤더 추가, 압축 |
| 예 | NLB, 네트워크 LB | ALB, 애플리케이션 LB, Envoy, nginx |

HTTP 서비스는 대개 L7, DB나 자체 TCP 프로토콜, 아주 많은 연결을 낮은 지연으로 처리해야 하는 경우는 L4를 쓴다.

## 3. 패킷은 어떻게 흘러가나: NAT, DSR, 프록시

로드밸런서가 패킷을 서버로 넘기는 방식도 세 가지가 있다.

**NAT 방식.** 로드밸런서가 목적지 주소를 서버 IP로 바꿔서 넘긴다(06편 DNAT). 응답도 로드밸런서를 지나면서 출발지를 원래 주소로 되돌린다. 들어오고 나가는 트래픽이 모두 로드밸런서를 지난다.

**DSR 방식**(Direct Server Return). 요청만 로드밸런서를 지나고, **응답은 서버가 클라이언트에게 직접** 보낸다. 웹 트래픽은 대개 요청은 작고 응답이 크기 때문에, 로드밸런서의 부담이 크게 준다. 대신 서버가 로드밸런서의 주소(VIP)로 응답할 수 있게 따로 설정해야 하고, L4에서만 가능하다.

```
NAT:
C → LB → S
C ← LB ← S

DSR:
C → LB → S
C ←───── S

프록시:
C ⇄ LB  (연결 1)
    LB ⇄ S (연결 2)
```

**프록시 방식.** L7 로드밸런서의 방식이다. 클라이언트-LB, LB-서버 두 개의 연결이 따로 있다. 이때 서버 입장에서 보이는 출발지 IP는 **로드밸런서의 IP**다. 진짜 클라이언트 IP가 필요하면 로드밸런서가 `X-Forwarded-For` 헤더에 적어 주거나(HTTP), PROXY 프로토콜로 앞에 붙여 준다(TCP). 로그와 접근 제어에서 이걸 놓치면 "모든 요청이 로드밸런서에서 왔다"고 찍힌다.

## 4. 누구에게 보낼까: 분배 알고리즘

**라운드 로빈.** 차례대로 돌아가며 보낸다. 서버 성능이 같고 요청 무게가 비슷할 때 충분하다. 가중치를 주면 성능이 다른 서버에 비율로 나눌 수 있다(가중 라운드 로빈). 새 버전에 10%만 보내는 카나리 배포도 이걸로 한다.

**최소 연결.** 지금 처리 중인 연결이 가장 적은 서버로 보낸다. 요청마다 처리 시간이 크게 다를 때 라운드 로빈보다 낫다.

**두 개 뽑아 비교하기**(power of two choices). 서버 둘을 무작위로 골라 그중 덜 바쁜 쪽에 보낸다. 모든 서버의 상태를 다 비교하지 않아도 쏠림이 크게 줄어서, 로드밸런서가 여러 대일 때 많이 쓴다.

**해시.** 클라이언트 IP나 요청 키의 해시로 서버를 정한다. 같은 키는 항상 같은 서버로 간다.

### 일관된 해싱: 서버가 늘어도 덜 흔들리게

해시 분배의 가장 단순한 방법은 `해시(키) mod 서버수` 다. 서버가 4대면 나머지 0~3으로 나눈다. 문제는 서버를 5대로 늘리는 순간이다. `mod 4` 가 `mod 5` 로 바뀌면서 **거의 모든 키의 담당 서버가 바뀐다.**

이게 왜 문제일까? 캐시 서버라고 해 보자. 각 서버는 자기가 맡은 키의 데이터를 기억하고 있다. 서버 하나를 추가했을 뿐인데 거의 모든 키가 다른 서버로 가면, 모든 캐시가 한꺼번에 비어 있는 것과 같다. 요청이 전부 DB로 몰린다.

**일관된 해싱**은 서버와 키를 같은 원(링) 위에 해시로 올려 두고, 각 키는 시계 방향으로 가장 먼저 만나는 서버가 맡게 한다.

```
      서버A
   키1     키2
서버D        서버B
   키4     키3
      서버C
```

서버가 하나 추가되면 원 위의 한 구간만 새 서버로 넘어간다. 서버가 N대일 때 대략 1/N의 키만 움직인다. 서버 하나를 원 위 여러 자리에 올려 두는(가상 노드) 방식으로 구간 크기를 고르게 만든다. 분산 캐시, 일부 로드밸런서의 해시 정책, 분산 DB의 데이터 배치가 이 원리를 쓴다.

## 5. 아픈 서버 빼기: 헬스체크와 이상치 감지

**능동 헬스체크.** 로드밸런서가 주기적으로 서버에 요청을 보낸다(예: `/healthz`). 정해진 횟수만큼 연속 실패하면 빼고, 정해진 횟수만큼 연속 성공하면 다시 넣는다. 간격과 횟수를 짧게 잡으면 빨리 반응하지만, 잠깐의 흔들림에도 서버가 들락날락한다.

**수동 헬스체크**(이상치 감지). 실제 요청의 결과를 본다. 어떤 서버가 최근 5xx를 연달아 내거나 응답이 유독 느리면, 일정 시간 분배에서 빼 두었다가 다시 넣어 본다. Envoy 같은 프록시가 잘하는 영역이다. 헬스체크 경로는 멀쩡한데 실제 요청만 실패하는 서버를 잡아낸다.

**무엇을 확인할지가 핵심이다.** 헬스체크가 DB 연결까지 확인한다고 해 보자. DB가 몇 초 느려지면 **모든 서버의 헬스체크가 동시에 실패**하고, 로드밸런서는 서버를 전부 빼 버린다. DB 지연이 전체 장애로 커진다. 그래서 보통 두 가지를 나눈다.

- **살아 있나**(liveness): 프로세스가 멈추지 않았나. 실패하면 재시작.
- **받을 준비가 됐나**(readiness): 지금 요청을 받아도 되나. 실패하면 분배에서만 뺀다.

로드밸런서의 헬스체크는 readiness에 가깝게, 그리고 외부 의존성은 가볍게 본다.

## 6. 기다림의 순서: 타임아웃 사슬

요청은 여러 층을 지난다.

```
클라이언트
  → 로드밸런서
    → 프록시
      → 앱
        → DB
```

각 층에 타임아웃이 있다. 원칙은 **바깥이 안쪽보다 길게**다.

안쪽이 더 길면 어떻게 될까? 앱은 DB 응답을 30초까지 기다리는데, 로드밸런서는 10초 만에 포기하고 504를 준다. 사용자는 실패를 받았는데 앱과 DB는 20초를 더 일한다. 결과도 버려지고 자원만 쓴다. 사용자가 다시 누르면 같은 일이 한 번 더 쌓인다.

바깥이 조금씩 길면, 안쪽이 먼저 포기하고 에러를 깔끔하게 바깥으로 올려 보낸다. 바깥은 그 에러를 받아 재시도할지 정할 수 있다.

### keep-alive와 유휴 타임아웃

로드밸런서는 서버와 맺은 연결을 재사용한다. 연결에 아무 요청이 없으면 일정 시간 뒤 끊는다(유휴 타임아웃). 앱 서버도 자기 keep-alive 시간이 지나면 끊는다.

**앱이 먼저 끊으면 문제가 생긴다.** 앱이 연결을 닫는 바로 그 순간, 로드밸런서는 그 연결이 아직 살아 있다고 믿고 요청을 보낸다. 요청은 닫힌 연결에 떨어지고, 로드밸런서는 502를 준다. 트래픽이 적을 때 간헐적으로 나서 찾기 어렵다.

해결은 **앱의 keep-alive를 로드밸런서의 유휴 타임아웃보다 길게** 두는 것이다. 그러면 항상 로드밸런서가 먼저 끊는다.

## 7. 실패를 다루는 기술

### 재시도와 백오프, 지터

일시적인 실패(연결 실패, 503)는 다시 보내면 성공할 때가 많다. 하지만 재시도는 잘못 쓰면 장애를 키운다.

**재시도 폭풍.** 서버가 과부하로 느려지면 요청이 실패하고, 모든 클라이언트가 즉시 재시도한다. 부하는 두 배, 세 배가 되고 회복은 더 멀어진다.

**재시도 증폭.** 클라이언트가 3번, 프록시가 3번, 앱이 DB 호출을 3번 재시도하면, 최악에는 요청 하나가 DB에 3 × 3 × 3 = 27번 닿는다. 재시도는 **한 층에서만** 하는 게 원칙이다.

**지수 백오프.** 재시도 간격을 1초, 2초, 4초처럼 늘린다. 서버에 회복할 시간을 준다.

**지터.** 간격에 무작위 값을 섞는다. 모두가 정확히 1초 뒤에 동시에 재시도하면 또 한꺼번에 몰리기 때문이다. 무작위로 흩어 놓으면 부하가 평평해진다.

**재시도 예산.** "재시도는 전체 요청의 일정 비율까지만" 같은 상한을 둔다. 장애 중에 재시도가 트래픽을 몇 배로 부풀리는 걸 막는다.

### 멱등 키: 두 번 와도 한 번만 처리

조회는 몇 번을 다시 보내도 결과가 같다. 하지만 "결제하기"는 두 번 처리되면 큰일이다. 문제는 클라이언트 입장에서 "실패했는지, 처리됐는데 응답만 못 받았는지"를 구별할 수 없다는 점이다.

**멱등 키**가 이걸 푼다.

1. 클라이언트가 요청마다 고유한 키(무작위 ID)를 만들어 헤더에 넣는다.
2. 서버는 처리하기 전에 그 키를 이미 처리했는지 본다.
3. 처음 보는 키면 처리하고, 결과를 키와 함께 저장한다.
4. 같은 키가 다시 오면 처리하지 않고 저장된 결과를 그대로 돌려준다.

이렇게 하면 클라이언트는 마음 놓고 재시도할 수 있다. 결제 API들이 이 방식을 쓴다.

### 서킷 브레이커: 빨리 포기하기

어떤 의존 서비스가 계속 실패하는데도 매번 호출하고 타임아웃까지 기다리면, 내 서비스의 스레드와 연결이 전부 그 기다림에 묶인다. 결국 내 서비스도 죽는다(연쇄 장애).

서킷 브레이커는 전기 차단기처럼 동작한다.

| 상태 | 동작 |
|---|---|
| 닫힘 | 정상 호출. 실패율을 센다 |
| 열림 | 실패율이 기준을 넘음. 호출하지 않고 바로 실패 |
| 반열림 | 잠시 뒤 일부만 시험 호출. 성공하면 닫힘으로 |

열림 상태에서는 기다리지 않고 바로 실패하거나 대체 응답(캐시된 값, 기본값)을 준다. 내 자원은 지키고, 아픈 서비스에는 회복할 틈을 준다.

## 8. 배포할 때 끊기지 않게: 드레이닝

서버를 교체하거나 줄일 때, 처리 중인 요청이 있는 서버를 바로 끄면 그 요청들이 끊긴다.

**연결 드레이닝**(AWS에서는 등록 해제 지연)은 서버를 분배 목록에서 먼저 빼고, **새 요청은 안 보내되 처리 중인 요청은 끝날 때까지** 기다린 뒤에 내린다.

앱 쪽도 준비가 필요하다(우아한 종료).

1. 종료 신호(SIGTERM)를 받으면 먼저 readiness를 실패로 바꾼다.
2. 로드밸런서가 그걸 보고 새 요청을 끊을 때까지 잠깐 기다린다.
3. 처리 중인 요청을 마저 끝낸다.
4. 그다음 종료한다.

이게 없으면 배포할 때마다 소수의 요청이 5xx로 끝난다. 배포가 잦을수록 쌓인다.

## 9. HTTP/2와 gRPC의 쏠림

HTTP/2와 그 위의 gRPC는 **연결 하나에 요청 여러 개를 동시에** 싣는다. 연결을 오래 유지하면서 그 안에서 요청을 계속 보낸다.

이게 L4 로드밸런서와 만나면 문제가 된다. L4는 **연결 단위**로 나눈다(2절). 클라이언트가 연결을 하나만 맺고 오래 쓰면, 그 클라이언트의 모든 요청이 서버 한 대로 간다. 서버를 늘려도 새 서버는 놀고, 기존 서버만 바쁘다.

대응:
- **L7 로드밸런서**를 쓴다. HTTP/2를 이해하는 로드밸런서는 연결 안의 요청을 하나씩 다른 서버로 나눈다.
- **클라이언트 측 분배**. gRPC 클라이언트가 서버 목록을 받아 직접 여러 연결을 맺고 나눈다.
- **연결 최대 수명**을 둔다. 서버가 일정 시간마다 연결을 정리하게 해서, 클라이언트가 다시 연결하면서 새 서버로 퍼지게 한다.

## 10. 스티키 세션의 대가

스티키 세션은 같은 사용자를 계속 같은 서버로 보낸다(쿠키나 IP 해시). 세션을 서버 메모리에 둔 앱도 스케일 아웃이 된다는 장점이 있다.

대가는 이렇다.
- 그 서버가 죽으면 그 사용자들의 세션이 사라진다.
- 특정 서버에 무거운 사용자가 몰려도 옮길 수 없다.
- 서버를 줄일 때(스케일 인) 그 서버의 사용자를 쉽게 옮기지 못한다.
- 회사 NAT 뒤의 수많은 사용자가 IP 하나로 보이면, IP 해시는 그들을 전부 한 서버로 보낸다.

그래서 임시방편으로만 쓰고, 근본적으로는 세션을 외부 저장소로 빼는 게 낫다.

## 11. 리전을 넘어서: 글로벌 분산

로드밸런서 하나는 보통 한 리전 안에서 여러 AZ에 걸쳐 동작한다. 리전 전체 장애나 전 세계 사용자를 생각하면 한 층이 더 필요하다.

**DNS 기반 분산**(GSLB). DNS가 사용자 위치나 지연 시간, 헬스체크 결과를 보고 다른 리전의 주소를 답한다. 구현이 쉽지만 08편에서 본 TTL과 캐시 때문에 전환에 시간이 걸린다.

**애니캐스트 기반 분산.** 전 세계 여러 거점이 같은 IP를 광고하고(08편), 사용자는 가장 가까운 거점으로 들어온다. 거점이 클라이언트 연결을 받은 뒤 클라우드 내부망으로 가장 가까운 정상 리전에 넘긴다. 주소가 바뀌지 않아서 DNS 캐시 문제가 없고 전환이 빠르다. AWS Global Accelerator, GCP의 글로벌 외부 애플리케이션 로드밸런서가 이 방식이다.

## 12. 오토스케일링: 언제 늘릴까

오토스케일링은 지표를 보고 서버 수를 자동으로 늘리고 줄인다. 어떤 지표를 보느냐가 중요하다.

| 지표 | 맞는 경우 |
|---|---|
| CPU 사용률 | 계산이 많은 서비스 |
| 서버당 요청 수 | 일반 웹·API |
| 대기열 길이 | 비동기 작업자 |
| 응답 지연 | 사용자 체감이 기준일 때 |

**늘어나는 데 시간이 걸린다.** 새 서버가 부팅되고, 앱이 뜨고, 캐시가 데워지고, 헬스체크를 통과하기까지 몇 분이 걸릴 수 있다. 트래픽이 갑자기 10배가 되면 그 몇 분 동안 기존 서버가 버텨야 한다. 그래서:

- **예정된 이벤트는 미리 늘린다.** 예약 스케일링.
- 늘릴 때는 빠르게, 줄일 때는 천천히. 줄였다가 다시 늘리는 출렁임(플래핑)을 막는다.
- 이미지에 앱을 미리 구워 두거나 컨테이너를 써서 기동 시간을 줄인다.

## 13. 서버까지 오기 전에 줄이기

서버를 늘리는 것보다 **서버까지 오는 요청을 줄이는 게** 싸고 빠르다. 앞에서부터 차례로 본다.

### 캐시 계층

```
브라우저 캐시
  → CDN
    → 리버스 프록시 캐시
      → 앱 캐시 (Redis)
        → DB
```

앞에서 걸릴수록 뒤는 편하다. 정적 파일과 자주 같은 응답은 CDN에서 끝나게 한다. 응답의 `Cache-Control` 헤더가 각 층의 캐시 여부와 기간을 정한다.

**캐시 쇄도**(stampede). 인기 있는 캐시 항목이 만료되는 순간, 동시에 들어온 수많은 요청이 전부 캐시 미스를 내고 DB로 몰린다. 대응은 같은 키의 동시 요청을 하나로 합치기(요청 병합), 만료 직전에 하나만 미리 갱신하기, 만료 시각에 무작위 값을 섞기다.

### 속도 제한

한 사용자나 IP가 보낼 수 있는 양에 상한을 둔다. 대표적인 방식이 **토큰 버킷**이다.

- 버킷에 토큰이 일정 속도로 채워진다. 이 속도가 **평균 허용량**이다.
- 요청 하나에 토큰 하나를 쓴다. 토큰이 없으면 거절한다.
- 버킷 크기만큼은 토큰이 모일 수 있어서, 잠깐의 **몰림**(버스트)은 허용한다.

다른 방식으로 일정한 속도로만 내보내는 리키 버킷, 시간 창마다 개수를 세는 고정·슬라이딩 윈도가 있다. 거절할 때는 429 응답과 `Retry-After` 헤더로 언제 다시 오라고 알려 준다. 서버가 여러 대면 개수를 공유해야 해서 Redis 같은 중앙 저장소를 쓰거나, 서버별 한도로 나눈다.

### 대기열

바로 응답할 필요가 없는 일(메일 발송, 이미지 변환, 통계 집계)은 큐에 넣고 작업자가 자기 속도로 처리한다. 트래픽이 몰려도 큐가 길어질 뿐 서버는 넘어지지 않는다.

## 14. 마지막 병목: DB

앞단을 다 늘려도 DB는 쉽게 늘어나지 않는다. 트래픽 문제의 끝은 대개 DB다.

- **연결 수 한계.** DB는 동시 연결 수에 한계가 있다. 앱 서버를 100대로 늘리고 각자 연결 풀을 20개씩 잡으면 2000개가 된다. 연결 풀링 프록시(PgBouncer, RDS Proxy 등)를 앞에 두어 실제 DB 연결 수를 묶는다.
- **읽기 복제본.** 읽기를 복제본으로 나눈다. 단, 복제는 약간 늦으므로(복제 지연) 방금 쓴 데이터를 바로 읽으면 안 보일 수 있다. 쓴 직후의 읽기는 주 DB로 보내는 식의 규칙이 필요하다.
- **캐시.** 자주 읽는 결과는 앱 캐시에.
- **쓰기 분산.** 쓰기가 한계면 큐로 완충하거나, 데이터를 나눠 여러 DB에 두는(샤딩) 설계까지 간다. 비용이 큰 결정이라 마지막이다.

## 15. 자주 막히는 장애 사례

**1. DB가 잠깐 느렸는데 전체 서비스가 죽었다**
- 원인: 헬스체크가 DB까지 확인해서 모든 서버가 동시에 빠졌다.
- 해결: 헬스체크를 가볍게, readiness와 liveness 분리.

**2. 트래픽이 적을 때 간헐적 502**
- 원인: 앱 keep-alive가 로드밸런서 유휴 타임아웃보다 짧다.
- 해결: 앱 keep-alive를 더 길게.

**3. 서버를 늘렸는데 새 서버가 논다**
- 원인: HTTP/2·gRPC 장기 연결이 L4에서 한 서버에 묶였다.
- 해결: L7 분배, 클라이언트 측 분배, 연결 최대 수명.

**4. 장애가 회복될 만하면 다시 넘어진다**
- 원인: 재시도 폭풍, 여러 층의 재시도 증폭.
- 해결: 한 층에서만 재시도, 백오프와 지터, 재시도 예산, 서킷 브레이커.

**5. 배포할 때마다 일부 요청 실패**
- 원인: 드레이닝과 우아한 종료가 없다.
- 해결: 등록 해제 지연 설정, SIGTERM 처리.

**6. 이벤트 시작 직후 몇 분간 장애, 그 뒤엔 정상**
- 원인: 오토스케일링이 늦었다.
- 해결: 예약 스케일링, 기동 시간 단축.

## 16. 클라우드에서는

- **AWS**: ALB(L7), NLB(L4, 고정 IP, 매우 많은 연결), 그리고 방화벽 같은 보안 장비를 끼워 넣는 GWLB. 대상 그룹마다 헬스체크와 등록 해제 지연을 설정한다. ALB의 유휴 타임아웃 기본값은 60초다.
- **GCP**: 애플리케이션 LB(L7)와 네트워크 LB(L4)가 있고, 각각 글로벌과 리전, 외부와 내부로 나뉜다. 글로벌 외부 LB는 애니캐스트 IP 하나로 여러 리전에 분산한다.
- **AZ 분산**: 로드밸런서와 뒤의 서버를 모두 여러 AZ에 둔다. 한쪽 AZ에만 서버가 몰려 있으면 AZ 장애 때 의미가 없다.
- **쿠버네티스**: Service(L4, kube-proxy), Ingress·Gateway API(L7), 서비스 메시(Envoy 사이드카로 재시도·서킷 브레이커·이상치 감지).

### 꼬리질문

**Q. L4와 L7은 언제 각각 쓰나요?**
L4는 연결 단위로 빠르게 전달해서 DB나 자체 TCP 프로토콜, 대량 연결에 씁니다. L7은 요청을 읽고 경로별로 나누거나 재시도할 수 있어서 HTTP 서비스에 씁니다.

**Q. 재시도가 장애를 키우는 경우는?**
과부하 중에 모든 클라이언트가 즉시 재시도하거나, 여러 층이 각각 재시도해서 요청이 곱으로 늘어날 때입니다. 한 층에서만, 백오프와 지터를 넣어 재시도합니다.

**Q. 서버를 추가할 때 캐시 적중률이 급락하는 이유는?**
해시를 서버 수로 나눈 나머지로 분배하면 서버 수가 바뀔 때 거의 모든 키의 담당이 바뀝니다. 일관된 해싱을 쓰면 일부 키만 이동합니다.

## 정답

1. L4는 연결 단위로 서버를 고르는데, gRPC(HTTP/2)는 연결 하나를 오래 유지하며 그 안에 요청을 계속 싣기 때문에 그 연결의 모든 요청이 한 서버로 간다.
2. 앱이 먼저 연결을 닫는 순간 로드밸런서가 그 연결로 요청을 보내면 502가 난다. 앱이 더 오래 유지하면 항상 로드밸런서가 먼저 끊어서 이런 경합이 없다.
