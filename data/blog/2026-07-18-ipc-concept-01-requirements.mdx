## 시험 직전 빈출도

> **우선순위 A · ★★★★☆**
>
> 요구사항 유형·검토 기법은 여러 연도에 걸쳐 단답형 식별 문제로 재등장했다.

- **최소 암기:** 기능/비기능 요구사항, 도출→분석→명세→확인, 동료검토·워크스루·인스펙션
- **5점 후보:** “작성자가 설명하고 동료가 검토”=동료검토, “검토 자료를 미리 배포”=워크스루, “훈련된 중재자와 공식 검토”=인스펙션
- **판정 기준:** 별점은 Q-Net의 공식 출제 확률이 아니다. 2020년 1회~2026년 1회 복원 목록과 2026 시나공 핵심요약의 실기 출제 이력 표기를 개념군 단위로 교차해 정한 **시험 전날 상대 우선순위**다.

정보처리기사 실기에서 요구사항 문제는 설명 속의 식별어를 보고 단계나 기법을 구분하는 형태로 출제된다. 핵심은 **기능과 품질 제약**, 그리고 **도출-분석-명세-확인**의 흐름이다.

### 내일 답안 작성 원칙

1. 문제에서 한글·영문 중 하나를 요구하지 않았다면 가장 확실한 표기 하나를 쓴다.
2. 약어만 외웠다면 풀네임도 한 번 확인한다. 철자 하나 때문에 5점을 잃지 않는다.
3. 여러 답을 요구하면 번호를 붙여 누락 개수를 확인한다.
4. 모르는 문제도 관련 용어를 길게 나열하지 말고, 요구한 개수만 정확히 쓴다.
5. 마지막 검토에서는 계산보다 **영문 철자, 부정어, 답 개수**를 먼저 확인한다.

## 1. 요구사항의 종류

| 구분              | 의미                          | 예시                          |
| ----------------- | ----------------------------- | ----------------------------- |
| 기능적 요구사항   | 시스템이 수행해야 하는 기능   | 회원은 이메일로 로그인한다    |
| 비기능적 요구사항 | 성능·품질·운영·보안 등의 제약 | 응답 시간은 2초 이하여야 한다 |

### 비기능적 요구사항 식별어

```text
성능: 응답 시간, 처리량, 동시 사용자
보안: 인증, 권한, 암호화, 감사 로그
신뢰성: 장애율, 복구, 오류 허용
가용성: 서비스 제공 시간, 가동률
자원: 메모리, CPU, 저장 공간
운영: 모니터링, 백업, 로그 관리
이식성: 다른 환경으로 이전
유지보수성: 수정과 확장의 용이성
```

## 2. 요구사항 개발 절차

```text
도출 → 분석 → 명세 → 확인
```

| 단계 | 핵심 활동                                |
| ---- | ---------------------------------------- |
| 도출 | 이해관계자로부터 요구사항 수집           |
| 분석 | 요구의 충돌·누락·범위·우선순위 검토      |
| 명세 | 요구사항을 명확하고 검증 가능하게 문서화 |
| 확인 | 요구가 올바르고 완전한지 검토·검증       |

## 3. 요구사항 도출 기법

| 기법         | 식별 키워드                       |
| ------------ | --------------------------------- |
| 인터뷰       | 이해관계자와 직접 대화            |
| 설문         | 다수에게 표준화된 질문 배포       |
| 브레인스토밍 | 비판 없이 다양한 아이디어 제시    |
| 워크숍       | 이해관계자가 함께 모여 집중 협의  |
| 관찰         | 실제 업무 수행 과정을 직접 확인   |
| 프로토타이핑 | 시제품으로 불명확한 요구 구체화   |
| 문서 분석    | 기존 규정·매뉴얼·시스템 문서 검토 |

## 4. 요구사항 분석

분석 단계에서는 요구사항이 실제로 구현 가능한지, 서로 충돌하지 않는지, 범위가 명확한지 판단한다.

```text
요구사항 분류
개념 모델링
요구사항 할당
요구사항 협상
정형 분석
```

### 구조적 분석 도구

| 도구          | 의미                                     |
| ------------- | ---------------------------------------- |
| DFD           | 시스템 내부의 자료 흐름과 처리 과정 표현 |
| 자료사전      | DFD에 사용된 자료 요소를 정의            |
| 소단위 명세서 | 최하위 프로세스의 처리 논리를 기술       |
| ERD           | 개체, 속성, 관계를 표현                  |

### 자료사전 기호

| 기호  | 의미      |
| ----- | --------- |
| `=`   | 정의      |
| `+`   | 연결      |
| `{ }` | 반복      |
| `[ ]` | 선택      |
| `( )` | 생략 가능 |
| `* *` | 설명·주석 |

## 5. 요구사항 명세

좋은 요구사항은 다음 특성을 가진다.

| 특성        | 의미                                |
| ----------- | ----------------------------------- |
| 명확성      | 하나의 의미로 해석 가능             |
| 완전성      | 필요한 내용이 빠지지 않음           |
| 일관성      | 다른 요구와 모순되지 않음           |
| 검증 가능성 | 테스트나 검토로 충족 여부 판단 가능 |
| 추적 가능성 | 출처와 설계·구현·테스트 연결 가능   |
| 수정 용이성 | 변경 시 영향 범위를 관리하기 쉬움   |

### 정형 명세와 비정형 명세

| 구분 | 정형 명세                | 비정형 명세             |
| ---- | ------------------------ | ----------------------- |
| 표현 | 수학적 기호와 논리       | 자연어, 표, 다이어그램  |
| 장점 | 모호성 감소, 정확한 검증 | 작성과 이해가 쉬움      |
| 단점 | 작성 난도가 높음         | 모호성과 해석 차이 가능 |

## 6. 요구사항 확인 기법

| 기법             | 핵심                               |
| ---------------- | ---------------------------------- |
| 요구사항 검토    | 명세서를 여러 이해관계자가 검토    |
| 프로토타이핑     | 시제품으로 요구 충족 여부 확인     |
| 모델 검증        | 분석 모델의 정확성·일관성 확인     |
| 인수 테스트 개발 | 요구를 테스트 가능한 조건으로 변환 |

### 검증과 확인

```text
Verification: 제품을 올바르게 만들고 있는가?
Validation: 올바른 제품을 만들고 있는가?
```

## 7. 요구사항 추적성

요구사항 추적표는 요구사항이 설계, 구현, 테스트까지 연결되는지를 관리한다.

```text
요구사항 → 설계 요소 → 소스·모듈 → 테스트 케이스
```

- 순방향 추적: 요구사항이 구현과 테스트에 반영됐는지 확인
- 역방향 추적: 구현 요소가 어떤 요구에서 시작됐는지 확인

## 8. 시험 직전 암기

```text
기능 = 무엇을 하는가
비기능 = 얼마나 잘하고 어떤 제약을 지키는가
요구사항 절차 = 도출-분석-명세-확인
DFD = 자료 흐름
자료사전 = 자료 정의
ERD = 개체·속성·관계
Verification = 올바르게 만드는가
Validation = 올바른 제품인가
```

문제에 `응답 시간`, `자원`, `보안`, `운영`이 나오면 비기능적 요구사항을 먼저 의심한다. `인터뷰·설문`은 도출, `충돌·우선순위`는 분석, `문서화`는 명세, `검토·테스트`는 확인이다.
