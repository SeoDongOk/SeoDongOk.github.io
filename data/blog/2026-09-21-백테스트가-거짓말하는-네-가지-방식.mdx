하루 동안 자동매매 봇의 손실 원인을 파고들었다. 결론부터 말하면 **전략이 아니라 측정이 틀려 있었다.**

네 가지를 순서대로 정리한다.

## 1. 레버리지를 테스트한 줄 알았는데 손절폭을 테스트하고 있었다

한 달 전 이런 표를 근거로 레버리지를 크게 낮춘 적이 있다.

```
레버리지   평균 총손익   흑자 구간 비율
30          -260          8.3%
20          -123         22.9%
10          +539         76.7%
 5          +816         88.8%
```

완전한 단조 관계다. "레버리지가 낮을수록 좋다"는 결론이 나온다.

그런데 이 실험은 **손절 기준을 마진 대비 % 로 고정**한 채 레버리지만 바꿨다. 그러면 실제로 변한 건 레버리지가 아니다.

```
가격 기준 손절폭 = 마진손절% ÷ 레버리지
```

마진 -30% 손절은 레버리지 5배에서 가격 -6%, 30배에서 가격 -1%가 된다. 즉 그 표는 **"기계적 진입에는 6% 손절이 1% 손절보다 낫다"** 를 증명한 것이지 레버리지를 평가한 게 아니었다.

이번엔 **건당 계좌 위험을 고정**하고 다시 돌렸다. 레버리지를 올리면 투입 비율이 그만큼 줄도록 묶은 것이다.

```python
# 엔진에 위험 고정 옵션을 주면
margin   = balance * risk_per_trade_pct / sl_pct
notional = margin * leverage
```

결과는 이랬다.

```
레버 20 / 30 / 50  →  모든 지표가 소수점까지 동일
```

**레버리지는 표기 방식의 차이일 뿐이었다.** 위험을 고정하는 순간 투입 비율이 상쇄해버린다. 진짜 변수는 가격 기준 손절폭 하나였다.

7개 심볼 1년치로 확인하니 예외가 없었다. **가장 좁은 손절폭이 7/7 심볼에서 최악**이었다.

## 2. 백테스트 엔진에 쿨다운이 없었다

실거래 봇에는 손절 직후 재진입을 막는 쿨다운이 있다. 그런데 백테스트 엔진에는 그 개념이 아예 없었다.

```python
# 엔진: 손절한 다음 봉에 바로 재진입 가능
# 실거래: 손절 후 60분 대기
```

즉 **그동안의 모든 백테스트가 재진입 기회를 과대평가**하고 있었다. 손절로 잘린 자리에 곧바로 다시 들어가는 걸 공짜로 가정한 셈이다.

엔진에 쿨다운을 넣고 다시 돌리니 같은 설정의 성적이 크게 달라졌다. 비교군(base)부터 실거래와 같은 조건으로 맞춰야 나머지 숫자가 의미를 갖는다.

```python
# 청산이 손절이면 쿨다운을 건다
if exit_reason == "stop_loss" and self.sl_cooldown_bars > 0:
    cooldown_until_idx = i + self.sl_cooldown_bars
```

**백테스트 엔진이 실거래와 다른 부분은 전부 편향이다.** 유리한 쪽으로 다르면 결과를 과대평가하고, 그 차이를 모르면 왜 실거래가 백테스트만 못한지 영영 알 수 없다.

## 3. 손익 기록이 7~8% 틀려 있었다

봇 로그를 보다가 이상한 걸 발견했다. 손절 기록이 전부 **정확히 같은 값**이었다.

```
손익=-14.0000 USDT   5건 전부 동일
```

거래소 실제 체결 내역과 대조해봤다.

```
           봇 기록      거래소 실제
─────────────────────────────────
거래 A     -14.0000     -14.9171
거래 B     -14.0000     -15.1064
```

원인은 두 가지였다.

**첫째, 체결가가 아니라 트리거 가격으로 계산하고 있었다.** 시장가 청산이라 실제 체결은 조금 불리하게 되는데, 그 차이를 반영하지 않았다.

```python
# 기존: SL 트리거 가격으로 계산
pnl = pos.unrealized_pnl(current_price)

# 수정: 주문 응답의 평균 체결가 사용
avg = float(order.get("avgPrice") or 0)
if avg > 0:
    pnl = pos.unrealized_pnl(avg)
```

이것만으로 거래소 실현손익과 소수점까지 일치했다.

**둘째, 수수료가 빠져 있었다.** 계좌 증감은 `실현손익 − 수수료`인데 수수료를 안 빼니 실제보다 낙관적이었다.

여기서 함정이 하나 더 있었다. 코드에 이미 수수료율 설정이 있었는데, **그건 주문 수량을 보수적으로 잡기 위한 상한값**이지 실제 체결 수수료가 아니었다.

```python
# 수량 계산용 (보수적 상한)
max_margin = balance / (1 + leverage * taker_fee_rate)
```

같은 이름을 손익 기록에 쓰면 5배 어긋난다. 실제 체결 내역에서 역산해 별도 설정으로 분리했다.

그리고 진입 수수료는 **진입 시점에 이미 계좌에서 나갔으므로** 청산에서 또 빼면 이중 계산이다. 실측으로 검산해 확인했다.

```
체결가 보정 + 청산 수수료만 차감  →  거래소 계좌 증감과 오차 0.0000
```

**손익 기록이 틀리면 일일 최대 손실 같은 안전장치가 늦게 걸린다.** 실제로는 한도를 넘었는데 봇은 아직 여유가 있다고 판단해 계속 거래한다.

## 4. 검증 없이 켠 기능이 손실만 만들었다

수익을 지키려고 넣은 트레일링 스탑이 있었다. 고점 대비 일정 % 밀리면 청산하는 흔한 구조다.

로그를 전수 조사했더니 이랬다.

```
트레일링으로 청산된 거래 4건  →  4건 모두 손실
수익 청산은 전부 거래소 익절 주문이 담당
```

예외가 하나도 없었다. 이유는 구조적이었다.

```
크게 오름        → 익절 주문이 먼저 체결 (+)
조금 오르다 밀림  → 트레일링 (-)
바로 밀림        → 손절 (-)
```

익절선이 트레일링보다 가까우면, **트레일링에 걸리는 건 "익절까지 못 가고 되돌아온 거래"뿐**이다. 설계 의도는 수익 보호였는데 실제로는 손실 전담 장치가 되어 있었다.

더 나쁜 건, 고레버리지에서 손절폭과 트레일링 폭이 같아지면서 **트레일링이 손절보다 먼저 발동**했다는 점이다. 원래 버틸 수 있던 구간에서 조기 청산됐다.

그리고 청산 직후 같은 가격에 재진입하는 일이 반복됐다. 손실을 확정하고 수수료를 두 번 내면서 포지션은 그대로인 순환매다.

## 배운 것

네 가지 모두 **전략이 아니라 측정과 실행의 문제**였다. 신호를 아무리 다듬어도 이걸 고치지 않으면 결과가 개선되지 않는다.

정리하면 이렇다.

```
① 실험 설계   한 변수만 바꾸고 있는지 확인. 고정한 값이 다른 변수를 움직이지 않는지
② 엔진 충실도 백테스트와 실거래가 다른 지점을 전부 찾아 맞추기
③ 기록 정확도 거래소 원장과 대조. 이론값이 아니라 체결값으로
④ 변경 검증   켜기 전에 백테스트, 켠 뒤엔 청산 사유별 집계로 실제 효과 확인
```

특히 ④는 대가를 치르고 배웠다. **원인을 알고도 "표본이 적다"며 판단을 미루는 동안 같은 손실이 반복됐다.** 설정끼리 산수가 안 맞는 게 명백할 때는 표본을 더 기다릴 이유가 없다.

지금은 워크포워드 검증을 돌리고 있다. 지금까지 찾은 값들이 **그 기간에만 맞는 값인지** 확인하기 위해서다. 앞의 데이터로 파라미터를 고르고 뒤의 데이터로 검증하는 방식인데, 폴드마다 선택값이 바뀌면 과최적화 신호다.

측정을 믿을 수 있게 만드는 데 하루가 걸렸다. 전략을 고치는 건 그다음이다.
