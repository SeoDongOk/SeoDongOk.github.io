## 질문

브라우저에 `https://example.com` 을 치고 엔터를 누르면, 화면이 뜨기 전까지 무슨 일이 일어날까?

면접 단골 질문이다. 이 질문이 자주 나오는 이유는 답 하나에 네트워크의 거의 모든 계층이 들어 있기 때문이다. 이름을 주소로 바꾸는 일(DNS), 주소까지 길을 찾는 일(라우팅), 믿을 수 있는 통로를 여는 일(TCP), 그 통로를 암호화하는 일(TLS), 그리고 실제로 원하는 것을 달라고 하는 일(HTTP). 이걸 막힘 없이 순서대로 말할 수 있으면, 장애가 났을 때 어디부터 볼지도 같이 정리된다.

답은 길지만 뼈대는 다섯 단계다. 이 글은 그 뼈대를 먼저 세우고, 각 단계 앞뒤에 숨어 있는 것들(브라우저 캐시, 연결 재사용, HTTP 버전 차이, CDN)을 하나씩 붙여 나간다.

## 한 장으로 보기

```
[0] 브라우저 안에서
    캐시·HSTS 확인
[1] 이름 → 주소  : DNS
[2] 길 찾기      : 라우팅
[3] 연결 만들기  : TCP
[4] 암호화 합의  : TLS
[5] 요청과 응답  : HTTP
[6] 화면 그리기  : 렌더링
```

[1]~[5]가 네트워크 구간이고, [0]과 [6]은 브라우저 안에서 일어난다. 그 뒤 브라우저는 HTML을 읽으며 CSS·JS·이미지를 받으려고 다시 요청을 보낸다. 이때 같은 서버라면 이미 맺은 연결을 다시 쓴다. 이 "다시 쓰기"가 성능의 핵심이라서 뒤에서 따로 다룬다.

## 왜 이렇게 여러 단계로 나뉘었나

처음부터 이렇게 설계된 건 아니다. 인터넷 초기에는 컴퓨터가 몇 대 안 돼서 이름과 주소를 파일 하나(hosts 파일)에 적어 두고 다 같이 나눠 썼다. 컴퓨터가 늘어나자 파일 하나로는 감당이 안 돼서 이름 관리를 나눠 맡는 DNS가 생겼다.

TCP와 IP도 원래는 한 덩어리였다가 나뉘었다. "어디로 보낼지(IP)"와 "빠짐없이 순서대로 보낼지(TCP)"를 분리하니, 신뢰성이 필요 없는 통신은 UDP를 쓰는 식으로 골라 쓸 수 있게 됐다.

TLS는 웹이 쇼핑과 결제에 쓰이기 시작하면서 끼어들었다. 원래 HTTP는 평문이라서, 중간에 있는 누구나 내용을 볼 수 있었다. 그래서 TCP와 HTTP 사이에 암호화 층을 끼워 넣은 게 HTTPS다.

각 단계가 따로 발전해 왔기 때문에, 하나를 바꿔도 나머지는 그대로 쓸 수 있다. HTTP/1.1이 HTTP/2로 바뀌어도 DNS와 IP는 그대로다. 이게 계층으로 나눈 설계의 가장 큰 장점이다(02편).

## [0] 네트워크로 나가기 전에: 브라우저 안

엔터를 누르자마자 네트워크로 나가는 게 아니다. 브라우저는 먼저 자기 안을 뒤진다.

**HSTS 확인.** 주소를 `example.com` 처럼 `https://` 없이 쳤다면, 원래는 평문 HTTP로 먼저 접속하고 서버가 "HTTPS로 가라"고 돌려보내야 한다. 그런데 이 첫 평문 요청은 중간에서 가로챌 수 있다. 그래서 서버는 응답 헤더 `Strict-Transport-Security` 로 "앞으로 일정 기간 우리 사이트는 무조건 HTTPS로만 와라"를 브라우저에 기억시킨다. 이걸 HSTS라고 한다. 한 번 기억한 브라우저는 평문 요청을 아예 보내지 않고 처음부터 HTTPS로 간다. 처음 방문하는 사이트도 보호하고 싶으면, 브라우저에 미리 내장된 목록(HSTS preload)에 도메인을 올린다.

**HTTP 캐시 확인.** 예전에 받아 둔 응답이 있고 아직 유효하면 네트워크에 나가지 않고 바로 쓴다. 유효한지는 서버가 보내 준 `Cache-Control` 헤더가 정한다.

- `max-age=3600`: 1시간 동안은 묻지도 않고 캐시를 쓴다.
- 유효 기간이 지났으면 서버에 "내가 가진 게 아직 최신이냐"고 짧게 묻는다. `ETag` 나 `Last-Modified` 값을 같이 보내고, 바뀐 게 없으면 서버는 본문 없이 `304 Not Modified` 만 돌려준다. 다운로드 양이 거의 0이 된다.
- `no-store`: 저장하지 마라. 개인 정보가 담긴 응답에 쓴다.

**DNS 캐시 확인.** 브라우저 자체의 DNS 캐시, 그다음 OS의 캐시를 본다. 여기서 답이 나오면 [1]은 거의 시간이 들지 않는다.

**이미 열린 연결 확인.** 같은 서버와 이미 맺어 둔 연결이 있으면 [3]·[4]를 건너뛴다. 이게 연결 재사용이다.

결국 "두 번째 방문이 첫 방문보다 훨씬 빠른" 이유는 거의 다 이 [0] 단계 덕분이다.

## [1] DNS: 이름을 주소로

캐시에 답이 없으면 OS는 설정된 DNS 서버(집에서는 공유기나 통신사, 회사에서는 사내 DNS)에 묻는다. 이 서버를 재귀 리졸버라고 부른다. 리졸버도 모르면 루트 서버 → `.com` 담당 서버 → `example.com` 담당 서버 순서로 차례로 물어서 답을 받아 온다. 받은 답은 TTL이라는 시간 동안 캐시한다.

여기서 기억할 점은 두 가지다.

- DNS는 보통 UDP를 쓴다. 연결을 맺지 않으니 빠르지만, 패킷이 사라지면 일정 시간 기다렸다가 다시 묻는다. 그래서 DNS가 느리면 페이지 전체가 "멈췄다가 뜨는" 느낌이 난다.
- 답으로 IP가 여러 개 올 수 있다. 큰 서비스는 사용자 위치에 따라 가까운 서버의 IP를 돌려주기도 한다. CDN이 이 방식을 쓴다.

자세한 조회 과정과 TTL 전략은 08편에서 다룬다.

## [2] 라우팅: 그 주소까지 가는 길

IP를 알았으니 패킷을 보내야 한다. 내 컴퓨터는 라우팅 테이블을 보고 판단한다. 목적지가 내 네트워크 안이면 직접 보내고, 밖이면 기본 게이트웨이(공유기)에 넘긴다.

같은 네트워크 안에서 실제 전달은 IP가 아니라 MAC 주소로 한다. 그래서 게이트웨이의 MAC 주소를 ARP로 알아낸다. 공유기를 지날 때는 NAT가 내 사설 IP를 공인 IP로 바꾼다. 그 뒤로는 인터넷의 라우터들이 각자 "다음 한 칸"만 정하며 패킷을 넘긴다. 전체 경로를 아는 장비는 없다.

라우팅은 04편, 주소 체계는 05편, NAT는 06편에서 깊게 본다.

## [3] TCP: 믿을 수 있는 통로 열기

데이터를 보내기 전에 양쪽이 "보낼 준비가 됐다"를 세 번의 패킷으로 확인한다.

```
클라이언트        서버
  SYN       →
            ←  SYN+ACK
  ACK       →
```

이 과정에 1 RTT(왕복 시간)가 든다. 서울에서 같은 서울 서버면 수 밀리초지만, 다른 대륙이면 100밀리초가 넘기도 한다. 이 시간은 서버를 아무리 빠르게 만들어도 줄지 않는다. 빛의 속도와 거리의 문제라서다. 그래서 줄이는 방법은 딱 두 가지다. 연결을 덜 맺거나(재사용), 서버를 가까이 두거나(CDN, 리전 선택).

TCP는 03편에서 깊게 다룬다.

## [4] TLS: 이 통로를 안전하게

서버가 인증서를 보내고, 브라우저는 그 인증서가 믿을 만한 기관이 서명한 `example.com` 의 것인지 확인한다. 그다음 이번 연결에서만 쓸 대칭키를 합의한다. TLS 1.3 기준 1 RTT가 든다. 예전 TLS 1.2는 2 RTT였다.

여기서 중요한 사실 하나: TCP와 TLS를 합치면, HTTPS 요청 하나를 보내기도 전에 이미 2 RTT가 지나간다. 왕복 50밀리초 서버라면 첫 바이트를 보내기 전에 100밀리초다. 연결 재사용이 왜 중요한지 숫자로 보이는 지점이다.

TLS는 07편에서 깊게 다룬다.

## [5] HTTP: 드디어 요청

암호화된 통로로 이런 요청을 보낸다.

```
GET / HTTP/1.1
Host: example.com
Accept: text/html
```

서버는 상태 코드와 헤더, 본문을 돌려준다.

```
HTTP/1.1 200 OK
Content-Type: text/html
Cache-Control: max-age=60

(HTML 본문)
```

`Host` 헤더가 있는 이유: 서버 하나(IP 하나)가 여러 도메인을 서비스할 수 있어서, "나는 example.com 을 원한다"를 알려 줘야 한다. 상태 코드는 첫 숫자로 성격을 안다. 2xx 성공, 3xx 다른 곳으로 가라, 4xx 요청한 쪽 잘못, 5xx 서버 쪽 잘못.

## [6] 화면 그리기와 추가 요청

브라우저는 HTML을 위에서부터 읽으며 화면 구조를 만든다. 중간에 CSS, JS, 이미지 링크가 나오면 그것도 받아야 한다. 페이지 하나에 요청이 수십~수백 개가 되는 이유다. 이때 [1]~[5]를 매번 처음부터 하면 너무 느리다. 그래서 연결 재사용과 HTTP 버전의 발전이 중요해진다.

## 심화 1: 연결 재사용과 HTTP 버전의 역사

### HTTP/1.0: 요청 하나에 연결 하나

초기 HTTP는 요청 하나를 보내고 응답을 받으면 연결을 끊었다. 이미지 열 개면 TCP 연결도 열 번 맺었다. 매번 핸드셰이크 비용을 낸 것이다.

### HTTP/1.1: keep-alive

연결을 끊지 않고 다음 요청에 다시 쓰는 keep-alive가 기본이 됐다. 하지만 한 연결에서는 **요청 하나를 보내고 응답을 다 받아야 다음 요청**을 보낼 수 있다. 앞의 응답이 느리면 뒤의 요청이 다 기다린다. 이걸 HOL(Head-of-Line) 블로킹이라고 한다. 줄 맨 앞 사람이 오래 걸리면 뒷사람 전부 못 가는 상황이다.

브라우저는 이걸 피하려고 같은 서버에 연결을 여러 개(보통 6개 안팎) 동시에 연다. 그래도 한계가 있어서, 개발자들은 이미지를 한 장으로 합치거나(스프라이트), 도메인을 여러 개로 쪼개는(도메인 샤딩) 꼼수를 썼다.

### HTTP/2: 한 연결에 여러 요청을 섞어서

HTTP/2는 연결 하나 안에 여러 개의 스트림을 만들고, 요청과 응답을 작은 프레임으로 쪼개 섞어서 보낸다. 앞 응답이 느려도 뒤 응답의 프레임이 먼저 도착할 수 있다. 이걸 멀티플렉싱이라고 한다. 헤더도 압축(HPACK)해서, 매번 반복되는 쿠키 같은 헤더 크기를 줄였다.

덕분에 HTTP 단계의 HOL 블로킹은 사라졌다. 그런데 문제가 하나 남았다. 그 아래 TCP는 여전히 "순서대로" 전달해야 한다. 패킷 하나가 사라지면, TCP는 그게 다시 올 때까지 뒤에 도착한 패킷들을 앱에 넘겨주지 않는다. 그 사라진 패킷이 스트림 A의 것이어도 스트림 B, C까지 다 같이 멈춘다. HTTP 층의 HOL은 풀었는데 TCP 층의 HOL이 남은 것이다. 손실이 많은 모바일 환경에서 이게 두드러진다.

### HTTP/3: TCP를 버리고 QUIC으로

HTTP/3는 TCP 대신 UDP 위에 QUIC이라는 새 전송 계층을 올렸다. QUIC은 스트림마다 따로 순서를 관리한다. 스트림 A의 패킷이 사라져도 B와 C는 계속 진행한다. TCP 층의 HOL까지 풀린 것이다.

QUIC은 TLS 1.3을 내장해서, 연결 맺기와 암호화 합의를 한 번에 한다. 그래서 첫 연결이 1 RTT, 다시 접속할 때는 0 RTT도 가능하다. 또 연결을 IP와 포트가 아니라 연결 ID로 구분해서, 와이파이에서 LTE로 바뀌어 IP가 달라져도 연결을 이어 갈 수 있다.

| 버전 | 한 연결에서 | 남은 HOL |
|---|---|---|
| HTTP/1.1 | 한 번에 하나 | HTTP·TCP 둘 다 |
| HTTP/2 | 여러 개 섞어서 | TCP 층 |
| HTTP/3 | 여러 개, 독립 | 거의 없음 |

브라우저는 처음에 HTTP/2 이하로 접속하고, 서버가 응답 헤더(`Alt-Svc`)로 "HTTP/3도 된다"고 알려 주면 다음부터 HTTP/3를 시도한다. 회사 방화벽이 UDP 443을 막고 있으면 자연스럽게 HTTP/2로 돌아간다.

## 심화 2: CDN은 경로 어디에 끼어드나

CDN은 전 세계 곳곳에 서버(엣지)를 두고, 사용자와 가까운 곳에서 응답하는 서비스다. 끼어드는 지점은 주로 [1] DNS다.

```
example.com 조회
 → CDN의 DNS가
   가까운 엣지 IP를 답함
 → 사용자는 엣지와
   TCP·TLS를 맺음 (가까움)
 → 엣지에 캐시가 있으면
   바로 응답
 → 없으면 엣지가
   원본 서버에 가져옴
```

효과는 세 가지다.

1. **RTT가 줄어든다.** TCP·TLS 핸드셰이크 상대가 가까운 엣지라서 2 RTT가 훨씬 짧아진다.
2. **원본 서버 부하가 줄어든다.** 이미지, JS 같은 정적 파일은 엣지가 대신 준다.
3. **엣지와 원본 사이 연결은 재사용된다.** 사용자가 처음 오더라도, 엣지는 원본과 이미 연결을 열어 두고 있다.

대신 캐시가 있다는 건 "옛날 내용을 보여 줄 수 있다"는 뜻이기도 하다. 배포했는데 사용자는 옛 화면을 본다면, CDN 캐시를 비우거나(invalidation), 파일 이름에 버전 해시를 붙여 새 파일로 인식시키는 게 정석이다.

## 심화 3: 단계별 시간 분해

"사이트가 느리다"는 말을 들으면, 어느 단계가 느린지부터 나눠야 한다. curl은 단계별 누적 시간을 보여 준다.

```
time_namelookup    DNS 끝
time_connect       TCP 끝
time_appconnect    TLS 끝
time_starttransfer 첫 바이트
time_total         전체
```

숫자는 누적이라서 빼서 본다.

| 구간 | 계산 | 느리면 의심 |
|---|---|---|
| DNS | namelookup | 리졸버, TTL |
| TCP | connect − DNS | 거리, 방화벽 |
| TLS | appconnect − connect | 인증서 체인, 거리 |
| 서버 처리 | starttransfer − appconnect | 앱, DB |
| 다운로드 | total − starttransfer | 크기, 대역폭 |

- TCP 구간이 길면 대개 물리적 거리(RTT)다. 서버를 가까이 두거나 CDN을 쓴다.
- TLS 구간이 TCP 구간의 두 배 가까이면 TLS 1.2일 가능성이 있다. 인증서 체인이 길어도 늘어난다.
- 서버 처리 구간(TTFB)이 길면 네트워크가 아니라 앱이나 DB 문제다. 이걸 네트워크 탓으로 돌리면 시간을 버린다.

## 자주 막히는 장애 사례

**1. 일부 사용자만 접속이 안 된다.**
- 증상: 같은 주소인데 어떤 사람은 되고 어떤 사람은 안 된다.
- 원인: DNS를 바꾼 직후, 사람마다 리졸버 캐시에 옛 IP가 남아 있다.
- 조치: 전환 전에 TTL을 미리 낮춘다. 옛 서버는 트래픽이 0이 될 때까지 남겨 둔다.

**2. 인증서 오류로 접속이 막힌다.**
- 증상: 브라우저에 "연결이 비공개로 설정되어 있지 않습니다".
- 원인: 인증서 만료, 도메인 이름 불일치, 중간 인증서 누락.
- 조치: 만료 알람, 관리형 인증서 자동 갱신. 이름이 인증서의 SAN에 있는지 확인.

**3. 배포했는데 옛 화면이 나온다.**
- 증상: 강력 새로고침을 하면 새 화면이 보인다.
- 원인: 브라우저나 CDN 캐시. `max-age` 가 길게 잡혀 있다.
- 조치: HTML은 짧게 캐시, JS·CSS는 파일 이름에 해시를 붙이고 길게 캐시.

**4. 첫 접속만 유독 느리다.**
- 증상: 새로고침하면 빨라진다.
- 원인: 첫 접속에만 DNS 조회, TCP·TLS 핸드셰이크가 다 들어간다. 먼 서버일수록 크다.
- 조치: CDN, 가까운 리전, TLS 1.3, HTTP/2·3 활성화.

**5. 회사망에서만 이상하게 느리다.**
- 증상: 집에서는 빠른데 회사에서만 느리다.
- 원인: 프록시나 방화벽이 UDP를 막아 HTTP/3가 실패하고 다시 HTTP/2로 돌아가는 과정, 또는 TLS 검사 장비가 중간에 끼어 있다.
- 조치: 같은 측정을 두 곳에서 해서 단계별로 비교한다.

## 클라우드에서는

| 단계 | 클라우드 구성 요소 |
|---|---|
| DNS | Route 53, Cloud DNS |
| 라우팅 | VPC 라우팅 테이블, IGW, NAT GW |
| TCP | 로드밸런서 유휴 타임아웃 |
| TLS | ACM, Certificate Manager |
| HTTP | L7 로드밸런서 경로 라우팅 |
| CDN | CloudFront, Cloud CDN |

- 사용자와 서버 사이 첫 지점은 대부분 로드밸런서나 CDN이다. TLS도 보통 여기서 끝난다. 뒤쪽 서버까지 암호화할지는 별도로 정한다.
- 로드밸런서와 앱 서버 사이 연결도 재사용된다. 앱의 keep-alive 시간이 로드밸런서의 유휴 타임아웃보다 짧으면, 앱이 먼저 연결을 끊으면서 간헐적 502가 날 수 있다(03편, 09편).
- 장애가 나면 이 글의 단계 순서대로 나눈다. 이름이 안 풀리는지(DNS) → 연결이 안 되는지(라우팅·보안 그룹·TCP) → 인증서 오류인지(TLS) → 서버가 에러를 주는지(HTTP). 이 순서가 그대로 장애 대응 순서다.

## 집에서 해보기 (지하철에서는 읽기만)

```bash
# [1] DNS
dig +short example.com

# [2] 기본 게이트웨이
route -n get default | grep gateway

# [2] 거치는 라우터들
traceroute -n example.com

# [3]~[5] 과정 전부 출력
curl -v https://example.com \
  -o /dev/null

# 단계별 시간
curl -o /dev/null -s -w \
'dns=%{time_namelookup}
tcp=%{time_connect}
tls=%{time_appconnect}
ttfb=%{time_starttransfer}
all=%{time_total}\n' \
https://example.com

# 캐시·HSTS·HTTP/3 헤더
curl -sI https://www.google.com \
 | grep -iE 'cache|strict|alt-svc'
```

같은 시간 측정을 가까운 서버와 먼 나라 서버에 각각 해 보면, tcp·tls 구간이 거리에 따라 같이 늘어나는 게 보인다. 같은 명령을 두 번 연속 실행하면 두 번째의 dns 구간이 거의 0이 된다. 캐시 덕분이다.

## 면접 한 줄 답

> DNSで名前を解決し、TCPで接続を確立、TLSで暗号化の合意をした後、HTTPでリクエストを送ります。障害対応でもこの順番で切り分けます。

DNS로 이름을 풀고, TCP로 연결을 맺고, TLS로 암호화를 합의한 뒤 HTTP로 요청을 보냅니다. 장애 대응도 이 순서로 나눠서 봅니다.

**꼬리질문 1. 두 번째 접속은 왜 빠른가요?**
브라우저와 OS에 DNS 결과가 캐시되고, HTTP 캐시로 일부 응답은 네트워크에 나가지 않으며, 이미 맺은 TCP·TLS 연결을 재사용하기 때문입니다.

**꼬리질문 2. HTTP/2와 HTTP/3의 차이는?**
HTTP/2는 TCP 연결 하나에 여러 요청을 섞어 보내지만, 패킷 하나가 사라지면 TCP가 순서를 맞추느라 모든 스트림이 멈춥니다. HTTP/3는 UDP 위의 QUIC을 써서 스트림마다 독립적으로 처리하고, 연결과 암호화 합의를 한 번에 합니다.

**꼬리질문 3. 사이트가 느리다는 보고를 받으면?**
DNS, TCP, TLS, 서버 처리, 다운로드 구간으로 시간을 나눠 측정합니다. 서버 처리 구간이 길면 앱이나 DB 문제, TCP·TLS 구간이 길면 거리나 네트워크 문제로 보고 각각 다르게 대응합니다.

## 정답

1. 사용자가 `https://` 없이 주소를 쳐서 첫 요청이 평문 HTTP로 나갈 때, 중간에서 그 요청을 가로채 가짜 페이지나 평문 연결로 유도하는 상황이다. HSTS를 기억한 브라우저는 처음부터 HTTPS로만 간다.
2. 2 RTT. TCP 핸드셰이크 1 RTT와 TLS 1.3 핸드셰이크 1 RTT. 그다음에 HTTP 요청이 나간다.
3. 사라진 것은 HTTP 층의 HOL(응답을 순서대로 기다리는 문제), 남은 것은 TCP 층의 HOL(패킷 하나가 사라지면 뒤 패킷이 다 기다리는 문제)이다.
4. 캐시 유효 기간이 지나 브라우저가 `ETag` 나 `Last-Modified` 로 "내 것이 아직 최신이냐"고 물었는데, 서버에서 바뀐 게 없을 때. 본문 없이 응답한다.
5. `time_starttransfer − time_appconnect`. TLS가 끝난 시점부터 첫 바이트가 올 때까지의 시간이다.
