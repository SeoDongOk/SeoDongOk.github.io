## 질문

서버에 `TIME_WAIT` 연결이 수천 개 쌓여 있다. 버그일까? 그리고 작은 요청을 보내는 API 응답이 이상하게 딱 40밀리초씩 늦다. 왜일까?

둘 다 TCP가 "믿을 수 있는 전달"을 약속하려고 만든 장치에서 나온다. 이 글은 TCP의 약속이 무엇이고 그걸 지키려고 어떤 장치를 두었는지, 그 장치들이 실무에서 어떤 장애로 나타나는지 본다.

## TCP가 약속하는 것

IP는 "최선을 다해 보내 보겠다"까지만 약속한다. 패킷이 사라지거나, 순서가 바뀌거나, 두 번 도착해도 IP는 책임지지 않는다. 그 위에서 TCP는 앱에게 이렇게 약속한다.

- **빠짐없이:** 사라진 건 다시 보낸다.
- **순서대로:** 뒤죽박죽 도착해도 앱에는 보낸 순서대로 준다.
- **깨지지 않게:** 체크섬으로 확인한다.
- **넘치지 않게:** 받는 쪽과 네트워크가 감당할 만큼만 보낸다.

앱 입장에서 TCP 연결은 "양쪽을 잇는 파이프"처럼 보인다. 파이프에 바이트를 넣으면 반대편에서 같은 순서로 나온다. 패킷이라는 단위는 앱에 보이지 않는다. 이 착각을 만들어 주는 게 TCP의 일이다.

이 약속을 지키려면 양쪽이 "어디까지 보냈고 어디까지 받았는지"를 기억해야 한다. 그래서 TCP는 데이터를 보내기 전에 **연결**을 맺어 서로의 상태를 맞춘다.

## 시퀀스 번호와 확인 번호

TCP는 패킷이 아니라 **바이트**에 번호를 붙인다.

```
보낸 쪽: 시퀀스 1000부터
 100바이트 전송
받는 쪽: "1100 받을 차례"
 → ACK 1100
```

- **시퀀스 번호:** 이 세그먼트의 첫 바이트가 전체 흐름에서 몇 번째인지.
- **확인 번호(ACK):** "여기까지 다 받았으니 다음엔 이 번호부터 보내라".

받는 쪽이 1000~1099와 1200~1299는 받았는데 1100~1199가 빠졌다면, ACK는 계속 1100이다. 중간이 비면 그 뒤를 받아도 "1100부터 달라"고 반복한다. 이게 뒤에서 볼 빠른 재전송의 신호가 된다.

시작 번호는 0이 아니라 무작위로 정한다. 예전 연결의 늦은 패킷이 새 연결과 번호가 겹치지 않게 하고, 공격자가 번호를 맞혀 가짜 패킷을 끼워 넣지 못하게 하려는 것이다.

## 연결 맺기: 3-웨이 핸드셰이크

```
클라이언트         서버(LISTEN)
SYN seq=x     →
         ←  SYN+ACK
            seq=y ack=x+1
ACK ack=y+1   →
ESTABLISHED      ESTABLISHED
```

세 번인 이유: 양쪽 모두 "내가 정한 시작 번호를 상대가 받았다"를 확인해야 한다. 두 번이면 서버는 자기 시작 번호 y가 클라이언트에 닿았는지 모른다. SYN 단계에서 MSS, 윈도 배율, SACK 사용 여부 같은 옵션도 같이 협상한다.

이 과정에 1 RTT가 든다. 그래서 연결을 재사용하는 HTTP keep-alive와 DB 연결 풀이 중요하다(01편).

### 서버 쪽 대기열: SYN 백로그와 accept 큐

서버 OS는 연결을 두 단계로 줄 세운다.

```
SYN 받음
 → 반쯤 열린 연결 (SYN 큐)
ACK 받음
 → 완성된 연결 (accept 큐)
앱이 accept()
 → 앱이 꺼내 감
```

앱이 바빠서 `accept()` 를 늦게 하면 accept 큐가 차고, 그 뒤 들어오는 연결은 버려지거나 거부된다. 앱이 `listen()` 할 때 정하는 backlog 값과 OS 상한이 이 큐 크기를 정한다. "서버 CPU는 여유 있는데 연결이 가끔 실패한다"면 이 큐를 의심한다.

### SYN 플러드와 SYN 쿠키

공격자가 SYN만 엄청 보내고 마지막 ACK를 안 보내면, 서버의 SYN 큐가 반쯤 열린 연결로 가득 찬다. 진짜 사용자의 SYN은 들어갈 자리가 없다. 이게 SYN 플러드다.

방어 방법이 SYN 쿠키다. 큐가 꽉 차면 서버는 반쯤 열린 연결을 저장하지 않는다. 대신 SYN+ACK의 시작 번호 y 안에 연결 정보를 암호학적으로 계산해 넣는다. 클라이언트가 진짜라면 ACK에 y+1을 돌려줄 테니, 서버는 그 번호를 검증해 연결 정보를 복원한다. 저장을 안 하니 큐가 넘치지 않는다. 리눅스에서는 `net.ipv4.tcp_syncookies` 로 켠다.

## 흐름 제어: 받는 쪽이 감당할 만큼

받는 쪽 OS는 도착한 데이터를 버퍼에 넣어 두고, 앱이 읽어 가면 비운다. 앱이 느리게 읽으면 버퍼가 찬다. 그래서 받는 쪽은 ACK를 보낼 때마다 "내 버퍼에 아직 이만큼 남았다"를 TCP 헤더의 윈도 크기(rwnd)로 알려 준다.

```
rwnd = 64KB
 → 보낸 쪽: ACK 없이도
   64KB까지 연달아 보냄
rwnd = 0
 → 보낸 쪽: 멈춤
   (가끔 살짝 찔러 봄)
```

이게 **슬라이딩 윈도**다. ACK를 하나하나 기다리지 않고, 윈도 크기만큼은 연달아 보낸다. ACK가 오면 창문이 앞으로 미끄러지며 다음 데이터를 보낼 수 있게 된다.

윈도 필드는 16비트라 최대 64KB 정도다. 요즘 고속 회선에는 너무 작아서, 핸드셰이크 때 **윈도 배율** 옵션으로 이 값에 곱할 배수를 정한다.

### 대역폭 × 지연 = 한 번에 떠 있어야 하는 양

멀리 있는 서버와 빠르게 통신하려면, ACK가 돌아오기 전까지 보낼 수 있는 양이 커야 한다. 회선 속도와 RTT를 곱한 값만큼은 "날아가는 중"이어야 회선을 꽉 채운다. 윈도가 그보다 작으면 회선이 아무리 빨라도 속도가 안 나온다. "대역폭은 넉넉한데 먼 리전과의 복사만 느리다"는 증상의 흔한 원인이다.

## 혼잡 제어: 네트워크가 감당할 만큼

흐름 제어는 받는 쪽만 본다. 그런데 중간의 라우터가 막히면 어떻게 될까. 모두가 최대 속도로 보내면 라우터 버퍼가 넘쳐 패킷이 사라지고, 모두가 재전송하면서 더 막힌다. 1980년대 인터넷에서 실제로 이런 붕괴가 있었고, 그 뒤 TCP에 혼잡 제어가 들어갔다.

보낸 쪽은 혼잡 윈도(cwnd)라는 값을 스스로 관리한다. 실제로 보낼 수 있는 양은 `min(rwnd, cwnd)` 다.

### 슬로 스타트

연결 직후에는 네트워크 상태를 모른다. 그래서 작게 시작해서 ACK가 올 때마다 cwnd를 늘린다. 이름과 달리 증가는 빠르다. RTT마다 대략 두 배가 된다.

```
RTT 1: 보낸 세그먼트 적게
RTT 2: 두 배
RTT 3: 또 두 배
...
임계값에 닿으면 → 혼잡 회피
```

새 연결은 처음 몇 RTT 동안 속도가 다 안 나온다. 짧은 요청마다 새 연결을 맺으면 매번 이 구간만 쓰다 끝난다. 연결 재사용이 중요한 또 하나의 이유다.

### 혼잡 회피

임계값을 넘으면 조심스럽게 RTT마다 조금씩만 늘린다. 손실이 생기면 "네트워크가 꽉 찼다"고 보고 cwnd를 크게 줄인다. 늘릴 때는 천천히, 줄일 때는 크게. 이 비대칭 덕분에 여러 연결이 한 회선을 나눠 쓸 때 서로 양보하게 된다.

### 빠른 재전송과 빠른 회복

손실을 알아내는 방법은 두 가지다.

1. **타임아웃:** 일정 시간 ACK가 안 온다. 기다리는 시간이 길고, 타임아웃이 나면 cwnd를 처음 수준까지 줄인다. 비싸다.
2. **중복 ACK:** 같은 확인 번호의 ACK가 연달아 세 번 더 온다. "그 뒤 데이터는 받고 있는데 중간 하나가 빠졌다"는 뜻이다. 타임아웃을 기다리지 않고 바로 그 부분만 다시 보낸다. 이게 **빠른 재전송**이다. 이때는 cwnd를 처음까지 줄이지 않고 반 정도로 줄여 이어 가는데, 이게 **빠른 회복**이다.

SACK 옵션을 쓰면 받는 쪽이 "1100~1199만 빠졌고 그 뒤는 받았다"를 구체적으로 알려 줄 수 있어서, 빠진 부분만 정확히 다시 보낸다.

### CUBIC과 BBR

혼잡 제어 방식은 여러 가지가 있고 OS가 고른다.

- **CUBIC:** 리눅스의 오랜 기본값. 손실을 혼잡 신호로 본다. 손실 직전 수준까지는 빠르게 회복하고 그 근처에서는 조심스럽게 늘린다.
- **BBR:** 구글이 만든 방식. 손실 대신 실제로 측정한 대역폭과 최소 RTT로 적정 속도를 추정한다. 손실이 잦지만 회선은 넓은 환경(장거리, 무선)에서 유리하다.

어떤 방식이든 핵심은 같다. **패킷 손실과 RTT가 TCP 속도를 정한다.** 손실률이 조금만 올라도 처리량이 크게 떨어질 수 있다.

## 네이글 알고리즘과 지연 ACK: 40밀리초의 정체

처음 질문의 두 번째 부분이다.

**네이글 알고리즘(보내는 쪽).** 1바이트짜리 데이터를 40바이트 헤더에 실어 보내는 건 낭비다. 그래서 "아직 ACK를 못 받은 작은 데이터가 있으면, 새 작은 데이터는 모아 뒀다가 ACK가 오면 같이 보낸다".

**지연 ACK(받는 쪽).** ACK만 단독으로 보내는 것도 낭비다. 그래서 받는 쪽은 ACK를 잠깐 미뤘다가, 그 사이 보낼 응답 데이터가 생기면 같이 실어 보낸다. 미루는 시간은 OS마다 다르다. 리눅스는 대략 수십 밀리초 수준이다.

둘이 만나면 서로를 기다린다.

```
보낸 쪽: 요청 앞부분 전송
 요청 뒷부분은 작아서
 → 네이글: ACK 기다림
받는 쪽: 요청이 덜 와서
 응답 못 함
 → 지연 ACK: 잠깐 미룸
… 지연 ACK 타이머 만료 …
받는 쪽: 이제 ACK
보낸 쪽: 이제 뒷부분 전송
```

결과적으로 작은 요청마다 지연 ACK 타이머만큼씩 일정하게 늦어진다. "작은 요청만 딱 일정 시간씩 늦다"는 증상이 나오면 이걸 의심한다.

해결은 지연에 민감한 앱(RPC, DB 드라이버, 게임)에서 소켓에 `TCP_NODELAY` 를 켜 네이글을 끄는 것이다. 요즘 대부분의 HTTP 클라이언트와 DB 드라이버는 이미 켜 두고 있다. 요청을 여러 번의 작은 write로 나눠 쓰지 말고 한 번에 쓰는 것도 같은 효과가 있다.

## 연결 끊기: 4-웨이 종료

```
먼저 끊는 쪽        상대
FIN          →
FIN_WAIT_1          CLOSE_WAIT
        ←  ACK
FIN_WAIT_2          (남은 것 전송)
        ←  FIN
                    LAST_ACK
ACK          →
TIME_WAIT           CLOSED
 (잠시 대기)
CLOSED
```

끊을 때는 네 번이다. TCP 연결은 양방향이라서, 한쪽이 "나는 다 보냈다(FIN)"고 해도 상대는 아직 보낼 게 남았을 수 있다. 그래서 방향마다 따로 닫는다. 상대가 보낼 게 없으면 ACK와 FIN을 합쳐 세 번에 끝나기도 한다.

## TIME_WAIT는 왜 있나

**먼저 끊은 쪽**이 마지막 ACK를 보낸 뒤 바로 사라지지 않고 일정 시간 기다린다. 리눅스는 60초다. 이유는 두 가지다.

1. **마지막 ACK가 사라졌을 때 대비.** 상대는 ACK를 못 받으면 FIN을 다시 보낸다. 이미 사라졌다면 상대는 에러(RST)를 받고, 깔끔하게 끝난 연결이 에러로 기록된다.
2. **늦게 도착한 옛 패킷 차단.** 같은 주소와 포트로 새 연결이 바로 생기면, 네트워크를 떠돌던 이전 연결의 늦은 패킷이 새 연결의 데이터로 섞일 수 있다. 충분히 기다리면 옛 패킷은 다 사라진다.

그래서 TIME_WAIT 자체는 버그가 아니라 정상이다. 다만 짧은 연결을 아주 많이 만드는 쪽에서는 쌓여서 문제가 된다.

### TIME_WAIT가 실제 문제가 되는 경우

연결은 출발지 IP, 출발지 포트, 목적지 IP, 목적지 포트 네 가지로 구분된다. 클라이언트가 **같은 목적지**에 연결할 때 바꿀 수 있는 건 출발지 포트뿐이다. 이 임시 포트 범위는 수만 개다. 초당 수천 개씩 새 연결을 만들고 끊으면, TIME_WAIT 60초 동안 포트가 묶여 바닥날 수 있다. 증상은 "연결을 맺을 수 없다", "주소가 이미 사용 중"이다. 프록시나 NAT 게이트웨이처럼 많은 연결이 같은 출구를 지나는 곳에서 특히 흔하다(06편).

대응 순서:
1. **연결을 재사용한다.** HTTP keep-alive, DB 연결 풀. 근본 해결이다.
2. **누가 먼저 끊는지 확인한다.** TIME_WAIT는 먼저 끊은 쪽에 남는다. 서버가 먼저 끊는 구조라면 서버에 쌓인다.
3. 그래도 필요하면 OS 설정을 검토한다. 리눅스 `net.ipv4.tcp_tw_reuse` 는 클라이언트 쪽에서 안전한 조건일 때 TIME_WAIT 포트를 새 연결에 재사용하게 해 준다. 임시 포트 범위를 넓히는 것도 방법이다.

예전 글에 자주 나오던 `tcp_tw_recycle` 은 NAT 뒤의 클라이언트들과 섞이면 연결을 엉뚱하게 거부하는 문제가 있어 리눅스에서 제거됐다. 따라 하면 안 된다.

### CLOSE_WAIT는 대개 버그

CLOSE_WAIT는 "상대는 FIN을 보내 끊었는데, 내 프로그램이 아직 소켓을 `close()` 하지 않은" 상태다. OS는 앱이 닫아 주기를 기다릴 뿐이라서, 앱이 안 닫으면 영원히 남는다. 쌓이면 파일 디스크립터가 바닥나 새 연결을 못 받는다. 원인은 거의 항상 코드다. 에러 경로에서 연결을 반환하지 않는 연결 풀, 응답 본문을 다 읽지 않고 버린 HTTP 클라이언트 같은 것들이다.

| 상태 | 남는 쪽 | 의미 |
|---|---|---|
| TIME_WAIT | 먼저 끊은 쪽 | 정상. 많으면 재사용 검토 |
| CLOSE_WAIT | 나중에 끊는 쪽 | 앱이 안 닫음. 버그 |

## RST: 정중한 종료가 아닌 즉시 끊기

FIN이 "다 보냈으니 닫자"라면, RST는 "이 연결은 없다, 당장 끊는다"다. RST가 오는 대표적인 경우:

- **닫힌 포트에 연결:** 아무도 듣지 않는 포트로 SYN을 보내면 RST가 온다. 클라이언트에는 "연결 거부(Connection refused)"로 보인다. 방화벽이 조용히 버리면 RST 대신 타임아웃이 난다. "거부"와 "타임아웃"의 차이로 앱이 죽었는지 방화벽이 막았는지 구분할 수 있다.
- **이미 잊어버린 연결에 데이터:** 서버가 재시작됐거나, 로드밸런서·NAT가 유휴 연결을 표에서 지운 뒤에 그 연결로 데이터가 오면 RST가 간다. 클라이언트에는 "연결이 상대에 의해 재설정됨(Connection reset by peer)"으로 보인다.
- **앱이 읽지 않은 데이터를 남기고 닫음:** 받은 데이터를 다 읽지 않은 채 `close()` 하면 FIN 대신 RST가 나가기도 한다.
- **의도적인 즉시 종료:** 프록시가 타임아웃이 지난 연결을 강제로 정리할 때.

## keepalive: 조용한 연결이 살아 있나

연결 위로 아무것도 오가지 않으면, 상대가 죽었는지 TCP는 모른다. 그 사이 중간의 NAT나 로드밸런서는 유휴 연결을 표에서 지워 버릴 수 있다. 그 뒤 데이터를 보내면 RST를 받거나 응답 없이 멈춘다.

TCP keepalive는 일정 시간 조용하면 빈 확인 패킷을 보내 상대가 살아 있는지 확인하는 기능이다. 리눅스 기본값은 두 시간 뒤에야 시작해서, 클라우드 NAT나 로드밸런서의 유휴 타임아웃보다 훨씬 길다. 그래서 오래 열어 두는 연결(DB 연결 풀, 메시지 큐)은 keepalive 시간을 짧게 잡거나, 연결 풀이 주기적으로 연결을 검사하게 한다.

HTTP의 keep-alive와 이름이 비슷하지만 다르다. HTTP keep-alive는 "요청이 끝나도 연결을 끊지 말고 다음 요청에 재사용하자"는 뜻이고, TCP keepalive는 "조용한 연결이 살아 있는지 찔러 보자"는 뜻이다.

## TCP와 UDP

| | TCP | UDP |
|---|---|---|
| 연결 | 맺는다 | 없다 |
| 순서·재전송 | 보장 | 없음 |
| 헤더 | 20바이트 이상 | 8바이트 |
| 쓰는 곳 | HTTP/1.1·2, DB, SSH | DNS, 영상 통화, QUIC |

UDP는 "빠르고 단순하게, 신뢰성은 필요한 만큼 앱이 직접"이다. 영상 통화에서 0.5초 전 화면 조각을 다시 받는 건 의미가 없다. 그래서 사라지면 그냥 넘어가는 UDP가 맞다. DNS는 질문과 답이 작아서 연결을 맺는 비용이 더 아깝다.

### QUIC: UDP 위에 다시 만든 TCP

TCP는 OS 커널 안에 있어서 바꾸기가 어렵다. 중간 장비들도 TCP 헤더 모양을 가정하고 동작해서 새 기능을 넣기 힘들다. 그래서 HTTP/3는 UDP 위에 QUIC이라는 새 전송 계층을 앱 쪽에 만들었다.

- 연결 맺기와 TLS 1.3 암호화 합의를 한 번에 해서 1 RTT, 재접속은 0 RTT.
- 스트림마다 독립적으로 재전송하므로, 패킷 하나가 사라져도 다른 스트림은 멈추지 않는다(01편의 HOL 블로킹).
- 연결을 연결 ID로 구분해서, IP가 바뀌어도(와이파이 → LTE) 연결이 이어진다.
- 혼잡 제어와 재전송은 TCP와 같은 원리를 쓴다. 바퀴를 새로 발명한 게 아니라, 바꾸기 쉬운 곳으로 옮긴 것이다.

## 자주 막히는 장애 사례

**1. 로드밸런서 뒤에서 간헐적 502.**
- 증상: 트래픽이 적을 때 가끔 502.
- 원인: 앱의 keep-alive 시간이 로드밸런서 유휴 타임아웃보다 짧다. 앱이 연결을 닫는 순간 로드밸런서가 그 연결로 요청을 보내 RST를 받는다.
- 조치: 앱 keep-alive를 로드밸런서 유휴 타임아웃보다 길게.

**2. 하룻밤 지나면 첫 DB 쿼리가 실패한다.**
- 증상: 아침 첫 요청만 "connection reset" 또는 오래 멈춘 뒤 실패.
- 원인: 연결 풀의 유휴 연결이 밤새 NAT·방화벽의 유휴 타임아웃에 걸려 중간에서 지워졌다.
- 조치: 풀의 연결 검사(유효성 확인), 최대 유휴 시간을 중간 장비 타임아웃보다 짧게, TCP keepalive 단축.

**3. 외부 API 호출이 "주소 사용 중"으로 실패.**
- 증상: 트래픽이 몰릴 때만 연결 생성 실패.
- 원인: 요청마다 새 연결을 맺고 끊어 TIME_WAIT로 임시 포트 고갈.
- 조치: HTTP 클라이언트 연결 재사용, 풀 크기 조정.

**4. 파일 디스크립터 고갈.**
- 증상: "Too many open files", CLOSE_WAIT 수천 개.
- 원인: 코드가 연결을 닫지 않음.
- 조치: 에러 경로의 연결 반환, 응답 본문 끝까지 읽기, 리소스 해제 코드 점검.

**5. 작은 요청만 일정하게 늦다.**
- 증상: 큰 요청은 빠른데 작은 요청이 매번 수십 밀리초씩 늦다.
- 원인: 네이글과 지연 ACK의 상호 대기.
- 조치: `TCP_NODELAY`, 요청을 한 번의 write로.

## 클라우드에서는

- **로드밸런서 유휴 타임아웃:** AWS ALB 기본 60초. 앱의 keep-alive를 이것보다 길게 잡는 게 정석이다.
- **NAT 게이트웨이:** 같은 목적지로 짧은 연결을 많이 만들면 포트가 모자란다. 유휴 연결도 일정 시간 뒤 지운다. 연결 재사용과 keepalive가 여기서도 답이다(06편).
- **DB 전환·장애 조치:** DB 주소가 바뀌어도 기존 TCP 연결은 옛 서버를 붙잡고 있다. 연결 풀이 끊긴 연결을 감지하고 다시 맺는 설정(유효성 검사, 재시도)이 필요하다.
- **리전 간 통신:** RTT가 커서 슬로 스타트와 윈도 크기의 영향이 커진다. 큰 데이터를 옮길 때는 병렬 연결이나 전송 전용 서비스를 쓴다.
- **보안 그룹은 상태를 기억한다:** 나가는 연결을 허용하면 그 응답은 자동으로 들어온다. 연결 추적 표 덕분이다. 반대로 상태를 기억하지 않는 NACL은 응답이 돌아올 임시 포트 범위를 따로 열어야 한다.

```bash
# 상태별 TCP 연결 수 (맥)
netstat -an -p tcp \
 | awk 'NR>2 {print $6}' \
 | sort | uniq -c

# 연결 하나 만들고 끊은 뒤
curl -s https://example.com \
  -o /dev/null
netstat -an -p tcp \
 | grep TIME_WAIT | head

# 닫힌 포트: 즉시 거부(RST)

# 리눅스 서버라면

ss -ti   # cwnd, rtt 등 내부값
sysctl net.ipv4.tcp_congestion_control
```

`ss -ti` 는 연결마다 cwnd, RTT, 재전송 횟수를 보여 준다. 혼잡 제어를 숫자로 볼 수 있는 가장 쉬운 방법이다.

## 면접 한 줄 답

> TIME_WAITは先に切断した側が、最後のACKの再送と古いパケットの混入を防ぐために待つ状態です。大量に溜まる場合は、まず接続の再利用を検討します。

TIME_WAIT는 먼저 끊은 쪽이 마지막 ACK 재전송과 옛 패킷 혼입을 막기 위해 기다리는 상태입니다. 많이 쌓이면 먼저 연결 재사용을 검토합니다.

**꼬리질문 1. 흐름 제어와 혼잡 제어의 차이는?**
흐름 제어는 받는 쪽 버퍼가 넘치지 않게 받는 쪽이 윈도 크기로 알려 주는 것이고, 혼잡 제어는 네트워크가 막히지 않게 보내는 쪽이 손실과 RTT를 보고 스스로 속도를 조절하는 것입니다. 실제 전송량은 둘 중 작은 값입니다.

**꼬리질문 2. CLOSE_WAIT가 많이 쌓이면?**
상대는 연결을 끊었는데 우리 앱이 소켓을 닫지 않은 상태라서 코드 문제로 봅니다. 에러 경로에서 연결을 반환하는지, 응답 본문을 끝까지 읽고 닫는지 확인합니다.

**꼬리질문 3. Connection refused와 타임아웃의 차이는?**
refused는 상대 호스트까지는 닿았지만 그 포트를 듣는 프로그램이 없어 RST가 온 것이고, 타임아웃은 방화벽이 조용히 버리거나 경로가 없어 아무 응답도 못 받은 것입니다.

## 정답

1. 양쪽 모두 자기가 정한 시작 번호를 상대가 받았다는 확인이 필요하다. 두 번이면 서버는 자기 시작 번호가 클라이언트에 도착했는지 확인할 수 없다.
2. 중간 데이터 하나가 빠졌다고 판단하고, 타임아웃을 기다리지 않고 그 부분을 바로 다시 보낸다(빠른 재전송). 혼잡 윈도는 처음까지가 아니라 절반 정도로 줄여 이어 간다(빠른 회복).
3. SYN만 보내고 ACK를 안 보내 서버의 반쯤 열린 연결 큐를 가득 채우는 SYN 플러드를 막는다. 큐에 저장하는 대신 연결 정보를 SYN+ACK의 시작 번호에 계산해 넣고, 돌아온 ACK 번호로 검증해 복원한다.
4. 보내는 쪽은 ACK를 기다리며 작은 데이터를 붙잡고, 받는 쪽은 응답과 같이 보내려고 ACK를 미뤄서 서로 기다린다. 작은 요청이 일정 시간씩 늦어진다. `TCP_NODELAY` 로 네이글을 끄거나 요청을 한 번에 쓴다.
5. TCP keepalive는 조용한 연결이 살아 있는지 빈 패킷으로 확인하는 기능이고, HTTP keep-alive는 요청이 끝나도 연결을 끊지 않고 다음 요청에 재사용하는 기능이다.
