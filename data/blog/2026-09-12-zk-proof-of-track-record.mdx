[지난 글](./2026-09-08-survivorship-bias-kills-alpha)에서 연 23.63%가 14.48%로
주저앉았고, 초과수익 p값이 0.566이 되면서 알파가 없다는 결론이 났다.

그런데 그 글을 쓰고 나서 더 신경 쓰인 건 숫자가 아니었다.

**조작한 게 하나도 없었다는 점이다.** 백테스트는 실제 가격으로 정확히 돌았다.
다만 다시 돌릴 수 있었을 뿐이다. 파라미터를 바꾸고, 유니버스를 다시 정의하고,
숫자가 예뻐질 때까지. 그리고 **그 과정은 흔적을 남기지 않는다.** 최종 숫자만
보는 사람은 그게 첫 시도인지 열 번째인지 알 방법이 없다.

이건 내 문제만이 아니다. 트랙 레코드를 볼 때 보통 "조작했나?"를 묻는데,
더 위험한 건 숫자가 전부 진짜인데도 거짓말이 되는 경우다.

> "1년 동안 전략 10개를 돌렸다. 이게 그중 이긴 거다."

모든 거래가 실제고, 모든 체결이 검증 가능하고, 수익률도 정확하다.
그런데 다음에 무슨 일이 일어날지에 대해서는 아무것도 말해주지 않는다.
선택이 숫자보다 **먼저** 일어났고, 선택은 흔적을 남기지 않기 때문이다.

그래서 만들었다. [proof-of-track-record](https://github.com/SeoDongOk/proof-of-track-record).

## 무엇을 만들었나

결과를 알기 **전에** 전략을 온체인에 커밋하고, 나중에 성과가 **그** 커밋된
전략에서 나왔음을 영지식으로 증명한다. 전략도 개별 거래도 공개되지 않는다.

주장 일곱 가지, 각각 하나의 회로다.

```
회로 1   거래 전에 전략을 커밋했다
회로 2-3 수익률이 커밋된 거래 로그에서 나왔다
회로 4   포지션별 리스크 한도를 지켰다
회로 5   수익률이 커밋된 계좌 NAV 와 맞는다      <- 손실을 뺄 수 없다
회로 6   전략을 몇 개 시도했는지가 공개된다       <- 체리피킹을 숨길 수 없다
회로 7   NAV 를 제3자가 공증했다                <- 자기신고가 아니다
```

회로 5와 6이 핵심이다.

**회로 5 (NAV 델타)**: 거래 로그만으로는 손실 거래를 애초에 커밋하지 않으면
된다. 그래서 계좌 잔고를 기간 시작·종료 시점에 커밋한다. 거래를 빼도 잔고는
바뀌지 않는다.

```
실제 거래: 5승 3패, 합계 -400bp   NAV 100,000,000 -> 96,000,000

이긴 5건만 골라 +950bp 주장  -> 거부: claimed return not met
실제 결과 (>= -400bp) 주장    -> 통과, 원장에 9600 기록
1bp 만 부풀려 (>= -399bp)     -> 거부
시작 NAV 를 사후에 반으로     -> 거부: open nav does not match its commitment
```

**회로 6 (전략 레지스트리)**: 컨트랙트 하나에 전략 하나를 잠그는 것만으로는
부족하다. 컨트랙트를 10개 배포하고 이긴 것만 보여주면 그만이다. 그래서 등록을
트레이더 식별자를 키로 하는 공유 레지스트리에 쌓고, **등록 개수를 공개한다.**

10개를 돌려 이긴 하나를 내미는 게 불가능해지는 건 아니다. **숨길 수 없게** 될
뿐이다. "1전 1승"과 "10개 중 1개"가 더는 같아 보이지 않는다.

## 왜 영지식이 필요한가

사전 커밋만이라면 쉽다. 문서를 해시해서 아무 체인에나 타임스탬프를 찍으면 된다.
실증 연구에서 이미 하는 일이다(OpenTimestamps 등).

문제는 트레이더가 전략을 공개할 수 없다는 것이다. 공개하면 알파가 죽는다.
그래서 커밋은 내용을 숨겨야 하고, 나중의 증명은 성과가 **그 숨겨진 것**에서
나왔음을 열어보지 않고 보여야 한다.

ZK 없이 "커밋된 전략으로 수익률 15% 이상"을 증명하려면, 결국 전략과 모든 거래를
공개해서 검증자가 직접 다시 계산하게 해야 한다.

## Compact 의 정보 흐름 타입 검사

Midnight 의 Compact 언어에서 가장 인상적이었던 건 이거다.
private 값이 public 원장에 도달하면 **컴파일이 거부된다.**

```
Exception: potential witness-value disclosure must be declared but is not:
  witness value potentially disclosed: the value of parameter h
  nature of the disclosure: ledger operation might disclose the witness value
```

공개하려면 `disclose()` 로 의도를 명시해야 한다. 그래서 공개되는 것은 내가
**공개하기로 결정한** 것이지, 실수로 새어 나간 것이 아니다. 프라이버시가
관례가 아니라 **타입 검사**로 강제된다.

개발 중에 실제로 두 건을 잡았다. 두 번째가 특히 좋았다.

1. 커밋 해시를 원장에 쓰는 것 — 해시도 witness 에서 파생된 값이니 `disclose()` 필요
2. **`checkRoot` 로 머클 루트를 확인하는 것** — 컴파일러가 "이 증명이 _어느_
   루트를 대상으로 하는지 드러난다"고 지적했다. 루트는 어차피 공개지만,
   사람 리뷰어라면 놓쳤을 채널이다.

## 그래서 NAV 가 진짜인지는 어떻게 아나

여기가 이 프로젝트의 한계였다. 커밋은 "내가 말한 걸 나중에 바꾸지 않았다"만
보장한다. 처음부터 지어낸 NAV 는 이후 모든 증명을 정직하게 통과한다.

**이건 설계로 없앨 수 없다.** 체인 안에서 바깥 사실("내 거래소 잔고가 X다")을
증명하려면 그것을 목격한 무언가가 필요하다. 그래서 숨기지 않고 슬롯으로 드러냈다.

설계상 핵심은 **서명 검증을 회로 밖에서 한다**는 것이다.

1. 공증인이 거래소 TLS 세션에서 잔고를 읽고 `(accountId, navCommitment)` 를 온체인에 올린다
2. 공증인 서명 검증은 체인과 검증자가 일반 도구로 한다 — 회로는 손대지 않는다
3. 회로는 "내 비공개 NAV 가 그 커밋을 연다"만 증명한다

이러면 Compact 0.31 에서 오늘 된다. 회로 안 서명 검증은 0.34 의
`secp256k1EcdsaVerify` 가 필요한데, 그건 ledger 9 대상이고 현재 네트워크는
ledger 8 이다.

### "브로커가 잔고에 서명하면 되잖아"는 성립하지 않는다

이걸 한동안 잘못 알고 있었다. 바이낸스의 Ed25519 서명은 **클라이언트가 요청에**
서명하는 방향이고, 거래소는 응답에 서명하지 않는다. 검증할 거래소 서명이 애초에
존재하지 않는다.

그래서 거래소 협조가 필요 없는 **zkTLS** 가 유일한 경로다.

## zkTLS 구현체 선택 — 둘은 탈락했다

|            | 상태                                                                                     | 헤드리스 CLI 적합성           |
| ---------- | ---------------------------------------------------------------------------------------- | ----------------------------- |
| TLSNotary  | `tlsn-js` **2026-02 아카이브**, Node 미지원. Rust 는 `0.1.0-alpha.15`(2025-05), CLI 없음 | ❌                            |
| Reclaim    | JS SDK 있음, 백엔드 `verifyProof()` 제공                                                 | ❌ QR 스캔/브라우저 확장 필수 |
| **Primus** | `zktls-core-sdk` 0.3.7 (2026-07), **네이티브 Node 애드온**                               | ✅                            |

Primus 문서에 이렇게 적혀 있었다 — _"사용자가 API 키를 에이전트 프로그램에
주면, 그 프로그램이 사용자를 대신해 zkTLS 증명을 생성한다."_ 정확히 내가 필요한
구조였다.

```js
const zkTLS = new PrimusCoreTLS()
await zkTLS.init(appId, appSecret)
const req = { url, method: 'GET', header, body: '' }
const resolves = [
  { keyName: 'totalMarginBalance', parseType: 'json', parsePath: '$.totalMarginBalance' },
]
const attRequest = zkTLS.generateRequestParams(req, resolves)
attRequest.setAttMode({ algorithmType: 'mpctls' })
const attestation = await zkTLS.startAttestation(attRequest)
if (zkTLS.verifyAttestation(attestation) !== true) throw new Error('검증 실패')
```

`mpctls` 는 공증인과 클라이언트가 MPC 로 세션 키를 나눠 갖는 모드다.
클라이언트가 응답을 고칠 수 없어 `proxytls` 보다 강하다.

실제로 돌린 결과, 라즈베리파이에서 돌고 있는 봇의 바이낸스 선물 계좌다.

```
[1] zkTLS 공증  (binance-futures, mpctls)
    GET https://fapi.binance.com/fapi/v3/account?recvWindow=60000&...
    증언 대상: $.totalMarginBalance

[2] 공증인 서명 검증 통과  (5.0s)
    읽어온 값: totalMarginBalance = 20.71157147
    공증인: 0xdb736b13e2f522dbe18b2015d0291e4b193d8ef6

[2b] 증언 값을 변조하면 검증이 거부하는가
    거부됨. 서명이 값에 묶여 있다.

[5] 증언된 NAV 로 ZK 증명  -> 통과. NAV 는 끝까지 비공개
[6] NAV 를 3배로 부풀려 시도 -> 거부
```

`[2b]` 를 매 실행마다 돌게 만든 게 중요했다. 값의 숫자 하나를 바꿔
`verifyAttestation()` 에 넣으면 `false` 가 나온다. 검증이 형식적이지 않다는 게
실행 결과로 남는다.

## 여기부터가 진짜 고생이었다 — SDK 지뢰 일곱 개

회로는 이틀이면 됐다. 온체인에 올리는 데 그보다 오래 걸렸다.
전부 "배포는 되는데 호출만 실패"하는 형태라 원인이 안 보였다.

### 1. wasm 클래스가 두 벌

```
Error: expected instance of StateValue
```

`onchain-runtime-v3` 가 3.1.1 과 3.0.0 두 벌 깔려 있었다. `compact-runtime` 은
`^3.0.0`, `midnight-js-protocol` 은 `3.0.0` 고정이라 npm 이 둘 다 설치했다.
같은 wasm 이라도 인스턴스가 분리되면 `instanceof` 가 깨진다.

`overrides` 로 3.0.0 에 맞추고 `npm dedupe` 로 **물리 복사본까지** 하나로
만들어야 했다. 버전만 맞추는 걸로는 부족했다.

### 2. 예외를 삼키는 SDK

```
POST /check -> 400  "bad input"
```

248바이트짜리 요청이 나가고 있었다. 회로 하나의 ZKIR 만 2607바이트인데.
프록시를 세워 본문을 떠 보니 이랬다.

```
midnight:(proof-preimage-versioned,option(wrapped-ir)):
```

IR 자리가 비어 있었다. 원인은 이거였다.

```js
const getKeyMaterial = async (zkConfigProvider, keyLocation) => {
  try {
    const zkConfig = await zkConfigProvider.get(keyLocation)
    return zkConfigToProvingKeyMaterial(zkConfig)
  } catch {
    return undefined
  } // ← 조용히 undefined
}
createCheckPayload(serializedPreimage, keyMaterial?.ir)
```

`httpClientProofProvider(url, zkConfigProvider, config)` 의 두 번째 인자가
필수인데 URL 만 넘겼다. `undefined.get()` 이 던진 예외를 `catch {}` 가 삼키고,
IR 없는 요청이 나가고, 증명서버는 `400 bad input` 만 돌려줬다.

**타입 정의는 필수 인자라고 말하고 있었다.** JS 라 런타임에 안 잡혔을 뿐이다.

### 3. 수수료 0 이면 거부당한다

```
RpcError 1010: Invalid Transaction: Custom error: 117
```

이 메시지만으로는 아무것도 알 수 없다. 노드 로그를 봐야 했다.

```
non-canonical dust actions: empty
Transaction malformed: transaction is not in normal form
Rejected ... Malformed(NotNormalized)
```

지갑이 만든 수수료 Intent 가 이랬다.

```
1: Intent {
    actions: [],
    dust_actions: Some(DustActions { spends: [], registrations: [], ... }),
}
```

`spends: []`. 호출 트랜잭션은 비용이 작아 수수료가 0 으로 계산되는데,
그런데도 빈 `DustActions` 를 붙인다. 노드는 그걸 비정규 형식으로 거부한다.
배포 트랜잭션은 쓰는 바이트가 많아 수수료가 양수라 이 문제를 비껴간다.

측정으로 확인했다.

```
additionalFeeOverhead 0        -> spends: []               -> 거부
additionalFeeOverhead 1000000  -> DustSpend{v_fee:1000001} -> SucceedEntirely
```

`MidnightWalletProvider.build()` 가 dust 옵션을 노출하지 않아
`FluentWalletBuilder` 로 직접 만들고 `withWallet()` 으로 감쌌다.

### 4~6. 공개 테스트넷은 또 다른 세계였다

로컬 devnet 에서 다 돌고 나서 Preview 에 올리려니, 세 개가 더 나왔다.

**`proofServer` 가 `undefined`** — 공개망은 증명서버를 각자 돌리는 구조라 설정에
URL 이 없다. 지갑 빌더가 `Invalid URL` 로 즉사한다.

**동기화 타임아웃 90초 하드코딩** — testkit 의 `start(true)` 는 로컬 devnet
기준이다. Preview 는 블록이 82만 개라 빈 지갑 동기화에 **19.6분** 걸렸다.
`syncWallet` 을 긴 타임아웃으로 직접 호출해야 했다.

**DUST 교착** — 이게 제일 재미있었다. Midnight 은 수수료를 DUST 로 내는데,
DUST 는 NIGHT UTXO 를 등록해야 생성되기 시작한다. 그런데 **등록 전에는 dust
동기화가 완료로 넘어가지 않는다.** "동기화가 끝나면 등록한다"는 순서 자체가
성립하지 않는다. unshielded 만 기다린 뒤 등록하고, 그다음에 DUST 를 폴링하도록
바꿔야 했다.

### 7. 공개 RPC 는 웹소켓을 끊는다

```
disconnected from wss://rpc.preview.midnight.network/: 1000:: Normal Closure
```

제출이 그 타이밍에 걸리면 실패한다. 백오프 재시도를 넣으니 1회 실패 후 성공했다.

## 안 되는 것도 적어둔다

**신뢰 가정이 사라지지 않았다.** "트레이더가 정직하다" 에서 "Primus 공증인
그룹이 정직하고 TLS 가 안 깨졌다" 로 옮겼을 뿐이다. 분산 공증인 그룹이라 훨씬
낫지만, 여전히 가정이다.

**시빌 저항이 없다.** 전략 레지스트리는 트레이더 식별자별로 세는데, 새 신원을
만들면 카운터가 0 으로 초기화된다. `accountId` 를 KYC 된 거래소 계좌에 묶어야
신원에 무게가 생긴다. 지금은 `sha256(apiKey)` 를 쓰고 있어서 키를 새로 발급하면
새 신원이 된다.

**선행 연구가 있다.** [Obscura](https://blog.horizen.io/trade-with-proof-not-trust-how-obscura-is-making-reputation-private-and-verifiable)
는 이미 라이브고, 거래소 API 로 데이터를 인증하는 더 어려운 절반을 풀었다.
다만 AWS Nitro TEE 를 쓴다 — 아마존 하드웨어와 그 증명 체인을 믿어야 하고,
TEE 는 사이드채널로 깨진 전력이 길다. 이 프로젝트에는 TEE 가 없다.
[Proof of Alpha](https://minaprotocol.com/blog/proof-of-alpha) 는 Mina 위에서
비슷한 걸 한다. 둘 다 **과거 성과**를 증명하지, 사전 커밋은 다루지 않는다.

내가 방어할 수 있는 좁은 주장은 이것뿐이다 —
**신뢰 하드웨어 없이, 히스토리를 고쳐 쓸 수 없는 자기증언 트랙 레코드.**

## 배운 점

**타입 시스템이 프라이버시를 강제하는 건 생각보다 강력하다.** `checkRoot` 건은
사람이라면 놓쳤을 채널이었다. "이건 어차피 공개니까 괜찮아"라는 판단조차
명시적으로 적게 만든다.

**SDK 가 예외를 삼키면 디버깅이 몇 배로 어려워진다.** `catch { return undefined }`
하나 때문에 프록시를 세워 HTTP 본문을 뜨고, 248바이트라는 숫자에서 역추적해야
했다. 타입 정의는 처음부터 필수 인자라고 말하고 있었다.

**에러 메시지가 없으면 로그를 봐야 한다.** `Custom error 117` 로는 아무것도
알 수 없었다. 노드 컨테이너 로그에 `non-canonical dust actions: empty` 가
찍혀 있었다. 클라이언트만 보고 있었으면 아직도 헤매고 있었을 것이다.

**"배포는 되는데 호출만 안 된다"는 패턴이 반복됐다.** 배포 트랜잭션이
호출보다 크고 무거워서, 크기·비용에 민감한 버그를 전부 비껴갔기 때문이다.
비슷한 증상을 만나면 두 경로의 차이부터 의심해볼 만하다.
