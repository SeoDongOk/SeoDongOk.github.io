## VPC의 기본 구성

VPC는 클라우드 안의 내 사설 네트워크다. 큰 주소 대역(예: `10.0.0.0/16`)을 잡고, 그 안을 서브넷으로 나눈다.

| 요소 | 역할 |
|---|---|
| 서브넷 | 가용 영역(AZ) 하나에 속하는 주소 구간 |
| 라우팅 테이블 | 서브넷에서 나가는 패킷이 어디로 갈지 |
| 인터넷 게이트웨이(IGW) | VPC와 인터넷을 잇는 문 |
| NAT Gateway | 사설 서브넷이 밖으로 **나가기만** 할 수 있게 해 주는 장치 |

**공인 서브넷과 사설 서브넷의 차이는 라우팅 테이블 한 줄이다.**

| 서브넷 | `0.0.0.0/0` 의 다음 홉 |
|---|---|
| 공인 | IGW |
| 사설 | NAT Gateway |

로드밸런서는 공인 서브넷에, 앱 서버와 DB는 사설 서브넷에 두는 것이 기본 모양이다.

## NAT Gateway로 나가는 길

사설 서브넷의 서버가 외부 API를 부르면, NAT Gateway가 출발 주소를 자기 공인 IP(Elastic IP)로 바꿔(SNAT) 내보낸다. 응답은 NAT Gateway가 기억한 연결 정보로 다시 원래 서버에 돌려준다.

여기서 생기는 실무 포인트가 있다.

- **외부에서 보이는 출발 IP는 NAT의 공인 IP 하나**다. 상대 시스템의 허용 목록에 이 IP를 넣는다.
- NAT를 다시 만들면 IP가 바뀐다. 허용 목록이 여러 곳에 흩어져 있으면 모두 고쳐야 한다. Elastic IP를 고정해 두는 이유다.
- NAT Gateway는 **켜 둔 시간 + 처리한 데이터 양**만큼 과금된다. 실습 뒤에는 반드시 지운다.

## 보안 그룹 vs NACL

| | 보안 그룹 | NACL |
|---|---|---|
| 붙는 곳 | 네트워크 인터페이스(인스턴스) | 서브넷 |
| 상태 | **상태 저장**: 나간 요청의 응답은 자동 허용 | 상태 비저장: 응답 방향도 따로 허용 |
| 규칙 | 허용만 | 허용·거부, 번호 순서대로 평가 |

대부분은 보안 그룹으로 충분하다. 보안 그룹은 다른 보안 그룹을 출발지로 지정할 수 있어서 "ALB에서 온 것만 앱으로" 같은 규칙을 IP 없이 쓸 수 있다.

## EKS에서 파드는 IP를 어떻게 받나

EKS는 관리형 쿠버네티스다. 제어부(API 서버)는 AWS가 운영하고, 노드는 내 VPC의 EC2다.

기본 네트워크 플러그인인 **AWS VPC CNI**는 파드에게 **VPC의 실제 IP**를 준다. 노드에 보조 네트워크 인터페이스(ENI)를 붙이고, 그 ENI의 보조 IP를 파드에 나눠 주는 방식이다.

- 장점: 파드가 VPC 안에서 일반 서버처럼 보인다. 보안 그룹, 라우팅을 그대로 쓴다.
- 주의 1: **서브넷 IP가 빨리 닳는다.** 노드 하나가 파드 수만큼 IP를 가져간다. 서브넷을 넉넉하게 잡는다.
- 주의 2: **인스턴스 타입마다 ENI 수와 IP 수 한도가 있다.** 작은 인스턴스는 파드를 많이 못 띄운다.

## 파드가 VPC 밖으로 나갈 때의 SNAT

VPC CNI는 파드가 VPC 밖 주소로 나갈 때 기본으로 노드 주 ENI의 IP로 SNAT한다. 그런데 파드가 보조 ENI에 있고 패킷이 보조 ENI로 나가면서 출발 주소가 주 ENI 주소로 바뀌면, VPC는 "이 인터페이스의 주소가 아닌 패킷"으로 보고 버린다.

증상은 "같은 파드에서 IP로 직접 붙으면 되는데, 쿠버네티스 Service(ClusterIP)를 거쳐 외부 주소로 가면 시간 초과"처럼 나타난다. kube-proxy의 DNAT와 CNI의 SNAT 순서가 얽힌 문제라 원인을 찾기 어렵다.

사설 서브넷에서 NAT Gateway로 나가는 구조라면 CNI의 SNAT를 끄고 NAT Gateway에 맡기는 설정(`AWS_VPC_K8S_CNI_EXTERNALSNAT=true`)이 해결책이 될 수 있다. 바꾸기 전에 확인할 것은 "파드가 밖에서 보이는 출발 IP가 바뀌는가"다. NAT Gateway를 거친다면 그대로다.

## EBS CSI

쿠버네티스 PersistentVolume으로 EBS 디스크를 쓰려면 EBS CSI 드라이버가 필요하다. EBS는 **AZ 하나에 묶인다.** 파드가 다른 AZ의 노드로 옮겨지면 디스크를 붙일 수 없다. DB 같은 상태 저장 파드는 이 제약을 알고 배치한다.

## 체크리스트

- [ ] 공인·사설 서브넷을 라우팅 테이블로 구분해 설명할 수 있다
- [ ] 외부에서 보이는 출발 IP가 무엇인지 안다 (NAT EIP)
- [ ] 서브넷 크기를 파드 수 기준으로 잡았다
- [ ] 실습 뒤 NAT Gateway와 EIP를 지웠다
