## 시험 직전 빈출도

> **우선순위 A · ★★★★☆**
>
> 애자일은 2020년 실기 출제 이력이 있고 XP 가치·스크럼 역할과 산출물이 자주 변형된다.

- **최소 암기:** 폭포수·프로토타입·나선형, 애자일 4가치, XP 5가치, 스크럼 역할·이벤트·산출물
- **5점 후보:** XP 5가치=의사소통·단순성·피드백·용기·존중 / 스크럼 3역할=PO·SM·개발자
- **판정 기준:** 별점은 Q-Net의 공식 출제 확률이 아니다. 2020년 1회~2026년 1회 복원 목록과 2026 시나공 핵심요약의 실기 출제 이력 표기를 개념군 단위로 교차해 정한 **시험 전날 상대 우선순위**다.

소프트웨어 생명주기 문제는 개발 모델의 특징과 위험 관리 여부를 구분한다. 애자일에서는 스크럼의 역할·이벤트·산출물과 XP의 실천 방법이 핵심이다.

## 1. 소프트웨어 생명주기

```text
계획·요구사항 → 분석 → 설계 → 구현 → 테스트 → 운영·유지보수
```

소프트웨어를 개발하고 운영·폐기할 때까지의 전체 과정을 체계적으로 정의한다.

## 2. 폭포수 모델

이전 단계를 완료한 뒤 다음 단계로 순차 진행한다.

```text
단계 구분과 산출물이 명확
관리가 단순
요구사항 변경에 유연하지 못함
후반에 사용자 피드백 반영이 어려움
```

문제 식별어:

```text
선형 순차
단계별 문서
이전 단계로 돌아가기 어려움
```

## 3. 프로토타입 모델

시제품을 빠르게 만들어 사용자 피드백으로 요구사항을 구체화한다.

```text
불명확한 요구사항 확인에 유리
사용자 참여 증가
시제품을 완성품으로 오해할 위험
품질이 낮은 임시 구조가 남을 수 있음
```

## 4. 나선형 모델

계획, 위험 분석, 개발, 평가를 반복한다.

```text
계획 → 위험 분석 → 개발·검증 → 고객 평가
```

- 위험 관리가 핵심이다.
- 대규모·고위험 프로젝트에 적합하다.
- 관리가 복잡하고 비용이 클 수 있다.

## 5. 반복·점진적 모델

시스템을 여러 증분으로 나눠 반복 개발하며 기능을 점진적으로 확장한다.

- 조기에 일부 기능을 제공할 수 있다.
- 피드백과 변경을 반영하기 쉽다.
- 전체 구조와 증분 사이의 일관성 관리가 필요하다.

## 6. 애자일 선언 가치

```text
프로세스와 도구보다 개인과 상호작용
포괄적인 문서보다 작동하는 소프트웨어
계약 협상보다 고객과의 협력
계획을 따르기보다 변화에 대응
```

오른쪽도 가치가 있지만 왼쪽을 더 중시한다.

## 7. 스크럼 역할

| 역할                       | 책임                                         |
| -------------------------- | -------------------------------------------- |
| 제품 책임자(Product Owner) | 제품 목표, 제품 백로그, 우선순위와 가치 관리 |
| 스크럼 마스터              | 스크럼 이해와 적용 지원, 장애물 제거 촉진    |
| 개발자                     | 스프린트 목표 달성을 위한 제품 증분 개발     |

```text
백로그 우선순위 = 제품 책임자
프로세스 촉진·장애물 제거 = 스크럼 마스터
제품 증분 구현 = 개발자
```

## 8. 스크럼 이벤트

| 이벤트        | 목적                            |
| ------------- | ------------------------------- |
| 스프린트      | 고정된 기간 동안 제품 증분 개발 |
| 스프린트 계획 | 스프린트 목표와 수행 작업 결정  |
| 데일리 스크럼 | 진행 상황 점검과 당일 계획 조정 |
| 스프린트 리뷰 | 결과물을 이해관계자와 검토      |
| 스프린트 회고 | 협업 방식과 프로세스 개선       |

```text
결과물 검토 = 리뷰
일하는 방식 개선 = 회고
```

## 9. 스크럼 산출물

| 산출물          | 의미                                    |
| --------------- | --------------------------------------- |
| 제품 백로그     | 제품에 필요한 작업의 우선순위 목록      |
| 스프린트 백로그 | 현재 스프린트에서 수행할 작업 계획      |
| 증분            | 완료 정의를 만족하는 사용 가능한 결과물 |

## 10. XP

변화하는 요구에 빠르게 대응하기 위해 의사소통, 단순성, 피드백, 용기, 존중을 강조한다.

### 주요 실천 방법

| 실천                    | 의미                                |
| ----------------------- | ----------------------------------- |
| Pair Programming        | 두 개발자가 함께 작업               |
| Test-Driven Development | 테스트를 먼저 작성하고 구현         |
| Continuous Integration  | 변경을 자주 통합하고 자동 검증      |
| Refactoring             | 외부 동작을 유지하며 내부 구조 개선 |
| Small Release           | 작은 단위로 자주 배포               |
| Collective Ownership    | 팀 전체가 코드에 공동 책임          |
| Simple Design           | 현재 요구를 만족하는 단순한 설계    |

## 11. 칸반

작업 흐름을 시각화하고 진행 중 작업 수를 제한하여 병목을 관리한다.

```text
작업 시각화
WIP 제한
흐름 관리
지속적 개선
```

## 12. DevOps

개발과 운영의 협업을 강화하고 자동화된 전달 파이프라인으로 빠르고 안정적인 배포를 추구한다.

```text
협업 문화
자동화
지속적 통합·전달
모니터링과 피드백
```

## 13. 시험 직전 암기

```text
선형 순차 = 폭포수
시제품으로 요구 확인 = 프로토타입
위험 분석 반복 = 나선형
짧은 반복과 변화 대응 = 애자일
백로그 우선순위 = 제품 책임자
장애물 제거 = 스크럼 마스터
결과물 검토 = 스프린트 리뷰
프로세스 개선 = 스프린트 회고
테스트 먼저 = TDD
둘이 함께 개발 = Pair Programming
작업 시각화·WIP 제한 = 칸반
```
