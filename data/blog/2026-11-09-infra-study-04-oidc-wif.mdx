## 왜 키를 없애야 하나

CI에서 클라우드에 배포하려면 권한이 필요하다. 가장 쉬운 방법은 액세스 키를 CI 비밀값에 넣는 것이다. 문제는 그 키가 **만료되지 않고**, 새면 누가 어디서 쓰는지 막기 어렵다는 점이다.

대안은 **신원 연합(identity federation)**이다. CI가 "나는 이 저장소의 main 브랜치에서 도는 작업이다"라는 서명된 토큰을 받고, 클라우드는 그 토큰을 확인한 뒤 **짧게 사는 임시 자격 증명**을 내준다.

## 흐름

```
GitHub Actions ──(1) OIDC 토큰 요청──▶ GitHub OIDC 발급자
       │ (2) 토큰: iss, aud, sub="repo:org/app:ref:refs/heads/main"
       ▼
  AWS STS AssumeRoleWithWebIdentity ──(3) 신뢰 정책 확인──▶ 임시 자격 증명 (1시간)
```

토큰 안의 클레임이 핵심이다.

| 클레임 | 뜻 | 신뢰 조건에서 |
|---|---|---|
| `iss` | 누가 발급했나 | IAM OIDC 공급자로 등록 |
| `aud` | 누구에게 쓰라고 발급했나 | `sts.amazonaws.com` 고정 |
| `sub` | 누구인가 (저장소·브랜치·환경) | **반드시 좁힌다** |

## 신뢰 조건이 전부다

```json
"Condition": {
  "StringEquals": {
    "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
    "token.actions.githubusercontent.com:sub": "repo:my-org/my-app:ref:refs/heads/main"
  }
}
```

`sub`를 `repo:my-org/*`처럼 넓히면 조직의 아무 저장소, 아무 브랜치(포크 PR 포함 가능)가 이 역할을 빌릴 수 있다. 연합 인증의 사고는 대부분 이 조건이 넓어서 생긴다.

저장소 이름 대신 **변하지 않는 ID**(저장소 ID, 소유자 ID)를 쓰는 형식도 있다. 저장소 이름을 바꾸거나 같은 이름으로 다시 만드는 경우까지 막을 수 있다.

## GCP의 Workload Identity Federation

GCP도 같은 구조다.

1. **워크로드 아이덴티티 풀**과 **공급자**(GitHub OIDC)를 만든다.
2. 공급자에 **속성 조건**을 건다. 예: `assertion.repository == "my-org/my-app"`
3. 서비스 계정에 "이 풀의 이 주체가 나를 흉내 낼 수 있다"(`roles/iam.workloadIdentityUser`)를 준다.

## 클라우드 사이의 연합

같은 방식으로 **GCP 워크로드가 AWS 권한을 빌릴** 수도 있다. GCP 서비스 계정이 Google ID 토큰을 받고, AWS IAM 역할이 `accounts.google.com`을 신뢰하되 조건으로 **그 서비스 계정의 고유 ID**를 고정한다.

```json
"Condition": { "StringEquals": { "accounts.google.com:sub": "<서비스 계정 고유 숫자 ID>" } }
```

이메일이 아니라 숫자 ID를 쓰는 이유는, 같은 이메일로 서비스 계정을 지웠다가 다시 만들어도 ID는 바뀌기 때문이다.

## 권한은 작게

연합으로 키를 없앴어도 빌린 역할의 권한이 넓으면 위험은 그대로다.

- 빌드용 역할은 이미지 저장소에 쓰기만.
- 배포용 역할은 해당 클러스터·네임스페이스만.
- "관리자 하나로 다 하기"는 편하지만, 그 하나가 뚫리면 모든 환경이 같이 뚫린다.

## 체크리스트

- [ ] 장기 액세스 키 대신 OIDC 연합을 쓴다
- [ ] `sub` 조건을 저장소·브랜치(또는 환경)까지 좁혔다
- [ ] 클라우드 간 연합은 이메일이 아닌 고유 ID로 고정했다
- [ ] 빌린 역할의 권한을 작업 단위로 나눴다
