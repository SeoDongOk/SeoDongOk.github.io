[Echo 인프라 시리즈 전체 목차](/blog/2026-11-05-echo-infra-series)

> 2026년 11월 4일 기준 해커톤 구현 회고입니다. 당시 코드와 작업 기록을 기준으로 정리했으며, 현재 서비스 상태나 모든 환경에 적용되는 설정을 보장하지 않습니다.

## 기술 명칭과 설명

Prometheus는 지표를 주기적으로 수집하는 시스템이고 Grafana는 지표를 화면으로 보여줍니다. Counter는 누적 건수, Histogram은 지연시간 같은 분포를 집계하는 도구입니다. p95는 관측 요청의 약 95%가 그 값 이내라는 백분위 지표입니다. k6는 합성 부하를 발생시키는 도구입니다.

## 내가 무엇을 했는가

진입점 Prometheus·Grafana와 /summary를 추가했습니다. 단계 승격용 /counters는 Prometheus가 아니라 Envoy 호스트 통계에서 환경별 요청·오류 누계를 즉시 읽게 했습니다. GKE 시연용 부하 발생기와 데이터 리허설 기록 스크립트도 추가했습니다.

## 트러블슈팅: 문제 → 원인/판단 → 조치

Prometheus는 5초 수집 간격이라 짧은 전환 단계의 첫 지표가 비거나 늦을 수 있습니다. 그래서 화면 요약용 /summary와 건수 판정용 /counters를 분리했습니다. 경로 aggregate 클러스터에 기록되는 응답 코드·지연과 실제 환경 호스트 통계를 혼동하지 않도록 문서화했습니다.

## 해결 결과와 아직 남은 한계

첫 이전 때 p95 null, 카운터 재시작·호스트 교체 시 감소 문제는 주의점입니다. 기준값을 재설정해야 합니다. 9초 이전·13초 복귀·실패 요청 0 등은 API 담당의 통합 시연 기록이며 본인 단독 성능 성과가 아닙니다. 클러스터 공통 OTel 수집기도 아직 후속입니다.

## 발표·면접에서 설명할 문장

> 화면용 지표와 자동 판정용 지표의 시간 특성이 다르다는 점을 반영해, 승격은 즉시 요청 카운터로 확인하도록 만들었습니다.

## 기여 범위와 검증 기준

본인 작성의 비병합 커밋과 변경 내용을 대조했습니다. 코드 구현, 적용 기록, 실측 결과는 구분합니다. 팀원이 만든 기반을 확장한 작업은 그 경계를 본문에 명시했고, 목표 수치는 완료 성과로 표현하지 않았습니다. 운영 경로와 식별자는 공개본에서 생략했습니다.
