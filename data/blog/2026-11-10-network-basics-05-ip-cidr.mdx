## 질문

VPC를 `10.0.0.0/16` 으로 만들고 서브넷을 `/24` 로 나누면, 서브넷은 몇 개이고 각각 몇 대를 넣을 수 있을까? 그리고 1년 뒤 다른 VPC와 연결하려는데 대역이 겹친다면?

첫 질문의 답은 256개, 클라우드 기준 각 251대다. 두 번째 질문은 답이 "처음부터 다시 설계"일 수도 있다. 이 글은 계산을 손에 익히고, 나중에 후회하지 않는 대역 설계까지 간다.

## 개념: 주소는 "동네 + 번지"

IP 주소는 두 부분으로 되어 있다.

- **네트워크 부분**: 어느 동네인가
- **호스트 부분**: 그 동네의 몇 번지인가

라우터는 네트워크 부분만 보고 길을 정한다(04편). 동네 안에서 번지를 찾는 건 그 동네의 몫이다. 이렇게 나누면 인터넷 라우터는 세상의 모든 컴퓨터가 아니라 **동네 목록만** 알면 된다.

어디까지가 동네인지를 알려 주는 게 **서브넷 마스크**, 또는 CIDR 표기의 `/숫자` 다.

## 이진수 연습: 여기서 막히면 전부 막힌다

IPv4 주소는 32비트다. `192.168.10.5` 는 8비트씩 끊어 10진수로 쓴 것이다. 8비트 한 칸(옥텟)의 자릿값은 이것만 외우면 된다.

```
128 64 32 16  8  4  2  1
```

**10진수 → 이진수**: 큰 자리부터 뺄 수 있으면 1, 못 빼면 0.

```
172 = 128+32+8+4
    = 1010 1100

130 = 128+2
    = 1000 0010

200 = 128+64+8
    = 1100 1000
```

**이진수 → 10진수**: 1인 자리만 더한다.

```
1111 0000 = 128+64+32+16
          = 240
1110 0000 = 224
1100 0000 = 192
1000 0000 = 128
```

마스크에 나오는 숫자는 앞에서부터 1이 채워진 모양뿐이라 종류가 적다. `128, 192, 224, 240, 248, 252, 254, 255` 여덟 개만 익숙해지면 된다.

**마스크 ↔ CIDR 변환**: 마스크의 1의 개수가 `/` 뒤 숫자다.

```
255.255.255.0   = /24 (8+8+8)
255.255.255.192 = /26 (8+8+8+2)
255.255.240.0   = /20 (8+8+4)
```

맥에서 `ifconfig` 를 보면 마스크가 `0xffffff00` 처럼 16진수로 나온다. `ff` 는 255, `00` 은 0이니 `/24` 다.

## 왜 클래스 방식이 사라졌나

처음에는 첫 숫자로 크기를 고정했다.

| 클래스 | 첫 비트 | 크기 |
|---|---|---|
| A | 0 | /8 (약 1,600만) |
| B | 10 | /16 (약 6만 5천) |
| C | 110 | /24 (254) |

300대가 필요한 회사는 C로 모자라서 B를 받았고, 6만 개 넘는 주소가 놀았다. 주소 낭비가 심해지고 인터넷 라우팅 표도 폭발적으로 커지자, 1993년에 **아무 비트 위치에서나 끊을 수 있는 CIDR**로 바뀌었다. 지금 "클래스 C"라는 말은 그냥 "/24 정도 크기"라는 관용어로만 남아 있다.

## 손 계산 공식

호스트 비트가 `h` 개면 주소는 `2^h` 개다. 이 중 2개는 못 쓴다.

- 맨 앞(호스트 부분 전부 0): 네트워크 자체를 가리키는 주소
- 맨 뒤(호스트 부분 전부 1): 브로드캐스트 주소

| CIDR | 주소 수 | 일반 | AWS |
|---|---|---|---|
| /16 | 65,536 | 65,534 | 65,531 |
| /20 | 4,096 | 4,094 | 4,091 |
| /24 | 256 | 254 | 251 |
| /26 | 64 | 62 | 59 |
| /28 | 16 | 14 | 11 |

AWS는 서브넷마다 5개를 예약한다(네트워크 주소, VPC 라우터, DNS, 예비 1개, 브로드캐스트). GCP는 서브넷 기본 범위에서 4개를 예약한다. 숫자를 외우기보다 "클라우드는 몇 개를 더 가져간다"를 기억하면 된다.

## 서브네팅 예제

**예제 1: /24 를 4개로**

`192.168.1.0/24` 를 4개로 나누려면 비트 2개를 더 빌린다(2^2=4). `/26` 이 되고, 한 칸은 64개다.

```
192.168.1.0/26    .0   ~ .63
192.168.1.64/26   .64  ~ .127
192.168.1.128/26  .128 ~ .191
192.168.1.192/26  .192 ~ .255
```

**예제 2: 이 주소는 어느 서브넷인가**

`10.20.37.200/20` 의 네트워크 주소와 브로드캐스트는?

1. `/20` 은 앞 16비트 + 셋째 칸 4비트가 네트워크다.
2. 셋째 칸의 한 블록 크기는 `2^(8-4) = 16`.
3. 37이 들어가는 16의 배수 구간: 32 ~ 47.
4. 네트워크 `10.20.32.0`, 브로드캐스트 `10.20.47.255`.

요령은 **"끊기는 칸"을 찾고, 그 칸의 블록 크기로 나누는 것**이다. 블록 크기는 `256 - 마스크값` 으로도 구한다. `/20` 마스크의 셋째 칸은 240이니 `256-240=16`.

**예제 3: /16 을 /24 로**

네트워크 비트가 8개 늘어나니 `2^8 = 256` 개 서브넷. `10.0.0.0/24`, `10.0.1.0/24`, …, `10.0.255.0/24`.

**예제 4: 필요한 크기에서 거꾸로**

서버 200대가 들어갈 서브넷의 최소 크기는? 2를 거듭제곱해서 200 + 예약분을 넘는 첫 값은 256이다. 그래서 `/24`. 클라우드에서는 앞으로 늘어날 몫까지 생각해 한 단계 크게 잡는 경우가 많다.

## 심화 1: 경로 요약 (슈퍼네팅)

서브네팅의 반대다. 작은 대역 여러 개를 큰 대역 하나로 묶어 라우팅 표를 줄인다.

```
192.168.0.0/24
192.168.1.0/24   →  192.168.0.0/22
192.168.2.0/24
192.168.3.0/24
```

넷째 칸 앞까지 공통 비트가 22개라서 `/22` 하나로 표현된다. 조건은 **연속되어 있고, 경계가 맞아야** 한다는 것이다. `192.168.1.0` ~ `192.168.4.0` 처럼 경계가 어긋나면 깔끔하게 묶이지 않는다.

이게 대역 설계에서 중요한 이유: 지역별, 환경별로 대역을 **연속된 덩어리**로 나눠 두면, 다른 네트워크에 알릴 때 한 줄로 요약할 수 있다. 표가 짧으면 실수도 줄고 장비 부담도 준다.

## 심화 2: VLSM — 크기가 다른 서브넷 섞기

모든 서브넷을 같은 크기로 자를 필요는 없다. `/24` 하나에서 100대, 50대, 20대, 장비 2대짜리 연결선이 필요하다면, **큰 것부터** 떼어 낸다.

```
.0   ~ .127  /25  100대용
.128 ~ .191  /26  50대용
.192 ~ .223  /27  20대용
.224 ~ .227  /30  2대 연결
.228 ~ .255  남김
```

큰 것부터 자르는 이유는 경계를 맞추기 위해서다. 작은 걸 먼저 앞에 두면 큰 블록이 들어갈 자리의 경계가 어긋난다. 이렇게 서브넷마다 다른 마스크를 쓰는 걸 VLSM이라고 한다. 라우터 두 대만 잇는 선은 `/31` 로 주소 2개만 쓰는 방식도 표준으로 허용된다.

## 심화 3: 조직 전체 대역 설계

클라우드 엔지니어가 "공통 기반"을 설계할 때 가장 먼저 하는 일 중 하나가 **IP 대역 할당표**다. 나중에 바꾸기가 가장 어려운 결정이라서다.

**원칙**

1. **겹치지 않게.** 회사 사무실, 데이터센터, 모든 VPC, 다른 클라우드까지 한 표에서 관리한다. 연결할 가능성이 조금이라도 있으면 겹치면 안 된다.
2. **요약되게.** 지역 → 환경 → 용도 순으로 큰 덩어리부터 자른다.
3. **넉넉하게, 하지만 무한하지 않게.** VPC 하나에 `/16` 을 습관처럼 주면 `10.0.0.0/8` 도 금방 바닥난다.

**예시 (가상의 회사)**

```
10.0.0.0/8 회사 전체
├ 10.0.0.0/12  도쿄 리전
│ ├ 10.0.0.0/16  공용(허브)
│ ├ 10.1.0.0/16  운영
│ ├ 10.2.0.0/16  스테이징
│ └ 10.3.0.0/16  개발
├ 10.16.0.0/12 오사카 리전
└ 10.240.0.0/12 사무실·데이터센터
```

허브-스포크 구조라면 공용 서비스(DNS, 공유 도구, 외부 연결)를 허브 VPC에 두고, 운영·개발 같은 스포크 VPC가 허브와만 연결된다. 스포크끼리는 직접 통하지 않게 해서 개발 환경에서 운영 DB로 가는 길을 원천적으로 막는다.

**쿠버네티스 대역은 따로 계산한다**

- **파드 대역**: 파드마다 IP를 받는다. AWS VPC CNI는 파드에 VPC 서브넷 IP를 직접 주므로, 노드 수 × 노드당 파드 수만큼 서브넷이 커야 한다. GKE의 VPC 네이티브 클러스터는 서브넷의 보조 범위를 파드용으로 쓴다.
- **서비스 대역**: ClusterIP가 쓰는 가상 대역. 클러스터 밖에서는 안 보이지만, **회사망 대역과 겹치면** 파드가 그 회사 서버로 가는 요청을 클러스터 안 서비스로 착각한다. kubeadm 기본값은 `10.96.0.0/12` 다.
- **도커 기본 대역**: 도커 기본 브리지는 `172.17.0.0/16` 이다. 회사망이 `172.16.0.0/12` 안을 쓰면 개발자 노트북에서 특정 사내 서버만 안 붙는 일이 생긴다.

## 심화 4: 특수 대역

| 대역 | 용도 |
|---|---|
| 10.0.0.0/8 | 사설 |
| 172.16.0.0/12 | 사설 |
| 192.168.0.0/16 | 사설 |
| 127.0.0.0/8 | 루프백 (자기 자신) |
| 169.254.0.0/16 | 링크 로컬 |
| 100.64.0.0/10 | 통신사 공유 NAT (CGNAT) |

- **루프백**: `127.0.0.1` 로 보내면 네트워크 카드 밖으로 나가지 않고 자기 자신에게 돌아온다. 서버에서 앱을 `127.0.0.1` 에만 열어 두면 밖에서는 접근할 수 없다. 반대로 컨테이너 안에서 `127.0.0.1` 은 **컨테이너 자신**이라, 호스트의 DB를 찾지 못하는 흔한 실수가 생긴다.
- **링크 로컬 169.254**: DHCP 서버를 못 찾았을 때 운영체제가 스스로 붙이는 주소이기도 하다. 노트북 IP가 `169.254.x.x` 로 나오면 "DHCP에서 주소를 못 받았다"는 뜻이다. 클라우드에서는 `169.254.169.254` 가 **인스턴스 메타데이터 서버**다. 인스턴스 안에서 이 주소로 자기 정보와 임시 자격 증명을 받는다. 그래서 서버가 사용자 입력 URL을 대신 요청해 주는 기능이 있으면, 공격자가 이 주소를 넣어 자격 증명을 빼 가는 공격(SSRF)이 가능하다. AWS가 토큰을 먼저 받아야 하는 IMDSv2를 권장하는 이유다.
- **100.64.0.0/10**: 통신사가 가입자들을 큰 NAT 뒤에 묶을 때 쓰라고 따로 떼어 둔 대역이다. 사설 대역과 겹치지 않게 하려는 것이다. 클라우드나 회사망에서 사설 대역이 모자랄 때 추가 대역으로 쓰기도 한다.

## 심화 5: IPv6

IPv4 주소가 바닥나는 문제의 근본 해결책이다.

- **128비트**. `2001:db8:0:0:0:0:0:1` 처럼 16비트씩 16진수로 쓰고, 연속된 0은 한 번만 `::` 로 줄여 `2001:db8::1` 로 쓴다.
- **서브넷은 보통 /64**. 앞 64비트가 네트워크, 뒤 64비트가 인터페이스다. 주소가 충분해서 아껴 쓸 필요가 없다.

**주소 종류**

| 종류 | 대역 | 뜻 |
|---|---|---|
| 글로벌 유니캐스트 | 2000::/3 | 인터넷 공인 주소 |
| 링크 로컬 | fe80::/10 | 같은 링크 안에서만 |
| 고유 로컬 | fc00::/7 | IPv4 사설과 비슷 |
| 멀티캐스트 | ff00::/8 | 여러 대에게 |
| 루프백 | ::1 | 자기 자신 |

**SLAAC (자동 주소 설정)**: DHCP 서버 없이도 주소를 만든다. 라우터가 "이 링크의 접두사는 이것"이라고 주기적으로 알리면(Router Advertisement), 각 장비가 그 접두사 뒤에 자기 인터페이스 값을 붙여 주소를 만든다. 인터페이스 값은 예전에는 MAC에서 만들었지만, 추적을 막으려고 요즘은 무작위 값을 많이 쓴다.

**ARP 대신 NDP**: IPv6에는 브로드캐스트가 없고, ARP 역할을 이웃 탐색 프로토콜(NDP)이 멀티캐스트로 한다.

**헤더**: 고정 길이로 단순해졌고, 헤더 체크섬이 없다(위아래 계층이 검사한다). 중간 라우터는 패킷을 쪼개지 않고, 크면 "너무 크다"고 알려 준다(02편 PMTUD).

**듀얼 스택**: 지금 대부분의 환경은 IPv4와 IPv6를 동시에 쓴다. AWS는 VPC에 IPv6 `/56` 을 붙이고 서브넷마다 `/64` 를 나눠 준다. 사설 서브넷의 IPv6 외부 통신은 NAT가 아니라 **나가기만 되는 인터넷 게이트웨이**(Egress-only IGW)로 처리한다. IPv6는 주소가 전부 공인이라 NAT로 숨기는 대신 "밖에서 먼저 들어오는 연결만 막는" 방식을 쓰는 것이다.

## 자주 막히는 장애 사례

**1. 연결하려는 두 네트워크의 대역이 겹친다**
- 증상: VPN이나 피어링 생성이 거부되거나, 연결은 됐는데 일부 서버로만 못 간다.
- 원인: 양쪽이 같은 `10.0.0.0/16` 을 쓰고 있다.
- 조치: 근본적으로는 한쪽 대역을 바꿔 다시 만든다. 당장은 중간에서 NAT로 다른 대역처럼 보이게 하거나, 필요한 서비스만 PrivateLink 같은 방식으로 노출한다. 그래서 처음의 대역 할당표가 중요하다.

**2. 쿠버네티스 노드는 남는데 파드가 안 뜬다**
- 증상: 파드가 대기 상태에 머물고, IP를 할당할 수 없다는 이벤트가 보인다.
- 원인: 파드가 VPC IP를 직접 받는 구성인데 서브넷 IP가 바닥났다.
- 조치: 서브넷을 더 큰 것으로 추가하거나, 파드 전용 보조 대역을 붙인다. 처음 설계 때 파드 수를 계산해 넣는다.

**3. 특정 사내 서버만 컨테이너에서 안 된다**
- 증상: 다른 곳은 다 되는데 `172.17.x.x` 의 사내 서버만 시간 초과.
- 원인: 도커 기본 브리지 대역과 겹쳐서, 요청이 컨테이너 네트워크 안으로 빠진다.
- 조치: 도커 데몬의 기본 대역을 회사에서 안 쓰는 대역으로 바꾼다.

**4. 노트북 주소가 169.254 로 시작한다**
- 증상: 와이파이는 붙었는데 인터넷이 안 된다.
- 원인: DHCP에서 주소를 못 받았다.
- 조치: 공유기 DHCP, 와이파이 재연결부터 확인한다.

## 클라우드에서는

- AWS VPC는 `/16` 에서 `/28` 사이로 만들 수 있고, 나중에 보조 CIDR을 추가할 수 있다. 하지만 기존 서브넷의 크기는 바꿀 수 없다. 서브넷은 처음에 넉넉히.
- GCP는 VPC가 전역이고 서브넷이 리전 단위다. 서브넷 기본 범위는 나중에 넓힐 수 있지만 좁힐 수는 없다.
- 보안 그룹·방화벽의 `/32` 는 주소 딱 하나, `/0` 은 전부다. `0.0.0.0/0` 을 허용 규칙에 넣는 건 "세상 전체에 연다"는 뜻이니, 들어오는 규칙에서는 로드밸런서 앞 정도로만 쓴다.
- 처음 질문으로 돌아가면: 지금 `/16` 을 하나 고르는 일은 몇 년 뒤의 연결 가능성을 정하는 일이다.

## 집에서 해보기 (지하철에서는 읽기만)

```bash
# 내 IP와 마스크
ifconfig en0 | grep 'inet '

# 범위 계산 확인
python3 -c "import ipaddress as i
n=i.ip_network('10.20.32.0/20')
print(n.network_address,
      n.broadcast_address,
      n.num_addresses)"

# 주소가 어느 대역 안인지
python3 -c "import ipaddress as i
print(i.ip_address('10.20.37.200')
 in i.ip_network('10.20.32.0/20'))"

# 요약 가능한지
python3 -c "import ipaddress as i
print(list(i.collapse_addresses(
 [i.ip_network(f'192.168.{x}.0/24')
  for x in range(4)])))"
```

손으로 먼저 계산하고 파이썬으로 답을 맞춰 보는 식으로 연습한다. 하루 다섯 문제면 일주일 안에 암산이 된다.

## 면접 한 줄 답

> /24はネットワーク部が24ビットで、256個のアドレスがあります。AWSでは5個が予約されるので、251個使えます。VPCのCIDRは、将来の接続に備えて重複しないように設計します。

/24는 네트워크 부분이 24비트라 주소가 256개입니다. AWS는 5개를 예약하므로 251개를 쓸 수 있습니다. VPC CIDR은 나중의 연결에 대비해 겹치지 않게 설계합니다.

**꼬리질문**

- Q. 대역이 겹친 두 VPC를 연결해야 한다면?
  A. 근본적으로는 한쪽을 재설계하고, 당장은 NAT나 PrivateLink처럼 필요한 서비스만 노출하는 방식으로 우회합니다.
- Q. 쿠버네티스를 올릴 VPC를 설계할 때 주의할 점은?
  A. 파드가 VPC IP를 쓰는지 확인해 노드 수와 파드 수로 서브넷 크기를 계산하고, 서비스 대역이 회사망과 겹치지 않게 합니다.
- Q. 169.254.169.254 는 무엇인가요?
  A. 클라우드 인스턴스 메타데이터 주소입니다. 자격 증명이 나오므로 SSRF 대책으로 IMDSv2 같은 토큰 방식을 씁니다.

## 정답

1. `/27`, 주소 32개(일반적으로 쓸 수 있는 건 30개). 넷째 칸 224 = 1110 0000 이라 1이 3개, 24+3=27.
2. `172.16.44.0`. `/22` 는 셋째 칸 블록 크기가 4이고, 45는 44~47 구간에 들어간다.
3. `10.1.0.0/22`.
4. 컨테이너 안의 `127.0.0.1` 은 컨테이너 자신이라서. 호스트는 별도 주소(도커의 호스트 게이트웨이 등)로 찾아야 한다.
5. Egress-only 인터넷 게이트웨이. 나가는 연결과 그 응답만 허용하고, 밖에서 먼저 들어오는 연결은 막는다.
