## 질문

서버에 `TIME_WAIT` 연결이 수천 개 쌓여 있다. 버그일까?

## TCP가 약속하는 것

TCP는 "보낸 순서대로, 빠짐없이, 깨지지 않게" 전달을 약속한다. 그러려고 세 가지를 한다.

- **번호 붙이기(시퀀스 번호):** 받는 쪽이 순서를 맞추고 빠진 걸 안다.
- **받았다는 확인(ACK):** 확인이 안 오면 다시 보낸다(재전송).
- **속도 조절:** 받는 쪽이 감당할 만큼만(흐름 제어), 네트워크가 막히지 않을 만큼만(혼잡 제어) 보낸다.

이 약속을 지키려면 양쪽이 서로의 상태를 기억해야 한다. 그래서 TCP는 **연결**을 맺는다.

## 연결 맺기: 3-웨이 핸드셰이크

```
클라이언트                      서버 (LISTEN)
  SYN (내 시작 번호는 x)  →
                         ←  SYN+ACK (내 시작 번호는 y, x+1 받을 차례)
  ACK (y+1 받을 차례)     →
ESTABLISHED                    ESTABLISHED
```

세 번인 이유: 양쪽 모두 "내가 보낸 시작 번호를 상대가 받았다"를 확인해야 하기 때문이다. 두 번이면 서버는 자기 번호가 클라이언트에 닿았는지 모른다.

이 과정에 1 RTT가 든다. 서울에서 도쿄 리전까지 RTT가 30ms라면, 데이터를 보내기 전에 30ms를 쓰는 셈이다. 그래서 연결을 재사용(keep-alive, 연결 풀)하는 게 중요하다.

## 연결 끊기: 4-웨이 종료

```
먼저 끊는 쪽                     상대
  FIN              →                       (CLOSE_WAIT)
FIN_WAIT_1
                   ←  ACK
FIN_WAIT_2                                 남은 데이터 마저 보냄
                   ←  FIN                  (LAST_ACK)
  ACK              →
TIME_WAIT (잠시 대기)                       CLOSED
```

끊을 때는 네 번이다. 한쪽이 "나는 다 보냈다(FIN)"고 해도 상대는 아직 보낼 게 남았을 수 있어서, 양방향을 따로 닫는다.

## TIME_WAIT는 왜 있나

**먼저 끊은 쪽**이 마지막 ACK를 보낸 뒤 바로 사라지지 않고 잠시(리눅스는 60초) 기다린다. 이유는 두 가지다.

1. **마지막 ACK가 사라졌을 때 대비.** 상대가 FIN을 다시 보내면 다시 ACK해 줘야 한다. 이미 사라졌다면 상대는 에러(RST)를 받는다.
2. **늦게 도착한 옛 패킷 차단.** 같은 주소·포트로 새 연결이 바로 생기면, 이전 연결의 늦은 패킷이 새 연결에 섞일 수 있다.

그래서 TIME_WAIT 자체는 버그가 아니라 정상이다. 다만 **짧은 연결을 아주 많이 만드는 쪽**(예: 연결을 재사용하지 않고 매번 새로 붙는 클라이언트, 프록시)에서는 쌓여서 포트가 모자랄 수 있다.

대응 순서:
1. **연결을 재사용한다.** HTTP keep-alive, DB 연결 풀. 근본 해결이다.
2. 누가 먼저 끊는지 확인한다. TIME_WAIT는 먼저 끊은 쪽에 남는다.
3. 그래도 필요하면 OS 설정(리눅스 `net.ipv4.tcp_tw_reuse`, 임시 포트 범위 확대)을 검토한다.

반대로 **CLOSE_WAIT**가 쌓이는 건 대개 버그다. 상대는 끊었는데 내 프로그램이 소켓을 닫지 않고 있다는 뜻이다.

## TCP와 UDP

| | TCP | UDP |
|---|---|---|
| 연결 | 맺는다 | 없다 |
| 순서·재전송 | 보장 | 없음 (앱이 알아서) |
| 헤더 | 20바이트 이상 | 8바이트 |
| 쓰는 곳 | HTTP/1.1·2, DB, SSH | DNS, 영상 통화, 게임, HTTP/3(QUIC) |

UDP는 "빠르고 단순하게, 신뢰성은 필요한 만큼 앱이 직접"이다. HTTP/3는 UDP 위에 QUIC이라는 자체 신뢰성 계층을 올려, TCP 핸드셰이크와 TLS 핸드셰이크를 하나로 합쳤다.

## 직접 확인 (맥 터미널)

```bash
# 지금 내 맥의 TCP 연결 상태별 개수
netstat -an -p tcp | awk 'NR>2 {print $6}' | sort | uniq -c

# 연결을 하나 만들었다 끊고 TIME_WAIT 확인
curl -s https://example.com -o /dev/null
netstat -an -p tcp | grep TIME_WAIT | head

# 리눅스 서버라면
ss -tan state time-wait | wc -l
```

## 클라우드에서는

- **로드밸런서 유휴 타임아웃**: ALB 기본 60초. 앱의 keep-alive가 이것보다 짧으면 앱이 먼저 끊으면서 간헐적 502가 날 수 있다. 앱 쪽 keep-alive를 LB보다 길게 잡는 게 정석이다.
- **NAT 게이트웨이**: 같은 목적지로 짧은 연결을 많이 만들면 NAT의 포트가 모자란다(06편). 연결 재사용이 여기서도 답이다.
- **DB 전환·장애 조치**: DB 주소가 바뀌어도 기존 TCP 연결은 옛 서버를 붙잡고 있다. 연결 풀이 끊긴 연결을 감지하고 다시 맺는 설정(유효성 검사, 재시도)이 필요하다.

## 면접 한 줄 답

> TIME_WAITは先に切断した側が、最後のACKの再送と古いパケットの混入を防ぐために待つ状態です。大量に溜まる場合は、まず接続の再利用を検討します。

TIME_WAIT는 먼저 끊은 쪽이 마지막 ACK 재전송과 옛 패킷 혼입을 막기 위해 기다리는 상태입니다. 많이 쌓이면 먼저 연결 재사용을 검토합니다.
