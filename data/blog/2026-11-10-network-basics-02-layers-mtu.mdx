## 질문

"L4 로드밸런서", "L7 방화벽"의 L은 뭘까? 그리고 왜 큰 요청만 가끔 멈출까?

## 계층: 일을 나눠 맡기

네트워크는 일을 층으로 나눈다. 각 층은 바로 아래층이 해 주는 일만 믿고 자기 일에 집중한다.

| TCP/IP 4계층 | OSI 7계층 | 하는 일 | 주소 | 대표 |
|---|---|---|---|---|
| 애플리케이션 | 7 응용 · 6 표현 · 5 세션 | 무엇을 주고받나 | URL, 호스트 이름 | HTTP, DNS, SSH |
| 전송 | 4 전송 | 어느 프로그램에게, 믿을 수 있게 | 포트 | TCP, UDP |
| 인터넷 | 3 네트워크 | 어느 컴퓨터에게, 어떤 길로 | IP 주소 | IP, ICMP |
| 링크 | 2 데이터 링크 · 1 물리 | 바로 옆 장비에게 | MAC 주소 | 이더넷, Wi-Fi |

실무에서 "L4"는 IP와 포트까지만 보고 판단한다는 뜻이고, "L7"은 HTTP 내용(경로, 헤더)까지 열어 본다는 뜻이다. OSI는 설명용 모델이고 실제 인터넷은 TCP/IP 4계층으로 돈다. 그래도 장비와 제품 이름은 OSI 번호로 부른다.

## 캡슐화: 내려가며 봉투를 씌운다

보낼 때는 위에서 아래로 내려가며 각 층이 자기 헤더를 앞에 붙인다. 받을 때는 아래에서 위로 올라가며 하나씩 벗긴다.

```
HTTP 데이터
[TCP 헤더 | HTTP 데이터]                         ← 세그먼트
[IP 헤더 | TCP 헤더 | HTTP 데이터]               ← 패킷
[이더넷 헤더 | IP | TCP | HTTP 데이터 | FCS]     ← 프레임
```

각 단계의 덩어리를 PDU라고 부르고, 층마다 이름이 다르다(세그먼트, 패킷, 프레임). 중간의 라우터는 프레임을 벗겨 IP 헤더까지만 보고 다음 길을 정한 뒤, 새 프레임으로 다시 씌워 보낸다. 그래서 MAC 주소는 구간마다 바뀌고 IP 주소는 끝까지 같다(NAT가 없다면).

오류 검사도 층마다 있다. 이더넷은 프레임 끝의 CRC(FCS)로, IPv4와 TCP·UDP는 헤더의 체크섬으로 깨진 데이터를 걸러 낸다.

## MTU와 MSS

**MTU**는 링크 한 구간이 한 번에 실을 수 있는 IP 패킷의 최대 크기다. 일반 이더넷은 1500바이트.
**MSS**는 그 안에서 TCP가 실을 수 있는 데이터의 최대 크기다.

```
MSS = MTU − IP 헤더(20) − TCP 헤더(20) = 1500 − 40 = 1460
```

TCP는 연결을 맺을 때 서로 MSS를 알려 주고, 그 크기에 맞춰 데이터를 잘라 보낸다.

## PMTUD와 "큰 것만 멈추는" 장애

경로 중간에 MTU가 더 작은 구간이 있을 수 있다. VPN, 터널, 일부 클라우드 간 연결이 그렇다(터널 헤더만큼 줄어든다).

- 패킷에 "쪼개지 마시오(DF)" 표시가 있으면, 작은 구간의 라우터는 버리고 ICMP로 "너무 크다, 이 크기로 보내라"를 돌려준다.
- 보낸 쪽은 그걸 보고 크기를 줄인다. 이게 **PMTUD**(경로 MTU 탐색)다.

문제는 방화벽이 ICMP를 전부 막아 둔 경우다. 그러면 "너무 크다"는 신호가 안 돌아오고, 작은 요청은 되는데 **큰 응답이나 업로드만 멈춘다.** SSH 접속은 되는데 파일 전송만 걸리는 식이다. 이걸 "PMTU 블랙홀"이라고 부른다.

대응은 두 가지다. 필요한 ICMP(타입 3 코드 4, IPv6는 Packet Too Big)는 열어 두거나, 터널 장비에서 MSS를 낮춰 강제한다(MSS clamping).

## 직접 확인 (맥 터미널)

```bash
# 내 인터페이스 MTU
ifconfig en0 | grep mtu

# 쪼개지 않고(-D) 1472바이트 데이터 보내기: 1472 + ICMP 8 + IP 20 = 1500
ping -D -s 1472 -c 2 example.com

# 1473이면 1501바이트라서 실패해야 정상
ping -D -s 1473 -c 2 example.com
```

1472가 되고 1473이 실패하면 경로 MTU가 1500이다. VPN을 켜고 다시 해 보면 통과하는 최대 크기가 줄어든 게 보인다.

## 클라우드에서는

- AWS VPC 안에서는 점보 프레임(MTU 9001)을 쓰지만, 인터넷 게이트웨이나 VPN·Transit Gateway를 지나면 1500 이하로 줄어든다.
- GCP VPC 기본 MTU는 1460이다. 다른 클라우드와 VPN으로 연결할 때 양쪽 MTU가 다르면 PMTU 문제가 생길 수 있다.
- 보안 그룹·방화벽 규칙을 만들 때 ICMP를 통째로 막지 않는 것이 이 장애를 막는 가장 쉬운 방법이다.

## 면접 한 줄 답

> MTUは1回で送れるIPパケットの最大サイズで、MSSはその中のTCPデータの最大サイズです。経路の途中でMTUが小さく、ICMPが遮断されていると、大きい通信だけが止まることがあります。

MTU는 한 번에 보낼 수 있는 IP 패킷의 최대 크기이고, MSS는 그 안의 TCP 데이터 최대 크기입니다. 경로 중간 MTU가 작고 ICMP가 막혀 있으면 큰 통신만 멈출 수 있습니다.
