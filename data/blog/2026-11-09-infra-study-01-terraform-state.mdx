## IaC란

인프라를 콘솔에서 클릭으로 만드는 대신 코드로 선언하고, 그 코드를 기준으로 만들고 바꾸고 지우는 방식이다. 얻는 것은 세 가지다.

- **재현성:** 같은 코드로 같은 환경을 다시 만든다.
- **검토 가능성:** 변경이 코드 차이로 남아 리뷰할 수 있다.
- **기록:** 누가 언제 무엇을 바꿨는지 git에 남는다.

## state는 무엇을 기억하나

Terraform은 코드(원하는 상태)와 클라우드(실제 상태)를 비교해 차이만 적용한다. 그런데 "코드의 이 블록이 클라우드의 어느 자원인지"는 클라우드 API만 봐서는 알 수 없다. 그 연결을 저장하는 파일이 **state**다.

```
코드 (resource "aws_vpc" "main")  ←state→  실제 자원 (vpc-0abc…)
```

state가 없거나 잘못되면 Terraform은 이미 있는 자원을 모른다고 판단해 새로 만들거나, 반대로 지우려 한다.

## 원격 state와 잠금

혼자 쓸 때는 로컬 `terraform.tfstate`로 충분하다. 팀에서는 문제가 생긴다.

| 문제 | 해결 |
|---|---|
| 각자 노트북에 다른 state가 있다 | 원격 저장소 (S3, GCS) 하나에 둔다 |
| 두 사람이 동시에 apply한다 | 잠금. S3는 잠금 파일(`use_lockfile`) 또는 DynamoDB, GCS는 기본 잠금 |
| state에 비밀값이 평문으로 들어간다 | 버킷 암호화, 접근 권한 최소화 |
| state를 실수로 덮어쓴다 | 버킷 버전 관리로 이전 버전 복구 |

```hcl
terraform {
  backend "s3" {
    bucket       = "my-tfstate"
    key          = "env/dev/terraform.tfstate"
    region       = "ap-northeast-1"
    use_lockfile = true
    encrypt      = true
  }
}
```

state를 담을 버킷 자체는 보통 별도의 작은 bootstrap 코드로 먼저 만든다. 닭과 달걀 문제다.

## plan과 apply를 나누는 습관

```bash
terraform plan -out=tfplan   # 무엇이 바뀌는지 저장
terraform show tfplan        # 사람이 확인
terraform apply tfplan       # 확인한 그 계획만 적용
```

`apply -auto-approve`는 plan을 보지 않고 적용한다. plan을 파일로 저장해 두면 "내가 본 것과 적용된 것이 같다"가 보장된다. 특히 `destroy`나 `replace`가 섞여 있는지 반드시 본다.

## drift: 코드 밖에서 바뀐 것

콘솔이나 CLI로 손으로 바꾸면 코드와 실제가 어긋난다. 다음 `plan`에서 Terraform은 그 변경을 되돌리려 한다.

| 상황 | 대응 |
|---|---|
| 손으로 만든 자원을 Terraform으로 관리하고 싶다 | `import` 블록 또는 `terraform import` |
| Terraform 관리에서 빼되 자원은 남기고 싶다 | `terraform state rm` (자원은 그대로, state에서만 제거) |
| 이름만 바꾸고 싶다 (재생성 없이) | `moved` 블록 |
| 손으로 바꾼 값을 유지하고 싶다 | 코드를 실제 값에 맞추거나 `lifecycle { ignore_changes = [...] }` |

손으로 바꿀 수밖에 없는 순간은 반드시 온다. 그때 **무엇을 왜 바꿨는지 문서에 남기는 것**이 drift 관리의 출발점이다.

## 변수 파일 관리

`terraform.tfvars`에는 환경마다 다른 값(허용 IP, 계정 ID 등)이 들어가 git에서 빼는 경우가 많다. 그러면 그 파일을 잃는 순간 apply가 막힌다. 비밀이 아닌 값은 `example.tfvars`로 커밋하고, 비밀값은 비밀 관리 서비스에서 읽게 하는 편이 안전하다.

## 체크리스트

- [ ] state는 원격 + 잠금 + 암호화 + 버전 관리
- [ ] apply는 저장한 plan 파일로만
- [ ] plan에 destroy·replace가 있으면 멈추고 이유 확인
- [ ] 손으로 바꾼 것은 문서로 남기고, import 하거나 state rm 한다
- [ ] tfvars는 잃어버려도 다시 만들 수 있게
