10월 29일 밤, 친구들과 함께 푸는 SAP-C02 스터디 방에서 두 시간 동안 48문항을 풀었다. 결과는 12문항 정답, 36문항 오답. 정답률 25%다. 숫자는 아프지만 어디가 비어 있는지는 선명해졌다.

이 글은 그 36문항의 오답노트다. 문제 원문을 옮기는 대신 **요구사항을 내 말로 요약하고, 정답 접근과 그 이유, 그리고 내가 빠졌을 만한 함정**을 적는다. 정답 기준은 함께 쓴 한국어 문제집의 정답이고, 각 항목은 AWS 공식 문서로 다시 확인했다. 문제집 정답이 의심스럽거나 번역이 빠진 곳은 따로 표시했다.

## 네트워크 (9문항)

### #264 온프레미스 프라이빗 DNS 존을 VPC에서 풀기

- **상황**: Site-to-Site VPN으로 연결된 온프레미스에만 있는 DNS 존의 호스트명을, VPC 안 EC2의 새 서비스가 풀어야 한다.
- **정답**: Route 53 Resolver **아웃바운드 엔드포인트**를 만들고, 그 도메인 질의를 온프레미스 네임서버로 전달하는 규칙을 건다.
- **왜**: 질의가 VPC에서 바깥으로 나가는 방향이면 아웃바운드다. 인바운드 엔드포인트는 반대로 온프레미스가 VPC 쪽 이름을 풀 때 쓴다.
- **함정**: 빈 프라이빗 호스티드 존에 NS 위임을 걸어도 Route 53이 권한 서버가 아니라서 동작하지 않는다. 호스트 파일을 Systems Manager로 뿌리는 건 운영 부담만 키운다.
- 참고: [Route 53 Resolver](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/resolver.html)

### #400 두 개의 Direct Connect 연결로 두 리전의 Transit Gateway에 닿기

- **상황**: 유럽 데이터센터에서 서로 다른 DX 위치로 1Gbps 연결 두 개가 있고, eu-west-1과 us-east-1에 각각 Transit Gateway가 있다. 온프레미스→어느 리전이든, 그리고 리전 간 VPC 직접 라우팅이 필요하며 단일 장애점은 안 된다.
- **정답**: 두 연결 각각에서 **transit VIF**를 만들어 **같은 Direct Connect 게이트웨이**에 붙이고, 두 리전의 TGW를 모두 그 DX 게이트웨이에 연결한 뒤, **TGW끼리 피어링**해서 리전 간 트래픽을 흘린다.
- **왜**: TGW를 DX에 붙이려면 private VIF가 아니라 transit VIF다. DX 게이트웨이는 여러 리전의 TGW를 하나로 묶을 수 있지만, 붙어 있는 TGW 사이의 트래픽을 중계해 주지는 않는다. 그래서 리전 간은 TGW 피어링이 따로 필요하다.
- **함정**: DX 게이트웨이끼리는 피어링이 없다. "DX 게이트웨이가 TGW 간 라우팅을 하도록 구성"이라는 선지는 존재하지 않는 기능이다.
- 참고: [Transit gateway associations](https://docs.aws.amazon.com/directconnect/latest/UserGuide/direct-connect-transit-gateways.html)

### #814 UDP 매치메이킹 서비스를 AWS로

- **상황**: 인터넷에 열린 UDP 전용 매치메이킹 서버를 AWS로 옮기면서 보안 수준을 높여야 한다. 세 가지 선택.
- **정답**: **NLB**(탄력적 IP를 Route 53에 매핑) + 로드밸런서 서브넷에 **UDP만 허용하는 네트워크 ACL** + **Shield Advanced**.
- **왜**: ALB, WAF, CloudFront는 전부 HTTP(S) 계층이라 UDP를 다루지 못한다. UDP를 받을 수 있는 로드밸런서는 NLB뿐이고, 계층 4 이하의 필터링은 NACL과 보안 그룹, DDoS는 Shield가 맡는다.
- **함정**: "보안"이라는 단어에 끌려 WAF를 고르면 틀린다. WAF는 HTTP 요청을 보는 서비스다.

### #110 CloudFront에서 `/path/` 요청을 `path/index.html`로 보내기

- **상황**: CloudFront + OAI + 프라이빗 S3 정적 사이트에서 슬래시로 끝나는 경로만 404가 난다. 캐싱을 해치지 않고 고쳐야 한다.
- **정답**: **오리진 요청(origin request)** 이벤트에 Lambda@Edge를 붙여 URL을 다시 쓴다.
- **왜**: 뷰어 요청 이벤트는 캐시 히트든 아니든 모든 요청마다 실행된다. 오리진 요청 이벤트는 캐시 미스일 때만 실행되므로 캐시 효율을 건드리지 않는다.
- **함정**: API Gateway를 오리진으로 바꾸는 선지는 정적 사이트에 과하다. 요즘이라면 CloudFront Functions도 후보지만, 이 문제는 두 Lambda@Edge 이벤트의 차이를 묻는다.
- 참고: [Lambda@Edge 이벤트 선택](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/lambda-how-to-choose-event.html)

### #116 게임 출시 전 멀티리전으로: S3 에셋 + DynamoDB 점수

- **상황**: 단일 리전의 S3 에셋 버킷과 DynamoDB 점수 테이블을, 지연을 줄이고 안정성을 높이되 구현 노력은 최소로 멀티리전화한다.
- **정답**: 새 리전에 버킷을 하나 더 만들어 **리전 간 복제(CRR)**, CloudFront에 두 버킷을 오리진으로 두고 **오리진 페일오버**, DynamoDB는 Streams를 켜고 **글로벌 테이블**에 복제 리전을 추가한다.
- **왜**: 에셋은 CRR + CloudFront 페일오버로 안정성과 지연을 동시에 잡고, 점수는 글로벌 테이블이 다중 리전 활성 복제를 관리형으로 해 준다.
- **함정**: DMS + CDC로 DynamoDB 간 복제를 꾸미는 선지는 "구현 노력 최소"에 어긋난다. 동일 리전 복제(SRR)는 멀티리전이 아니다.
- 참고: [DynamoDB 글로벌 테이블](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/GlobalTables.html)

### #594 글로벌 발행을 앞둔 읽기 위주 동적 사이트의 응답 시간

- **상황**: ALB + EC2 + Aurora MySQL 구성의 잡지 사이트가 처음으로 전 세계 독자를 받는다. 트래픽은 거의 읽기 전용, 정적 콘텐츠 일부 포함. 두 가지 선택.
- **정답**: **Aurora 글로벌 데이터베이스** + 정적 콘텐츠용 **S3 CRR** + 웹·앱 계층의 다중 리전 배포, 그리고 **Route 53 지연 시간 기반 라우팅 + CloudFront** + 웹·앱 계층 Auto Scaling.
- **왜**: 읽기 위주라면 리전별로 읽기 복제본을 두고 사용자를 가까운 리전으로 보내면 된다. 정적 콘텐츠는 CloudFront 캐시로 끝난다.
- **함정**: "웹 서버를 S3로 교체"는 동적 사이트라 불가능하고, Direct Connect는 사용자 지연과 무관하다.
- 참고: [Aurora 글로벌 데이터베이스](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-global-database.html)

### #359 EC2 위 자체 SFTP 서버의 안정성과 확장성

- **상황**: 퍼블릭 서브넷의 EC2 한 대가 SFTP 서버 + cron으로 데이터 레이크 적재를 맡고 있다. DNS는 Route 53.
- **정답**: **AWS Transfer Family(SFTP)**로 옮기고 DNS 레코드를 서버 엔드포인트로 바꾼다.
- **왜**: S3를 백엔드로 쓰는 관리형 SFTP라 업로드가 곧바로 데이터 레이크에 떨어지고 cron도 사라진다. 다중 AZ와 스케일링은 서비스가 해 준다.
- **함정**: ALB는 SFTP(TCP 22)를 못 받고, NLB 뒤에 EC2를 두어도 인스턴스 운영 부담은 그대로다. File Gateway는 SFTP 서버가 아니다.
- 참고: [AWS Transfer Family](https://docs.aws.amazon.com/transfer/latest/userguide/what-is-aws-transfer-family.html)

### #448 IoT Core 수집 경로를 두 리전으로

- **상황**: 전국 대기질 센서가 IoT Core로 시계열 데이터를 보내 DynamoDB에 저장한다. 비즈니스 연속성을 위해 두 리전에서 수집·저장해야 한다.
- **정답**: 리전마다 **IoT Core 도메인 구성**(사용자 지정 엔드포인트)을 만들고, Route 53 **상태 검사 + 장애 조치 라우팅**으로 묶은 뒤, DynamoDB를 **글로벌 테이블**로 바꾼다.
- **왜**: IoT 디바이스가 바라보는 엔드포인트를 리전에 묶이지 않은 내 도메인으로 두어야 페일오버가 가능하다. 저장소는 글로벌 테이블이 양방향 복제를 맡는다.
- **함정**: "Aurora 글로벌 테이블", "MemoryDB 리전 간 복제"처럼 그럴듯하지만 없는 조합이 섞여 있다. 지연 시간 기반 라우팅은 장애 감지가 아니다.
- 참고: [IoT Core 구성 가능한 엔드포인트](https://docs.aws.amazon.com/iot/latest/developerguide/iot-custom-endpoints-configurable.html)

### #628 원격 근무자 증가로 포화된 데이터센터 VPN

- **상황**: 직원들이 데이터센터 VPN으로 Windows 홈 디렉터리에 접근하는데, 업무 시간엔 회선이 100%다. 운영 부담은 줄여야 한다. 두 가지 선택.
- **정답**: 홈 디렉터리를 **FSx for Windows File Server**로 옮기고, 원격 사용자를 **AWS Client VPN**으로 돌린다.
- **왜**: 파일과 접속 지점을 둘 다 AWS로 옮겨야 데이터센터 회선에서 트래픽이 빠진다. 하나만 옮기면 여전히 데이터센터를 거친다.
- **함정**: 볼륨 게이트웨이는 온프레미스 서버에 볼륨을 붙이는 것이라 회선 사용량을 줄이지 못한다. Lustre는 SMB 홈 디렉터리 용도가 아니다. Direct Connect는 데이터센터와 AWS 사이 회선이지 원격 직원 접속이 아니다.

## 데이터베이스 (7문항)

### #291 Lambda가 Aurora 연결을 너무 많이 연다

- **상황**: API Gateway 리전 엔드포인트 + Lambda + Aurora MySQL(읽기 복제본 3개). 읽기만 하는데도 부하 시 연결 수가 폭증해 성능이 안 나온다. 두 가지 선택.
- **정답**: **RDS Proxy**를 리더 엔드포인트 앞에 두어 연결 풀을 만들고, **DB 연결 코드를 핸들러 바깥**으로 옮겨 실행 환경이 재사용될 때 연결을 재활용한다.
- **왜**: Lambda는 동시 실행마다 연결을 새로 열기 때문에 연결 풀이 바깥에 있어야 한다. 핸들러 밖 초기화는 웜 스타트에서 연결을 다시 쓰게 한다.
- **함정**: 프로비저닝된 동시성은 콜드 스타트 문제지 연결 수 문제가 아니다. 사용자가 리전 가까이 있으니 엣지 최적화 엔드포인트도 의미가 없다. 클러스터 엔드포인트는 쓰기 노드로 가서 읽기 복제본을 버린다.
- 참고: [RDS Proxy](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/rds-proxy.html)

### #872 보조 리전에 인스턴스를 띄우지 않는 Aurora DR

- **상황**: Aurora PostgreSQL을 보조 리전으로 확장하되 RTO 15분, RPO 5분, 그리고 평시에는 보조 리전에서 DB 인스턴스를 돌리면 안 된다.
- **정답**: 같은 **글로벌 데이터베이스**에 속한 **헤드리스(인스턴스 없는) 보조 클러스터**를 만든다.
- **왜**: 글로벌 데이터베이스는 스토리지 계층에서 복제되므로 보조 클러스터에 인스턴스가 없어도 데이터는 따라간다. 장애 시 인스턴스를 추가하고 승격하면 15분 안에 끝난다.
- **함정**: DMS나 AWS Backup으로 5분마다 복사하는 선지는 RPO 5분을 안정적으로 못 맞추고 운영 부담이 크다.

### #385 EC2와 Aurora 사이 최소 권한 보안 그룹

- **상황**: 같은 보안 그룹의 EC2들과 자체 보안 그룹의 Aurora 클러스터. 최소 권한으로 접근을 허용하는 규칙 두 개.
- **정답**: EC2 보안 그룹에 **아웃바운드**(대상: DB 보안 그룹, Aurora 포트), DB 보안 그룹에 **인바운드**(소스: EC2 보안 그룹, Aurora 포트).
- **왜**: 연결을 시작하는 쪽은 아웃바운드, 받는 쪽은 인바운드다. 보안 그룹은 상태 저장이라 응답 트래픽 규칙은 필요 없다.
- **함정**: "DB 보안 그룹의 아웃바운드에 임시 포트"는 상태 비저장인 NACL에서나 나오는 발상이다. EC2 쪽 인바운드에 DB를 소스로 넣는 건 방향이 거꾸로다.

### #696 단일 Tomcat + EC2 위 MySQL, 트래픽 폭증마다 장애

- **상황**: 웹사이트는 한 VPC의 퍼블릭 서브넷 한 개에 EC2 한 대, 데이터베이스는 다른 VPC의 EC2 위 MySQL. VPC 피어링 하나. 세 가지 선택.
- **정답**: Tomcat을 **ALB 뒤 Auto Scaling 그룹**으로, MySQL을 **복제본 하나 있는 Aurora**로, 그리고 웹사이트 VPC에 **다른 AZ의 퍼블릭 서브넷을 추가**한다.
- **왜**: ALB는 최소 두 AZ의 서브넷이 필요하므로 서브넷 추가가 선행 조건이다. 데이터베이스도 관리형 다중 AZ로 바꿔야 한쪽만 튼튼해지는 걸 피한다.
- **함정**: 피어링 연결을 더 만들거나 NAT 게이트웨이를 추가하는 건 장애 원인과 무관하다.

### #311 스마트 미터 수집 Lambda가 느려지고 DynamoDB가 스로틀링

- **상황**: API Gateway → Lambda → DynamoDB. 미터가 늘자 Lambda 실행 시간이 3~5초에서 1~2분으로 늘었고, DynamoDB에선 ProvisionedThroughputExceeded, Lambda에선 TooManyRequests가 난다. 두 가지 선택.
- **정답(문제집)**: DynamoDB **WCU 증설** + Lambda **메모리 증설**(CPU가 같이 늘어 실행 시간이 줄고 동시 실행 점유가 준다).
- **왜**: 두 증상을 각각 가장 짧은 경로로 잡는 답이다. Lambda TooManyRequests는 동시 실행 한도이고, 실행 시간이 줄면 같은 요청량에 필요한 동시 실행 수가 준다.
- **검토 필요**: 설계 관점에서는 Kinesis Data Streams로 받아 배치 처리하는 선지가 더 근본적이다. 시험에서는 "이미 운영 중, 가장 단순한 수정"이라는 맥락을 읽어야 한다. 실무라면 둘 다 하되 순서를 정하겠다.

### #323 DynamoDB를 서버리스 HTTPS API로 공개

- **상황**: 여러 DynamoDB 테이블의 데이터를 간단한 공개 API로, 서버리스로, 수요에 따라 자동 확장되게. 두 가지 선택.
- **정답**: **REST API + DynamoDB 직접(AWS 서비스) 통합**, 또는 **HTTP API + Lambda 통합**.
- **왜**: REST API는 AWS 서비스 통합으로 Lambda 없이 DynamoDB를 호출할 수 있다. HTTP API는 DynamoDB 직접 통합이 없어서 Lambda를 끼워야 한다.
- **함정**: "HTTP API + DynamoDB 직접 통합"은 없는 조합이다. Global Accelerator와 Lambda@Edge, NLB는 이 문제의 서버리스 API 요구와 맞지 않는다.
- 참고: [HTTP API vs REST API](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-vs-rest.html)

### #560 CPU 100%에 수동 패치로 다운되는 단일 EC2 + EC2 MySQL

- **상황**: 상태 비저장 앱이 큰 EC2 한 대, MySQL은 또 다른 EC2 한 대. 가용성을 높이되 개발 부담은 최소.
- **정답**: **SSM Agent를 넣은 새 AMI** + **ALB 뒤 Auto Scaling 그룹**(더 작은 인스턴스, CPU 기준 스케일링) + MySQL을 **Aurora MySQL**로 이전.
- **왜**: 코드를 바꾸지 않고 가용성을 올리는 전형적인 경로다. 패치는 Systems Manager Patch Manager로 자동화하고, 데이터베이스는 엔진 호환 관리형으로 간다.
- **함정**: DynamoDB, Neptune, DocumentDB로 옮기는 선지는 전부 애플리케이션 코드를 바꿔야 한다. "개발 부담 최소"가 결정 축이다.

## 아키텍처 설계 (5문항)

### #632 Organizations에서 일부 서비스만 막고 계정을 묶기

- **상황**: 여러 DevOps 계정을 조직에 초대했다. 지금 쓰는 서비스는 허용하고 몇 가지만 차단하며, 계정을 하나의 단위로 관리하고 싶다. 세 가지 선택.
- **정답**: **거부 목록(deny list) 전략**, **IAM 액세스 관리자(Access Advisor)**로 최근 사용 서비스 확인, **OU를 만들어 계정 배치**.
- **왜**: 기본 FullAWSAccess SCP를 유지한 채 Deny SCP를 얹는 것이 거부 목록 전략이다. "몇 가지만 차단"이면 이 방식이 맞다. 어떤 서비스를 쓰는지는 Access Advisor가 보여 준다.
- **함정**: FullAWSAccess를 제거하면 허용 목록 전략으로 바뀌어 모든 서비스를 일일이 허용해야 한다. Trusted Advisor는 사용 서비스 목록을 주지 않고, DenyAWSAccess라는 기본 SCP는 없다.
- 참고: [SCP 전략](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_scps_strategies.html)

### #861 Kafka 클라이언트 전부 mTLS, 운영 부담 최소

- **정답**: **AWS Private CA** + **Amazon MSK**. MSK가 Private CA를 신뢰하도록 설정하고 클라이언트 인증서는 Private CA로 발급한다.
- **왜**: MSK는 Private CA가 발급한 클라이언트 인증서로 TLS 상호 인증을 기본 지원한다. 관리형 PKI + 관리형 Kafka 조합이라 운영 부담이 가장 작다.
- **함정**: ACM 퍼블릭 인증서는 클라이언트 인증서로 쓸 수 없다. IAM에 서버 인증서를 올리는 건 ELB용이고, EKS에 cert-manager로 Kafka를 직접 띄우는 건 운영 부담이 가장 크다.
- 참고: [MSK 인증](https://docs.aws.amazon.com/msk/latest/developerguide/msk-authentication.html)

### #386 프리미엄 고객만 429를 받는데 Lambda는 호출조차 안 됐다

- **상황**: 같은 프로덕션 계정, 여러 리전의 REST API. 프리미엄 계층은 API 키당 초당 3,000회. 피크 때 여러 프리미엄 고객이 429를 받았고 로그엔 Lambda 호출이 없다.
- **정답**: **API Gateway 계정 수준 초당 호출 한도**에 도달했다.
- **왜**: Lambda가 호출되지 않았으니 Lambda 동시성 한도는 원인이 아니다. 사용량 계획 한도(3,000)보다 위에 계정 단위 한도(기본 10,000 RPS)가 있고, 프리미엄 고객 넷만 피크를 치면 넘는다.
- **함정**: "메서드별 기본 한도"는 별도 기본값이 있는 게 아니라 계정 한도를 상속한다. 선지가 비슷해서 기본값 숫자를 알아야 가른다.
- 참고: [API Gateway 요청 스로틀링](https://docs.aws.amazon.com/apigateway/latest/developerguide/api-gateway-request-throttling.html)

### #630 ALB 인트라넷 앱을 AWS Managed Microsoft AD로 인증

- **상황**: 자체 사용자 DB로 인증하던 ALB 뒤 앱을, 기존 AWS Managed Microsoft AD 계정으로 인증하게 바꾼다. 디렉터리에 계정이 있으면 모두 접근 가능해야 한다.
- **정답(문제집)**: **Cognito 사용자 풀**을 디렉터리를 페더레이션 IdP로 두어 구성하고, ALB 리스너 규칙에 **authenticate-cognito** 액션을 건다.
- **왜**: ALB의 내장 인증은 OIDC 또는 Cognito 두 가지다. AD는 OIDC 공급자가 아니므로 Cognito를 중간에 두고 디렉터리와 페더레이션한다. IAM SAML 역할은 콘솔·API 접근용이지 ALB 리스너 인증이 아니다.
- **검토 필요**: 실제로는 Managed Microsoft AD가 SAML을 직접 내지 않아 AD FS 같은 SAML 게이트웨이가 필요하다. 문제는 그 단계를 "디렉터리 메타데이터"로 뭉뚱그렸다.
- 참고: [ALB 사용자 인증](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/listener-authenticate-users.html)

### #254 Windows 서버 리프트 앤 시프트, 전환 다운타임 최소

- **상황**: 온프레미스 Windows 서버들을 us-east-1 EC2로. 에이전트 설치 가능, 전송·저장 암호화, 비즈니스 크리티컬이라 다운타임 최소, CloudWatch·CloudTrail로 모니터링.
- **정답**: **AWS Application Migration Service(MGN)**. 복제 설정 템플릿을 만들고 소스 서버에 복제 에이전트를 설치한다.
- **왜**: MGN은 블록 수준 지속 복제라 컷오버 창이 분 단위다. 전송·저장 암호화가 기본이고 CloudWatch·CloudTrail과 통합된다.
- **함정**: DataSync는 파일 데이터 이동 도구지 서버 이전 도구가 아니다. 구 Server Migration Service(SMS)는 종료된 서비스이고, Migration Hub는 진행 상황 추적만 한다.
- 참고: [AWS MGN](https://docs.aws.amazon.com/mgn/latest/ug/what-is-application-migration-service.html)

### #6 회전되지 않는 DB 자격 증명과 암호화되지 않은 RDS

- **정답**: Lambda가 **Secrets Manager**에서 자격 증명을 읽게 하고 **자동 회전**을 켠다. 암호화는 **스냅샷 → 암호화된 사본 → 새 인스턴스로 교체**로 해결한다.
- **왜**: 기존 RDS 인스턴스는 저장 암호화를 나중에 켤 수 없다. 암호화된 읽기 복제본도 소스가 암호화돼 있어야 만들 수 있다. 유일한 경로가 스냅샷 복사다.
- **함정**: IAM DB 인증은 자격 증명 회전 문제를 피해 가는 좋은 선택이지만, 같은 선지에 "기존 인스턴스를 수정해 암호화 활성화"가 붙어 있어 전체가 틀린다. Parameter Store는 자동 회전이 없다.
- 참고: [RDS 리소스 암호화](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Overview.Encryption.html)

### #522 개별 계정들을 중앙 청구로 묶고 Azure AD로 페더레이션

- **정답**: 새 관리 계정으로 **Organizations**를 만들어 기존 계정을 초대, 관리 계정에 **IAM Identity Center**를 켜고 Azure AD(Entra ID)와 연결해 사용자·그룹 **자동 동기화(SCIM)**, **권한 세트**를 만들어 그룹과 계정에 할당.
- **왜**: 중앙 청구 = Organizations, 페더레이션 + 임시 자격 증명 = Identity Center다. 권한 세트가 각 계정의 역할로 실체화된다.
- **함정**: AWS Managed Microsoft AD를 RAM으로 공유하거나 계정마다 IAM을 AD에 붙이는 선지는 "수동 사용자 관리 대신"이라는 요구를 만족하지 못한다. 이메일 주소 규칙은 청구 중앙화가 아니다.

### #678 Control Tower 환경에서 모든 계정의 보안 상태를 한눈에

- **정답**: 조직에 대해 **Security Hub**를 켜고 한 계정을 **위임된 관리자**로 지정한다.
- **왜**: Security Hub가 Config, GuardDuty, Inspector 등의 결과를 모아 조직 전체 보안 상태를 한 화면으로 준다. Control Tower의 예방·탐지 제어 결과도 여기로 모인다.
- **함정**: Detective는 조사 도구이지 상태 대시보드가 아니다. Config 적합성 팩을 StackSets로 뿌리는 건 제어를 배포하는 것이지 중앙 뷰가 아니다.
- 참고: [Security Hub 위임된 관리자](https://docs.aws.amazon.com/securityhub/latest/userguide/designate-orgs-admin-account.html)

### #46 인프라 계정의 서브넷을 다른 계정이 쓰게

- **정답**: Organizations **관리 계정에서 리소스 공유를 활성화**하고, 인프라 계정의 **RAM 리소스 공유**에 서브넷을 넣어 OU에 공유한다.
- **왜**: VPC 공유는 RAM으로 서브넷 단위로 공유하며, 조직 단위 공유를 쓰려면 관리 계정에서 먼저 Organizations와의 공유를 켜야 한다. 참가자 계정은 공유 서브넷에 리소스를 만들 수 있지만 네트워크 자체는 못 바꾼다.
- **함정**: 접두사 목록 공유는 CIDR 목록을 공유하는 것이지 서브넷을 주는 게 아니다. 같은 CIDR로 VPC를 만들어 피어링하는 선지는 CIDR 겹침 때문에 불가능하다.
- 참고: [VPC 공유](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-sharing.html)

### #834 기본 AWS 관리형 키로 암호화된 시크릿을 다른 계정과 공유

- **상황**: 앱 계정의 Secrets Manager 시크릿이 기본 AWS 관리형 KMS 키로 암호화돼 있다. DBA 계정의 EC2가 시크릿을 복사 없이 읽어야 한다.
- **정답**: **앱 계정에 시크릿 읽기 권한 + DBA 계정을 신뢰하는 IAM 역할**을 만들고, DBA 계정의 EC2 역할이 그 역할을 **수임(AssumeRole)**한다.
- **왜**: AWS 관리형 키(aws/secretsmanager)는 키 정책을 수정할 수 없어 다른 계정에 복호화 권한을 줄 수 없다. 그러니 시크릿 리소스 정책만으로는 교차 계정 접근이 안 되고, 앱 계정 안의 역할로 들어가서 읽어야 한다.
- **함정**: 리소스 정책 + 키 정책 조합은 고객 관리형 키일 때만 가능하다. SCP는 권한을 주는 도구가 아니고, RAM은 시크릿을 공유하지 않는다.

### #554 주소 공간을 늘리지 않고 세 번째 AZ 도입

- **상황**: VPC /23, AZ1·AZ2 서브넷이 각각 /24로 공간을 다 썼다. ASG 최대 20대, 온프레미스 연결은 끊기면 안 된다. 새 AZ3를 무중단으로 추가한다.

- **함정**: "서브넷 주소 공간을 업데이트"하는 선지는 존재하지 않는 작업이다. 인스턴스를 먼저 종료하는 선지는 다운타임, 새 VPC는 온프레미스 연결을 잃는다.
- 참고: [VPC 서브넷](https://docs.aws.amazon.com/vpc/latest/userguide/configure-subnets.html)

### #23 Organizations 밖 계정에서 t3.small·us-east-2만 허용

- **정답**: `ec2:InstanceType`과 `aws:RequestedRegion` 조건을 건 **IAM 정책**을 개발자 역할·그룹에 붙인다.

- 참고: [IAM 글로벌 조건 키](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_condition-keys.html)

### #545 매일 4시간만 바쁜 DynamoDB, 비용과 운영 부담을 함께 줄이기

### #166 팀별 EMR 예산을 중앙에서 사전 예방적으로

- **정답**: CloudFormation 템플릿에 **AWS::Budgets::Budget**(NotificationsWithSubscribers 포함)을 추가하고, 팀별 **Service Catalog 포트폴리오**에 EMR 클러스터 템플릿을 제품으로 등록한다.
- **왜**: 예산 알림은 Budgets 리소스가 맡고, "사전 예방적 시행"은 승인된 템플릿만 띄울 수 있는 Service Catalog가 맡는다. 둘 다 다중 계정에 코드로 배포된다.
- **함정**: CloudWatch 대시보드나 청구 지표 알람은 사후 관찰이다. 부트스트랩 액션에서 Cost Explorer API를 부르는 선지는 존재하지 않는 조합이다.
- 참고: [AWS::Budgets::Budget](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/aws-resource-budgets-budget.html)

### #25 프라이빗 서브넷 플릿의 SSH 통제와 명령 감사

- **정답**: **AmazonSSMManagedInstanceCore** 역할을 모든 인스턴스에 붙이고, 포트 22 규칙을 전부 제거한 뒤 **Session Manager**로 접속한다.
- **왜**: 인바운드 포트 자체가 사라지고, 세션 로그를 CloudWatch Logs나 S3에 남겨 명령 감사가 된다.
- **함정**: EC2 Instance Connect는 여전히 포트 22를 쓰고 명령 감사가 없다. 보안 그룹을 IP로 좁히는 선지는 감사를 해결하지 못한다.
- 참고: [Session Manager](https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager.html)

### #43 GitHub + Jenkins에 CodePipeline을 얹어 무중단 배포와 롤백

- **정답(문제집)**: GitHub **웹훅**으로 파이프라인 트리거, **CodeBuild용 Jenkins 플러그인**으로 단위 테스트, **CodeDeploy 블루/그린** 배포.
- **왜**: 블루/그린이면 무중단이고 되돌리기가 트래픽 전환 한 번이다. X-Ray는 테스트 도구가 아니고, 제자리(in-place) 배포는 다운타임과 롤백 문제가 남는다.
- **번역 누락**: 영어 원문의 정답 선지에는 "빌드 실패 시 SNS 토픽으로 알림"이 들어 있다. 한국어판에서 그 문장이 빠져 선지가 요구사항을 다 못 채운 것처럼 보인다. 웹소켓이라고 적힌 선지들은 전부 오답이다.

## 스토리지 (3문항)

### #819 S3 API를 당장 못 쓰는 CPU 집약 문서 처리

- **상황**: 초당 5개 문서를 S3에 두되 EC2 리눅스 서버가 빠른 로컬 접근을 해야 하고, 몇 달간 S3 API를 쓸 수 없다.
- **정답**: **FSx for Lustre**를 가져오기/내보내기 정책으로 S3 버킷에 연결하고 Lustre 클라이언트로 마운트한다.
- **왜**: S3와 연결된 데이터 리포지토리로 파일 시스템처럼 읽고 쓰며 S3와 동기화한다. CPU 집약 고성능 워크로드 전용 설계다.
- **함정**: EFS와 Transfer Family는 S3 동기화 조합이 아니고, DataSync는 마운트 도구가 아니다. File Gateway는 NFS·SMB이지 SFTP가 아니다. 선지에 "NFS로 마운트"라고 적혔지만 Lustre는 자체 클라이언트를 쓴다. 번역 오류로 보인다.
- 참고: [FSx for Lustre 데이터 리포지토리](https://docs.aws.amazon.com/fsx/latest/LustreGuide/create-dra-linked-data-repo.html)

### #614 Docker 컨테이너 + 공유 스토리지, 더는 개발도 호스트 관리도 못 한다

- **정답**: **ECS on Fargate** + **EFS 볼륨**을 작업 정의에 추가.
- **왜**: 여러 작업이 동시에 쓰는 공유 파일 스토리지는 EFS이고, 처리량이 수요에 따라 자동으로 늘어난다. Fargate라 호스트 관리가 없다.
- **함정**: EBS는 Fargate 작업 간 공유 불가, S3로 바꾸면 코드 수정이 필요하다. EC2에 Docker를 직접 깔면 호스트 관리가 남는다.
- 참고: [ECS EFS 볼륨](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/efs-volumes.html)

### #182 1년간 수정 불가, 즉시 접근 가능한 금융 기록

- **정답**: 새 버킷에 **S3 Object Lock**을 켜고 기본 보존 1년, **규정 준수(compliance) 모드**.
- **왜**: 규정 준수 모드는 루트 사용자도 보존 기간 안에 지우거나 덮어쓸 수 없다. S3 Standard라 즉시 접근 가능하다.
- **함정**: Glacier Vault Lock은 즉시 접근이 안 되고, Intelligent-Tiering엔 보존 기능이 없다. 헤더 값으로 PutObject를 거부하는 버킷 정책은 Object Lock 없이는 불변성을 보장하지 못한다.
- 참고: [S3 Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html)

## 마이그레이션 (1문항)

### #714 온프레미스 NFS 아카이브를 Deep Archive로, 대역폭 제한과 야간 예약

- **상황**: 하루 수백만 장을 1GB 단위로 압축해 NFS에 보관. Hyper-V 컴퓨팅은 넉넉, 스토리지만 부족. 복구는 요청 후 1주일 안, 10Gbps DX, 대역폭 제한과 업무 외 시간 예약 필요.
- **정답**: **DataSync 에이전트를 Hyper-V VM으로 배포**하고 NFS → **S3 Glacier Deep Archive**로 복사, 완료 후 온프레미스에서 삭제.
- **왜**: DataSync는 대역폭 제한과 스케줄을 기본 지원하고, 에이전트는 소스 옆(온프레미스)에 있어야 한다. 1주일 복구 허용이면 가장 싼 Deep Archive다.
- **함정**: 에이전트를 EC2(그것도 GPU 인스턴스)에 두는 선지는 방향이 틀렸다. S3 Standard를 거쳐 하루 뒤 전환하는 선지는 비용이 더 든다. Tape Gateway는 테이프 운영이 더 붙는다.
- 참고: [AWS DataSync](https://docs.aws.amazon.com/datasync/latest/userguide/what-is-datasync.html)

- **왜 틀렸나**: 주 1회 제출, 월 1회 보고서 수준의 데이터에 상시 클러스터는 과하다. "운영 부담 최소"면 서버리스 조합이 답이다. EC2·ECS에 스케줄링 스케일링을 거는 선지도 같은 이유로 탈락한다.

## 틀린 패턴 네 가지

1. **자체 운영을 관리형으로 바꾸는 문제에서 자체 운영을 고른다.** Transfer Family, FSx, Aurora, Session Manager, MGN, MSK + Private CA. "운영 부담 최소"가 붙으면 EC2 위에 직접 올리는 선지는 먼저 지운다.
2. **다중 계정 거버넌스 도구의 전제 조건을 모른다.** SCP는 조직 안에서만, RAM 조직 공유는 관리 계정에서 켜고 나서, 거부 목록 전략은 FullAWSAccess를 남긴 채, Security Hub는 위임된 관리자로.
3. **네트워크는 "방향"과 "불변"을 묻는다.** Resolver 인바운드/아웃바운드, 보안 그룹 아웃바운드/인바운드, transit VIF와 TGW 피어링, 서브넷 CIDR은 수정 불가.
4. **서버리스 스로틀링은 한도가 몇 겹인지 세어야 한다.** API Gateway 계정 한도, Lambda 동시 실행, DynamoDB WCU, RDS 연결 수. 로그에 Lambda 호출이 없으면 그 앞 단계다.
