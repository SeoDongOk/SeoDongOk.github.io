요즘IT에서 [「어느 순간부터 저는 PR의 Diff를 읽지 않고 머지합니다」](https://yozm.wishket.com/magazine/detail/4051/)(글: 핸디)를 읽었다. 읽는 내내 11월 SoftBank Hackathon 본선 준비 기간이 떠올랐다. 나는 팀 Echo에서 인프라를 맡았다. AI로 코드를 쓰니 PR은 금방 쌓였는데, 인프라는 그 속도를 따라가지 못했고 테스트도 제때 돌지 못했다.

먼저 글의 내용을 정리하고, 내가 한 작업과 비교해 본다.

## 글 정리

### 질문을 바꾼다

저자는 프론트엔드 개발자다. 사이드 프로젝트와 회사 일 모두에서 AI가 코드 작성과 리뷰를 대부분 맡게 되면서, 사람이 Diff를 한 줄씩 읽는 방식이 병목이 됐다고 한다.

그래서 리뷰의 질문을 바꿨다.

> "이 코드가 틀렸다면 시스템이 알려주는가?"

코드를 읽는 것은 코드가 맞다는 확신을 얻는 수단 중 하나다. 확신을 다른 장치로 얻을 수 있다면 줄 단위 읽기를 줄일 수 있다는 주장이다. 이 생각은 Cursor·xAI 엔지니어 Lauren Tan이 한 달에 PR 2,500개를 머지한 사례를 다룬 발표에서 시작됐다고 한다.

신입 때 겪은 일화도 같은 이야기다. 띄어쓰기 같은 스타일 지적을 사람이 리뷰로 반복했는데, 돌아보면 그건 린터가 할 일이었다. 반복되는 지적은 규칙에 맡긴다.

### 대신 믿는 네 가지 장치

| 장치        | 저자가 하는 것                                                                                                                                                                           |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 테스트      | 구현보다 테스트를 먼저 본다. AI가 구현과 테스트를 같이 쓰고, 사람은 `it` 블록에 적힌 요구사항이 맞는지만 확인한다. Vitest 300개 이상, Playwright E2E 16개, 매일 새벽 스모크 테스트       |
| 타입·린트   | husky 훅으로 커밋·푸시 때 강제한다. Oxlint에 함수 길이·복잡도·매개변수 수 같은 규칙을 추가하고, Archlint로 아키텍처 경계를 막는다. 기계가 못 잡는 기준은 AGENTS.md 같은 규칙 문서로 둔다 |
| 작은 PR     | PR 제목을 한 문장으로 못 쓰면 쪼갠다. 한 주에 PR 136개를 열어 134개를 머지했고, 대부분 커밋 하나짜리였다                                                                                 |
| 눈으로 확인 | 화면이 결과물이니 어드민에 화면 플로우 페이지를 만들어 Figma·모바일 웹·앱을 나란히 본다. 30일 지난 캡처는 표시된다                                                                       |

### 아직 남은 불안

테스트는 통과했는데 화면이 이상한 일이 여러 번 있었다고 한다. 특정 조건에서만 보이는 UI는 테스트가 재현하지 못했다. 그래서 API 스펙 기반 Mock 데이터로 검증하고, PR에 Before/After 스크린샷을 붙이게 했다. 저자도 완전 자동화는 아직이라고 선을 긋는다.

저자의 권유는 테스트 하나, 규칙 문서 한 장부터 깔아 두라는 것이다. Diff를 아예 보지 말라는 뜻은 아니라고 덧붙인다.

> 제 눈은 가장 비싼 자원이니까, 가장 마지막에 가장 중요한 곳에만 쓰기로 했습니다.

## 해커톤에서 겪은 것

아래 숫자와 사례는 모두 내가 맡은 인프라 작업만 센 것이다.

### 인프라가 초기 병목이었다

AI가 Terraform 코드를 몇 분 만에 써 줘도 클라우드는 그 속도로 움직이지 않았다. 11월 2~3일 이틀 동안 적어 둔 인프라 문제만 20개가 넘는다. 시간을 가장 많이 잡아먹은 것은 이런 것들이었다.

- **EKS 노드 그룹이 18분째 생성 중에서 멈췄다.** Terraform 출력에는 에러가 없었다. CloudTrail을 열어 보니 계정이 AWS 무료 플랜이라 t3.large 기동이 거부되고 있었다. 실패한 노드 그룹이 지워지길 기다린 뒤 m7i-flex.large로 바꿔 다시 올렸다.
- **새 계정의 vCPU 한도가 5개였다.** 노드 몇 대만 띄워도 모자라서 할당량 상향을 요청하고 기다려야 했다.
- **DB 디스크가 붙지 않았다.** 클러스터는 떴는데 EBS CSI 드라이버가 없어서 DB 볼륨이 Pending에 머물렀다. "클러스터가 떴다"와 "앱이 돌 수 있다"는 다른 이야기였다.
- **Terraform 밖에서 만든 리소스가 재구축을 깨뜨렸다.** 급해서 손으로 만든 ALB·IAM·인증서 때문에 VPC 삭제가 실패했고, 클러스터를 다시 만들면 권한이 사라졌다.

그동안 앱 쪽은 올릴 곳을 기다려야 했다. 프론트 연동이 급해서 API 서버를 일단 도쿄 EKS에 먼저 올렸는데, 도쿄는 재난 시연에서 죽는 쪽이었다. 전환을 지시할 관제탑이 같이 죽는 구조라 GCP 서울에 관제탑 기반을 따로 만들어 옮겼다. 인프라가 늦은 만큼 일정이 밀렸고, 옮기는 작업이 한 번 더 생겼다.

AI 덕분에 코드를 쓰는 시간은 줄었다. 그런데 계정 플랜, 할당량, 드라이버처럼 코드 밖에 있는 제약은 AI가 줄여 주지 못했다. 여기서는 Diff를 읽는 것보다 CloudTrail과 실제 환경을 여는 쪽이 문제를 더 빨리 찾았다.

### 테스트가 레포에 없었다

내가 echo-infra에 연 PR을 다시 뽑아 봤다(11월 3일~8일).

| 항목                           |   값 |
| ------------------------------ | ---: |
| 연 PR                          |   48 |
| 머지                           |   46 |
| 변경 줄 수 중앙값              | 46줄 |
| 열고 머지까지 걸린 시간 중앙값 | 12분 |
| 10분 안에 머지한 PR            |   23 |
| GitHub 리뷰 기록               |    0 |
| PR에서 돈 자동 체크            |    0 |

PR은 글이 말하는 기준대로 작았다. 문제는 자동 체크가 하나도 없었다는 점이다. `terraform validate`를 돌리는 `check.sh`는 만들어 두었지만 내 손으로 돌려야 했고, PR에서 자동으로 돌지는 않았다. 그마저도 처음에는 개인 AWS 프로필로 state를 읽으려다 403으로 실패했다.

그래서 실제 검증은 전부 손으로 하는 시험이었다.

1. **Terraform plan 파일.** 브랜치에서 `plan -out`을 만들고, 그 plan을 읽은 뒤 같은 파일로 apply했다. 인프라에서는 코드 Diff보다 plan의 "무엇이 생기고 무엇이 지워지는가"가 더 정확한 리뷰 대상이었다.
2. **장애 시험 실측.** 진입점 장애 시험에서 요청을 흘리면서 진입점을 죽였다. 1차에서는 126건 중 15건이 실패하고 실패 구간이 74.6초였다. 헬스체크를 보는 NLB를 앞에 둔 2차에서는 344건 중 12건 실패, 실패 구간 3.8초였다.
3. **시작 전 점검 스크립트.** 전체 테스트 전에 `preflight.sh`로 환경 상태를 확인했다.
4. **실제 환경 값 열어 보기.** "만들었다"는 보고와 실제로 반영된 값 사이에 틈이 자주 생겼다. 그래서 머지 전에 실제 환경 값을 직접 열어 봤다.

문제는 이 시험들이 늦게, 한꺼번에 돌았다는 점이다. 인프라가 늦게 준비되니 리허설은 11월 4일, 전체 테스트는 제출 전날인 11월 6일에야 할 수 있었다. 그 사이 내가 plan을 직접 돌리지 않은 PR은 아무 검증 없이 들어갔다. 시험 결과도 PR에 붙지 않고 문서와 슬랙에 흩어졌다.

저자의 질문인 "이 코드가 틀렸다면 시스템이 알려주는가"로 보면 답은 "아니오"였다. 틀린 걸 알려 줄 수 있는 건 나 하나뿐이었다.

## 다음에 한다면

인프라 레포를 처음 만들 때 이것부터 깔겠다.

- **계정 제약을 첫날 확인한다.** 무료 플랜 여부, vCPU 할당량, 필요한 드라이버를 코드보다 먼저 본다. 인프라가 늦으면 팀 전체가 늦는다.
- PR마다 `terraform fmt -check`, `validate`, `tflint`, `plan`을 돌리고 plan 요약을 PR 댓글로 남긴다.
- PR 템플릿에 "실측 값(전/후)" 칸을 만든다. 숫자가 없으면 "무중단"이라고 쓰지 않는다.
- 장애 시험을 마지막에 몰아서 하지 않고, 진입점·DB처럼 단위별로 나눠 작은 시험을 자주 돌린다.
- Terraform 밖 수동 변경도 PR로 기록해 레포에 남긴다.

## 배운 점

- AI는 코드를 쓰는 시간을 줄여 주지만, 클라우드 계정과 환경의 제약은 줄여 주지 않는다. 그래서 인프라는 처음부터 병목이 되기 쉽다.
- 작은 PR만으로는 부족하다. 내 PR은 중앙값 46줄로 작았지만 자동 체크가 없어서 틀려도 알려 주는 장치가 없었다.
- 검증 장치는 레포에 있어야 한다. 내 손에만 있는 시험은 늦게 돌고, 내가 바쁠 때는 아예 돌지 않는다.
