## 문제 상황

해커톤 프로젝트에서 PostgreSQL 논리 복제로 두 클라우드와 온프레미스 사이에 데이터를 실시간으로 맞춰 두었다. 한쪽이 죽으면 다른 쪽이 몇 초 안에 이어받는다. 무중단 이전 리허설에서는 쓰기 정지 약 10초, 누락·중복 0건까지 확인했다.

그런데 마지막에 점검해 보니 **과거 시점으로 되돌릴 수 있는 백업이 하나도 없었다.** 덤프 작업도, 디스크 스냅샷도, WAL 보관도 없었다. 사본은 셋이나 있었지만 전부 "지금" 상태였다.

## 왜 이렇게 되나

처음 설계에는 백업 갈래가 있었다. 변경 데이터 캡처(CDC)로 변경 로그를 따로 쌓아 두는 구조였다. 그런데 데이터 이전 방식을 논리 복제로 바꾸면서 CDC를 걷어냈고, 백업은 "나중에 별도로" 하기로 한 일감이 됐다. 그 일감은 구현되지 않은 채 닫혔다.

이게 흔한 패턴인 이유는 단순하다. **복제가 있으면 데이터가 안전하다고 느껴진다.** 사본이 여러 곳에 있으니 하나가 망가져도 괜찮다는 감각이 백업의 우선순위를 밀어낸다.

## 복제와 백업은 다른 질문에 답한다

| | 복제 | 백업 |
|---|---|---|
| 답하는 질문 | 지금 데이터를 **다른 곳에서** 살릴 수 있나 | 데이터를 **과거 시점으로** 되돌릴 수 있나 |
| 막는 재난 | 장소가 사라지는 재난 (정전, 지진, 리전 장애, 서버 고장) | 데이터가 망가지는 재난 (실수로 지움, 잘못된 배포, 앱 버그, 랜섬웨어) |
| 원본이 망가지면 | 사본도 몇 초 안에 같이 망가진다 | 망가지기 전 시점이 그대로 남아 있다 |
| 핵심 지표 | RTO (얼마나 빨리 다시 서나) | RPO (얼마만큼의 데이터를 잃나) |

PostgreSQL 논리 복제의 기본 발행(`CREATE PUBLICATION … FOR ALL TABLES`)은 INSERT·UPDATE·DELETE·TRUNCATE를 모두 사본으로 보낸다. 누군가 `DELETE FROM orders;`를 실행하면, 복제가 빠를수록 모든 사본에서 더 빨리 사라진다. 복제가 잘 될수록 백업 역할은 더 못 한다는 역설이다.

## 3-2-1에서 3-2-1-1-0으로

전통적인 3-2-1 규칙은 이렇다.

- **3** 데이터 사본 3개 (원본 포함)
- **2** 서로 다른 저장 매체 2종
- **1** 그중 하나는 다른 장소(오프사이트)

랜섬웨어가 백업까지 노리게 되면서 두 개가 더 붙었다.

- **1** 그중 하나는 **변경 불가(immutable) 또는 오프라인**
- **0** 복원 시험 결과 **오류 0**

마지막 두 개가 핵심이다.

**변경 불가.** 공격자가 관리자 권한을 얻으면 백업부터 지운다. 그래서 백업 저장소는 원본 시스템의 자격 증명으로 지울 수 없어야 한다. 클라우드에서는 이렇게 만든다.

- AWS S3 Object Lock 준수(compliance) 모드: 보존 기간 안에는 루트 계정도 삭제할 수 없다.
- GCS 버킷 보존 정책 잠금: 잠근 뒤에는 정책을 줄이거나 지울 수 없다.
- 백업은 **별도 계정·별도 프로젝트**에 두고, 운영 시스템에는 쓰기 권한만 준다. 읽기·삭제 권한은 주지 않는다.

**복원 시험 0.** 복원해 본 적 없는 백업은 백업이 아니라 희망이다. 정기적으로 실제로 띄워 보고, 행 수와 내용이 맞는지 기계적으로 확인한다. 확인 방법은 [2편](/blog/2026-11-08-dr-basics-02-consistency-vs-integrity)에서 다룬다.

## PostgreSQL에서의 최소 구성

| 단계 | 방법 | 얻는 것 |
|---|---|---|
| 1 | `pg_dump` 를 하루 1회 이상, 변경 불가 저장소로 | 하루 단위 과거 시점 |
| 2 | 복원 시험 자동화 (임시 인스턴스에 복원 → 대조 → 폐기) | 백업이 실제로 쓸 수 있다는 증거 |
| 3 | `pg_basebackup` + WAL 보관 (`archive_command` 또는 `pg_receivewal`) | 임의 시점 복구(PITR), RPO 수 초~수 분 |

논리 복제를 쓰는 환경이라면 주의할 점이 하나 더 있다. **논리 복제는 시퀀스 값과 스키마 변경(DDL)을 옮기지 않는다.** 사본을 백업 대신 쓰려고 하면 시퀀스가 원본보다 뒤처져 있어 새 행에서 키 충돌이 나거나, 원본에만 있는 칸이 사본에 없는 문제가 생긴다. 이것도 사본이 백업이 될 수 없는 이유다.

## 배운 점

- 복제를 만들 때 "그러면 과거로는 어떻게 되돌리지?"를 같은 자리에서 묻는다. 둘을 따로 일감으로 쪼개면 백업 쪽이 먼저 사라진다.
- 백업이 있다는 것은 "덤프 파일이 있다"가 아니라 "어제 복원해 봤고 오류가 0이었다"여야 한다.
- 백업 저장소의 삭제 권한은 운영 시스템이 가진 어떤 자격 증명에도 주지 않는다.

다음 글에서는 복원이 잘 됐는지 확인하는 방법, 그리고 "두 DB가 같다"는 확인이 왜 충분하지 않은지를 다룬다.
