## 이 글에서 답할 면접 질문

- 가용성 99.9%와 99.99%는 한 달에 각각 얼마나 멈춰도 된다는 뜻인가?
- 구성 요소가 여러 개 이어진 시스템의 가용성은 어떻게 계산하나?
- 멀티 AZ와 멀티 리전은 각각 어떤 장애를 막고, 언제 멀티 리전까지 가야 하나?
- SLI, SLO, SLA는 어떻게 다르고, 에러 예산은 어떻게 쓰나?
- 알림이 너무 많아서 아무도 안 본다. 어떻게 고치겠나?
- 의존하는 서비스가 느려질 때 우리 서비스가 같이 죽지 않게 하려면?
- 큰 장애가 났을 때 처음 30분 동안 무엇을 하나?
- 회고(포스트모템)는 어떻게 쓰고, 왜 "비난 없는" 회고여야 하나?

## 개념과 배경

### 신뢰성은 "안 멈추는 것"이 아니다

신뢰성(reliability)은 시스템이 **사용자가 기대하는 일을, 기대하는 만큼 잘** 해내는 정도다. 여기서 중요한 단어는 "사용자"와 "기대하는 만큼"이다.

- 서버 CPU가 100%여도 사용자가 느끼지 못하면 신뢰성 문제가 아니다.
- 서버가 모두 살아 있어도 결제 버튼이 5초씩 걸리면 신뢰성 문제다.
- 100% 신뢰성은 목표가 아니다. 사용자의 휴대폰 회선, 집 와이파이, 통신사가 이미 100%가 아니기 때문에, 그보다 높은 신뢰성은 비용만 들고 아무도 느끼지 못한다.

그래서 신뢰성 공학의 출발점은 "얼마나 믿을 만해야 하나"를 **숫자로 합의**하는 것이다. 그 숫자가 SLO다.

### SRE는 무엇인가

SRE(Site Reliability Engineering)는 Google이 운영 업무를 소프트웨어 공학 방식으로 풀면서 정리한 접근이다. 핵심 생각은 세 가지다.

1. **신뢰성 목표를 숫자로 정한다.** SLO와 에러 예산.
2. **운영을 코드로 줄인다.** 반복되는 수작업(토일)은 자동화한다.
3. **장애에서 배운다.** 사람을 탓하지 않고 시스템을 고친다.

클라우드 엔지니어 면접에서 SRE를 묻는 이유는 단순하다. 공통 기반을 만드는 사람은 그 기반 위의 모든 서비스가 얼마나 믿을 만할지를 함께 결정하기 때문이다.

## 깊게 1 — 가용성을 직접 계산한다

### 나인(nine)의 의미

가용성 99.9%를 "쓰리 나인"이라고 부른다. 숫자를 시간으로 바꿔 두면 대화가 쉬워진다.

| 가용성 | 한 달(30일) 허용 중단 | 1년 허용 중단 |
|---|---|---|
| 99% | 약 7.2시간 | 약 3.65일 |
| 99.9% | 약 43분 | 약 8.8시간 |
| 99.95% | 약 22분 | 약 4.4시간 |
| 99.99% | 약 4.3분 | 약 53분 |
| 99.999% | 약 26초 | 약 5.3분 |

계산은 단순하다. 30일은 43,200분이다. 99.9%면 0.1%가 허용되니 43,200 × 0.001 = 43.2분이다.

이 표가 주는 감각이 중요하다. **99.99%는 한 달에 4분**이다. 사람이 알림을 받고 노트북을 열고 로그인하는 데만 5분이 걸린다. 그래서 99.99% 이상은 "사람이 고치는" 구조로는 불가능하고, **자동으로 넘어가는** 구조가 있어야 한다.

### 직렬 구성: 곱한다

요청이 로드밸런서 → 앱 → DB를 차례로 지나야 한다면, 셋 다 살아 있어야 성공한다. 이때 전체 가용성은 각 가용성을 곱한다.

```
LB 99.99% × 앱 99.9% × DB 99.95%
= 0.9999 × 0.999 × 0.9995
≈ 0.9984 → 약 99.84%
```

구성 요소를 하나 더할 때마다 전체 가용성은 **가장 약한 고리보다도 낮아진다.** 마이크로서비스 20개가 한 요청 안에서 줄줄이 호출되면, 각각이 99.9%여도 전체는 약 98%까지 떨어진다(0.999의 20제곱). 그래서 "호출 사슬을 짧게", "꼭 필요하지 않은 의존은 비동기로"가 신뢰성 설계의 기본이 된다.

### 병렬 구성: 실패 확률을 곱한다

같은 앱을 두 AZ에 하나씩 두고, 하나만 살아 있어도 된다면 계산이 반대가 된다. **둘 다 죽을 확률**을 구해서 1에서 뺀다.

```
각 99.9% → 실패 0.1%
둘 다 실패 = 0.001 × 0.001
           = 0.000001
가용성 = 1 − 0.000001
       = 99.9999%
```

숫자는 아주 좋아 보인다. 그런데 이 계산은 **두 실패가 서로 독립**이라는 가정 위에 있다. 현실에서는 독립이 아닌 경우가 많다.

- 같은 버그가 있는 버전을 두 AZ에 동시에 배포했다.
- 두 AZ가 같은 설정 저장소, 같은 인증 서비스, 같은 DNS에 기대고 있다.
- 한 AZ가 죽자 트래픽이 다른 AZ로 몰려 그쪽도 과부하로 죽었다.

그래서 면접에서는 계산을 보여 준 뒤 반드시 "다만 실패가 상관돼 있으면 이 숫자는 성립하지 않는다"를 덧붙여야 한다. 이 한 문장이 계산할 줄 아는 사람과 운영해 본 사람을 가른다.

## 깊게 2 — 장애 영역(failure domain)

장애 영역은 "한 번에 같이 죽을 수 있는 범위"다. 설계할 때는 각 영역이 죽었을 때 무엇이 남는지를 차례로 묻는다.

| 영역 | 무엇이 같이 죽나 | 대비 |
|---|---|---|
| 인스턴스·파드 | 프로세스 하나, 노드 하나 | 여러 대 + 헬스체크 + 자동 교체 |
| 가용 영역(AZ) | 데이터센터 묶음 하나 (전원, 냉각, 네트워크) | 멀티 AZ 배치, AZ마다 NAT·LB 대상 |
| 리전 | 지역 전체, 리전 단위 서비스 | 멀티 리전, 다른 리전 백업 |
| 클라우드 제공자 | 특정 회사의 전역 서비스 | 멀티 클라우드, 탈출 계획 |
| 우리 자신 | 잘못된 배포, 잘못된 설정, 지워진 데이터 | 점진 배포, 변경 검토, 불변 백업 |

마지막 줄이 가장 자주 일어난다. 실제 장애 원인을 세어 보면 하드웨어보다 **사람이 넣은 변경**이 훨씬 많다. 멀티 리전을 해도 잘못된 설정을 모든 리전에 동시에 밀어 넣으면 전부 죽는다. 그래서 배포 전략(06편)도 신뢰성 설계의 일부다.

### 컨트롤 플레인과 데이터 플레인

클라우드 서비스는 두 부분으로 나뉜다.

- **컨트롤 플레인:** 자원을 만들고, 바꾸고, 지우는 API. 예를 들어 "인스턴스를 하나 더 만들어라", "로드밸런서 대상을 바꿔라".
- **데이터 플레인:** 이미 만들어진 자원이 실제 일을 하는 부분. 인스턴스가 요청을 처리하고, 로드밸런서가 패킷을 나르는 것.

데이터 플레인은 보통 컨트롤 플레인보다 단순하고 더 높은 가용성으로 설계된다. 반대로 컨트롤 플레인은 장애가 나면 "새로 만들기"가 안 된다. 여기서 중요한 설계 원칙이 나온다.

**장애 복구 경로가 컨트롤 플레인에 기대면 안 된다.** "AZ가 죽으면 다른 AZ에 인스턴스를 새로 만들어서 버틴다"는 계획은, 마침 그때 컨트롤 플레인도 혼잡하거나 장애면 실패한다. 큰 장애 때는 모두가 동시에 새 자원을 만들려고 하기 때문에 실제로 자주 막힌다.

### 정적 안정성(static stability)

AWS가 강조하는 개념으로, "장애가 나도 **아무것도 새로 만들거나 바꾸지 않고** 버틸 수 있게 미리 준비해 둔다"는 뜻이다.

- 3개 AZ에 걸쳐 평소 필요한 용량의 150%를 미리 띄워 둔다. 한 AZ가 죽어도 남은 두 AZ가 100%를 감당한다.
- DNS 장애 조치를 컨트롤 플레인 API 호출로 하지 않고, 헬스체크에 따라 데이터 플레인에서 자동으로 바뀌게 둔다.
- 설정 값을 시작할 때 원격에서 받아 오는 대신, 마지막으로 받은 값을 로컬에 캐시해 두고 원격이 죽으면 캐시로 계속 돈다.

정적 안정성은 돈이 든다. 놀고 있는 용량을 늘 들고 있어야 하기 때문이다. 그래서 "어느 서비스까지 정적 안정성을 줄 것인가"가 비용과 신뢰성의 거래가 된다.

## 깊게 3 — 멀티 AZ와 멀티 리전 패턴

### 멀티 AZ는 기본값

대부분의 클라우드 관리형 서비스(로드밸런서, 관리형 DB의 다중 AZ 옵션, 오브젝트 스토리지)는 AZ 장애를 견디도록 만들 수 있다. 앱은 다음만 지키면 된다.

- 인스턴스·파드를 AZ마다 고르게 나눈다(쿠버네티스는 topology spread 제약).
- 상태는 앱 밖(관리형 DB, 캐시, 오브젝트 스토리지)에 둔다.
- NAT 게이트웨이처럼 AZ에 묶인 자원은 AZ마다 둔다.
- AZ 하나가 빠져도 남은 AZ가 감당할 용량을 둔다.

멀티 AZ는 비용 대비 효과가 커서, 공통 기반에서는 **기본값으로 강제**하는 경우가 많다.

### 멀티 리전은 선택

멀티 리전은 비싸고 어렵다. 데이터를 리전 사이로 복제해야 하고, 빛의 속도 때문에 리전 간 왕복에 수십 밀리초가 든다. 강한 일관성과 낮은 지연을 동시에 가질 수 없다.

| 패턴 | 평소 | 장애 시 | 비용·난도 |
|---|---|---|---|
| 백업만 다른 리전 | 한 리전만 운영 | 다른 리전에 새로 구축 | 낮음, 복구 느림 |
| 액티브-패시브 (웜 스탠바이) | 보조 리전에 작은 규모 대기 | 보조를 키우고 트래픽 전환 | 중간 |
| 액티브-액티브 | 두 리전이 동시에 처리 | 남은 리전이 전부 받음 | 높음, 데이터 충돌 설계 필요 |

리전 장애 대비 수준을 고르는 방법(백업·파일럿 라이트·웜 스탠바이·멀티 사이트)과 RTO·RPO는 [재해 복구 기초 04편](/blog/2026-11-08-dr-basics-04-dr-tiers-and-priority)에 정리했다. 여기서는 면접 관점의 판단 기준만 둔다.

- **법·계약이 요구하나?** 금융, 통신처럼 리전 장애에도 서비스해야 한다는 규제가 있으면 간다.
- **멈추면 잃는 돈이 멀티 리전 비용보다 큰가?** 대부분의 내부 시스템은 아니다.
- **데이터 일관성을 어떻게 할 건가?** 쓰기를 한 리전에만 받는지(단일 쓰기), 양쪽에서 받는지(다중 쓰기, 충돌 해결 필요)를 먼저 정한다.

### 셀 기반 아키텍처

큰 서비스는 전체를 여러 개의 독립된 복제본("셀")으로 나누고, 사용자를 셀에 나눠 배정한다. 셀마다 앱·DB·캐시를 따로 갖는다.

```
  라우터 (사용자 → 셀)
   ├─ 셀 A: 앱 + DB  (사용자 1~25%)
   ├─ 셀 B: 앱 + DB  (사용자 26~50%)
   └─ ...
```

얻는 것은 **폭발 반경(blast radius)의 제한**이다. 나쁜 배포나 독한 요청 하나가 셀 하나만 죽인다. 배포도 셀 하나씩 차례로 한다. 대신 라우팅 계층이 새로운 단일 장애점이 되므로, 라우터는 최대한 단순하게 만든다.

## 깊게 4 — SLI, SLO, SLA, 에러 예산

### 세 단어 구분

| 용어 | 뜻 | 예 |
|---|---|---|
| SLI | 측정값. 사용자 경험을 나타내는 지표 | 성공한 요청 비율, 300ms 안에 끝난 요청 비율 |
| SLO | 내부 목표. SLI가 이만큼은 돼야 한다 | 30일 동안 성공률 99.9% |
| SLA | 고객과의 계약. 못 지키면 보상 | 월 99.5% 미만이면 요금 10% 환불 |

SLA는 SLO보다 **느슨하게** 잡는다. 내부 목표를 먼저 어기고 경보가 울려야, 계약을 어기기 전에 손쓸 시간이 생긴다.

### 좋은 SLI 고르기

SLI는 "사용자가 느끼는 것"에 가까울수록 좋다.

- 나쁨: CPU 사용률, 서버 생존 여부. 사용자 경험과 연결이 약하다.
- 좋음: 로드밸런서에서 센 "5xx가 아닌 응답 비율", "300ms 안에 끝난 요청 비율".
- 더 좋음: 실제 사용자 여정(로그인 → 장바구니 → 결제)을 흉내 낸 합성 모니터링 성공률.

보통 SLI는 **좋은 이벤트 수 ÷ 전체 이벤트 수**의 비율로 정의한다. 비율로 쓰면 SLO와 에러 예산 계산이 바로 된다.

### 에러 예산: 계산 예

SLO가 "30일 성공률 99.9%"이고, 30일 동안 요청이 1,000만 건 들어온다고 하자.

```
허용 실패율 = 1 − 0.999 = 0.1%
에러 예산   = 1,000만 × 0.001
           = 1만 건
```

한 달에 실패 1만 건까지는 "써도 되는 돈"이다. 이 예산을 어디에 쓸지가 팀의 결정이 된다.

- 예산이 많이 남았다 → 새 기능 배포를 빠르게, 실험을 과감하게.
- 예산이 바닥났다 → 기능 배포를 멈추고 안정화 작업에 집중.

에러 예산의 진짜 가치는 **개발과 운영의 다툼을 숫자로 끝내는 것**이다. "배포 좀 그만해라"와 "왜 막느냐"의 싸움이 "예산이 남았나"라는 질문 하나로 바뀐다.

### 소진율(burn rate)과 알림

에러 예산을 얼마나 빨리 쓰고 있는지가 소진율이다. 소진율 1은 "이 속도면 30일 끝에 예산을 딱 다 쓴다"는 뜻이다. 소진율 10이면 3일 만에 다 쓴다.

알림은 소진율로 건다. Google SRE 워크북이 제시하는 출발점은 이렇다.

| 조건 | 의미 | 대응 |
|---|---|---|
| 1시간 동안 소진율 14.4 이상 | 1시간에 한 달 예산의 2%를 씀 | 즉시 호출 |
| 6시간 동안 소진율 6 이상 | 6시간에 5%를 씀 | 즉시 호출 |
| 3일 동안 소진율 1 이상 | 3일에 10%를 씀 | 티켓 |

여기에 **짧은 창을 하나 더** 붙인다(예: 1시간 조건에는 5분 창). 이미 회복된 문제로 계속 울리는 것을 막기 위해서다. 긴 창은 "진짜 큰 문제인가", 짧은 창은 "지금도 계속되나"를 본다.

## 깊게 5 — 알림 설계

### 원인이 아니라 증상에 건다

"CPU 90%", "디스크 80%", "파드 재시작" 같은 원인 기반 알림은 대부분 사용자에게 아무 영향이 없을 때 울린다. 그러다 보면 사람들이 알림을 무시하게 되고(알림 피로), 진짜 장애 알림도 묻힌다.

원칙은 이렇다.

- **사람을 깨우는 알림은 사용자 영향(증상)에만.** SLO 소진율, 핵심 여정 실패.
- **원인 지표는 대시보드와 티켓으로.** 디스크 80%는 "이번 주 안에 처리" 티켓이면 충분하다. 단, 몇 시간 안에 꽉 찰 속도라면 그건 곧 증상이 되므로 호출할 수 있다.
- **모든 호출 알림에는 대응 문서(런북) 링크.** 새벽 3시의 사람은 생각을 잘 못 한다.
- **울렸는데 할 일이 없었던 알림은 지운다.** 매주 알림 목록을 보고 "이번 주에 받은 알림 중 실제 행동으로 이어진 비율"을 센다.

## 깊게 6 — 관측 가능성(observability)

### 세 가지 신호

| 신호 | 잘하는 것 | 약점 |
|---|---|---|
| 메트릭 | 추세, 알림, 싸다 | 개별 요청은 안 보인다 |
| 로그 | 무슨 일이 있었는지 자세히 | 많고 비싸다, 찾기 어렵다 |
| 트레이스 | 요청 하나가 어느 서비스에서 시간을 썼나 | 샘플링해야 감당 가능 |

세 신호를 **같은 요청 ID(트레이스 ID)로 엮는 것**이 핵심이다. 메트릭에서 지연이 튄 걸 보고 → 그 시간의 느린 트레이스를 열고 → 그 트레이스 ID로 로그를 찾는 흐름이 돼야 장애 시간이 줄어든다.

### 무엇을 잴까: RED와 USE

- **RED (요청을 받는 서비스용):** Rate(초당 요청), Errors(실패 비율), Duration(지연 분포).
- **USE (자원용):** Utilization(사용률), Saturation(포화, 대기열 길이), Errors(오류).
- Google의 **네 가지 황금 신호**(지연, 트래픽, 오류, 포화)도 같은 생각이다.

지연은 **평균이 아니라 백분위수**(p50, p95, p99)로 본다. 평균은 소수의 아주 느린 요청을 숨긴다. 그리고 그 소수가 가장 많이 요청하는 큰 고객일 수 있다.

### OpenTelemetry

OpenTelemetry(OTel)는 메트릭·로그·트레이스를 만드는 방법과 보내는 형식을 통일한 오픈 표준이다. 앱은 OTel SDK로 신호를 만들고, OTel Collector가 받아서 원하는 백엔드(클라우드 모니터링 서비스, Prometheus, 상용 APM)로 보낸다.

공통 기반 관점의 장점은 **백엔드를 바꿔도 앱 코드를 안 고친다**는 것이다. 멀티 클라우드라면 클라우드마다 다른 에이전트를 심는 대신 Collector 설정만 바꾼다.

### 카디널리티 비용

메트릭에 붙는 라벨(태그) 조합의 수를 카디널리티라고 한다. `http_requests_total` 에 `method`, `status`, `path` 라벨을 붙이면 조합마다 별도의 시계열이 생긴다. 여기에 `user_id` 를 붙이면 사용자 수만큼 시계열이 폭발한다.

- 메트릭 백엔드는 시계열 수로 메모리와 돈을 쓴다. 카디널리티 폭발은 모니터링 시스템 자체를 죽인다.
- 사용자 ID, 요청 ID처럼 값이 무한한 것은 메트릭이 아니라 **로그나 트레이스**에 넣는다.
- 공통 기반에서는 라벨 규칙을 정해 두고, 새 메트릭이 들어올 때 시계열 수를 확인하는 장치를 둔다.

## 깊게 7 — 용량 계획과 부하 시험

용량 계획은 "다음 달, 다음 분기, 행사 날에 얼마가 필요한가"를 미리 계산하는 일이다.

1. **수요 예측:** 지난 추세 + 예정된 행사·출시. 사업 쪽 계획을 먼저 듣는다.
2. **한 대당 처리량 측정:** 부하 시험으로 "인스턴스 하나가 SLO를 지키며 처리하는 최대 초당 요청"을 잰다. 추측하지 않는다.
3. **필요 대수 = 최대 수요 ÷ 한 대 처리량**, 여기에 AZ 하나 장애 여유와 성장 여유를 더한다.
4. **병목 확인:** 앱을 늘려도 DB 연결 수, 외부 API 호출 한도, 클라우드 계정 할당량(quota)에 먼저 막힐 수 있다. 할당량 상향은 시간이 걸리니 미리 요청한다.

부하 시험의 종류도 구분한다.

| 종류 | 목적 |
|---|---|
| 부하 시험 | 예상 최대치에서 SLO를 지키나 |
| 스트레스 시험 | 어디서 어떻게 무너지나 (무너지는 모양이 중요) |
| 내구 시험 | 몇 시간 계속 돌릴 때 메모리 누수·연결 고갈이 있나 |
| 스파이크 시험 | 갑자기 10배가 오면 오토스케일링이 따라오나 |

"무너지는 모양"이 중요한 이유: 과부하에서 전체가 0이 되는 시스템보다, 처리량은 유지하면서 초과분만 거절하는 시스템이 훨씬 낫다. 그게 다음 절의 주제다.

## 깊게 8 — 우아한 성능 저하(graceful degradation)

의존하는 것이 느려지거나 죽었을 때 **같이 죽지 않고, 덜 좋은 상태로 계속 도는** 기술들이다.

### 타임아웃

모든 원격 호출에는 타임아웃이 있어야 한다. 타임아웃이 없으면 느린 의존 하나가 우리 쪽 스레드·연결을 다 붙잡아 우리까지 멈춘다. 값은 의존 서비스의 p99 지연을 보고, 사용자에게 약속한 전체 시간 안에 들어오게 정한다. 바깥 계층일수록 길게, 안쪽일수록 짧게.

### 재시도

일시적 실패는 재시도로 대부분 사라진다. 대신 위험하다.

- **지수 백오프 + 지터:** 1초, 2초, 4초…로 늘리고 무작위를 섞는다. 모두가 같은 순간에 재시도하면 회복 중인 서버를 다시 쓰러뜨린다.
- **재시도 예산:** 전체 요청의 일정 비율까지만 재시도한다. 여러 계층이 각각 3번씩 재시도하면 맨 아래는 3 × 3 × 3 = 27배 부하를 받는다.
- **멱등성:** 쓰기 요청은 멱등 키가 있을 때만 재시도한다.

### 서킷 브레이커

의존 서비스의 실패율이 기준을 넘으면 **호출을 아예 멈추고** 바로 실패(또는 대체 응답)를 돌려준다. 일정 시간 뒤 소수의 요청만 시험 삼아 보내 보고(반열림 상태), 성공하면 다시 연다. 죽은 서비스에 계속 매달리는 낭비를 막고, 그 서비스가 회복할 틈을 준다.

### 벌크헤드(격벽)

배의 격벽처럼 자원을 칸막이로 나눈다. 의존 서비스마다 연결 풀·스레드 풀을 따로 두면, 추천 서비스가 느려져도 결제 호출용 풀은 멀쩡하다. 셀 기반 아키텍처는 이걸 서비스 전체 규모로 키운 것이다.

### 부하 차단(load shedding)과 역압(backpressure)

- **부하 차단:** 감당 못 하는 요청은 빨리 거절한다(HTTP 503, 429). 모든 요청을 받아서 모두 느려지는 것보다, 일부를 빨리 거절하고 나머지를 제대로 처리하는 게 낫다. 우선순위가 낮은 요청(분석용 수집, 미리 불러오기)부터 버린다.
- **역압:** 받는 쪽이 "천천히 보내라"를 보내는 쪽에 알린다. 대기열 길이에 상한을 두고, 꽉 차면 생산자를 멈추게 한다. 상한 없는 대기열은 지연을 무한히 늘리고 결국 메모리를 터뜨린다.

### 기능 단위의 저하

- 추천 서비스가 죽으면 "인기 상품" 고정 목록을 보여 준다.
- 검색이 느리면 캐시된 결과를 보여 준다.
- 쓰기가 안 되면 읽기 전용 모드로 바꾸고 안내 문구를 띄운다.

어떤 기능을 먼저 포기할지는 **평소에 정해 둬야** 한다. 장애 중에 정하면 늦다.

## 깊게 9 — 의존성 관리

서비스의 가용성은 의존하는 것들의 가용성을 넘을 수 없다(직렬 계산을 떠올리자). 그래서 의존성을 목록으로 관리한다.

- **필수 의존과 선택 의존을 구분한다.** 선택 의존이 죽었을 때 우리 서비스가 계속 도는지 시험으로 확인한다.
- **의존 서비스의 SLO를 안다.** 내 SLO가 99.99%인데 필수 의존이 99.9%면, 내 목표는 거짓말이다. 캐시·대체 경로를 두거나 목표를 낮춘다.
- **시작 시 의존을 줄인다.** 앱이 뜰 때 설정 서버·비밀 저장소·DB가 모두 살아 있어야 한다면, 대규모 재시작 때 모두가 동시에 몰려 서로를 죽인다.
- **순환 의존을 없앤다.** A가 B를, B가 A를 필요로 하면, 둘 다 꺼진 상태에서 아무도 못 켠다. 특히 "복구에 필요한 도구가 복구 대상 위에서 돈다"(모니터링이 장애 난 클러스터 안에 있다, 배포 도구가 장애 난 리전에 있다)를 경계한다.

## 깊게 10 — 장애 대응

### 역할을 나눈다

큰 장애에서 가장 흔한 실패는 기술이 아니라 **모두가 같은 걸 들여다보고, 아무도 전체를 안 보는 것**이다. 그래서 역할을 나눈다.

| 역할 | 하는 일 |
|---|---|
| 인시던트 커맨더(IC) | 전체 지휘. 직접 고치지 않는다. 우선순위와 결정 |
| 기술 담당 | 원인 조사와 조치. 여러 명일 수 있다 |
| 커뮤니케이션 담당 | 고객·경영진·다른 팀에 정해진 주기로 상태 공유 |
| 기록 담당 | 시각과 함께 무엇을 보고 무엇을 했는지 타임라인 기록 |

작은 장애에서는 한 사람이 여러 역할을 맡아도 되지만, IC가 직접 키보드를 잡기 시작하면 지휘가 사라진다.

### 심각도 등급

미리 정의해 두면 "이게 깨울 일인가"를 고민하지 않는다.

| 등급 | 예 | 대응 |
|---|---|---|
| SEV1 | 핵심 기능이 전체 사용자에게 안 됨, 데이터 손실 | 즉시 전원 호출, 경영진 공유 |
| SEV2 | 일부 사용자·기능 장애, 우회 가능 | 담당 호출, 업무 시간 내 해결 |
| SEV3 | 사용자 영향 작음 | 티켓 |

### 처음 30분의 순서

1. **선언한다.** "장애다"라고 말하고 채널을 연다. 늦은 선언이 가장 비싸다.
2. **영향을 파악한다.** 누가, 얼마나, 언제부터. SLI 대시보드가 여기서 쓰인다.
3. **완화가 먼저, 원인은 나중.** 최근 배포가 있으면 먼저 롤백한다. 트래픽을 다른 AZ·리전으로 돌린다. 기능 플래그로 문제 기능을 끈다. 원인 분석은 서비스가 돌아온 다음이다.
4. **정해진 주기로 알린다.** "원인 조사 중, 다음 공유 30분 뒤"도 정보다. 침묵이 가장 나쁘다.
5. **회복을 확인한다.** SLI가 정상으로 돌아왔는지, 대기열에 쌓인 일이 처리되는지 확인한 뒤 종료를 선언한다.

"최근에 무엇이 바뀌었나"가 가장 강력한 질문이다. 그래서 배포·설정 변경 이력이 한곳에 시각과 함께 남아 있어야 한다.

## 깊게 11 — 비난 없는 회고(blameless postmortem)

### 왜 비난하지 않나

사람을 탓하면 다음부터 사람들이 실수를 숨긴다. 숨긴 실수는 고쳐지지 않는다. "누가 잘못했나" 대신 **"시스템이 어떻게 그 실수를 허용했나"**를 묻는다. 운영자가 잘못된 명령을 쳤다면, 그 명령을 검토 없이 운영에 칠 수 있게 만든 구조가 진짜 원인이다.

### 회고 문서의 뼈대

```
1. 요약 (세 줄)
2. 영향: 누구, 얼마나, 몇 분
3. 타임라인 (시각별 사실)
4. 원인과 기여 요인
5. 잘된 점 / 운이 좋았던 점
6. 조치 항목 (담당, 기한)
```

- **"운이 좋았던 점"** 칸이 중요하다. 다음에는 운이 없을 수 있는 지점을 보여 준다.
- 원인은 하나가 아닌 경우가 많다. "왜?"를 여러 번 물어 기여 요인을 모두 적는다.
- **조치 항목에는 담당자와 기한**을 붙이고 추적한다. 조치가 안 된 회고는 다음 장애의 예고다.
- 조치는 "더 조심한다"가 아니라 **장치**여야 한다. 검토 단계 추가, 자동 검사, 권한 축소, 경보 추가.

## 깊게 12 — 카오스 엔지니어링과 게임 데이

### 카오스 엔지니어링

운영 환경(또는 그와 같은 환경)에 **일부러 장애를 넣어서** 시스템이 예상대로 버티는지 확인하는 실험이다. Netflix의 Chaos Monkey가 잘 알려진 예이고, 클라우드에도 관리형 도구가 있다(AWS Fault Injection Service, Azure Chaos Studio).

실험 순서는 과학 실험과 같다.

1. **정상 상태를 정의한다.** 예: 결제 성공률 99.9% 이상.
2. **가설을 세운다.** "AZ 하나의 인스턴스를 모두 끄면 5분 안에 성공률이 정상으로 돌아온다."
3. **작게 시작한다.** 영향 범위를 한정하고, 즉시 멈추는 조건을 정해 둔다.
4. **결과를 비교하고 고친다.** 가설이 틀렸다면, 그건 실제 장애 전에 찾은 약점이다.

### 게임 데이

사람과 절차를 함께 시험하는 훈련이다. 정해진 날에 장애 상황을 연출하고, 실제로 호출을 받아 런북대로 대응해 본다. 런북이 낡았는지, 권한이 없는 사람이 있는지, 백업이 정말 복구되는지가 이때 드러난다. **복구해 보지 않은 백업은 백업이 아니다**라는 말이 여기서 나온다.

## 깊게 13 — 토일과 온콜

### 토일(toil)

토일은 수작업이고, 반복되고, 자동화할 수 있고, 장기적 가치가 없고, 서비스가 커질수록 같이 늘어나는 일이다. 인증서 손 갱신, 디스크 꽉 차면 손으로 정리, 매번 손으로 하는 권한 요청 처리 같은 것.

Google SRE는 엔지니어 시간의 절반 이상을 토일이 아닌 공학 작업에 쓰도록 목표를 둔다. 실천은 단순하다. 토일을 기록하고, 가장 시간을 많이 먹는 것부터 자동화하고, 자동화가 또 다른 토일을 만들지 않게 한다.

### 건강한 온콜

- **호출 수를 센다.** 한 번의 당번 동안 호출이 너무 많으면 사람이 지친다. 지친 사람은 실수한다.
- **업무 시간에 할 수 있는 건 업무 시간으로.** 새벽 호출은 사용자 영향이 있을 때만.
- **당번 뒤 회복 시간**과 보상을 준다.
- **당번이 받은 알림은 다음 주 개선 목록이 된다.** 같은 알림이 두 번 울리면 자동화 대상이다.

## 장애 대응 예시 — 의존 서비스가 느려져 전체가 멈췄다

증상: 오후 2시부터 메인 페이지 p99 지연이 300ms에서 30초로 뛰고, 5xx가 늘었다. 앱 인스턴스 CPU는 낮다.

1. **선언과 영향 파악:** SEV2 선언. 메인 페이지 사용자 약 40%가 실패. IC 지정, 커뮤니케이션 담당이 상태 페이지 갱신.
2. **최근 변경 확인:** 1시 50분에 추천 서비스 배포가 있었다.
3. **트레이스 확인:** 느린 요청의 트레이스를 열자 대부분 추천 서비스 호출에서 30초를 쓰고 있다. 메인 페이지의 추천 호출에 타임아웃이 없었다.
4. **완화:** 추천 서비스를 이전 버전으로 롤백. 동시에 기능 플래그로 메인 페이지의 추천 영역을 끄고 고정 목록으로 대체. 5분 뒤 지연 정상화.
5. **원인:** 새 버전의 추천 쿼리가 인덱스를 타지 않아 느려졌다. 하지만 **진짜 문제는 선택 의존이 필수 경로를 막은 것**이다. 타임아웃이 없어서 앱의 연결 풀이 추천 호출로 가득 찼다.
6. **조치 항목:** 모든 외부 호출에 타임아웃 기본값을 강제하는 공통 HTTP 클라이언트, 추천 호출에 서킷 브레이커와 대체 응답, 의존별 연결 풀 분리, 추천 서비스 배포에 카나리 단계 추가, 쿼리 실행 계획을 확인하는 사전 검사.

면접에서 이런 사례를 말할 때는 **"원인을 고쳤다"보다 "다시는 같은 모양으로 무너지지 않게 구조를 바꿨다"**가 핵심이다.

## 자주 하는 실수

- **병렬 가용성 계산만 보여 주고 상관 실패를 말하지 않는다.** 같은 배포, 같은 설정, 같은 의존이면 두 AZ도 같이 죽는다.
- **SLO를 100%나 너무 높게 잡는다.** 예산이 0이라 배포를 못 하거나, 아무도 지키지 않는 목표가 된다.
- **원인 지표로 사람을 깨운다.** 알림 피로가 진짜 장애를 묻는다.
- **평균 지연만 본다.** 가장 중요한 소수가 숨는다.
- **재시도를 계층마다 따로 건다.** 부하가 곱으로 불어난다.
- **장애 중에 원인부터 찾는다.** 롤백·전환 같은 완화가 먼저다.
- **회고의 조치가 "주의하겠다"로 끝난다.** 장치가 없는 다짐은 반복된다.
- **백업 복구를 시험하지 않는다.** 장애 날 처음 해 보는 복구는 대개 실패한다.
- **복구 경로가 장애 영역 안에 있다.** 모니터링·배포 도구·비밀 저장소가 같이 죽는다.

## 면접 질문 10개와 답

**1. 99.9%와 99.99%의 차이를 설명해 달라.**
한 달 기준으로 99.9%는 약 43분, 99.99%는 약 4분의 중단을 허용한다. 4분은 사람이 알림을 받고 접속하는 시간보다 짧아서, 99.99%부터는 사람이 고치는 구조로는 불가능하고 자동 장애 조치가 있어야 한다. 그래서 9 하나를 더할 때마다 비용과 복잡도가 크게 뛴다. 목표는 사용자가 실제로 체감하는 수준과 사업 영향을 보고 정한다.

**2. LB 99.99%, 앱 99.9%, DB 99.95%가 직렬이면 전체 가용성은?**
직렬은 곱하므로 약 99.84%다. 구성 요소를 더할수록 전체는 가장 약한 고리보다 낮아진다. 개선하려면 가장 약한 앱을 여러 AZ에 병렬로 두거나, 호출 사슬을 줄이거나, 선택 의존을 비동기로 뺀다. 병렬 계산을 쓸 때는 실패가 서로 독립이라는 가정이 깨지지 않는지 함께 확인한다.

**3. 멀티 AZ와 멀티 리전은 언제 쓰나?**
멀티 AZ는 비용 대비 효과가 커서 운영 서비스의 기본값으로 둔다. 멀티 리전은 리전 단위 장애까지 견뎌야 할 규제나 사업 이유가 있을 때 선택한다. 리전 간 지연 때문에 데이터 일관성 설계가 어려워지므로, 쓰기를 한 리전에서만 받을지 양쪽에서 받을지 먼저 정한다. 대부분은 웜 스탠바이와 다른 리전 백업으로 충분하다.
> 日本語: マルチAZは基本とし、マルチリージョンは規制や事業影響がある場合に選びます。

**4. SLI, SLO, SLA의 차이는?**
SLI는 사용자 경험을 나타내는 측정값, SLO는 그 측정값의 내부 목표, SLA는 고객과의 계약이다. SLA는 SLO보다 느슨하게 잡아서, 내부 목표를 먼저 어기고 손쓸 시간을 번다. SLI는 성공 요청 비율처럼 사용자에게 가까운 지표를 비율로 정의한다. 그래야 에러 예산 계산과 알림이 바로 연결된다.

**5. 에러 예산은 어떻게 쓰나?**
SLO에서 허용된 실패량이 에러 예산이다. 예를 들어 월 1,000만 요청에 99.9%면 1만 건이다. 예산이 남으면 배포를 빠르게 하고, 바닥나면 기능 배포를 멈추고 안정화에 집중한다. 개발 속도와 안정성 사이의 다툼을 숫자 하나로 정리하는 도구다.

**6. 알림이 너무 많다. 어떻게 고치나?**
사람을 깨우는 알림은 SLO 소진율 같은 사용자 영향 지표에만 남기고, 원인 지표는 대시보드와 티켓으로 내린다. 소진율 알림은 긴 창과 짧은 창을 함께 써서 큰 문제이면서 지금 계속되는 경우에만 울린다. 모든 호출 알림에 런북을 붙이고, 행동으로 이어지지 않은 알림은 정기적으로 지운다.

**7. 의존 서비스가 느려질 때 같이 죽지 않으려면?**
모든 원격 호출에 타임아웃을 두고, 재시도는 백오프와 지터, 재시도 예산 안에서만 한다. 실패율이 높으면 서킷 브레이커로 호출을 끊고 대체 응답을 준다. 의존별로 연결 풀을 나누는 벌크헤드로 한 의존의 문제가 다른 기능으로 번지지 않게 한다. 어떤 기능을 먼저 포기할지 평소에 정해 둔다.
> 日本語: タイムアウト、リトライの制限、サーキットブレーカーで障害の連鎖を防ぎます。

**8. 큰 장애가 나면 처음에 무엇을 하나?**
먼저 장애를 선언하고 인시던트 커맨더와 커뮤니케이션 담당을 정한다. SLI로 영향 범위를 파악하고, 최근 변경을 확인해 롤백·트래픽 전환·기능 끄기 같은 완화를 원인 분석보다 먼저 한다. 정해진 주기로 상태를 공유하고, 지표가 정상으로 돌아온 것을 확인한 뒤 종료한다. 원인 분석은 회고에서 한다.

**9. 비난 없는 회고는 왜 필요한가?**
사람을 탓하면 실수를 숨기게 되고, 숨긴 실수는 고쳐지지 않는다. 그래서 "누가"가 아니라 "시스템이 어떻게 그 실수를 허용했나"를 묻는다. 회고에는 영향, 타임라인, 기여 요인, 운이 좋았던 점, 담당자와 기한이 있는 조치 항목을 남긴다. 조치는 다짐이 아니라 검사·권한·자동화 같은 장치여야 한다.
> 日本語: 個人を責めず、仕組みの問題として再発防止策を決めます。

**10. 정적 안정성이란?**
장애가 나도 새 자원을 만들거나 설정을 바꾸지 않고 버티도록 미리 준비해 두는 설계다. 예를 들어 AZ 하나가 빠져도 남은 AZ가 감당할 용량을 평소에 띄워 둔다. 큰 장애 때는 컨트롤 플레인이 혼잡하거나 함께 장애일 수 있어서, 복구가 API 호출에 기대면 실패하기 쉽다. 대신 여유 용량 비용이 들기 때문에 중요한 서비스부터 적용한다.

## 정답

1. 약 22분. 43,200분 × 0.0005 = 21.6분.
2. 같은 버전·설정을 두 곳에 동시에 배포해 같이 실패하는 경우, 같은 의존(인증·DNS·설정 저장소)에 함께 기대는 경우. 한쪽이 죽은 뒤 트래픽이 몰려 다른 쪽도 과부하로 죽는 경우도 있다.
3. 에러 예산을 "30일에 딱 다 쓰는 속도"의 14.4배로 쓰고 있다는 뜻이다. 이 속도가 1시간 이어지면 한 달 예산의 약 2%를 쓴다.
4. 값의 종류가 무한해서 시계열 수(카디널리티)가 폭발하고, 메트릭 백엔드의 메모리와 비용을 크게 늘려 모니터링 자체를 죽일 수 있다. 이런 값은 로그나 트레이스에 넣는다.
5. 최근 배포 롤백, 트래픽을 다른 AZ·리전으로 전환, 기능 플래그로 문제 기능 끄기(그 밖에 부하 차단, 읽기 전용 모드).
