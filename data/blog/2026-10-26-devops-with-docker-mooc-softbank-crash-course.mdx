## 1부: Docker 기본기

### 이미지와 컨테이너를 구분하자

가장 먼저 고정해야 할 개념은 다음과 같다.

```text
Dockerfile ──build──> Image ──run──> Container
설계도                 불변 템플릿        실행 중인 인스턴스
```

- **Dockerfile**: 이미지를 만드는 명령을 선언한 파일
- **Image**: 애플리케이션과 실행에 필요한 의존성을 포함한 읽기 전용 레이어 묶음
- **Container**: 이미지로부터 생성된 격리된 실행 프로세스

이미지 하나에서 여러 컨테이너를 만들 수 있다. 컨테이너를 수정했다고 원본 이미지가 바뀌는 것도 아니다. 이 구분을 놓치면 삭제, 데이터 보존, 배포 버전 관리에서 계속 혼란이 생긴다.

### 최소 명령어 흐름

```bash
# 이미지 확인
docker image ls

# 컨테이너 실행
docker run --name web -d -p 8080:80 nginx

# 실행 중인 컨테이너 확인
docker ps

# 종료된 컨테이너까지 확인
docker ps -a

# 로그와 상세 설정 확인
docker logs web
docker inspect web

# 종료와 삭제
docker stop web
docker rm web

# 사용하지 않는 리소스 확인 후 정리
docker system df
docker system prune
```

`prune`은 편리하지만 학습 환경이 아닌 공유 개발환경이나 운영 장비에서 무작정 실행하면 안 된다. 무엇이 삭제되는지 먼저 확인하는 습관이 중요하다.

### `CMD`와 `ENTRYPOINT`

둘 다 컨테이너 시작 명령과 관련되지만 역할은 다르다.

- `ENTRYPOINT`: 이 이미지가 반드시 실행할 프로그램
- `CMD`: 기본 명령 또는 `ENTRYPOINT`에 전달할 기본 인자

```dockerfile
ENTRYPOINT ["node"]
CMD ["dist/main.js"]
```

위 이미지를 그냥 실행하면 `node dist/main.js`가 실행된다. 실행 시 인자를 전달하면 `CMD` 부분을 바꿀 수 있다. 셸 형식보다 JSON 배열 형태인 exec form을 사용하면 신호 전달과 프로세스 종료 동작을 더 예측하기 쉽다.

### 포트는 `EXPOSE`만으로 열리지 않는다

```dockerfile
EXPOSE 3000
```

`EXPOSE`는 이 애플리케이션이 어떤 포트를 사용할지 설명하는 메타데이터에 가깝다. 호스트에서 접근하려면 실행할 때 포트 매핑이 필요하다.

```bash
docker run -p 8080:3000 my-api
```

이제 호스트의 `8080`으로 들어온 요청이 컨테이너의 `3000`으로 전달된다.

### 컨테이너가 삭제되면 데이터도 사라진다

컨테이너의 writable layer에 저장된 데이터는 컨테이너와 생명주기를 함께한다. DB나 업로드 파일처럼 보존해야 하는 데이터는 컨테이너 밖에 둬야 한다.

```bash
# 이름 있는 볼륨
docker volume create postgres-data
docker run -v postgres-data:/var/lib/postgresql/data postgres:16

# 호스트 디렉터리를 연결하는 bind mount
docker run -v "$PWD:/app" my-dev-image
```

- **named volume**: Docker가 관리한다. DB 데이터처럼 지속성이 필요한 데이터에 적합하다.
- **bind mount**: 호스트 경로를 직접 연결한다. 소스코드 hot reload 같은 개발 환경에 편리하다.

면접에서는 “볼륨은 데이터를 영구 보존한다”에서 멈추지 말고, **컨테이너 교체와 데이터 생명주기를 분리한다**고 설명하는 편이 정확하다.

## 2부: 좋은 Dockerfile 만들기

### 레이어와 빌드 캐시

Dockerfile의 각 명령은 대체로 새로운 레이어를 만든다. 이전 레이어가 바뀌면 그 아래 단계의 캐시도 무효화된다.

Node.js 프로젝트에서는 의존성 파일을 먼저 복사하는 이유가 여기에 있다.

```dockerfile
FROM node:22-alpine AS build
WORKDIR /app

COPY package.json package-lock.json ./
RUN npm ci

COPY . .
RUN npm run build
```

소스코드는 자주 바뀌지만 `package-lock.json`은 상대적으로 덜 바뀐다. 이 순서라면 소스만 수정했을 때 `npm ci` 레이어를 다시 실행하지 않아도 된다.

### 태그를 무조건 `latest`로 두지 않는다

```dockerfile
# 재현성이 낮음
FROM node:latest

# 메이저·런타임 환경을 명시
FROM node:22-alpine
```

`latest`는 어느 날 같은 Dockerfile을 다시 빌드했는데 전혀 다른 결과가 나올 수 있다. 운영 환경에서는 태그를 명시하고, 더 강한 재현성이 필요하면 digest 고정도 검토한다. 다만 버전을 고정한 뒤 보안 업데이트를 방치해서도 안 된다. **재현성과 업데이트 정책을 함께 운영해야 한다.**

### Multi-stage build

빌드 도구와 운영 런타임을 한 이미지에 모두 넣을 필요는 없다.

```dockerfile
FROM node:22-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:22-alpine AS runtime
WORKDIR /app
ENV NODE_ENV=production

COPY package.json package-lock.json ./
RUN npm ci --omit=dev && npm cache clean --force
COPY --from=build /app/dist ./dist

USER node
EXPOSE 3000
CMD ["node", "dist/main.js"]
```

빌드 단계에는 TypeScript 컴파일러와 개발 의존성이 있지만 최종 단계에는 실행에 필요한 파일만 남긴다.

효과는 세 가지다.

1. 이미지 크기가 줄어 전송과 배포가 빨라진다.
2. 불필요한 패키지가 사라져 공격 표면이 줄어든다.
3. 빌드 환경과 실행 환경의 책임이 분리된다.

### `.dockerignore`

빌드 컨텍스트에 필요 없는 파일을 보내지 않는다.

```gitignore
.git
node_modules
coverage
*.log
.env
.env.*
Dockerfile*
docker-compose*.yml
```

특히 `.env`, DB 백업, 인증서, 개인 키가 이미지 레이어에 들어가면 나중에 파일을 삭제해도 이전 레이어에 남을 수 있다. 비밀값은 빌드 산출물에 넣지 말고 런타임의 secret 관리 기능으로 주입해야 한다.

## 3부: Docker Compose로 서비스를 연결하기

Docker Compose는 여러 컨테이너로 구성된 애플리케이션을 하나의 YAML로 선언한다.

```yaml
services:
  api:
    build: ./api
    ports:
      - '3000:3000'
    environment:
      DATABASE_URL: postgresql://app:app@db:5432/app
      REDIS_URL: redis://redis:6379
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_started

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app
      POSTGRES_DB: app
    volumes:
      - postgres-data:/var/lib/postgresql/data
    healthcheck:
      test: ['CMD-SHELL', 'pg_isready -U app']
      interval: 5s
      timeout: 3s
      retries: 10

  redis:
    image: redis:7-alpine

volumes:
  postgres-data:
```

실행은 간단하다.

```bash
docker compose up --build
docker compose ps
docker compose logs -f api
docker compose down
```

### `localhost` 함정

`api` 컨테이너 안에서 `localhost`는 호스트도 PostgreSQL 컨테이너도 아니다. **현재 api 컨테이너 자신**이다.

Compose가 만든 기본 네트워크에서는 서비스 이름이 DNS 이름이 된다.

```text
api → db:5432
api → redis:6379
```

따라서 DB 주소는 `localhost:5432`가 아니라 `db:5432`다. 컨테이너 네트워크 문제를 만났을 때 가장 먼저 확인할 항목이다.

### `depends_on`은 준비 완료를 보장하지 않는다

단순 `depends_on`은 컨테이너 시작 순서만 다룰 수 있고, DB가 쿼리를 받을 준비까지 끝났다는 뜻은 아니다. healthcheck, 애플리케이션 재시도, 지수 백오프가 함께 필요하다.

해커톤에서는 이 차이가 중요하다. 내 컴퓨터에서는 우연히 DB가 먼저 올라왔는데 발표 직전에 API가 먼저 시작되면서 실패할 수 있기 때문이다.

### Compose의 역할과 한계

Compose는 다음에 강하다.

- 로컬 개발환경 통일
- 단일 호스트의 소규모 배포
- 통합 테스트 환경
- 해커톤 데모의 재현 가능한 실행

반면 다수 호스트의 스케줄링, 자동 복구, 롤링 업데이트, 고급 secret 관리까지 요구되면 Kubernetes나 관리형 오케스트레이션을 검토해야 한다. 도구 선택은 규모와 운영 요구사항에 따라 달라져야 한다.

## 4부: 보안과 이미지 최적화

### 신뢰할 수 있는 베이스 이미지

이미지는 실행 가능한 코드다. 별 수가 많다는 이유만으로 임의 이미지를 사용하지 않는다.

확인할 것:

- Docker Official Image 또는 검증된 게시자인가
- 마지막 업데이트가 언제인가
- 알려진 취약점이 있는가
- 필요한 패키지보다 지나치게 큰가
- 태그 정책과 지원 기간이 명확한가

작은 이미지가 항상 안전한 것은 아니지만, 불필요한 도구와 라이브러리가 적으면 공격 표면과 관리 대상이 줄어든다.

### root로 실행하지 않는다

컨테이너 격리는 완전한 보안 경계가 아니다. 런타임이나 커널 취약점, 잘못된 mount 설정이 결합되면 영향이 호스트로 이어질 수 있다.

```dockerfile
RUN addgroup --system app && adduser --system --ingroup app app
COPY --chown=app:app . /app
USER app
```

공식 Node 이미지처럼 이미 비특권 사용자가 포함돼 있다면 `USER node`를 사용할 수 있다. 중요한 것은 애플리케이션이 root 권한을 실제로 필요로 하는지 먼저 의심하는 것이다.

### 이미지 크기를 줄이는 판단 순서

1. 더 적절한 베이스 이미지 선택
2. Multi-stage build 적용
3. 개발 의존성과 빌드 도구 제거
4. 패키지 관리자 캐시 정리
5. `.dockerignore`로 컨텍스트 축소
6. 명령 순서를 바꿔 캐시 활용
7. `docker history`로 큰 레이어 확인

크기만 줄이려고 디버깅 가능성이나 호환성을 무시하면 운영 난도가 높아질 수 있다. 최적화 목표는 가장 작은 숫자가 아니라 **필요한 기능·보안·운영성을 만족하는 최소 이미지**다.

## 5부: CI/CD와 배포

좋은 Dockerfile이 있어도 사람이 매번 로컬에서 이미지를 만들어 서버에 복사하면 결과가 달라질 수 있다. CI/CD의 기본 흐름은 다음과 같다.

```text
commit
  → test
  → image build
  → vulnerability scan
  → registry push
  → deploy
  → health check
  → 실패 시 rollback
```

GitHub Actions를 사용한다면 최소한 다음을 자동화할 수 있다.

```yaml
name: container-ci

on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - name: Build image
        uses: docker/build-push-action@v6
        with:
          context: .
          push: false
          tags: my-api:${{ github.sha }}
```

운영에서는 `latest` 하나만 덮어쓰기보다 commit SHA처럼 어떤 코드에서 만들어졌는지 추적 가능한 태그를 함께 사용한다. 이미지 digest까지 배포 기록에 남기면 같은 태그가 바뀌는 문제도 줄일 수 있다.

## AI 도구를 사용하는 방법

이 과정은 Claude Code, GitHub Copilot, Codex 같은 코딩 에이전트의 사용을 허용한다. 대신 **정답 파일을 대신 만들게 하고 이해하지 못한 채 제출하는 방식은 학습을 무효화한다**고 강조한다.

내 학습 규칙은 다음과 같이 잡았다.

1. 먼저 직접 Dockerfile이나 Compose 파일을 작성한다.
2. 막히면 정답이 아니라 오류의 의미와 확인 순서를 묻는다.
3. 수정은 직접 적용하고 다시 실행한다.
4. 작동한 뒤 이미지 크기, 캐시, 보안과 실패 가능성을 리뷰받는다.
5. 모든 줄을 면접에서 설명할 수 없으면 완료로 처리하지 않는다.

Docker 문제는 호스트, 네트워크, 볼륨, 권한과 여러 컨테이너를 동시에 건드린다. 에이전트가 만든 설정을 이해하지 못하면 운영 장애에서 원인을 분리할 수 없다.

## 기술면접에서 나올 수 있는 질문

### 이미지와 컨테이너의 차이는?

이미지는 애플리케이션과 의존성을 포함하는 불변 템플릿이고, 컨테이너는 그 이미지로부터 만들어진 실행 인스턴스다. 이미지 하나로 여러 컨테이너를 만들 수 있으며 각 컨테이너는 별도의 writable layer를 가진다.

### Dockerfile 레이어 순서가 왜 중요한가?

변경된 레이어 아래의 캐시가 다시 계산되기 때문이다. 자주 바뀌지 않는 의존성 파일을 먼저 복사하고 설치한 뒤 소스코드를 복사하면, 소스 변경 시 의존성 설치 캐시를 재사용할 수 있다.

### 컨테이너 안에서 DB를 `localhost`로 부르면 왜 실패하는가?

각 컨테이너는 자신의 네트워크 네임스페이스를 가지므로 `localhost`는 현재 컨테이너 자신을 가리킨다. Compose 네트워크에서는 DB 서비스 이름을 DNS 이름으로 사용한다.

### Multi-stage build를 왜 사용하는가?

빌드 도구와 개발 의존성을 최종 런타임 이미지에서 제거하기 위해서다. 이미지 전송 속도와 빌드 결과의 분리를 개선하고, 공격 표면도 줄일 수 있다.

### 컨테이너를 root로 실행하면 어떤 문제가 있는가?

컨테이너 격리 취약점이나 잘못된 mount·capability 설정이 있을 때 피해 범위가 커질 수 있다. 애플리케이션에 필요한 최소 권한의 비특권 사용자로 실행하고, 필요하지 않은 capability와 파일 권한을 줄여야 한다.

### Compose와 Kubernetes의 차이는?

Compose는 로컬 개발과 단일 호스트의 여러 컨테이너 구성을 간단히 선언하는 데 적합하다. Kubernetes는 다수 노드에서 스케줄링, 자동 복구, 서비스 디스커버리, 롤링 업데이트와 확장을 관리하지만 복잡성과 운영비용이 더 크다.

## 체크리스트

### Dockerfile

- [ ] 베이스 이미지 버전을 명시했다.
- [ ] 의존성 설치 레이어가 캐시되도록 순서를 구성했다.
- [ ] Multi-stage build로 빌드 도구를 제거했다.
- [ ] 비특권 사용자로 실행한다.
- [ ] secret을 이미지에 복사하지 않는다.
- [ ] `.dockerignore`를 사용한다.
- [ ] 종료 신호가 애플리케이션 프로세스에 전달된다.

### Compose

- [ ] 서비스 이름 기반으로 내부 통신한다.
- [ ] DB 데이터가 named volume에 저장된다.
- [ ] healthcheck와 애플리케이션 재시도를 구분한다.
- [ ] 외부에 필요한 포트만 공개한다.
- [ ] 환경별 설정과 secret을 코드에서 분리한다.
- [ ] `docker compose down` 후 다시 올려도 재현된다.

### 운영과 배포

- [ ] 이미지 태그로 코드 버전을 추적할 수 있다.
- [ ] CI에서 테스트와 이미지 빌드를 재현한다.
- [ ] 로그가 표준 출력으로 수집된다.
- [ ] 이미지 크기와 취약점을 확인한다.
- [ ] 실패 시 이전 이미지로 되돌리는 절차가 있다.

## 마무리

Docker를 공부한다는 것은 명령어를 많이 외우는 것이 아니다. **애플리케이션, 의존성, 데이터, 네트워크, 권한과 배포 버전의 경계를 명확히 만드는 법**을 배우는 것이다.

SoftBank 해커톤에서도 중요한 것은 서비스를 몇 개 사용했는지가 아니다. 팀원이 같은 환경을 재현할 수 있고, 배포가 실패했을 때 원인을 설명하며, 발표 직전에도 안전하게 복구할 수 있어야 한다. 우선 7일 압축 실습으로 이 능력을 만들고, 본선 이후 공식 MOOC의 나머지 실습까지 완료해 1~3 ECTS와 수료 증빙으로 연결할 계획이다.
