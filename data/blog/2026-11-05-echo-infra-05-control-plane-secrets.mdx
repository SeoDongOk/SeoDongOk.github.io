[Echo 인프라 시리즈 전체 목차](/blog/2026-11-05-echo-infra-series)

> 2026년 11월 4일 기준 해커톤 구현 회고입니다. 당시 코드와 작업 기록을 기준으로 정리했으며, 현재 서비스 상태나 모든 환경에 적용되는 설정을 보장하지 않습니다.

## 기술 명칭과 설명

Control Plane은 배포·이전 명령과 상태를 관리하는 관제 영역입니다. Workload Identity는 Kubernetes 워크로드와 클라우드 서비스 계정을 연결합니다. CSI는 외부 저장소를 Pod에 연결하는 인터페이스이며, 이 프로젝트에서는 Secret Manager 비밀을 전달하는 데 사용합니다. SecretSync는 비밀을 Kubernetes Secret으로 동기화하는 기능입니다.

## 내가 무엇을 했는가

AWS 출발 리전 장애와 관제탑 장애를 분리하기 위해 GCP GKE에 echo-was 기반을 준비했습니다. 전용 서비스 계정·Workload Identity·Secret Manager 비밀 껍데기·고정 IP·관리형 인증서를 정의하고 CSI·SecretSync를 활성화했습니다. API 담당에게 앱 배포와 비밀값 입력 경계를 넘겼습니다.

## 트러블슈팅: 문제 → 원인/판단 → 조치

11/2에는 인증서가 DNS 연결 전 PROVISIONING이고 비밀 version이 0개였습니다. 기반 자원 생성과 앱 준비 완료를 혼동하지 않아야 하는 인수인계 이슈였습니다. 또한 전체 plan에 별도 진입점 VM 파괴 변경이 있어 해당 변경은 적용하지 않고 관제탑 대상만 확인했습니다.

## 해결 결과와 아직 남은 한계

관제탑 기반 apply 및 대상 reconcile 0 add/0 change/0 destroy는 전략 기록으로 확인됩니다. echo-was API·Worker·관리 DB 구현과 비밀값 입력까지 본인이 모두 했다고 표현하지 않습니다.

## 발표·면접에서 설명할 문장

> 장애가 나는 출발 환경과 관제탑을 분리하고, 신원·비밀 전달·네트워크 기반까지만 책임 경계를 명시해 인수인계했습니다.

## 기여 범위와 검증 기준

본인 작성의 비병합 커밋과 변경 내용을 대조했습니다. 코드 구현, 적용 기록, 실측 결과는 구분합니다. 팀원이 만든 기반을 확장한 작업은 그 경계를 본문에 명시했고, 목표 수치는 완료 성과로 표현하지 않았습니다. 운영 경로와 식별자는 공개본에서 생략했습니다.
