## 이 글에서 답할 면접 질문

- Terraform state는 왜 필요하고, 팀에서는 어떻게 관리하나?
- 환경(dev, stg, prod)을 Terraform에서 어떻게 나누나? 워크스페이스와 디렉터리 중 무엇을 쓰나?
- state 하나에 모든 인프라를 넣으면 무엇이 문제인가?
- CloudFormation, Bicep, Pulumi 대신 Terraform을 고른 이유는? 반대로 언제 다른 도구가 낫나?
- CI에서 클라우드 권한은 어떻게 주나? 액세스 키를 비밀값으로 넣으면 안 되나?
- 블루그린과 카나리의 차이, 그리고 각각 언제 쓰나?
- 컬럼 이름을 바꾸는 DB 변경을 무중단으로 배포하려면?
- 인프라 팀의 성과를 무엇으로 재나?

## 개념과 배경

### IaC가 푸는 문제

콘솔에서 클릭으로 만든 인프라에는 세 가지 문제가 있다.

1. **재현이 안 된다.** 같은 환경을 하나 더 만들려면 누군가의 기억에 기대야 한다.
2. **검토가 안 된다.** 누가 무엇을 바꿨는지, 바꾸기 전에 누가 봤는지가 남지 않는다.
3. **흘러간다(drift).** 시간이 지나면 환경마다 조금씩 달라지고, 그 차이가 장애를 만든다.

IaC(Infrastructure as Code)는 인프라를 코드로 적고, 그 코드를 git으로 검토·기록하고, 도구가 그 코드대로 만들게 하는 방식이다. 공통 기반을 만드는 클라우드 엔지니어에게 IaC는 선택이 아니라 **작업 방식 그 자체**다. 회사 전체의 계정 구조, 네트워크, 권한 경계가 모두 코드로 표현되고, 그 코드가 곧 정책 문서가 된다.

### 선언형과 명령형

| 방식 | 적는 것 | 예 |
|---|---|---|
| 명령형 | "이렇게 해라" 순서 | 셸 스크립트, CLI 명령 나열 |
| 선언형 | "이런 상태여야 한다" 결과 | Terraform, CloudFormation, 쿠버네티스 매니페스트 |

명령형 스크립트는 두 번 돌리면 문제가 생긴다. "VPC를 만들어라"를 두 번 하면 VPC가 두 개다. 선언형 도구는 "VPC가 하나 있어야 한다"를 보고 **지금 상태와 비교해서 차이만** 적용한다. 몇 번을 돌려도 결과가 같은 성질(멱등성)이 선언형의 핵심이다.

## 깊게 1 — Terraform의 구조

### 프로바이더

Terraform 자체는 클라우드를 모른다. AWS, Google Cloud, Azure, 쿠버네티스, GitHub 같은 대상마다 **프로바이더**라는 플러그인이 API 호출을 맡는다. 그래서 같은 문법으로 여러 클라우드를 다룰 수 있다. 단, 같은 문법일 뿐 **같은 코드는 아니다.** AWS의 VPC 자원과 Google Cloud의 VPC 자원은 이름도 속성도 다르다. "Terraform을 쓰면 멀티 클라우드가 공짜"라는 말은 틀렸다.

프로바이더 버전은 반드시 고정한다. 버전이 올라가며 기본값이 바뀌면 코드는 그대로인데 plan에 변경이 생길 수 있다. 잠금 파일(`.terraform.lock.hcl`)을 git에 올려 모두가 같은 버전을 쓰게 한다.

### state

Terraform은 "코드의 이 블록이 클라우드의 어느 자원인가"를 state 파일에 적어 둔다. 클라우드 API만 봐서는 그 연결을 알 수 없기 때문이다.

- state가 없으면 이미 있는 자원을 모른다고 보고 새로 만들려 한다.
- state가 틀리면 엉뚱한 자원을 바꾸거나 지우려 한다.
- state에는 **비밀값이 평문으로** 들어갈 수 있다(DB 비밀번호 출력값 등).

그래서 팀에서는 state를 다음처럼 다룬다.

| 요구 | 방법 |
|---|---|
| 모두 같은 state를 본다 | 원격 백엔드 (S3, GCS, Azure Blob, HCP Terraform) |
| 동시에 두 명이 적용 못 하게 | 잠금 (S3 잠금 파일 또는 DynamoDB, GCS·Azure Blob 기본 잠금) |
| 비밀 노출 방지 | 버킷 암호화, 접근 권한 최소화, 비밀값은 출력하지 않기 |
| 실수 복구 | 버킷 버전 관리로 이전 state 복원 |

### 모듈 설계

모듈은 재사용할 수 있는 Terraform 코드 묶음이다. 공통 기반 팀의 주요 산출물이 바로 모듈이다. "회사 표준 VPC", "회사 표준 쿠버네티스 클러스터"를 모듈로 만들어 각 팀이 가져다 쓰게 한다.

좋은 모듈의 조건:

- **한 가지 일을 한다.** "네트워크"와 "DB"를 한 모듈에 넣지 않는다.
- **안전한 기본값.** 암호화 켜기, 공개 접근 끄기, 태그 강제를 기본값으로 둔다. 쓰는 팀이 아무것도 안 해도 회사 기준을 지키게 된다.
- **입력은 적게, 출력은 필요한 만큼.** 입력 변수가 50개인 모듈은 아무도 제대로 못 쓴다.
- **버전을 붙인다.** git 태그나 모듈 레지스트리로 버전을 매기고, 쓰는 쪽은 버전을 고정한다. 모듈을 고치면 새 버전을 내고, 각 팀이 자기 일정에 맞춰 올린다.
- **예시와 시험을 같이 둔다.** 모듈 저장소에 사용 예시를 두고, CI에서 예시를 실제로 plan(또는 임시 환경에 apply 후 destroy)해 본다.

### 환경 나누기: 디렉터리 vs 워크스페이스

| 방식 | 구조 | 장점 | 단점 |
|---|---|---|---|
| 디렉터리 분리 | `envs/dev`, `envs/prod` 각자 state | 환경마다 다른 설정·권한·백엔드가 쉽다, 실수로 prod를 건드리기 어렵다 | 코드 중복이 생기기 쉽다 (모듈로 줄인다) |
| 워크스페이스 | 같은 코드, state만 여러 개 | 중복이 적다 | 지금 어느 워크스페이스인지 착각하기 쉽다, 환경별 권한 분리가 어렵다 |

운영 환경이 있는 조직에서는 **디렉터리 분리 + 공통 모듈**이 흔한 선택이다. prod 디렉터리는 prod 계정의 권한으로만 적용되게 하면, 개발 환경 작업 중 실수가 운영으로 번지지 않는다. 워크스페이스는 기능 브랜치마다 잠깐 띄우는 임시 환경처럼, 구조가 완전히 같은 복제본에 잘 맞는다.

### state 나누기: 폭발 반경

state 하나에 회사 전체 인프라를 넣으면 이렇게 된다.

- plan 한 번에 몇 분씩 걸린다(모든 자원을 클라우드에 조회한다).
- 한 사람이 적용하는 동안 잠금 때문에 모두 기다린다.
- 사소한 변경의 plan에도 수백 개 자원이 걸려 있어서, 실수 하나가 전체를 날릴 수 있다.

그래서 **바뀌는 빈도와 위험도**로 state를 쪼갠다.

```
org/        계정·폴더·조직 정책
network/    VPC·서브넷·연결
platform/   클러스터·공용 DB
apps/xxx/   서비스별 자원
```

아래층(네트워크)은 드물게, 위층(앱)은 자주 바뀐다. 위층은 아래층의 출력값을 읽어서 쓴다(원격 state 데이터 소스나, 더 느슨하게는 태그·이름으로 조회). 이렇게 하면 앱 팀의 실수가 네트워크까지 닿지 않는다.

### 기존 자원과 리팩터링: import, moved, removed

- **import 블록:** 콘솔로 이미 만든 자원을 코드로 가져온다. 코드에 import 블록을 적고 plan을 보면, 무엇이 state에 들어올지 검토한 뒤 적용할 수 있다. 예전에는 CLI 명령(`terraform import`)으로 한 줄씩 했지만, 블록으로 쓰면 PR에서 검토가 된다.
- **moved 블록:** 자원의 코드 주소가 바뀌었을 때(이름 변경, 모듈 안으로 이동) "지우고 새로 만들기"가 아니라 "이름만 바뀐 것"이라고 알려 준다. 이걸 안 쓰면 DB 같은 자원이 삭제 후 재생성될 수 있다.
- **removed 블록:** 자원을 Terraform 관리에서만 빼고 실제 자원은 남긴다. 다른 state로 옮길 때 쓴다.

세 블록 모두 **코드로 남기 때문에 검토할 수 있다**는 점이 핵심이다. 같은 일을 CLI의 state 조작 명령으로 하면 기록도 검토도 없이 state가 바뀐다.

### drift 감지

누군가 콘솔에서 보안 그룹 규칙을 하나 추가했다. 코드에는 없다. 다음 apply가 그 규칙을 지워 버리고, 그 규칙에 기대던 서비스가 죽는다. 이것이 drift 사고다.

- **정기적으로 plan을 돌린다.** 매일 밤 CI에서 각 state에 plan을 돌리고, 변경이 나오면 알린다. "코드를 안 바꿨는데 plan에 변경이 있다"가 drift의 신호다.
- **콘솔 쓰기 권한을 줄인다.** 운영 계정은 사람에게 읽기 권한만 주고, 변경은 파이프라인으로만.
- **drift를 발견하면 둘 중 하나를 고른다.** 수동 변경이 맞다면 코드에 반영하고, 틀렸다면 apply로 되돌린다. 무엇을 골랐는지 기록한다.

### plan을 PR에서 검토한다

가장 효과가 큰 습관이다.

1. PR을 열면 CI가 `terraform plan` 을 돌리고 결과를 PR 댓글로 붙인다.
2. 리뷰어는 코드가 아니라 **plan을 읽는다.** 특히 `destroy`, `replace`(지우고 다시 만들기)를 찾는다.
3. 승인 후 머지하면, CI가 **그 PR에서 검토한 plan 파일 그대로** 적용한다.

```bash
terraform plan -out=tfplan
terraform show -json tfplan > plan.json
terraform apply tfplan
```

plan 파일로 적용하면 "검토한 것과 적용된 것이 다른" 문제가 없다. 검토와 적용 사이에 누가 다른 걸 머지했다면 plan 파일이 낡았다고 실패하므로 다시 plan을 돌리면 된다.

## 깊게 2 — 다른 IaC 도구를 고르는 기준

| 도구 | 성격 | 잘 맞는 경우 |
|---|---|---|
| Terraform / OpenTofu | 여러 클라우드, HCL, state 직접 관리 | 멀티 클라우드, SaaS까지 한 도구로 |
| AWS CloudFormation / CDK | AWS 전용, state를 AWS가 관리 | AWS만 쓰고 관리형 state를 원할 때. CDK는 프로그래밍 언어로 쓰고 CloudFormation으로 바뀐다 |
| Azure Bicep (ARM) | Azure 전용, ARM 템플릿으로 바뀜 | Azure 중심 조직 |
| Google Infrastructure Manager | Google Cloud의 관리형 Terraform 실행 | Google Cloud에서 Terraform을 관리형으로 돌리고 싶을 때. 예전 Deployment Manager의 후계 |
| Pulumi | 일반 프로그래밍 언어 (TypeScript, Python, Go) | 반복·조건이 복잡하고 개발자가 직접 인프라를 쓰는 팀 |
| Crossplane | 쿠버네티스 위에서 클라우드 자원을 CRD로 | 플랫폼을 쿠버네티스 API로 통일하고 GitOps로 운영할 때 |

면접에서 "왜 Terraform인가"를 물으면 이렇게 답할 수 있다.

- 여러 클라우드와 SaaS(DNS, 모니터링, GitHub)를 **한 문법, 한 워크플로**로 다룬다.
- plan이 명확해서 검토 문화를 만들기 쉽다.
- 생태계(모듈, 정책 도구, 정적 분석)가 크다.

반대로 단점도 말해야 공정하다. state를 직접 관리해야 하고, 클라우드 신기능이 프로바이더에 늦게 들어올 수 있고, 조건·반복이 복잡해지면 HCL이 읽기 어려워진다. 단일 클라우드 조직이라면 그 클라우드의 네이티브 도구가 관리 부담이 더 적을 수 있다.

## 깊게 3 — 정책을 코드로: 가드레일

공통 기반 팀은 수십 개 팀이 인프라를 만드는 걸 일일이 검토할 수 없다. 그래서 **위반하면 자동으로 막히는 규칙**을 만든다. 이게 가드레일이다.

### 두 층의 가드레일

| 층 | 언제 막나 | 예 |
|---|---|---|
| 배포 전 (CI) | PR의 plan을 검사 | OPA/Conftest, Sentinel, Checkov·Trivy 같은 정적 검사 |
| 클라우드 자체 | API 호출 자체를 거부 | AWS SCP·RCP, Azure Policy, Google Cloud 조직 정책 |

- **CI 단계 정책:** `terraform show -json` 으로 뽑은 plan을 정책 엔진에 넣어 검사한다. "공개 버킷 금지", "태그 필수", "허용된 리전만", "prod에서 삭제가 있으면 별도 승인" 같은 규칙을 코드로 적는다. 빨리 실패하고 이유를 알려 준다는 장점이 있다.
- **클라우드 단계 정책:** CI를 우회한 변경(콘솔, 다른 도구)까지 막는다. 마지막 방어선이다. 대신 실패 메시지가 불친절하므로, CI 정책과 같은 규칙을 양쪽에 두는 게 좋다.

### 가드레일 설계 원칙

- **막는 규칙은 적게, 확실하게.** 위반 시 사고가 되는 것(공개 노출, 감사 로그 끄기, 허용 안 된 리전)만 막는다.
- **나머지는 경고와 대시보드.** 모든 걸 막으면 팀들이 우회로를 찾는다.
- **예외 절차를 만든다.** 정당한 예외는 있다. 예외는 기한과 사유와 함께 코드로 등록한다.
- **"올바른 길이 가장 쉬운 길"이 되게.** 안전한 기본값을 가진 모듈을 쓰면 정책을 저절로 통과하게 만든다.

## 깊게 4 — 파이프라인의 비밀과 OIDC

### 장기 액세스 키의 문제

CI에 클라우드 액세스 키를 비밀값으로 넣는 방식은 흔하지만 위험하다.

- 키는 **만료되지 않는다.** 한 번 새면 누군가 지울 때까지 유효하다.
- 키는 **복사된다.** CI 로그, 개발자 노트북, 다른 저장소로 퍼진다.
- 키를 **돌리는(rotate) 일이 수작업**이 되고, 결국 안 돌린다.

### OIDC 신원 연합

요즘 방식은 **키를 아예 두지 않는 것**이다.

```
CI 작업 시작
 → CI가 "나는 저장소 X의
    main 브랜치 작업"이라는
    서명된 토큰(OIDC) 발급
 → 클라우드가 토큰을 검증
 → 짧게 쓰는 임시 자격 증명
```

- AWS: IAM OIDC 공급자와 역할 신뢰 정책(`AssumeRoleWithWebIdentity`)
- Google Cloud: Workload Identity Federation
- Azure: 앱 등록이나 관리 ID의 페더레이션 자격 증명

핵심은 **신뢰 조건을 좁히는 것**이다. "이 CI 서비스의 아무 저장소"를 믿으면, 남의 저장소 작업도 우리 역할을 받을 수 있다. 토큰의 주체(sub) 조건을 **특정 저장소, 특정 브랜치나 배포 환경**으로 한정한다. prod 역할은 main 브랜치의 prod 환경 작업만 받을 수 있게 한다.

### 그 밖의 파이프라인 비밀

- 앱이 쓰는 비밀값은 파이프라인이 아니라 **비밀 저장소**(Secrets Manager, Secret Manager, Key Vault)에 두고, 실행 시점에 워크로드 신원으로 읽게 한다.
- CI 로그에 비밀이 찍히지 않게 마스킹하고, `set -x` 같은 디버그 출력에 주의한다.
- 외부 PR(포크)에서 도는 작업에는 비밀과 클라우드 권한을 주지 않는다. 악의적인 PR이 CI 설정을 바꿔 비밀을 빼 갈 수 있다.
- CI에서 쓰는 외부 액션·플러그인은 버전(가능하면 커밋 해시)으로 고정한다. 남이 관리하는 코드가 우리 파이프라인 권한으로 돈다.

## 깊게 5 — CI/CD 파이프라인 설계

### 빌드는 한 번, 승격은 여러 번

```
커밋
 → 빌드·시험 → 이미지 1개
 → dev 배포
 → stg 배포 (같은 이미지)
 → 승인
 → prod 배포 (같은 이미지)
```

환경마다 다시 빌드하면 "stg에서 시험한 것과 prod에 나간 것이 다른" 일이 생긴다. 의존성 버전이 그 사이에 바뀌었을 수도 있다. 그래서 **한 번 만든 결과물(컨테이너 이미지)을 태그가 아니라 다이제스트로 고정해** 환경을 따라 올린다. 환경마다 다른 것은 설정과 비밀값뿐이다.

### 파이프라인의 단계

| 단계 | 하는 일 |
|---|---|
| 정적 검사 | 린트, 형식, 보안 정적 분석, IaC 정책 |
| 빌드 | 결과물 생성, SBOM, 서명 |
| 시험 | 단위·통합 시험, 이미지 취약점 검사 |
| 배포 | 환경별 승격, 점진 배포 |
| 검증 | 배포 뒤 스모크 시험, 지표 확인, 자동 롤백 |

### 트렁크 기반 개발

오래 사는 브랜치는 머지할 때 충돌과 사고를 만든다. 트렁크 기반 개발은 작은 변경을 자주 main에 머지하고, 아직 공개하면 안 되는 기능은 **기능 플래그**로 숨긴다. 배포(코드를 서버에 올리기)와 출시(사용자에게 켜기)를 분리하는 것이 핵심이다.

### 승인

prod 배포 전 사람 승인은 필요한 만큼만 둔다. 모든 배포에 승인을 붙이면 승인이 형식이 된다. 위험한 변경(인프라 삭제, 권한 변경, DB 스키마)에는 승인을, 일반 앱 배포에는 자동 시험과 점진 배포를 믿는 쪽이 낫다.

## 깊게 6 — GitOps

GitOps는 **git에 적힌 상태가 곧 운영 상태**가 되게 하는 방식이다. 쿠버네티스에서 많이 쓴다.

| 방식 | 누가 적용하나 | 특징 |
|---|---|---|
| 푸시 | CI가 클러스터에 `kubectl apply` | 단순하다. CI가 클러스터 권한을 가져야 한다 |
| 풀 (GitOps) | 클러스터 안의 에이전트가 git을 보고 맞춘다 | 클러스터 밖에 권한을 안 둔다, drift를 자동 복구 |

Argo CD와 Flux가 대표 도구다. 클러스터 안에서 git 저장소를 주기적으로 보고, 실제 상태가 다르면 git 쪽으로 되돌린다.

- **장점:** 모든 변경이 git 커밋으로 남는다. 롤백은 git revert다. 누가 `kubectl edit` 으로 몰래 바꿔도 되돌아간다. 클러스터 자격 증명이 CI에 없어도 된다.
- **주의:** 비밀값을 git에 평문으로 둘 수 없으므로 외부 비밀 저장소 연동이나 암호화가 필요하다. 그리고 "git에서 바꿨는데 왜 안 바뀌지"를 디버깅하려면 에이전트의 동기화 상태를 볼 줄 알아야 한다.

## 깊게 7 — 배포 전략

| 전략 | 방법 | 장점 | 단점 |
|---|---|---|---|
| 롤링 | 인스턴스를 몇 대씩 차례로 교체 | 추가 자원 적음, 기본값 | 섞여 도는 시간이 있다, 롤백도 롤링이라 느림 |
| 블루그린 | 새 환경을 통째로 띄우고 트래픽을 한 번에 전환 | 즉시 전환·즉시 롤백 | 순간적으로 자원 두 배, 한 번에 100% 노출 |
| 카나리 | 일부 트래픽(예: 1%, 10%)만 새 버전으로, 지표 보고 늘림 | 문제를 작은 범위에서 발견 | 지표와 자동 분석이 필요, 구성 복잡 |
| 기능 플래그 | 코드는 배포, 기능은 설정으로 켜고 끔 | 출시와 배포 분리, 사용자 단위 제어 | 플래그 부채가 쌓인다, 정리 필요 |

### 점진 배포와 자동 분석

카나리를 사람이 눈으로 보면 놓친다. **점진 배포(progressive delivery)**는 단계마다 지표를 자동으로 비교한다.

1. 새 버전에 5% 트래픽.
2. 10분 동안 오류율·지연을 기존 버전과 비교.
3. 기준 안이면 25%, 50%, 100%로 늘림.
4. 기준을 넘으면 자동으로 0%로 되돌리고 알림.

쿠버네티스에서는 Argo Rollouts, Flagger 같은 도구가 이 흐름을 맡는다. 비교 지표는 05편의 SLI와 같은 것을 쓰면 된다.

### 롤백과 롤 포워드

- **롤백:** 이전 버전으로 되돌린다. 빠르고 확실하다. 장애 중 첫 선택이다.
- **롤 포워드:** 고친 새 버전을 빨리 낸다. 롤백할 수 없는 변경(되돌릴 수 없는 DB 변경, 이미 외부에 나간 데이터 형식)이 있을 때 선택한다.

롤백이 가능하려면 **새 버전이 데이터를 옛 버전이 못 읽는 형태로 바꾸지 않아야** 한다. 그래서 DB 변경은 다음 절처럼 나눠서 한다.

## 깊게 8 — DB 스키마 변경: 확장과 축소

컬럼 `name` 을 `full_name` 으로 바꾸는 상황이다. 한 번에 바꾸면, 배포가 롤링으로 도는 동안 옛 버전 앱은 `name` 을 찾다가 실패한다. 롤백해도 이미 컬럼 이름이 바뀌어 있다.

**확장과 축소(expand and contract)**로 나눈다.

```
1 확장: full_name 컬럼 추가
2 앱 v2: 두 컬럼에 다 쓰고
        full_name 우선 읽기
3 기존 데이터 채우기(backfill)
4 앱 v3: full_name만 읽고 쓰기
5 축소: name 컬럼 삭제
```

- 각 단계는 **앞뒤 버전과 호환**된다. 어느 단계에서든 한 단계 롤백이 가능하다.
- 큰 테이블의 데이터 채우기는 나눠서 천천히 한다. 한 번에 하면 잠금과 복제 지연을 만든다.
- 축소(삭제)는 충분히 시간이 지나고, 아무도 옛 컬럼을 안 쓰는 걸 확인한 뒤에 한다.
- 컬럼 추가도 DB 종류와 버전에 따라 테이블 전체를 다시 쓰는 경우가 있으니, 운영 규모 데이터로 먼저 시험한다.

## 깊게 9 — 플랫폼 엔지니어링: 골든 패스

공통 기반 팀의 목표는 "모든 팀이 인프라 전문가가 되게 하기"가 아니라 **"인프라 전문가가 아니어도 올바르게 하게 만들기"**다. 그 수단이 골든 패스(포장된 길)다.

- **템플릿:** 새 서비스를 만들면 저장소, CI/CD, 대시보드, 알림, 기본 SLO, 보안 설정이 한 번에 생긴다.
- **표준 모듈:** 회사 기준을 기본값으로 가진 IaC 모듈.
- **셀프 서비스:** 티켓을 넣고 기다리는 대신, 포털이나 PR로 필요한 자원을 직접 만든다. 가드레일이 위험한 요청을 막는다.
- **문서와 예시:** "이렇게 하면 된다"가 코드로 있다.

골든 패스는 강제가 아니다. 벗어날 수는 있지만, 벗어나면 그만큼 스스로 책임진다. 대신 길 위가 충분히 편해야 사람들이 따라온다. 공통 기반 팀은 자기 플랫폼의 **사용자 경험**을 제품처럼 다뤄야 한다.

## 깊게 10 — 배포 성과 재기: DORA 지표

DORA 연구에서 나온 네 가지 지표가 소프트웨어 배포 능력을 재는 사실상 표준이다.

| 지표 | 뜻 | 성격 |
|---|---|---|
| 배포 빈도 | 운영에 얼마나 자주 배포하나 | 속도 |
| 변경 리드 타임 | 커밋에서 운영 반영까지 걸린 시간 | 속도 |
| 변경 실패율 | 배포 중 장애·롤백을 부른 비율 | 안정성 |
| 복구 시간 | 배포로 생긴 장애에서 회복까지 걸린 시간 | 안정성 |

연구의 핵심 결론은 **속도와 안정성이 반대가 아니라는 것**이다. 잘하는 조직은 둘 다 좋다. 작은 변경을 자주 내면 한 번의 위험이 작고, 문제가 생겨도 원인 찾기와 되돌리기가 쉽기 때문이다. 플랫폼 팀은 이 지표로 "우리 골든 패스가 팀들을 빠르고 안전하게 만들었나"를 보여 줄 수 있다. 단, 지표를 팀 평가에 직접 쓰면 숫자를 꾸미게 되므로 개선 방향을 보는 데만 쓴다.

## 장애 대응 예시 — 머지 한 번에 운영 DB가 "재생성" 대상이 됐다

상황: 공통 모듈의 DB 자원 이름을 정리하는 리팩터링 PR. 리뷰어는 코드 차이만 보고 승인했다. 그런데 plan에는 운영 DB가 `must be replaced` 로 나와 있었다.

1. **다행히 막혔다.** 정책 검사가 "prod에서 상태 저장 자원의 삭제·교체가 있으면 실패"를 걸고 있어서 CI가 멈췄다.
2. **원인:** 자원의 코드 주소가 바뀌었는데 `moved` 블록이 없었다. Terraform은 옛 주소의 자원을 지우고 새 주소에 새로 만들려 했다.
3. **조치:** `moved` 블록을 추가하자 plan이 `No changes` 로 바뀌었다.
4. **추가 방어:**
   - 운영 DB에 삭제 방지 설정(클라우드의 deletion protection)과 Terraform의 `prevent_destroy` 수명 주기 규칙을 켠다.
   - PR 템플릿에 "plan의 destroy·replace 개수"를 적게 하고, 0이 아니면 추가 승인.
   - 리뷰 가이드: 코드가 아니라 plan을 읽는다.
5. **운이 좋았던 점:** 정책 검사가 없었다면 리뷰어 한 명의 눈에 운영 DB가 걸려 있었다.

## 자주 하는 실수와 예방

| 사고 | 원인 | 예방 |
|---|---|---|
| state 손상·분실 | 로컬 state, 손으로 편집, 동시 적용 | 원격 백엔드 + 잠금 + 버전 관리, state 직접 편집 금지 |
| 실수로 삭제 | 주소 변경, 잘못된 워크스페이스, `-target` 남용 | moved 블록, 디렉터리 분리, 삭제 정책 검사, 삭제 방지 |
| drift 싸움 | 콘솔 수정과 코드가 서로 덮어씀 | 정기 plan, 운영 콘솔 쓰기 권한 제한, 한쪽으로 정리 |
| 파이프라인 자격 증명 유출 | 장기 키, 로그 노출, 포크 PR에 비밀 | OIDC, 좁은 신뢰 조건, 마스킹, 포크 작업 분리 |
| "stg에선 됐는데" | 환경마다 다시 빌드 | 빌드 한 번, 다이제스트로 승격 |
| 롤백 불가 | 호환 안 되는 DB 변경을 한 번에 | 확장과 축소 |
| 모듈 변경이 전 팀을 깨뜨림 | 버전 없이 main을 참조 | 모듈 버전 고정, 변경 기록, 단계적 업그레이드 |
| 플래그 부채 | 끝난 기능 플래그를 안 지움 | 플래그에 만료일, 정기 정리 |

## 면접 질문 10개와 답

**1. Terraform state는 왜 필요하고 어떻게 관리하나?**
state는 코드의 자원 블록과 실제 클라우드 자원을 연결하는 기록이다. 이게 없으면 Terraform은 이미 있는 자원을 모르고 새로 만들려 한다. 팀에서는 원격 백엔드에 두고 잠금을 걸어 동시 적용을 막고, 버킷 암호화와 버전 관리로 비밀 노출과 실수에 대비한다. state를 손으로 고치지 않고, 필요한 변경은 import·moved·removed 블록처럼 코드로 남긴다.
> 日本語: stateはコードと実際のリソースの対応表で、リモートに置いてロックをかけて管理します。

**2. 환경은 디렉터리와 워크스페이스 중 어떻게 나누나?**
운영 환경이 있으면 디렉터리 분리와 공통 모듈을 선호한다. 환경마다 state, 백엔드, 권한을 따로 둘 수 있어서 개발 작업 중 실수가 운영으로 번지지 않는다. 워크스페이스는 구조가 완전히 같은 임시 환경에 맞는다. 중복은 모듈로 줄인다.

**3. state 하나에 다 넣으면 무엇이 문제인가?**
plan이 느려지고, 잠금 때문에 모두 기다리고, 작은 변경에도 전체 인프라가 위험 범위에 들어간다. 그래서 조직, 네트워크, 플랫폼, 앱처럼 변경 빈도와 위험도로 state를 나눈다. 위층은 아래층의 출력값을 읽어서 쓰게 해 의존 방향을 한쪽으로 둔다. 폭발 반경을 줄이는 설계다.

**4. 왜 Terraform인가? 다른 도구는 언제 쓰나?**
여러 클라우드와 SaaS를 한 문법과 한 워크플로로 다룰 수 있고, plan 기반 검토 문화를 만들기 쉽기 때문이다. 단, 같은 문법일 뿐 클라우드마다 코드는 다르고, state 관리 부담이 있다. 단일 클라우드라면 CloudFormation이나 Bicep 같은 네이티브 도구가 관리가 쉽고, 복잡한 로직이 많고 개발자가 인프라를 직접 쓰면 Pulumi, 쿠버네티스 중심 플랫폼이면 Crossplane도 후보다.

**5. CI에 클라우드 권한을 어떻게 주나?**
장기 액세스 키 대신 OIDC 신원 연합을 쓴다. CI가 발급한 짧은 토큰을 클라우드가 검증하고 임시 자격 증명을 준다. 신뢰 조건은 특정 저장소와 브랜치, 배포 환경으로 좁혀서 다른 저장소나 포크 PR이 권한을 받지 못하게 한다. 앱 비밀은 비밀 저장소에 두고 실행 시점에 워크로드 신원으로 읽는다.
> 日本語: 長期のアクセスキーではなく、OIDCで一時的な認証情報を使います。

**6. 정책을 코드로 어떻게 강제하나?**
두 층으로 둔다. CI에서는 plan을 JSON으로 뽑아 OPA나 Sentinel 같은 정책 엔진으로 검사해서 공개 노출, 태그 누락, 운영 자원 삭제를 PR 단계에서 막는다. 클라우드 쪽에서는 SCP, Azure Policy, 조직 정책으로 CI를 우회한 변경까지 거부한다. 막는 규칙은 사고가 되는 것만 적게 두고, 나머지는 경고로 하며 예외 절차를 만든다.

**7. 블루그린과 카나리의 차이는?**
블루그린은 새 환경을 통째로 띄우고 트래픽을 한 번에 넘긴다. 전환과 롤백이 즉시지만 순간 자원이 두 배이고 문제가 있으면 전체 사용자가 바로 맞는다. 카나리는 일부 트래픽만 새 버전으로 보내고 지표를 비교하며 늘린다. 위험을 작게 나누는 대신 지표와 자동 분석이 필요하다.

**8. 컬럼 이름 변경을 무중단으로 배포하려면?**
확장과 축소로 나눈다. 새 컬럼을 추가하고, 앱이 두 컬럼에 모두 쓰게 한 뒤, 기존 데이터를 채우고, 앱이 새 컬럼만 쓰게 바꾼 다음, 마지막에 옛 컬럼을 지운다. 각 단계가 앞뒤 버전과 호환되므로 롤링 배포 중에도 깨지지 않고 한 단계씩 롤백할 수 있다. 데이터 채우기는 나눠서 천천히 해서 잠금과 복제 지연을 피한다.
> 日本語: 列の追加、両方への書き込み、移行、旧列の削除の順で段階的に進めます。

**9. GitOps의 장점과 주의점은?**
git의 상태를 클러스터 안 에이전트가 끌어와 맞추므로, 클러스터 권한을 CI 밖에 두지 않아도 되고 모든 변경이 커밋으로 남는다. 롤백은 revert이고, 손으로 바꾼 drift도 자동으로 되돌린다. 주의할 점은 비밀값을 git에 평문으로 둘 수 없다는 것과, 동기화가 안 될 때 에이전트 상태를 읽을 줄 알아야 한다는 것이다.

**10. 인프라·플랫폼 팀의 성과를 무엇으로 재나?**
DORA 네 지표인 배포 빈도, 변경 리드 타임, 변경 실패율, 복구 시간을 쓴다. 속도와 안정성을 함께 보는 지표라서, 골든 패스와 가드레일이 팀들을 빠르면서 안전하게 만들었는지 보여 줄 수 있다. 여기에 플랫폼 사용률, 새 서비스 준비에 걸리는 시간 같은 사용자 경험 지표를 더한다. 지표를 개인 평가에 쓰면 숫자를 꾸미게 되므로 개선 방향을 보는 데 쓴다.

## 정답

1. `moved` 블록. 주소만 바뀌었다고 알려 주면 삭제 후 재생성이 아니라 이름 변경으로 처리된다. 추가 방어로 `prevent_destroy` 와 클라우드 삭제 방지를 켠다.
2. 태그는 다른 이미지로 옮겨 붙을 수 있지만 다이제스트는 내용의 해시라서 바뀌지 않는다. stg에서 시험한 바로 그 결과물이 prod에 나간다는 것을 보장한다.
3. 같은 CI 서비스를 쓰는 다른 저장소나 포크 PR의 작업이 우리 역할의 임시 자격 증명을 받을 수 있다. 신뢰 조건을 특정 저장소·브랜치·환경으로 한정해야 한다.
4. CI 정책은 빨리 실패하고 이유를 친절하게 알려 주지만 콘솔이나 다른 도구로 우회할 수 있다. 클라우드 정책은 우회 불가능한 마지막 방어선이지만 메시지가 불친절하다. 둘을 같이 써서 서로의 약점을 메운다.
5. 변경 실패율과 복구 시간.
