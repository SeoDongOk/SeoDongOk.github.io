## 두 종류의 재난

| | 정전·지진·리전 장애 | 랜섬웨어·데이터 오염 |
|---|---|---|
| 망가지는 것 | 장소 | 데이터 |
| 필요한 것 | 다른 곳의 최신 사본 | 과거 깨끗한 시점 |
| 방향 | 옆으로 (다른 곳에서 다시 서기) | 뒤로 (과거로 되돌리기) |
| 복제의 역할 | 해결책 | 피해를 퍼뜨리는 길 |

해커톤에서 만든 시스템은 앞의 재난을 풀었다. 온프레미스가 꺼지면 약 20초 안에 클라우드 사본이 이어받는다. 그런데 같은 구조를 랜섬웨어 앞에 세워 보니, 우리가 자랑한 "몇 초 안에 모든 사본이 같아진다"는 성질이 그대로 약점이 됐다.

## 전파되는 길 1 — 데이터 복제

PostgreSQL 논리 복제는 WAL을 해석해 **행 변경**을 사본으로 보낸다. 그래서 공격 방식에 따라 결과가 갈린다.

| 공격 방식 | 사본으로 전파 | 이유 |
|---|---|---|
| SQL로 값을 암호화 (`UPDATE … SET 칸 = 암호문`) | **된다** | 행 변경이다 |
| SQL로 삭제 (`DELETE`, `TRUNCATE`) | **된다** | 기본 발행은 TRUNCATE도 보낸다 |
| 서버 디스크의 데이터 파일 암호화 | 안 된다 | 파일이 아니라 행 변경을 보내므로 원본 DB만 멈춘다 |
| `DROP TABLE` 등 스키마 변경 | 안 된다 | DDL은 논리 복제 대상이 아니다. 대신 복제가 멈춘다 |

디스크 암호화형이라면 오히려 복제가 구해 준다. 원본은 멈추고 사본은 직전 상태로 남으니 사본으로 장애 이전하면 된다. 문제는 공격자가 **DB 권한**을 가졌을 때다. 그러면 SQL형으로 바꾸는 건 어렵지 않고, 그 순간 모든 사본이 같이 망가진다.

앱이 슈퍼유저 계정으로 DB에 붙어 있다면 더 나쁘다. 슈퍼유저는 표를 지우는 것뿐 아니라 `COPY … PROGRAM` 으로 DB 서버에서 명령까지 실행할 수 있다. 앱 계정은 필요한 표에 대한 최소 권한만 가진 일반 계정이어야 한다.

## 전파되는 길 2 — 관리 평면

여러 클라우드에 서비스를 옮기는 관제 시스템은 기능상 모든 환경에 손을 대야 한다. 우리 시스템의 관제 신원도 한쪽 클라우드에서는 클러스터 관리자, 다른 쪽에서는 프로젝트 전체 배포 권한을 갖고 있었다.

데이터를 다른 클라우드에 나눠 둔 이유는 "한 곳이 망가져도 다른 곳은 안전하다"는 분리였다. 그런데 **모든 곳의 열쇠를 가진 신원이 하나** 있으면 그 분리는 의미를 잃는다. 실제로 알려진 클라우드 랜섬웨어 사고 중에는 인프라 관리자 계정 하나가 탈취돼 대규모 암호화로 이어진 사례가 있다. 공격자는 데이터보다 관리 권한을 먼저 노린다.

## 전파되는 길 3 — 자동화

- 랜섬웨어로 앱이 오류를 내면 헬스체크가 실패한다. 자동 장애 이전이 켜져 있으면 시스템은 **이미 오염된 사본 쪽으로** 트래픽을 옮긴다. 화면에는 "복구 완료"가 뜨지만 데이터는 그대로 망가져 있다.
- 정합성 검사는 출발과 도착이 똑같이 암호화돼 있으면 MATCH를 낸다([2편](/blog/2026-11-08-dr-basics-02-consistency-vs-integrity)).

자동화는 재난을 빠르게 처리하라고 만든 것인데, 재난의 종류를 구분하지 못하면 잘못된 처리도 빠르게 한다.

## 막는 순서

감지가 복제보다 빠를 수는 없다. 복제는 수 초 만에 끝나고, 감지는 아무리 빨라도 그 뒤다. 그래서 순서가 중요하다. **되돌아갈 곳을 먼저 만들고, 전파를 줄이는 것은 그다음이다.**

| 순서 | 할 일 | 막는 것 |
|---|---|---|
| 1 | 변경 불가 백업 (별도 계정 + S3 Object Lock / GCS 보존 잠금) | 되돌아갈 곳이 없음 |
| 2 | 복원 시험 자동화 | 복원이 안 되는 백업 |
| 3 | WAL 보관과 PITR | 마지막 백업 뒤의 손실 |
| 4 | 최소 권한 (앱 일반 계정, 관제 신원을 네임스페이스 단위로, 만료 있는 토큰) | 하나가 뚫렸을 때의 범위 |
| 5 | 전파 차단 스위치 | 오염이 모든 사본으로 퍼짐 |
| 6 | 지연 사본 | 감지 전에 퍼진 오염 |
| 7 | TRUNCATE 발행 제외 | 한 줄로 표 전체가 빔 |
| 8 | 오염 감지 시 자동 이전 대신 복원 경로로 | 오염된 사본으로의 자동 이전 |

몇 가지는 구체적인 방법이 있다.

**전파 차단 스위치.** 짧은 시간에 대량 UPDATE·DELETE가 감지되면 모든 구독을 멈춘다.

```sql
ALTER SUBSCRIPTION my_sub DISABLE;
```

이미 넘어간 변경은 되돌리지 못하지만, 감지 뒤의 피해가 사본으로 더 가는 것은 막는다.

**지연 사본.** 논리 복제에는 적용을 일부러 늦추는 설정이 없다. 대신 물리 복제 대기 서버에는 있다.

```ini
# 대기 서버 postgresql.conf
recovery_min_apply_delay = '1h'
```

이 사본은 항상 1시간 전 상태를 유지한다. 원본이 오염된 것을 1시간 안에 알아채면, 대기 서버의 재생을 멈추고 오염 직전 시점까지만 적용할 수 있다.

**TRUNCATE 발행 제외.**

```sql
CREATE PUBLICATION my_pub FOR ALL TABLES
  WITH (publish = 'insert, update, delete');
```

## 배운 점

- 재해 시나리오를 세울 때 "장소가 사라지는가, 데이터가 망가지는가"부터 나눈다. 두 재난의 해법은 방향이 반대다.
- 빠른 복제는 가용성을 높이지만, 같은 성질 때문에 오염도 빨리 퍼진다. 복제를 강화할수록 백업의 중요성은 커진다.
- 모든 환경의 열쇠를 가진 신원이 있다면, 그 신원이 곧 재해 복구 설계의 가장 약한 고리다.

마지막 글에서는 재난이 났을 때 무엇부터 옮기고 무엇을 포기할지, 우선순위를 다룬다.
