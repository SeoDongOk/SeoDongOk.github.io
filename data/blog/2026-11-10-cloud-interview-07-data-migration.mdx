## 이 글에서 답할 면접 질문

- 블록, 파일, 오브젝트 스토리지는 무엇이 다르고, 각각 언제 쓰나?
- "내구성 99.999999999%"와 "가용성 99.9%"는 같은 말인가?
- 이 서비스에는 어떤 데이터베이스를 고르겠는가? 근거는?
- 온프레 시스템을 클라우드로 옮기는 계획을 세워 보라. 무엇부터 하겠는가?
- 7R 중에서 이 시스템은 어떤 전략이 맞는가?
- 회사 데이터센터와 클라우드를 어떻게 연결하겠는가? 이중화는?
- 운영 중인 데이터베이스를 거의 멈추지 않고 옮기려면?
- 이전이 실패하면 어떻게 되돌리는가?

클라우드 엔지니어 면접에서 이 주제가 중요한 이유는 간단하다. 회사가 클라우드 엔지니어를 뽑는 가장 흔한 이유가 "지금 있는 시스템을 클라우드로 옮기고, 옮긴 뒤 안정적으로 돌리는 것"이기 때문이다. 새로 짓는 것보다 옮기는 일이 훨씬 많고, 옮길 때 가장 어려운 것은 언제나 데이터다.

## 개념과 배경

### 스토리지는 세 종류다

컴퓨터가 데이터를 저장하는 방식은 크게 세 가지 모양으로 나뉜다. 클라우드도 이 세 모양을 그대로 서비스로 판다.

| 종류 | 모양 | 대표 서비스 |
|---|---|---|
| 블록 | 빈 디스크. OS가 파일 시스템을 올린다 | EBS, Persistent Disk, Managed Disks |
| 파일 | 폴더와 파일. 여러 서버가 같이 마운트 | EFS, Filestore, Azure Files |
| 오브젝트 | 키 하나에 파일 하나. HTTP로 넣고 뺀다 | S3, Cloud Storage, Blob Storage |

**블록 스토리지**는 서버에 꽂은 디스크와 같다. 클라우드는 이 디스크를 네트워크 너머에 두고 서버에 붙여 준다. OS는 그냥 디스크로 보고 그 위에 ext4나 xfs 같은 파일 시스템을 만든다. 지연이 낮고 작은 읽기·쓰기를 빠르게 처리하므로 데이터베이스, OS 부트 디스크에 쓴다. 보통 한 번에 한 서버에만 붙는다(일부 서비스는 여러 서버 동시 연결을 지원하지만, 그때는 클러스터 파일 시스템 같은 별도 조율이 필요하다). 그리고 대개 한 가용 영역(AZ) 안에 산다. 다른 AZ의 서버에는 바로 붙일 수 없고, 스냅샷을 떠서 다른 AZ에 새 디스크로 만들어야 한다.

**파일 스토리지**는 NFS나 SMB 같은 프로토콜로 여러 서버가 같은 폴더를 동시에 마운트한다. 여러 웹 서버가 같은 업로드 폴더를 봐야 하는 옛날식 애플리케이션, 공유 홈 디렉터리, 일부 분석 작업에 쓴다. 온프레의 NAS를 그대로 옮길 때 가장 자연스러운 대응물이다.

**오브젝트 스토리지**는 폴더 구조처럼 보여도 실제로는 "키 → 데이터" 한 쌍의 평평한 저장소다. 파일 일부만 고쳐 쓰는 것이 안 되고, 바꾸려면 통째로 다시 올린다. 대신 용량이 사실상 무한하고, 리전 안 여러 시설에 자동으로 복제되며, HTTP로 어디서든 접근할 수 있다. 정적 파일, 이미지, 백업, 로그, 데이터 레이크가 모두 여기에 간다. 클라우드에서 가장 싸고 가장 튼튼한 저장소다.

### 일관성: 쓰고 나서 바로 읽으면 보이는가

오브젝트 스토리지를 설명할 때 자주 나오는 단어가 일관성이다.

- **강한 일관성**: 쓰기가 끝났다고 응답한 순간부터 누가 읽어도 새 값이 보인다.
- **최종적 일관성**: 언젠가는 모두 새 값을 보지만, 잠깐 동안 옛 값이 보일 수 있다.

예전에는 오브젝트 스토리지 일부 동작이 최종적 일관성이라 "올리자마자 목록에 안 보인다" 같은 문제가 있었다. 지금은 S3, Cloud Storage, Blob Storage 모두 기본 객체 읽기·쓰기에 대해 강한 일관성을 제공한다고 문서화하고 있다. 다만 리전 간 복제, CDN 캐시, 검색 인덱스처럼 **복사본이 생기는 곳**에서는 여전히 시간 차가 있다. 면접에서는 "저장소 자체는 강한 일관성이지만, 그 앞에 붙은 캐시나 다른 리전 복제본은 늦을 수 있다"고 나눠서 말하면 정확하다.

### 내구성과 가용성은 다른 말이다

오브젝트 스토리지 소개에 나오는 "11나인(99.999999999%)"은 **내구성**이다. 1년 동안 저장한 객체를 잃어버리지 않을 확률이다. 리전 안 여러 시설에 나눠 저장하기 때문에 이 숫자가 나온다.

**가용성**은 "지금 요청하면 응답이 오는가"다. 데이터는 안전하게 있어도 서비스 장애로 잠깐 읽지 못할 수 있다. 그래서 같은 저장소라도 내구성은 11나인이고 가용성 약속(SLA)은 훨씬 낮은 숫자다. 저장 등급마다 가용성 약속도 다르다.

면접에서 자주 나오는 함정 질문이 있다. "S3는 11나인이니까 백업이 필요 없죠?" 답은 아니다. 내구성은 **클라우드가 실수로 잃어버리지 않을** 확률이지, **우리가 실수로 지우거나 랜섬웨어가 덮어쓰는 것**을 막아 주지 않는다. 버전 관리, 삭제 방지(Object Lock, 보존 정책), 다른 계정으로의 복사가 따로 필요하다. 복제와 백업이 왜 다른지는 [재해 복구 기초 01](/blog/2026-11-08-dr-basics-01-replication-is-not-backup)에서 자세히 다뤘다.

### 저장 등급과 수명 주기

오브젝트 스토리지는 자주 읽는 데이터와 거의 안 읽는 데이터의 값을 다르게 받는다.

| 등급 | 저장 비용 | 꺼내는 비용·시간 |
|---|---|---|
| 표준 | 높다 | 없음, 즉시 |
| 저빈도 | 중간 | 꺼낼 때 요금, 최소 보관 기간 |
| 아카이브 | 낮다 | 요금이 크고, 서비스에 따라 수 시간 |

세 클라우드 모두 이름은 달라도 이 구조다. AWS는 S3 Standard, Standard-IA, Glacier 계열, 그리고 접근 패턴에 따라 자동으로 옮겨 주는 Intelligent-Tiering이 있다. GCP는 Standard, Nearline, Coldline, Archive가 있고, Azure Blob은 Hot, Cool, Cold, Archive 계층이 있다.

**수명 주기 규칙**을 걸면 "만든 지 30일 지나면 저빈도로, 1년 지나면 아카이브로, 7년 지나면 삭제" 같은 규칙이 자동으로 돈다. 로그와 백업은 거의 항상 이 규칙을 건다. 함정은 **최소 보관 기간**이다. 아카이브로 옮긴 객체를 바로 지우면 남은 기간 요금이 청구될 수 있다. 그리고 아주 작은 객체를 많이 아카이브로 옮기면 객체당 요금 때문에 오히려 비싸질 수 있다. 수명 주기는 데이터 크기와 접근 패턴을 보고 정한다.

### 데이터베이스는 "무엇을 묻는가"로 고른다

데이터베이스 선택은 유행이 아니라 **데이터의 모양과 질문의 모양**으로 정한다.

| 질문의 모양 | 맞는 종류 | 예 |
|---|---|---|
| 여러 표를 조인, 트랜잭션 | 관계형 | RDS, Aurora, Cloud SQL, AlloyDB, Azure SQL |
| 키로 바로 찾기, 대량 처리 | 키-값·문서 | DynamoDB, Firestore, Cosmos DB |
| 시계열·대량 쓰기 | 넓은 열 | Bigtable, Cosmos DB(Cassandra API) |
| 전 세계 강한 일관성 | 분산 관계형 | Spanner |

**관계형**은 기본값이다. 주문, 결제, 회원처럼 정합성이 중요하고 질문이 다양한 데이터는 관계형으로 시작하는 게 맞다. 관리형 서비스로는 AWS RDS(MySQL, PostgreSQL 등)와 Aurora, GCP Cloud SQL과 AlloyDB(PostgreSQL 호환), Azure SQL Database와 Azure Database for PostgreSQL·MySQL이 있다. Aurora와 AlloyDB는 스토리지 계층을 클라우드 방식으로 다시 만든 PostgreSQL·MySQL 호환 엔진이라 복제 지연과 장애 조치가 일반 관리형보다 유리하다는 것이 핵심 차별점이다.

**키-값·문서형**은 "이 사용자 ID의 세션", "이 상품의 장바구니"처럼 키 하나로 바로 찾는 질문에 강하고, 거의 무한히 수평 확장된다. 대신 조인이 없고, 질문 패턴을 미리 정해서 키를 설계해야 한다. 나중에 "이 조건으로 검색하고 싶다"가 생기면 보조 인덱스를 추가하거나 데이터를 다시 설계해야 한다. DynamoDB, Firestore, Cosmos DB가 여기에 속한다. Cosmos DB는 여러 API(NoSQL, MongoDB, Cassandra, PostgreSQL 등)를 고를 수 있는 멀티 모델 서비스다.

**넓은 열**인 Bigtable은 IoT 센서, 시계열, 광고 이벤트처럼 쓰기가 엄청나게 많고 키 범위로 읽는 데이터에 쓴다.

**Spanner**는 여러 리전에 걸쳐 강한 일관성 트랜잭션을 제공하는 분산 관계형 데이터베이스다. "전 세계 어디서 써도 바로 정확한 잔액"이 필요할 때 후보가 된다. 대신 비용과 설계 난이도가 높아서, 단일 리전 PostgreSQL로 충분한 서비스에 쓰면 과하다.

면접 답의 틀은 이렇다. "데이터 모양(관계가 많은가), 질문 모양(조인·검색이 다양한가), 일관성 요구(돈인가), 규모(초당 쓰기, 데이터 크기), 운영 부담(팀이 잘 아는가), 이식성(나중에 다른 클라우드로 옮길 가능성)을 보고 고른다. 특별한 이유가 없으면 관리형 PostgreSQL로 시작한다."

## 깊게

### 읽기 복제본과 연결 풀

관계형 데이터베이스가 버거워지면 순서대로 손을 쓴다.

1. **쿼리와 인덱스부터.** 느린 쿼리 로그를 보고 인덱스를 고친다. 서버를 키우기 전에 가장 싸고 효과가 크다.
2. **연결 풀.** 데이터베이스는 연결 하나마다 메모리와 프로세스(PostgreSQL은 연결마다 프로세스)를 쓴다. 웹 서버가 늘 때마다 연결이 늘면 데이터베이스가 연결만으로 지친다. PgBouncer 같은 풀러나 RDS Proxy 같은 관리형 프록시를 앞에 두어 실제 연결 수를 묶는다. 서버리스 함수처럼 순간적으로 수백 개가 뜨는 환경에서는 거의 필수다.
3. **캐시.** 자주 읽고 잘 안 바뀌는 데이터는 Redis(ElastiCache, Memorystore, Azure Cache for Redis)에 둔다.
4. **읽기 복제본.** 읽기 요청을 복제본으로 나눈다. 비동기 복제라서 **방금 쓴 데이터가 복제본에 아직 없을 수 있다.** "방금 저장한 글이 목록에 안 보인다"는 이 때문이다. 쓴 직후 읽는 화면은 주 서버에서 읽도록 라우팅한다.
5. **스케일 업.** 더 큰 인스턴스로.
6. **분할(샤딩)이나 다른 데이터베이스.** 마지막 수단이다. 애플리케이션이 크게 바뀐다.

### 데이터베이스의 HA와 DR은 다르다

- **고가용성(HA)**: 같은 리전 안에서 서버 한 대나 AZ 하나가 죽어도 몇십 초~몇 분 안에 다른 AZ의 대기 서버가 이어받는다. RDS Multi-AZ, Cloud SQL 고가용성 구성, Azure SQL의 영역 중복이 이것이다. 보통 **동기 복제**라서 데이터 손실이 거의 없다.
- **재해 복구(DR)**: 리전 전체가 안 될 때 다른 리전에서 다시 돌린다. 거리가 멀어서 보통 **비동기 복제**라 몇 초~몇 분의 데이터 손실(RPO)을 감수한다. 교차 리전 읽기 복제본을 승격하거나, Aurora Global Database 같은 기능을 쓰거나, 백업을 다른 리전에 복사해 두고 복원한다.

면접에서 "Multi-AZ니까 DR도 됩니다"라고 하면 틀린다. Multi-AZ는 같은 리전 안의 대비이고, 리전 장애나 사람의 실수(잘못된 DELETE가 대기 서버에도 그대로 복제됨)는 막지 못한다. 그래서 HA, DR, 백업 세 가지를 따로 설계한다.

### 캐시 계층

요청이 데이터베이스에 닿기 전에 여러 겹의 캐시가 있다.

```
브라우저 캐시
  → CDN (정적 파일, 일부 API)
    → 애플리케이션 메모리
      → Redis 같은 분산 캐시
        → 데이터베이스
```

캐시를 넣을 때 면접관이 묻는 것은 세 가지다.

- **무효화**: 데이터가 바뀌면 캐시를 어떻게 지우나? 짧은 TTL로 두는가, 쓰기 때 지우는가.
- **캐시 쇄도**: 인기 키가 만료되는 순간 수많은 요청이 동시에 데이터베이스로 몰린다. 한 요청만 다시 채우게 잠그거나, 만료 시간을 조금씩 흩뜨린다.
- **캐시가 죽으면**: 캐시가 없어도 데이터베이스가 버티는가? 버티지 못하면 캐시는 성능 장치가 아니라 **필수 구성 요소**가 되고, 그러면 캐시의 이중화도 설계해야 한다.

### 데이터 전송과 송신 비용

클라우드는 데이터를 **넣을 때는 대부분 무료이고, 뺄 때 돈을 받는다.** 인터넷으로 나가는 송신(egress), 리전 사이 전송, 서비스에 따라서는 AZ 사이 전송에도 요금이 붙는다.

설계에서 의미하는 바:

- 데이터와 그걸 처리하는 컴퓨트는 같은 리전, 가능하면 같은 AZ에 둔다.
- 사용자에게 많이 내보내는 정적 파일은 CDN을 거쳐 내보낸다.
- 멀티 클라우드로 데이터를 계속 동기화하면 송신 비용이 계속 나온다. "멀티 클라우드라서 안전하다"는 설계는 이 비용을 같이 말해야 한다.
- 사설 서브넷에서 NAT 게이트웨이를 거쳐 같은 리전의 오브젝트 스토리지로 가면 NAT 처리 비용이 붙는다. VPC 엔드포인트(Private Service Connect, Private Endpoint)를 쓰면 줄일 수 있다.

## 클라우드 이전 전략

### 먼저 평가(assessment)

이전 계획은 "무엇이 있는지 모르는 상태"에서 시작한다. 그래서 첫 단계는 목록 만들기다.

- **자산 목록**: 서버, OS 버전, CPU·메모리 사용률, 디스크 크기, 데이터베이스 엔진과 크기, 라이선스.
- **의존성 지도**: 이 서버는 누구와 통신하는가. 네트워크 흐름을 일정 기간 수집해서 보면, 문서에 없던 연결(예: 밤마다 도는 배치가 다른 서버의 공유 폴더를 읽는다)이 나온다.
- **업무 중요도**: 멈추면 얼마나 아픈가, 얼마나 오래 멈춰도 되는가(RTO), 데이터를 얼마나 잃어도 되는가(RPO).
- **제약**: 규제(데이터가 국내에 있어야 하는가), 라이선스가 클라우드에서 허용되는가, 하드웨어 의존(특정 장비, 동글).

각 클라우드는 이 단계를 돕는 도구를 제공한다. AWS는 Migration Hub와 Application Discovery Service, Azure는 Azure Migrate, GCP는 Migration Center가 있다. 도구 이름보다 중요한 것은 "**측정한 데이터로 결정한다**"는 태도다. 온프레 서버의 사양을 그대로 클라우드에 옮기면 대개 과하다. 실제 사용률을 보고 크기를 정한다.

### 7R: 각 시스템을 어떻게 옮길 것인가

시스템마다 옮기는 방식이 다르다. 업계에서 흔히 쓰는 분류가 7R이다.

| 전략 | 뜻 | 언제 |
|---|---|---|
| Retire | 없앤다 | 아무도 안 쓰는 시스템 |
| Retain | 그대로 둔다 | 아직 옮길 수 없거나 이유가 없다 |
| Rehost | 그대로 옮긴다 (리프트 앤 시프트) | 빨리 데이터센터를 비워야 할 때 |
| Relocate | 가상화 플랫폼째 옮긴다 | VMware 환경을 클라우드의 VMware 서비스로 |
| Replatform | 조금 손본다 | 자체 DB를 관리형 DB로, 서버를 컨테이너로 |
| Refactor | 다시 설계한다 | 확장성·민첩성이 사업상 꼭 필요할 때 |
| Repurchase | 다른 제품으로 바꾼다 | 자체 메일 서버를 SaaS로 |

면접에서 중요한 포인트는 이것이다.

- **모든 시스템을 같은 전략으로 옮기지 않는다.** 포트폴리오로 본다. 대부분은 Rehost나 Replatform, 소수의 핵심 시스템만 Refactor.
- **Retire를 먼저 찾는다.** 평가를 해 보면 생각보다 많은 서버가 아무도 안 쓰거나 중복이다. 옮기지 않는 것이 가장 싼 이전이다.
- **Rehost로 시작해서 나중에 최적화**하는 것도 정당한 전략이다. 데이터센터 계약 만료처럼 시간이 정해져 있으면 먼저 옮기고, 클라우드에서 운영 데이터를 보며 다듬는다. 다만 "나중에"가 영원히 오지 않는 경우가 많으므로 최적화 계획도 같이 세운다.
- **Replatform의 대표**는 데이터베이스다. 직접 관리하던 PostgreSQL을 관리형으로 옮기면 백업, 패치, 장애 조치를 클라우드가 맡는다. 대신 슈퍼유저 권한이나 특정 확장 기능을 못 쓸 수 있으니 미리 확인한다.

### 랜딩 존이 먼저다

시스템을 옮기기 전에 **옮겨 갈 땅**을 먼저 다진다. 이게 랜딩 존이다.

- 계정·구독·프로젝트 구조 (운영·개발 분리, 공통 서비스 계정, 보안·로그 계정)
- 신원과 권한 (회사 계정으로 SSO, 역할 기반 권한, 최소 권한)
- 네트워크 (IP 대역 할당표, 허브 앤 스포크, 온프레 연결)
- 로그와 감사 (모든 계정의 감사 로그를 별도 계정으로 모으기)
- 보안 가드레일 (조직 정책으로 금지할 것: 공개 버킷, 허용 안 된 리전 등)
- 비용 (태그 규칙, 예산 알림)

랜딩 존 없이 첫 시스템을 옮기면, 그 시스템이 만든 임시 구조가 나중 시스템들의 표준이 되어 버린다. 회사 전체의 "공통 기반"을 설계하는 것이 클라우드 엔지니어 직무의 핵심인 이유다. 자세한 구조는 이 시리즈의 랜딩 존 편에서 다룬다.

### 웨이브 계획

시스템을 한꺼번에 옮기지 않고 묶음(웨이브)으로 나눈다.

1. **파일럿 웨이브**: 중요도가 낮고 의존성이 적은 시스템 몇 개. 절차·도구·체크리스트를 검증하는 목적이다.
2. **의존성으로 묶기**: 서로 자주 통신하는 시스템은 같은 웨이브로 옮긴다. 하나만 옮기면 온프레와 클라우드 사이를 오가는 통신이 늘어 지연과 전송 비용이 커진다.
3. **중요한 시스템은 뒤로**: 앞 웨이브에서 배운 것을 반영한 뒤 옮긴다.
4. **웨이브마다 회고**: 무엇이 예상과 달랐는지, 체크리스트를 고친다.

## 하이브리드 연결

이전 기간에는 온프레와 클라우드가 반드시 공존한다. 그리고 많은 회사는 이전이 끝나도 일부 시스템을 온프레에 남긴다. 그래서 둘을 잇는 네트워크가 기반 설계의 핵심이다.

### 선택지

| 방식 | 특징 | 서비스 |
|---|---|---|
| 사이트 간 VPN | 인터넷 위 암호화 터널. 빠르게 구성, 품질은 인터넷 따라 | AWS Site-to-Site VPN, Cloud VPN, Azure VPN Gateway |
| 전용선 | 사업자 회선으로 직결. 대역·지연이 안정적 | AWS Direct Connect, Cloud Interconnect, ExpressRoute |

VPN은 몇 시간이면 만들 수 있어서 이전 초기나 백업 경로로 좋다. 전용선은 개통에 시간이 걸리지만 대역폭과 지연이 일정하고, 많은 경우 데이터 송신 요금도 인터넷보다 유리하다. 대량 데이터 이전이나 운영 트래픽에는 전용선이 맞다.

### 이중화

전용선 한 줄은 단일 장애점이다. 회선, 사업자 장비, 클라우드 쪽 접속 지점 어느 하나만 고장 나도 끊긴다. 그래서:

- **회선 두 개 이상**, 가능하면 **다른 접속 지점(로케이션)**과 다른 장비로.
- **전용선 + VPN 백업**도 흔한 구성이다. 평소에는 전용선, 끊기면 VPN으로.
- 클라우드마다 "이 정도 구성을 하면 이 정도 SLA" 같은 권장 구성을 문서로 제공한다. 설계할 때 그 기준을 따른다.

### BGP로 경로를 주고받는다

전용선과 대부분의 VPN은 **BGP**로 경로를 교환한다. 온프레 라우터가 "우리 쪽 대역은 10.0.0.0/16"을, 클라우드 라우터(Virtual Private Gateway·Transit Gateway, Cloud Router, Azure의 게이트웨이)가 "클라우드 쪽 대역은 10.100.0.0/16"을 서로 알린다.

경로가 두 개일 때 어느 쪽을 주 경로로 쓸지도 BGP 속성으로 정한다. 같은 대역을 양쪽 회선에서 광고하되, 백업 쪽은 덜 선호되게(예: AS 경로를 길게 보이게) 만든다. 면접에서는 "두 회선의 BGP 경로 우선순위를 설정해서 평소엔 A로, A가 끊기면 BGP가 경로를 철회하고 자동으로 B로 넘어간다"고 설명하면 된다.

자주 나오는 문제:

- **비대칭 경로**: 갈 때는 전용선, 올 때는 VPN으로 오면 상태 저장 방화벽이 응답을 버린다. 양방향 우선순위를 맞춘다.
- **대역 겹침**: 온프레와 클라우드 VPC 대역이 겹치면 라우팅이 불가능하다. 이전 프로젝트 첫날 IP 할당표를 만드는 이유다.
- **광고 경로 수 제한**: 클라우드 쪽에 광고할 수 있는 경로 수에 상한이 있다. 경로를 요약해서 보낸다.

### MTU

VPN은 암호화 헤더만큼 한 번에 보낼 수 있는 크기가 줄어든다. 전용선은 서비스에 따라 큰 MTU(점보 프레임)를 지원하기도 한다. 양쪽 MTU가 다르고 중간에서 "너무 크다" ICMP가 막히면, 작은 요청은 되는데 큰 전송만 멈추는 증상이 난다. 이전 기간에 데이터베이스 복제나 대용량 파일 전송이 이상하게 멈추면 MTU를 의심한다. 터널 장비에서 TCP MSS를 낮추는 설정(MSS 클램핑)으로 해결하는 경우가 많다.

## 데이터베이스 이전

### 방식 세 가지

| 방식 | 중단 시간 | 적합한 경우 |
|---|---|---|
| 덤프 후 복원 | 덤프·전송·복원 시간 전체 | 작은 DB, 주말 점검 가능 |
| 물리 복제·백업 복원 + 로그 적용 | 짧음 | 같은 엔진·버전, 관리형 지원 시 |
| 논리 복제·CDC | 컷오버 순간만 | 큰 DB, 거의 무중단, 버전·엔진 변경 |

**덤프 후 복원**은 가장 단순하다. `pg_dump`·`mysqldump`로 뽑아 옮겨서 넣는다. 그동안 쓰기를 멈춰야 하므로 데이터가 크면 중단 시간이 길어진다.

**논리 복제·CDC(변경 데이터 캡처)**는 먼저 전체 데이터를 한 번 복사하고, 그 뒤로 생기는 변경을 계속 따라 보낸다. 원본이 계속 운영되는 동안 대상이 따라잡고, 마지막 순간에 짧게 멈추고 전환한다. PostgreSQL의 논리 복제(발행·구독), MySQL의 binlog 기반 복제, 그리고 관리형 서비스인 AWS DMS, Google Cloud의 Database Migration Service, Azure Database Migration Service가 이 방식을 지원한다. 엔진을 바꾸는 이전(예: Oracle에서 PostgreSQL)은 스키마 변환 도구와 함께 쓴다.

CDC의 함정:

- **기본 키 없는 테이블**은 변경을 정확히 따라가기 어렵다. 이전 전에 찾아서 기본 키를 만들거나 다른 방법을 정한다.
- **DDL**(테이블 구조 변경)은 논리 복제에서 자동으로 따라가지 않는 경우가 많다. 이전 기간에는 스키마 변경을 동결한다.
- **시퀀스 값**은 복제되지 않을 수 있다. 전환 직후 새 쪽에서 ID가 겹치는 사고가 난다. 컷오버 절차에 시퀀스 맞추기를 넣는다.
- **복제 지연**을 계속 측정한다. 지연이 줄지 않으면 컷오버 시점을 잡을 수 없다.
- **원본의 로그 보존**: 복제가 오래 끊기면 원본이 변경 로그를 계속 쌓아 디스크가 찰 수 있다.

### 컷오버: 쓰기 정지 → 따라잡기 → 전환

거의 무중단 이전의 핵심은 **아주 짧은 쓰기 정지 창**이다.

```
1. 원본 쓰기 정지 (앱 쓰기 차단)
2. 복제 지연 0 확인
3. 데이터 검증
4. 대상 쓰기 허용, 시퀀스 맞춤
5. 앱 연결 대상으로 전환
6. 쓰기 재개
```

쓰기 정지를 앱에서 할지(유지보수 모드, 쓰기 API 차단), 데이터베이스에서 할지(읽기 전용 전환, 연결 풀 일시 정지) 정한다. 연결 풀러를 쓰면 새 요청을 잠깐 붙잡아 두었다가 전환 후 풀어 주는 방식으로 사용자가 에러 대신 짧은 지연만 보게 할 수 있다. 그동안 앱의 타임아웃이 쓰기 정지 시간보다 길어야 에러가 안 난다. 앞단 프록시의 시도당 타임아웃이 정지 창보다 짧으면 사용자는 504를 본다. 리허설에서 반드시 확인한다.

### 검증

"복제가 정상이라고 나온다"는 검증이 아니다. 데이터를 직접 비교한다.

- **행 수 비교**: 테이블마다 양쪽 행 수가 같은가. 가장 싸고 먼저 하는 검사.
- **체크섬 비교**: 테이블이나 기본 키 범위별로 내용을 해시해서 비교한다. 행 수는 같은데 값이 다른 경우를 잡는다.
- **샘플 비교**: 최근 변경된 행 몇 개를 양쪽에서 직접 조회해 본다.
- **애플리케이션 검증**: 핵심 화면과 API를 실제로 돌려 본다(스모크 테스트).

검증은 쓰기 정지 중에 하는 것과 전환 후에 하는 것으로 나눈다. 정지 중에는 빠른 검사(행 수, 일부 체크섬)만, 무거운 전체 비교는 전환 전날 리허설이나 전환 후 조용한 시간에.

### 롤백 계획

이전 계획서에서 면접관이 가장 먼저 찾는 것이 롤백이다.

- **되돌아갈 조건을 미리 정한다.** "전환 후 30분 안에 오류율이 기준을 넘으면 되돌린다"처럼 숫자로. 현장에서 판단하려 하면 늦는다.
- **되돌아갈 길을 열어 둔다.** 전환 후 새 쪽에 쌓인 쓰기를 옛 쪽으로 보낼 방법이 있어야 한다. 역방향 복제를 걸어 두거나, 전환 후 일정 시간 쓰기를 기록해 다시 재생할 수 있게 한다. 이게 없으면 롤백하는 순간 전환 후의 데이터를 잃는다.
- **옛 환경을 바로 지우지 않는다.** 안정화 기간 동안 원본을 읽기 전용으로 남긴다.
- **롤백도 리허설한다.** 한 번도 해 보지 않은 롤백은 롤백 계획이 아니다.

### 대용량 데이터 옮기기

데이터가 수십 TB를 넘어가면 네트워크로 옮기는 시간을 먼저 계산한다. 예를 들어 실효 1Gbps 회선이면 초당 약 125MB, 하루에 약 10TB 남짓이다. 회선을 다른 업무와 나눠 쓰면 더 느리다.

- **온라인 전송**: 전용선이나 인터넷으로 전송 도구를 사용한다. AWS DataSync, Google Cloud의 Storage Transfer Service, Azure의 AzCopy·Data Box Gateway 같은 도구가 병렬 전송, 재시도, 검증을 해 준다.
- **오프라인 장치**: 클라우드 사업자가 보내 주는 저장 장치에 데이터를 담아 택배로 돌려보낸다. AWS Snowball 계열, Google Transfer Appliance, Azure Data Box가 있다. 회선으로 몇 주 걸리는 양을 며칠로 줄일 때 쓴다.
- **보통은 둘을 섞는다**: 대량 과거 데이터는 장치로 한 번에, 그 이후 변경분은 네트워크로 따라잡는다. 데이터베이스의 "전체 복사 + CDC"와 같은 구조다.

## 설계·이전 예시: 중간 규모 웹 서비스를 온프레에서 클라우드로

가상의 서비스를 하나 정한다.

- 웹 서버 4대, API 서버 6대, 배치 서버 2대 (VM)
- PostgreSQL 주 서버 1대 + 대기 1대, 데이터 2TB
- NAS에 사용자 업로드 파일 20TB
- 매일 밤 배치가 NAS와 DB를 읽어 리포트 생성
- 목표: 6개월 안에 데이터센터 철수, 서비스 중단은 30분 이내 1회

### 0단계: 평가 (1개월)

- 서버·DB·NAS 목록과 사용률 수집. API 서버 CPU 평균이 낮아 클라우드에서는 더 작은 크기로 시작 가능.
- 네트워크 흐름 수집. 문서에 없던 연결 발견: 배치 서버가 외부 결제사 SFTP에 접속하고, 상대가 우리 **공인 IP를 허용 목록**에 등록해 두었다. 이전 후 출발 IP가 바뀌면 끊긴다. 결제사에 새 고정 IP를 미리 등록 요청해야 한다.
- RTO·RPO 합의: 서비스 RTO 1시간, RPO 5분.

### 1단계: 랜딩 존과 연결 (1개월)

- 운영·개발 계정 분리, 네트워크·보안·로그 공통 계정.
- IP 할당표 작성. 온프레 대역과 겹치지 않는 VPC 대역.
- 전용선 2회선(서로 다른 접속 지점) + VPN 백업. BGP 우선순위 설정 후 한 회선 끊기 시험.
- NAT 게이트웨이에 고정 IP를 붙여 결제사에 등록 요청.

### 2단계: 전략 결정

| 구성 요소 | 전략 | 이유 |
|---|---|---|
| 웹·API | Replatform (컨테이너) | 무상태라 옮기기 쉽고 오토스케일 이득 |
| 배치 | Rehost 후 개선 | 의존성이 많아 먼저 그대로 |
| PostgreSQL | Replatform (관리형) | 백업·HA를 맡김 |
| NAS 파일 | 오브젝트 스토리지로 | 앱의 파일 접근 코드 수정 필요 |
| 사내 위키 | Repurchase (SaaS) | 운영 부담 제거 |

NAS를 오브젝트 스토리지로 바꾸는 것은 코드 변경이 필요하다. 시간이 부족하면 1차로 관리형 파일 스토리지(EFS, Filestore, Azure Files)로 옮기고 나중에 바꾸는 선택도 있다. 면접에서는 이런 **선택지와 판단 기준**을 같이 말하는 게 점수가 된다.

### 3단계: 데이터 이동 (2개월, 서비스 운영 중)

- 업로드 파일 20TB: 전송 도구로 전용선 너머 오브젝트 스토리지로 복사. 이후 매일 증분 동기화. 앱은 **새 파일은 양쪽에 쓰도록** 바꾸거나, 컷오버 때 마지막 증분을 돌린다.
- DB 2TB: 관리형 DB로 CDC 이전 시작. 기본 키 없는 테이블 3개 발견, 기본 키 추가. 스키마 변경 동결 공지. 복제 지연과 원본 로그 보존량을 대시보드로 감시.
- 클라우드 쪽 앱을 띄워 **읽기 전용 스모크 테스트**. 성능 시험으로 인스턴스 크기와 연결 풀 크기를 정한다.

### 4단계: 리허설 (2회 이상)

- 개발 환경에서 전체 컷오버 절차를 그대로 돌리고, 단계별 시간을 잰다. 쓰기 정지가 목표 시간 안에 끝나는가.
- 앱·프록시 타임아웃이 쓰기 정지 시간보다 긴지 확인.
- **롤백 리허설**: 전환 후 역방향 복제로 원본에 되돌리기.
- 체크리스트와 담당자, 연락 채널, 판단 기준(언제 되돌리는가)을 문서로 고정.

### 5단계: 컷오버 (당일)

1. DNS TTL은 며칠 전에 짧게 낮춰 둠
2. 유지보수 공지, 쓰기 차단
3. 복제 지연 0 확인 → 행 수·체크섬 빠른 검증 → 시퀀스 맞춤
4. 역방향 복제 시작 (롤백 대비)
5. 앱 연결을 클라우드 DB로, 트래픽을 클라우드 앞단으로
6. 쓰기 재개, 스모크 테스트, 오류율·지연 감시
7. 기준 시간 동안 이상 없으면 컷오버 완료 선언

### 6단계: 안정화와 정리 (1개월)

- 온프레는 읽기 전용으로 2주 유지 후 최종 백업, 철수.
- 클라우드에서 실제 사용량을 보고 인스턴스 크기와 예약 할인 결정.
- 배치 서버를 관리형 스케줄러나 컨테이너 작업으로 개선(아까 미뤄 둔 최적화).
- 회고: 예상과 달랐던 점을 다음 이전 프로젝트의 체크리스트로.

## 자주 하는 실수

- **사양을 그대로 옮긴다.** 온프레는 몇 년 뒤를 보고 크게 샀다. 클라우드는 지금 필요만큼 시작하고 늘린다.
- **의존성 조사를 건너뛴다.** 문서에 없는 연결(허용 목록에 박힌 IP, 하드코딩된 서버 이름, 밤에만 도는 배치)이 컷오버 날 터진다.
- **데이터 전송 시간을 계산하지 않는다.** 회선 속도와 데이터 크기로 먼저 계산한다.
- **롤백 계획이 "원래대로 돌린다" 한 줄이다.** 전환 후 쌓인 쓰기를 어떻게 되돌릴지가 빠져 있다.
- **HA를 DR로 착각한다.** Multi-AZ는 리전 장애와 사람 실수를 막지 못한다.
- **11나인이라 백업을 안 한다.** 삭제와 덮어쓰기는 내구성과 관계없다.
- **송신 비용을 설계에 넣지 않는다.** 이전 기간 온프레와 클라우드 사이 트래픽, 멀티 클라우드 동기화 비용을 미리 계산한다.
- **랜딩 존 없이 첫 시스템부터 옮긴다.** 임시 구조가 표준이 된다.
- **DNS TTL을 컷오버 당일에 낮춘다.** 이전 TTL 동안은 캐시가 남는다. 며칠 전에 낮춘다.

## 면접 질문 10개와 답

**1. 블록·파일·오브젝트 스토리지의 차이는?**
블록은 서버에 붙는 디스크로 지연이 낮아 DB와 부트 디스크에, 파일은 여러 서버가 같이 마운트하는 공유 폴더로 옛 앱의 공유 디렉터리에, 오브젝트는 HTTP로 접근하는 키-데이터 저장소로 용량이 무한하고 가장 튼튼해 정적 파일·백업·로그에 쓴다. 블록은 보통 한 AZ에 묶이고, 오브젝트는 리전 단위로 복제된다는 점도 같이 말한다.

> ブロックはサーバーに接続するディスク、ファイルは複数サーバーで共有するフォルダ、オブジェクトはHTTPでアクセスするキーと値のストレージです。

**2. 11나인 내구성이면 백업이 필요 없나?**
필요하다. 내구성은 클라우드가 데이터를 잃지 않을 확률이고, 사람의 삭제·덮어쓰기나 랜섬웨어 암호화는 그대로 복제된다. 버전 관리, 삭제 방지 잠금, 다른 계정으로의 복사를 둔다.

**3. 관계형과 NoSQL 중 무엇을 고르겠나?**
데이터에 관계가 많고 질문이 다양하며 정합성이 중요하면 관계형, 키로 바로 찾는 단순한 질문이 대량으로 오고 수평 확장이 필요하면 키-값·문서형이다. 특별한 이유가 없으면 관리형 PostgreSQL로 시작하고, 특정 부분에 한계가 오면 그 부분만 다른 저장소로 뺀다.

**4. Multi-AZ와 교차 리전 복제본의 차이는?**
Multi-AZ는 같은 리전 안의 동기 복제로 AZ 장애에 자동으로 넘어가고 데이터 손실이 거의 없다. 교차 리전 복제본은 비동기라 리전 장애 대비용이고, 승격할 때 몇 초에서 몇 분의 데이터를 잃을 수 있다.

**5. 읽기 복제본을 넣었더니 "방금 쓴 글이 안 보인다"는 문의가 왔다.**
비동기 복제 지연 때문이다. 쓴 직후 읽는 요청은 주 서버로 보내거나, 사용자 세션마다 일정 시간 주 서버를 읽게 하거나, 복제 지연을 감시해서 기준을 넘으면 복제본을 빼는 방식으로 해결한다.

**6. 온프레 시스템을 클라우드로 옮기는 계획에서 가장 먼저 무엇을 하나?**
평가다. 자산 목록, 실제 사용률, 의존성 지도, 업무 중요도와 RTO·RPO, 규제·라이선스 제약을 모은다. 동시에 옮겨 갈 랜딩 존(계정 구조, 권한, 네트워크, 로그, 보안 규칙)을 준비한다.

> まず現状を把握します。資産の一覧、実際の使用率、依存関係、業務の重要度を整理してから、移行の方法を決めます。

**7. 7R 중 Rehost와 Replatform의 차이와 고르는 기준은?**
Rehost는 그대로 옮기는 것이라 빠르지만 클라우드 이점이 적고, Replatform은 DB를 관리형으로 바꾸는 정도의 작은 변경으로 운영 부담을 줄인다. 데이터센터 철수 기한이 급하면 Rehost로 먼저 옮기고 최적화 계획을 같이 세우며, 여유가 있고 효과가 큰 부분(DB, 무상태 앱)은 Replatform한다.

**8. 온프레와 클라우드 연결을 어떻게 이중화하나?**
전용선을 서로 다른 접속 지점에 두 회선 이상 두거나, 전용선과 VPN을 함께 둔다. BGP로 경로 우선순위를 정해 평소엔 주 회선, 장애 시 자동으로 보조 회선으로 넘어가게 하고, 실제로 한 회선을 끊어 보는 시험을 한다. 대역이 겹치지 않게 IP 할당표를 먼저 만든다.

**9. 2TB 데이터베이스를 30분 이내 중단으로 옮기려면?**
전체 복사 후 CDC로 변경을 계속 따라가게 해서 원본 운영 중에 대상이 따라잡게 한다. 컷오버 때 쓰기를 짧게 멈추고, 복제 지연 0과 행 수·체크섬을 확인하고, 시퀀스를 맞춘 뒤 앱 연결을 바꾼다. 역방향 복제로 롤백 길을 열어 두고, 전체 절차를 리허설해서 시간을 잰다.

> 全件コピーの後、CDCで差分を同期し、切り替えの時だけ書き込みを短く止めます。件数とチェックサムで検証し、切り戻しの手順も事前にリハーサルします。

**10. 이전 후 비용이 예상보다 많이 나왔다. 어디부터 보나?**
과하게 잡은 인스턴스 크기, 꺼지지 않은 개발 리소스, 데이터 송신과 NAT 처리 비용, 아카이브로 안 내려간 스토리지 순서로 본다. 비용을 서비스·팀별로 나눠 볼 수 있게 태그가 붙어 있어야 원인을 찾을 수 있다.

## 정답

1. 블록 스토리지는 보통 한 AZ에 묶여 있어서 바로 붙일 수 없다. 스냅샷을 떠서 다른 AZ에 새 디스크를 만든 뒤 붙인다.
