## 질문

"L4 로드밸런서", "L7 방화벽"의 L은 뭘까? 그리고 VPN을 켜면 왜 큰 파일 업로드만 멈출까?

두 질문은 따로 놀지 않는다. 첫 번째는 "데이터가 어떤 층을 거쳐 포장되는가", 두 번째는 "그 포장이 한 번에 실을 수 있는 크기를 넘으면 어떻게 되는가"의 문제다. 이 글은 포장(캡슐화)의 구조를 먼저 보고, 포장의 크기 제한(MTU)에서 생기는 장애로 넘어간다.

## 계층: 일을 나눠 맡기

네트워크는 일을 층으로 나눈다. 각 층은 바로 아래층이 해 주는 일만 믿고 자기 일에 집중한다. 택배에 비유하면 이렇다. 보내는 사람은 물건만 잘 싸면 되고, 택배 회사는 주소만 보고 배송하면 되고, 트럭 기사는 다음 터미널까지만 가면 된다. 누구도 다른 사람 일을 다 알 필요가 없다.

| 층 (TCP/IP) | 하는 일 | 주소 |
|---|---|---|
| 애플리케이션 | 무엇을 주고받나 | URL, 호스트 이름 |
| 전송 | 어느 프로그램에게 | 포트 |
| 인터넷 | 어느 컴퓨터에게 | IP 주소 |
| 링크 | 바로 옆 장비에게 | MAC 주소 |

### 왜 두 개의 모델이 있나

OSI 7계층은 1980년대에 국제 표준 기구가 "이상적인 네트워크는 이렇게 나뉘어야 한다"며 만든 설명용 모델이다. 그런데 실제 인터넷은 그보다 먼저 미국 연구망에서 자란 TCP/IP 방식으로 퍼졌다. 결국 실제로 돌아가는 건 TCP/IP 4계층이고, OSI는 용어와 번호로 남았다.

| OSI | TCP/IP | 대표 |
|---|---|---|
| 7 응용, 6 표현, 5 세션 | 애플리케이션 | HTTP, DNS, SSH |
| 4 전송 | 전송 | TCP, UDP |
| 3 네트워크 | 인터넷 | IP, ICMP |
| 2 데이터 링크, 1 물리 | 링크 | 이더넷, Wi-Fi |

그래서 실무에서 "L4"라고 하면 IP와 포트까지만 보고 판단한다는 뜻이고, "L7"은 HTTP 내용(경로, 헤더, 쿠키)까지 열어 본다는 뜻이다. L2 스위치는 MAC 주소로, L3 스위치·라우터는 IP로 전달을 판단한다.

### 층을 나눠서 얻는 것

- **갈아 끼우기.** 링크가 유선이든 Wi-Fi든 LTE든 위의 IP와 TCP는 그대로다.
- **장애 나누기.** "IP까지는 닿는데(ping 됨) 포트가 안 열린다(연결 거부)"처럼 층별로 원인을 좁힐 수 있다.
- **장비 역할 나누기.** 스위치는 L2까지, 라우터는 L3까지, 로드밸런서는 L4 또는 L7까지 본다.

## 캡슐화: 내려가며 봉투를 씌운다

보낼 때는 위에서 아래로 내려가며 각 층이 자기 헤더를 앞에 붙인다. 받을 때는 아래에서 위로 올라가며 하나씩 벗긴다.

```
[HTTP 데이터]
[TCP|HTTP]          세그먼트
[IP|TCP|HTTP]       패킷
[ETH|IP|TCP|HTTP|FCS] 프레임
```

층마다 덩어리의 이름이 다르다. 이걸 통틀어 PDU(프로토콜 데이터 단위)라고 한다. 전송 계층은 세그먼트(UDP는 데이터그램), 인터넷 계층은 패킷, 링크 계층은 프레임이다. 면접에서 "패킷과 프레임의 차이"를 물으면 이 표를 떠올리면 된다.

받는 쪽은 각 헤더 안의 "다음 층이 누구인지" 정보를 보고 위로 넘긴다. 이더넷 헤더의 타입 필드는 "안에 든 게 IPv4다", IP 헤더의 프로토콜 필드는 "안에 든 게 TCP다", TCP 헤더의 목적지 포트는 "443번을 듣는 프로그램에게 줘라"를 알려 준다.

## 홉마다 일어나는 일: MAC은 바뀌고 IP는 남는다

라우터를 하나 지날 때마다 무슨 일이 생기는지 따라가 보자. 노트북 → 공유기 → 통신사 라우터 → … → 서버.

```
노트북 → 공유기
 출발 MAC: 노트북
 도착 MAC: 공유기
 출발 IP : 노트북
 도착 IP : 서버

공유기 → 다음 라우터
 출발 MAC: 공유기
 도착 MAC: 다음 라우터
 출발 IP : 공인 IP(NAT)
 도착 IP : 서버
```

라우터는 들어온 프레임을 벗겨 IP 헤더까지 확인하고, 라우팅 테이블로 다음 칸을 정한 뒤, **새 프레임으로 다시 씌워** 보낸다. 그래서 MAC 주소는 구간마다 바뀌고, IP 주소는 끝까지 같다. 예외는 NAT다. 공유기나 NAT 게이트웨이를 지날 때는 IP 주소도 바뀐다(06편).

라우터는 이 과정에서 IP 헤더의 TTL을 1 줄이고, 그에 맞춰 IP 헤더 체크섬을 다시 계산한다.

## IP 헤더에서 꼭 알아야 할 필드

IPv4 헤더는 옵션이 없으면 20바이트다. 전부 외울 필요는 없고, 장애와 관련된 것만 알면 된다.

| 필드 | 뜻 |
|---|---|
| 버전 | 4 또는 6 |
| 헤더 길이 | 4바이트 단위. 옵션 없으면 5(=20바이트) |
| 전체 길이 | 헤더+데이터 크기 |
| 식별자, 플래그, 오프셋 | 단편화용 |
| TTL | 남은 홉 수 |
| 프로토콜 | 안의 내용. TCP=6, UDP=17, ICMP=1 |
| 헤더 체크섬 | 헤더가 깨졌는지 |
| 출발지·목적지 IP | 각 4바이트 |

**TTL.** 라우터를 지날 때마다 1씩 줄고, 0이 되면 라우터가 패킷을 버리고 ICMP "시간 초과"를 돌려준다. 라우팅이 꼬여 패킷이 같은 곳을 영원히 도는 걸 막는 장치다. traceroute는 이걸 이용한다. TTL을 1, 2, 3으로 늘려 가며 보내고, 각 라우터가 돌려주는 "시간 초과"로 경로를 그린다.

**플래그의 DF와 MF.** DF(Don't Fragment)는 "쪼개지 마라", MF(More Fragments)는 "뒤에 조각이 더 있다"다. 아래 단편화와 PMTUD에서 핵심이 된다.

**헤더 길이.** 보통 5지만, IP 옵션이 붙으면 더 커진다. IP 옵션은 일반 통신에서 거의 안 쓴다. 그래서 일부 보안 대응에서는 "헤더 길이가 5보다 큰 TCP 패킷은 버린다" 같은 규칙으로 옵션을 악용하는 공격을 걸러 내기도 한다.

## TCP 헤더에서 꼭 알아야 할 필드

TCP 헤더도 옵션 없이 20바이트다.

| 필드 | 뜻 |
|---|---|
| 출발지·목적지 포트 | 어느 프로그램 |
| 시퀀스 번호 | 이 데이터의 위치 |
| 확인 번호 | 다음에 받을 위치 |
| 플래그 | SYN, ACK, FIN, RST 등 |
| 윈도 크기 | 더 받을 수 있는 양 |
| 체크섬 | 헤더+데이터 검사 |
| 옵션 | MSS, 윈도 배율, SACK 등 |

시퀀스 번호, 확인 번호, 윈도 크기는 03편에서 자세히 본다. 여기서 기억할 것은 **MSS가 TCP 헤더의 옵션으로 오간다**는 점이다. 연결을 맺는 SYN 패킷에 "나는 이만큼까지 받을 수 있다"를 실어 보낸다.

## 오류 검사: 체크섬과 CRC

층마다 깨진 데이터를 걸러 내는 장치가 있다.

- **이더넷의 FCS(CRC).** 프레임 끝에 붙는다. 다항식 나눗셈 기반이라 전선 잡음으로 생기는 연속된 비트 오류를 잘 잡는다. 계산은 네트워크 카드 하드웨어가 한다. 깨진 프레임은 조용히 버려진다.
- **IPv4 헤더 체크섬.** 헤더만 검사한다. 16비트씩 더해 1의 보수를 취하는 단순한 방식이다. 라우터가 TTL을 바꿀 때마다 다시 계산해야 해서 단순해야 했다.
- **TCP·UDP 체크섬.** 헤더와 데이터, 그리고 출발지·목적지 IP 일부(가상 헤더)까지 포함해 검사한다. 같은 1의 보수 합 방식이다.

체크섬은 계산이 싸지만 잡는 오류의 종류가 CRC보다 적다. 그래서 링크 구간은 CRC로 강하게, 끝과 끝은 체크섬으로 한 번 더 확인하는 구조다. IPv6는 아예 헤더 체크섬을 없앴다. 링크 층과 전송 층이 이미 검사하니, 라우터마다 다시 계산하는 비용을 줄이자는 판단이다.

## MTU와 MSS

**MTU**는 링크 한 구간이 한 번에 실을 수 있는 IP 패킷의 최대 크기다. 일반 이더넷은 1500바이트다.
**MSS**는 그 안에서 TCP가 실을 수 있는 데이터의 최대 크기다.

```
MSS = MTU − IP(20) − TCP(20)
    = 1500 − 40
    = 1460
```

TCP는 연결을 맺을 때 서로 MSS를 알려 주고, 둘 중 작은 값에 맞춰 데이터를 잘라 보낸다. 이렇게 TCP가 미리 잘라 주니까, 정상이라면 IP 층에서 다시 쪼갤 일이 없다.

여기서 주의할 점: MSS는 **양 끝의 링크**만 보고 정한다. 중간 경로에 더 작은 MTU가 있는지는 모른다. 문제는 거기서 시작된다.

## 단편화: 쪼개서라도 보내기

IPv4 라우터는 다음 구간의 MTU보다 큰 패킷을 받으면, DF 표시가 없을 때 패킷을 조각으로 쪼개서 보낸다. 조각들은 같은 식별자를 갖고, 오프셋으로 위치를 표시하고, 마지막 조각을 빼면 MF가 켜져 있다. 다시 합치는 건 **최종 목적지**가 한다.

단편화는 피하는 게 좋다.

- 조각 하나만 사라져도 전체 패킷을 다시 보내야 한다.
- 받는 쪽은 조각이 다 올 때까지 메모리에 들고 기다려야 한다.
- 방화벽이나 로드밸런서는 첫 조각에만 TCP 포트 정보가 있어서, 나머지 조각을 제대로 판단하지 못하기도 한다.

그래서 요즘 TCP는 거의 항상 DF를 켜고 보낸다. IPv6는 아예 중간 라우터가 쪼개지 못하게 했다. 쪼개야 한다면 보내는 쪽이 직접 한다.

## PMTUD: 경로의 가장 좁은 곳 찾기

DF가 켜진 큰 패킷이 MTU가 작은 구간을 만나면 어떻게 될까.

```
보내는 쪽 1500 DF →
 라우터: 다음 구간 1400
 → 패킷 버림
 ← ICMP "너무 크다,
         1400으로"
보내는 쪽: 크기 줄여 재전송
```

라우터는 패킷을 버리고 ICMP 메시지(IPv4는 타입 3 코드 4 "단편화 필요", IPv6는 Packet Too Big)에 다음 구간 MTU를 담아 돌려준다. 보낸 쪽 OS는 그 목적지에 대한 경로 MTU를 기억하고, 그 크기에 맞춰 다시 보낸다. 이걸 PMTUD(경로 MTU 탐색)라고 한다.

### PMTU 블랙홀

PMTUD는 ICMP가 돌아와야 동작한다. 그런데 "ICMP는 위험하니 다 막자"는 방화벽 설정이 흔하다. 그러면 이런 일이 생긴다.

- TCP 핸드셰이크는 패킷이 작아서 성공한다.
- 작은 요청과 응답도 잘 된다.
- 큰 응답이나 업로드에서 1500바이트짜리 패킷이 중간에서 조용히 사라진다. ICMP가 막혀 보낸 쪽은 이유를 모른다.
- 보낸 쪽은 같은 크기로 계속 재전송하다가 결국 타임아웃이 난다.

증상은 "연결은 되는데 특정 페이지만 끝까지 안 뜬다", "SSH 로그인은 되는데 `ls` 결과가 길면 멈춘다", "작은 API는 되는데 파일 업로드만 실패한다"다. 이걸 PMTU 블랙홀이라고 부른다.

### MSS 클램핑

ICMP를 열 수 없는 환경도 있다. 그럴 때 쓰는 방법이 MSS 클램핑이다. 터널 장비나 라우터가 지나가는 TCP SYN 패킷을 보고, 그 안의 MSS 옵션 값을 경로에 맞게 **강제로 낮춰** 버린다.

```
클라이언트 SYN: MSS 1460
 → VPN 장비가 고쳐 씀
   MSS 1360
 → 서버는 1360에 맞춰 보냄
```

양 끝이 처음부터 작은 크기로 보내니 경로 MTU 문제를 만나지 않는다. 리눅스에서는 iptables의 TCPMSS 규칙이 이 일을 한다. 단점은 TCP에만 통한다는 것이다. UDP는 MSS 협상이 없어서 이 방법으로 고칠 수 없다.

## 터널과 VPN에서 MTU가 줄어드는 이유

터널은 패킷을 통째로 다른 패킷 안에 넣는다. 바깥에 헤더가 하나 더 붙으니, 안쪽 패킷이 쓸 수 있는 크기는 그만큼 줄어든다.

```
바깥 MTU 1500
[바깥IP|터널헤더|안쪽 패킷]
 안쪽 패킷 = 1500 − 바깥 헤더들
```

IPsec VPN, WireGuard, GRE, VXLAN 같은 오버레이 네트워크 모두 마찬가지다. 줄어드는 양은 프로토콜과 암호화 방식에 따라 다르다. 그래서 터널 인터페이스는 보통 MTU를 1500보다 작게 설정한다. 이 설정이 빠지면 앞에서 본 블랙홀 증상이 그대로 나온다. 쿠버네티스의 일부 오버레이 CNI도 파드 인터페이스 MTU를 노드보다 작게 잡는 이유가 이것이다.

## 자주 막히는 장애 사례

**1. VPN 연결 후 일부 사이트만 안 뜬다.**
- 증상: 접속은 시작되는데 페이지가 반쯤에서 멈춘다.
- 원인: 터널로 MTU가 줄었는데, 경로 어딘가에서 ICMP가 막혀 PMTUD가 실패.
- 조치: 터널 장비에 MSS 클램핑, 또는 필요한 ICMP 허용.

**2. 서버 간 대용량 전송만 실패한다.**
- 증상: 헬스체크와 작은 API는 정상, 백업이나 파일 복사만 타임아웃.
- 원인: 한쪽이 점보 프레임(9000대) MTU, 중간 구간이 1500. 큰 패킷이 사라진다.
- 조치: 경로의 MTU를 맞추거나, 다른 네트워크로 나가는 구간은 1500 기준으로.

**3. 방화벽 규칙을 강화한 뒤 간헐적 실패.**
- 증상: 규칙 변경 후 특정 고객만 업로드 실패.
- 원인: ICMP를 통째로 막아 그 고객 경로의 PMTUD가 깨짐.
- 조치: ICMP 중 "단편화 필요"와 IPv6 Packet Too Big은 허용 목록에 둔다.

**4. ping은 되는데 서비스가 안 된다.**
- 증상: ping 성공, 웹 접속 실패.
- 원인: ping은 L3(ICMP)만 확인한다. 포트가 막혔거나(L4) 앱이 죽었을 수 있다(L7).
- 조치: 층별로 확인. `nc -vz 호스트 포트` 로 L4, `curl` 로 L7.

## 클라우드에서는

- AWS VPC 안에서는 점보 프레임(MTU 9001)을 쓴다. 하지만 인터넷 게이트웨이, VPN, 다른 리전과의 연결을 지나면 1500 이하로 줄어든다. 같은 VPC 안에서 되던 대용량 전송이 밖으로 나가면 다르게 동작할 수 있다.
- GCP VPC는 기본 MTU가 1460이고, VPC를 만들 때 더 큰 값으로 바꿀 수 있다.
- 클라우드 사이를 VPN으로 이을 때 양쪽 MTU 기본값이 다르면 PMTU 문제가 생기기 쉽다. 터널 MTU와 MSS 클램핑을 먼저 확인한다.
- 보안 그룹·방화벽 규칙에서 ICMP를 통째로 막지 않는 것이 이 장애를 막는 가장 쉬운 방법이다.
- "L4 로드밸런서(NLB 등)는 TCP 내용을 안 보고 넘긴다, L7(ALB 등)은 HTTP를 열어 본다"는 차이가 곧 이 글의 계층 이야기다.

## 집에서 해보기 (지하철에서는 읽기만)

```bash
# 내 인터페이스 MTU
ifconfig en0 | grep mtu

# DF 켜고 1472바이트 데이터
# 1472+ICMP 8+IP 20=1500
ping -D -s 1472 -c 2 example.com

# 1501바이트: 실패해야 정상
ping -D -s 1473 -c 2 example.com

# TTL 1부터 경로 그리기
traceroute -n example.com

# 포트까지 열렸나 (L4 확인)
nc -vz example.com 443
```

1472가 되고 1473이 실패하면 경로 MTU가 1500이다. VPN을 켜고 다시 해 보면 통과하는 최대 크기가 줄어든 게 보인다. 크기를 조금씩 줄여 가며 통과하는 최대값을 찾으면, 그게 그 경로의 MTU에서 28을 뺀 값이다.

## 면접 한 줄 답

> MTUは1回で送れるIPパケットの最大サイズで、MSSはその中のTCPデータの最大サイズです。経路の途中でMTUが小さく、ICMPが遮断されていると、大きい通信だけが止まることがあります。

MTU는 한 번에 보낼 수 있는 IP 패킷의 최대 크기이고, MSS는 그 안의 TCP 데이터 최대 크기입니다. 경로 중간 MTU가 작고 ICMP가 막혀 있으면 큰 통신만 멈출 수 있습니다.

**꼬리질문 1. 라우터를 지날 때 바뀌는 것과 안 바뀌는 것은?**
MAC 주소는 구간마다 바뀌고, IP 주소는 NAT가 없다면 끝까지 같습니다. 라우터는 TTL을 1 줄이고 IP 헤더 체크섬을 다시 계산합니다.

**꼬리질문 2. ICMP를 열 수 없는 환경이면 어떻게 하나요?**
터널 장비나 라우터에서 TCP SYN의 MSS 값을 경로에 맞게 낮추는 MSS 클램핑을 씁니다. 다만 UDP에는 적용되지 않습니다.

**꼬리질문 3. L4와 L7 로드밸런서의 차이는?**
L4는 IP와 포트까지만 보고 연결 단위로 넘기고, L7은 HTTP 경로나 헤더까지 열어 보고 요청 단위로 나눕니다.

## 정답

1. 패킷은 인터넷 계층(IP), 프레임은 링크 계층(이더넷)의 PDU다. 전송 계층은 세그먼트(UDP는 데이터그램)다.
2. 라우팅이 꼬여 패킷이 영원히 도는 걸 막으려고 필요하다. 라우터마다 1씩 줄고 0이면 버려진다. traceroute는 TTL을 1, 2, 3으로 늘려 보내며 각 라우터가 돌려주는 "시간 초과" 메시지로 경로를 알아낸다.
3. 1500에서 IPv4 헤더 20바이트와 TCP 헤더 20바이트를 뺀 값이다(옵션이 없을 때).
4. 증상은 연결과 작은 요청은 되는데 큰 응답이나 업로드만 멈추는 것이다. 원인은 경로 중간 MTU가 더 작은데 ICMP가 막혀 보낸 쪽이 크기를 줄이라는 신호를 못 받는 것이다.
5. 패킷을 쪼개는 단편화와 헤더 체크섬 재계산을 하지 않는다. 쪼개야 하면 보내는 쪽이 하고, 오류 검사는 링크·전송 계층에 맡긴다.
