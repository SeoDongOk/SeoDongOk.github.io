## 질문

DB 접속에 `sslmode=require` 를 걸었다. 이제 안전할까?

답: 엿보기는 막지만 **가짜 서버는 못 막는다.** 왜 그런지가 이 글의 핵심이다.

## TLS가 지키는 세 가지

| 위협 | 지키는 것 | 방법 |
|---|---|---|
| 엿보기 (도청) | 기밀성 | 암호화 |
| 중간에서 바꾸기 (변조) | 무결성 | 메시지 인증 |
| 가짜 서버 (위장) | 인증 | 인증서 검증 |

셋 중 하나라도 빠지면 안전하지 않다. 특히 세 번째를 빼먹는 경우가 많다.

## 대칭키와 공개키를 같이 쓰는 이유

- **대칭키:** 같은 키로 잠그고 연다. 빠르다. 문제는 "그 키를 처음에 어떻게 안전하게 나누나".
- **공개키:** 공개키로 잠근 건 개인키로만 열린다. 처음 보는 상대와도 안전하게 합의할 수 있다. 대신 느리다.

그래서 TLS는 **처음에 공개키 방식으로 대칭키를 합의하고, 실제 데이터는 대칭키로** 암호화한다. 요즘은 키를 직접 보내지 않고, 양쪽이 각자 값을 섞어 같은 키를 만들어 내는 방식(ECDHE)을 쓴다. 이렇게 하면 나중에 서버 개인키가 털려도 지난 대화는 풀 수 없다(전방 비밀성).

## TLS 1.3 핸드셰이크

```
클라이언트                                서버
ClientHello  →
 (지원하는 암호 방식, 키 합의용 값, SNI=example.com)
                              ←  ServerHello (고른 방식, 키 합의용 값)
                              ←  인증서, 서명, Finished   ← 여기부터 암호화
인증서 검증
Finished     →
HTTP 요청    →   (암호화)
```

TLS 1.2는 2 RTT, 1.3은 1 RTT다. 다시 접속할 때는 0 RTT도 가능하다.

**SNI:** 서버 하나(IP 하나)가 여러 도메인을 서비스할 때, 클라이언트가 "나는 example.com 에 왔다"를 처음에 알려 줘야 서버가 맞는 인증서를 꺼낼 수 있다. 로드밸런서 하나에 인증서 여러 개를 붙일 수 있는 이유다.

## 인증서 검증이 확인하는 것

인증서는 "이 공개키는 example.com 의 것"이라고 인증기관(CA)이 서명한 문서다. 클라이언트는 다음을 확인한다.

1. **체인:** 서버 인증서 → 중간 CA → 루트 CA로 서명이 이어지고, 루트가 내 OS·브라우저에 미리 들어 있는 신뢰 목록에 있는가.
2. **이름:** 인증서의 이름(SAN)이 내가 접속한 도메인과 같은가.
3. **기간:** 만료되지 않았는가.
4. **소유:** 서버가 그 인증서의 개인키를 정말 갖고 있는가(핸드셰이크 중 서명으로 증명).

서버가 중간 CA 인증서를 빠뜨리고 보내면 브라우저는 알아서 채우기도 하지만, curl이나 앱은 실패한다. "브라우저는 되는데 앱만 안 된다"의 흔한 원인이다.

## 처음 질문의 답: require vs verify-full

PostgreSQL 기준이다.

| sslmode | 암호화 | 인증서 체인 확인 | 호스트 이름 확인 | 가짜 서버 차단 |
|---|---|---|---|---|
| require | O | X | X | X |
| verify-ca | O | O | X | 일부 |
| verify-full | O | O | O | O |

`require` 는 "암호화만 하자"다. 중간에서 누군가 자기 인증서로 대신 받으면, 클라이언트는 그 가짜와 암호화된 대화를 한다. 암호화는 됐지만 상대가 틀렸다. 내부망이라도 중요한 구간은 `verify-full` 로, 그러려면 서버 인증서를 발급한 CA를 클라이언트에 배포해야 한다.

## 직접 확인 (맥 터미널)

```bash
# 인증서 체인과 협상 결과 보기
openssl s_client -connect example.com:443 -servername example.com -showcerts < /dev/null

# 인증서의 이름(SAN)과 기간만
openssl s_client -connect example.com:443 -servername example.com < /dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName

# TLS 버전 지정해서 붙어 보기
curl -sv --tlsv1.3 https://example.com -o /dev/null 2>&1 | grep -E 'SSL connection|subject|issuer'
```

`-servername` 을 빼면 SNI 없이 붙는다. 여러 도메인을 서비스하는 서버라면 다른 인증서가 나오는 걸 볼 수 있다.

## 클라우드에서는

- **TLS 종단 위치를 정한다.** 보통 로드밸런서에서 끝내고(ACM, Google 관리형 인증서) 뒤로는 평문 또는 다시 TLS. 구간마다 "어디서 끝나고 어디가 평문인가"를 그림으로 그려 두는 게 보안 점검의 시작이다.
- **인증서 만료는 장애다.** 관리형 인증서로 자동 갱신하거나, 만료 알람을 건다.
- **서비스 간 통신은 mTLS**(양쪽 모두 인증서 제시)로 서로를 인증할 수 있다. 서비스 메시가 이걸 대신 해 준다.

## 면접 한 줄 답

> TLSは公開鍵暗号で共通鍵を合意し、データは共通鍵で暗号化します。暗号化だけでなく、証明書の検証でなりすましを防ぐことが重要で、DB接続でもverify-fullを使うべきです。

TLS는 공개키 암호로 대칭키를 합의하고 데이터는 대칭키로 암호화합니다. 암호화뿐 아니라 인증서 검증으로 위장을 막는 게 중요하고, DB 접속에도 verify-full을 써야 합니다.
