## 트래픽 비율을 어디서 나눌까

두 환경(예: 두 클라우드)으로 트래픽을 9:1, 5:5처럼 나누는 방법은 크게 둘이다.

| | DNS 가중치 | L7 프록시 가중치 |
|---|---|---|
| 단위 | DNS 조회 단위 | **요청 단위** |
| 반영 시간 | TTL과 클라이언트 캐시에 좌우 | 설정을 바꾸는 즉시 |
| 관측 | 어렵다 | 프록시가 목적지별 요청 수·오류를 센다 |
| 대가 | 없음 | 프록시가 경로에 끼어 **단일 장애점**과 홉 하나가 생긴다 |

"요청 몇 건이 어디로 갔고 몇 건이 실패했나"를 근거로 비율을 올리려면 프록시 쪽이 맞다. 대신 프록시 자체의 이중화가 숙제로 남는다([10편](/blog/2026-11-09-infra-study-10-entrypoint-ha)).

## Envoy 구조

```
리스너(포트 80) → 라우트(Host·경로 매칭) → 클러스터(목적지 묶음) → 엔드포인트
```

가중치는 라우트에서 여러 클러스터로 나눈다.

```yaml
route:
  weighted_clusters:
    clusters:
      - { name: env_a, weight: 90 }
      - { name: env_b, weight: 10 }
```

## 재시작 없이 바꾸기: 동적 설정 (xDS)

Envoy는 설정을 xDS라는 API로 받는다. 제어 서버를 두는 대신 **파일 기반 동적 설정**도 쓸 수 있다. 라우트 파일을 원자적으로 바꿔 쓰면(임시 파일에 쓰고 `rename`) Envoy가 감지해 다시 읽는다. 작은 관리 API가 이 파일을 다시 쓰게 하면 "가중치 변경 API"가 된다.

설정이 거부됐는지 꼭 확인한다. 관리 포트의 통계에서 `rds…update_rejected` 같은 카운터가 늘면 새 설정이 적용되지 않은 것이다.

## 헬스체크와 자동 전환

- **능동 헬스체크:** Envoy가 주기적으로 `/healthz`를 찔러 본다. 연속 N번 실패하면 그 엔드포인트를 뺀다.
- **이상치 감지(outlier detection):** 실제 요청에서 5xx가 연속되면 잠시 뺀다.
- **aggregate 클러스터:** 우선 클러스터가 전부 비정상이면 다음 클러스터로 넘긴다. "평소에는 A, A가 죽으면 B"를 표현할 수 있다.

헬스체크 간격과 실패 횟수가 전환 시간을 정한다. 2초 간격·2회 실패면 감지에만 최소 수 초가 걸린다.

## 백엔드가 잠깐 멈출 때: 타임아웃과 재시도

DB 전환처럼 백엔드가 **수 초간 의도적으로 응답을 멈추는** 상황이 있다. 이때 프록시 설정이 짧으면 손님은 504를 본다.

| 설정 | 뜻 |
|---|---|
| `timeout` (route) | 요청 전체에 허용하는 시간 (재시도 포함) |
| `per_try_timeout` | 시도 한 번에 허용하는 시간 |
| `num_retries`, `retry_on` | 몇 번, 어떤 실패에 다시 보낼지 |

예를 들어 시도당 5초에 백엔드가 9초 멈추면, 첫 시도는 5초에 끊기고 재시도도 멈춘 백엔드에 걸려 결국 504가 난다. 멈춤 시간보다 시도당 시간을 길게(예: 30초) 잡으면 첫 시도가 기다렸다가 성공한다.

**재시도는 공짜가 아니다.** 쓰기 요청을 다시 보내면 같은 쓰기가 두 번 일어날 수 있다.

- 연결 실패·리셋처럼 "서버가 받지 못했을 가능성이 높은" 실패에만 재시도한다.
- 쓰기 API는 **멱등 키**(`Idempotency-Key`)를 받아, 같은 키로 두 번 와도 한 번만 처리하게 만든다.
