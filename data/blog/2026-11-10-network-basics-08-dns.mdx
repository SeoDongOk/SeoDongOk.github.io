## 질문

DNS 레코드를 새 서버로 바꿨다. 그런데 일부 사용자는 한 시간째 옛 서버로 간다. 왜일까?

답: **캐시**다. 그리고 그 시간은 내가 정해 둔 TTL이 결정한다.

## 두 종류의 DNS 서버

| | 재귀 리졸버 | 권한(권위) 서버 |
|---|---|---|
| 하는 일 | 사용자 대신 끝까지 물어서 답을 가져온다 | 자기 도메인의 정답을 갖고 있다 |
| 예 | 통신사 DNS, 8.8.8.8, 1.1.1.1, VPC 리졸버 | Route 53 호스팅 영역, Cloud DNS 영역 |
| 캐시 | 한다 | 안 한다 (원본) |

## 조회 순서

`www.example.com` 을 처음 물을 때, 리졸버는 위에서부터 내려간다.

```
리졸버 → 루트 서버:        www.example.com?  → ".com 담당은 저쪽"
리졸버 → .com 서버:        www.example.com?  → "example.com 담당은 저쪽 (NS)"
리졸버 → example.com 서버: www.example.com?  → "93.184.215.14 (A), TTL 300"
리졸버 → 사용자:           93.184.215.14
```

이 결과를 리졸버도, OS도, 브라우저도 TTL 동안 캐시한다. 다음 사람은 루트까지 안 가고 바로 답을 받는다. DNS가 빠른 이유이자, 바꿔도 바로 반영이 안 되는 이유다.

DNS 조회는 보통 UDP 53번 포트를 쓴다. 응답이 크면 TCP로 다시 묻는다.

## 자주 쓰는 레코드

| 레코드 | 뜻 | 예 |
|---|---|---|
| A / AAAA | 이름 → IPv4 / IPv6 | `api.example.com → 203.0.113.10` |
| CNAME | 이름 → 다른 이름 (별명) | `www → example.cdn.net` |
| NS | 이 영역의 권한 서버 | `example.com → ns-1.awsdns...` |
| MX | 메일 서버 | |
| TXT | 아무 글자 (도메인 소유 확인, SPF) | |

CNAME은 도메인 맨 꼭대기(`example.com` 자체)에는 못 쓴다. 그래서 클라우드는 꼭대기에서도 로드밸런서를 가리킬 수 있는 자체 기능(Route 53 Alias 등)을 준다.

## TTL과 전환 계획

TTL이 3600(1시간)이면, 레코드를 바꾼 직후에도 최대 1시간 동안 옛 답을 가진 사람이 있다. 그래서 DNS로 서버를 옮길 때는 순서가 있다.

1. **전환 하루 전쯤 TTL을 60초로 낮춘다.** 이전 TTL이 다 지날 때까지 기다린다.
2. 레코드를 새 주소로 바꾼다. 1분 안에 대부분 넘어온다.
3. 문제없으면 TTL을 다시 올린다.

그래도 TTL을 무시하고 오래 캐시하는 클라이언트(일부 JVM 앱, 오래된 라이브러리)가 있다. **옛 서버를 바로 끄지 말고 트래픽이 0이 될 때까지 남겨 두는** 이유다. 즉시 전환이 꼭 필요하면 DNS 대신 로드밸런서나 프록시의 가중치로 트래픽을 옮긴다.

## 직접 확인 (맥 터미널)

```bash
# 답과 남은 TTL (두 번째 열의 숫자)
dig example.com A +noall +answer

# 루트부터 내려가는 전체 과정
dig +trace www.example.com

# 리졸버를 바꿔서 물어보기 (전파 확인)
dig @8.8.8.8 example.com +short
dig @1.1.1.1 example.com +short

# 권한 서버에 직접 (캐시 없는 정답)
dig NS example.com +short

# 맥 DNS 캐시 비우기
sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder
```

같은 질문을 두 번 하면 두 번째의 TTL이 줄어 있다. 캐시에서 나온 답이라는 뜻이다.

## 클라우드에서는

- **사설 DNS:** VPC 안에서만 보이는 영역(Route 53 Private Hosted Zone, Cloud DNS 비공개 영역)을 만들어 `db.internal` 같은 이름을 쓴다. IP가 바뀌어도 앱 설정은 그대로다.
- **하이브리드:** 회사 데이터센터와 VPC가 서로의 이름을 풀어야 하면 조건부 전달(Route 53 Resolver 엔드포인트, Cloud DNS 전달 영역)을 설정한다.
- **장애 조치 레코드:** 헬스체크와 묶어서, 주 서버가 죽으면 보조 주소를 답하게 할 수 있다. 다만 위의 TTL 한계는 그대로라서 즉시 전환은 아니다.
- 쿠버네티스 안에서는 CoreDNS가 `서비스이름.네임스페이스.svc.cluster.local` 을 ClusterIP로 풀어 준다.

## 면접 한 줄 답

> DNSはリゾルバがルートから順に権威サーバーに問い合わせて名前を解決し、TTLの間キャッシュします。切り替えの前にTTLを短くしておき、古いサーバーはトラフィックがなくなるまで残します。

DNS는 리졸버가 루트부터 차례로 권한 서버에 물어 이름을 풀고 TTL 동안 캐시합니다. 전환 전에 TTL을 줄여 두고, 옛 서버는 트래픽이 없어질 때까지 남겨 둡니다.
