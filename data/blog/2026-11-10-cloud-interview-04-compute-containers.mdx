## 이 글에서 답할 면접 질문

- VM, 컨테이너, 서버리스 중 무엇을 고를지 어떤 기준으로 판단하는가?
- 컨테이너가 VM보다 가벼운 이유를 리눅스 기능으로 설명해 보라.
- 쿠버네티스에서 `kubectl apply` 를 하면 파드가 뜨기까지 무슨 일이 일어나는가?
- liveness, readiness, startup 프로브는 각각 언제 쓰는가?
- requests와 limits를 어떻게 정하는가? OOMKilled와 CPU 스로틀링은 왜 생기는가?
- 파드가 Pending에서 멈췄다. 어디부터 보겠는가?
- EKS, GKE, AKS를 고를 때 무엇이 다른가?
- 서버리스의 콜드 스타트는 왜 생기고 어떻게 줄이는가?

## 개념과 배경

### 세 가지 실행 방식

애플리케이션을 클라우드에서 돌리는 방식은 크게 셋이다. 무엇을 내가 관리하고 무엇을 맡기느냐의 차이다.

| | VM | 컨테이너 (쿠버네티스) | 서버리스 |
|---|---|---|---|
| 내가 관리 | OS부터 위 전부 | 이미지와 배포 설정 | 코드(또는 이미지) |
| 시작 시간 | 분 단위 | 초 단위 | 밀리초~초 (콜드 스타트) |
| 확장 | 인스턴스 그룹 | 파드·노드 오토스케일 | 요청에 따라 자동, 0까지 |
| 과금 | 켜 둔 시간 | 노드를 켜 둔 시간 | 요청·실행 시간 |
| 잘 맞는 일 | 레거시, 특수 OS·커널, 라이선스 | 여러 서비스를 표준화해 운영 | 이벤트 처리, 트래픽이 들쭉날쭉한 API |

고르는 질문은 이렇다.

1. **OS나 커널을 직접 만져야 하는가?** 그렇다면 VM.
2. **오래 떠 있는 프로세스, 상태, 특수 네트워크가 필요한가?** 그렇다면 VM이나 컨테이너.
3. **트래픽이 0인 시간이 길고, 요청 단위로 짧게 끝나는가?** 그렇다면 서버리스가 싸고 편하다.
4. **서비스가 많고 팀이 여럿인가?** 공통된 배포·관측·보안 방식을 강제하려면 쿠버네티스 같은 플랫폼이 유리하다. 다만 운영할 사람이 있어야 한다.

정답은 하나가 아니다. 면접에서는 "요구 사항 → 기준 → 선택 → 포기한 것"을 말하는 것이 중요하다.

## 깊게 1 — 컨테이너는 리눅스 기능의 조합이다

컨테이너는 가상 머신이 아니다. **같은 커널을 쓰는 프로세스에게 "자기만의 세상"이 있는 것처럼 보이게 하는** 리눅스 기능의 묶음이다.

### 네임스페이스: 무엇이 보이는가

네임스페이스는 프로세스가 볼 수 있는 범위를 나눈다.

| 네임스페이스 | 나누는 것 |
|---|---|
| PID | 프로세스 번호. 컨테이너 안의 첫 프로세스가 1번 |
| NET | 네트워크 인터페이스, IP, 라우팅, 포트 |
| MNT | 파일 시스템 마운트 |
| UTS | 호스트 이름 |
| IPC | 프로세스 간 통신 자원 |
| USER | 사용자 ID 매핑 (안의 root를 밖의 일반 사용자로) |
| cgroup | cgroup 계층의 보이는 범위 |

컨테이너 안에서 `ps` 를 치면 자기 프로세스만 보이고, 자기 IP와 포트를 가진 것처럼 보이는 이유다. 쿠버네티스 파드는 여러 컨테이너가 **NET 네임스페이스를 공유**하는 묶음이라, 같은 파드 안 컨테이너끼리는 `localhost` 로 통신한다.

### cgroups: 얼마나 쓸 수 있는가

cgroups는 프로세스 묶음이 쓸 수 있는 CPU, 메모리, I/O, 프로세스 수를 제한하고 측정한다. 요즘 배포판과 쿠버네티스는 계층이 하나로 통일된 cgroup v2를 쓴다.

- **메모리 한도**를 넘으면 커널의 OOM 킬러가 그 cgroup 안의 프로세스를 죽인다. 쿠버네티스에서 `OOMKilled` 로 보이는 것이다.
- **CPU 한도**는 일정 주기마다 쓸 수 있는 CPU 시간 할당량으로 걸린다. 할당량을 다 쓰면 그 주기의 나머지 동안 멈춘다. 이게 **스로틀링**이다. 죽지는 않지만 응답 지연이 튄다.

### 오버레이 파일 시스템: 이미지가 가벼운 이유

컨테이너 이미지는 **읽기 전용 레이어**의 쌓음이다. 실행할 때 맨 위에 쓰기 가능한 얇은 레이어를 하나 더 얹는다(OverlayFS).

```
[쓰기 레이어]  ← 컨테이너마다
[앱 레이어]
[라이브러리 레이어]  ← 이미지,
[베이스 OS 레이어]     여러 컨테이너 공유
```

같은 베이스 이미지를 쓰는 컨테이너 100개가 베이스 레이어를 한 벌만 디스크에 둔다. 컨테이너 안에서 파일을 고치면 위 레이어로 복사한 뒤 고친다(copy-on-write). 컨테이너가 사라지면 쓰기 레이어도 사라진다. 그래서 **남겨야 할 데이터는 볼륨에** 둔다.

### 런타임 사슬

`docker run` 이나 쿠버네티스가 컨테이너를 띄울 때의 사슬은 이렇다.

```
kubelet
  │ CRI (gRPC)
containerd
  │ 이미지 받기, 스냅샷
runc (OCI 런타임)
  │ 네임스페이스·cgroup 설정
컨테이너 프로세스
```

- **CRI**: 쿠버네티스가 런타임과 대화하는 표준 인터페이스. 쿠버네티스는 예전의 Docker 전용 연결(dockershim)을 없애고 CRI를 지원하는 containerd나 CRI-O를 직접 쓴다. Docker로 만든 이미지는 OCI 표준이라 그대로 돈다.
- **runc**: OCI 런타임 표준의 구현. 실제로 리눅스 기능을 호출해 프로세스를 컨테이너로 만든다.

### 왜 VM보다 가벼운가, 그리고 한계

VM은 하이퍼바이저 위에 **게스트 OS 커널 전체**를 부팅한다. 컨테이너는 호스트 커널을 공유하는 **프로세스**일 뿐이다. 그래서 시작이 빠르고, 메모리를 적게 쓰고, 한 노드에 많이 올라간다.

대가는 **격리의 강도**다. 커널을 공유하므로 커널 취약점 하나가 모든 컨테이너에 영향을 준다. 특권 컨테이너나 호스트 경로 마운트는 사실상 호스트 권한이다. 그래서 신뢰할 수 없는 코드를 돌리는 환경은 격리를 더한다.

- **gVisor**: 사용자 공간에서 커널 시스템 호출을 대신 처리해 호스트 커널 노출을 줄인다(GKE Sandbox가 이걸 쓴다).
- **Firecracker**: 아주 가벼운 마이크로 VM. 컨테이너처럼 빨리 뜨지만 VM 수준으로 격리한다(AWS Lambda와 Fargate의 기반 기술로 알려져 있다).
- 기본 보안 설정: 루트가 아닌 사용자로 실행, 읽기 전용 루트 파일 시스템, 권한(capabilities) 제거, seccomp 기본 프로파일, 쿠버네티스 Pod Security Standards의 restricted 수준.

## 깊게 2 — 이미지와 레지스트리

좋은 이미지의 조건:

1. **작다.** 멀티 스테이지 빌드로 빌드 도구는 버리고 실행에 필요한 것만 남긴다. distroless나 경량 베이스를 쓴다. 작을수록 받는 시간과 공격 표면이 줄어든다.
2. **재현 가능하다.** 베이스 이미지와 의존성 버전을 고정한다. 배포는 태그가 아니라 다이제스트로 한다.
3. **비밀이 없다.** 빌드 중에 넣은 비밀은 레이어에 남는다. 지워도 이전 레이어에 있다.
4. **레이어 순서를 캐시에 맞춘다.** 잘 안 바뀌는 것(의존성 설치)을 위에, 자주 바뀌는 것(소스 코드)을 아래에 둔다.

레지스트리는 클라우드마다 ECR, Artifact Registry, ACR이 있다. 운영 관점에서 볼 것:

- **같은 리전에 둔다.** 노드가 이미지를 받는 시간과 전송 비용이 줄어든다.
- **스캔과 정리 정책.** 푸시 때 취약점 스캔, 오래된 이미지 자동 삭제.
- **사설 접근.** 노드가 인터넷을 거치지 않고 프라이빗 엔드포인트로 받게 한다. NAT 비용도 준다.
- **도커 허브 같은 공용 레지스트리 의존을 줄인다.** 받기 횟수 제한과 가용성 문제가 있으니 미러나 풀스루 캐시를 둔다.

## 깊게 3 — 쿠버네티스 구조

### 컨트롤 플레인과 노드

```
컨트롤 플레인
 ├ kube-apiserver   모든 요청의 입구
 ├ etcd             클러스터 상태 저장
 ├ kube-scheduler   파드를 노드에 배치
 └ controller-manager 상태 맞추기

노드
 ├ kubelet          파드 실행 책임자
 ├ 컨테이너 런타임   containerd 등
 └ kube-proxy       Service 규칙
```

- **API 서버**: 유일한 입구다. kubectl도, 컨트롤러도, kubelet도 전부 API 서버와만 대화한다. 인증·인가(RBAC)·승인 제어(admission)가 여기서 일어난다.
- **etcd**: 분산 키-값 저장소. 클러스터의 "원하는 상태"와 "현재 상태"가 전부 여기 있다. etcd를 잃으면 클러스터를 잃는다. 관리형 쿠버네티스에서는 클라우드가 운영한다.
- **스케줄러**: 아직 노드가 정해지지 않은 파드를 보고, 자원·조건이 맞는 노드를 골라 기록한다. 실제 실행은 하지 않는다.
- **컨트롤러 매니저**: Deployment, ReplicaSet, Node, Job 같은 컨트롤러들이 돈다.
- **kubelet**: 자기 노드에 배정된 파드를 보고 런타임에 실행시키고, 상태를 API 서버에 보고한다.
- **kube-proxy**: Service의 가상 IP로 온 트래픽을 실제 파드로 보내는 규칙(iptables나 IPVS)을 노드에 만든다. 일부 CNI(eBPF 기반)는 이 역할을 대신한다.

플러그인 표준 세 개도 알아 둔다.

| 표준 | 하는 일 | 예 |
|---|---|---|
| CRI | 컨테이너 실행 | containerd, CRI-O |
| CNI | 파드 네트워크 | VPC CNI, Calico, Cilium |
| CSI | 스토리지 연결 | EBS, Persistent Disk, Azure Disk 드라이버 |

### 조정 루프: 쿠버네티스의 본질

쿠버네티스는 명령을 실행하는 시스템이 아니라 **상태를 맞추는 시스템**이다. 컨트롤러는 끝없이 반복한다.

```
원하는 상태 읽기
현재 상태 관찰
차이가 있으면 줄이는 행동
다시 처음으로
```

`replicas: 3` 인 Deployment에서 파드 하나가 죽으면, 누가 명령하지 않아도 ReplicaSet 컨트롤러가 "3개여야 하는데 2개다"를 보고 하나를 만든다. 노드가 죽어도 같다. 이 성질 때문에 **선언형**(무엇이어야 하는지를 적는다) 운영과 GitOps가 자연스럽다.

### kubectl apply부터 파드 실행까지

1. kubectl이 Deployment를 API 서버에 보낸다. 인증, 인가, 승인 제어(기본값 채우기, 정책 검사)를 거쳐 etcd에 저장된다.
2. Deployment 컨트롤러가 ReplicaSet을 만든다.
3. ReplicaSet 컨트롤러가 파드 객체 3개를 만든다. 아직 노드가 없다(Pending).
4. 스케줄러가 각 파드에 노드를 고르고 기록한다.
5. 그 노드의 kubelet이 자기 파드를 발견하고, CNI로 네트워크를 만들고, CSI로 볼륨을 붙이고, 런타임으로 이미지를 받아 컨테이너를 띄운다.
6. 프로브가 통과하면 파드가 Ready가 되고, EndpointSlice에 IP가 등록되어 Service 트래픽을 받기 시작한다.

이 흐름을 알면 장애 위치를 바로 짚는다. Pending이면 4번(스케줄링), ContainerCreating에서 멈추면 5번(네트워크·볼륨·이미지), Running인데 트래픽이 안 오면 6번(프로브·Service)이다.

## 깊게 4 — 프로브와 파드 수명

| 프로브 | 실패하면 | 쓰는 곳 |
|---|---|---|
| liveness | 컨테이너 재시작 | 프로세스가 멈춰서 스스로 못 살아나는 상태 |
| readiness | Service에서 빠짐 (재시작 안 함) | 아직 준비 안 됨, 잠깐 과부하 |
| startup | 통과 전까지 다른 프로브 보류 | 시작이 오래 걸리는 앱 |

자주 하는 실수:

- **liveness에 외부 의존성(DB)을 넣는다.** DB가 잠깐 느려지면 모든 파드가 재시작되어 장애가 커진다. liveness는 "이 프로세스 자체가 살아 있나"만 본다.
- **startup 없이 liveness를 짧게 잡는다.** 시작이 느린 앱이 준비되기 전에 계속 죽는다(재시작 반복).
- **readiness가 없다.** 시작 직후 준비 안 된 파드로 트래픽이 가서 에러가 난다.

종료도 중요하다. 파드를 지울 때 쿠버네티스는 SIGTERM을 보내고, `terminationGracePeriodSeconds` 동안 기다린 뒤 SIGKILL을 보낸다. 동시에 엔드포인트에서 빠지는데, 이 두 일이 **동시에** 일어나서 빠지기 직전 잠깐 트래픽이 더 올 수 있다. 그래서 앱은 SIGTERM을 받으면 새 요청을 받지 않고 처리 중인 요청을 마친 뒤 종료하고, 필요하면 `preStop` 훅으로 몇 초 기다려 엔드포인트 반영을 기다린다. 배포 때마다 에러가 조금씩 나는 문제의 흔한 원인이다.

## 깊게 5 — 리소스와 QoS

- **requests**: 스케줄러가 노드를 고를 때 쓰는 "예약량". 노드에 requests 합이 들어갈 자리가 있어야 배치된다.
- **limits**: 실제로 쓸 수 있는 상한. 메모리를 넘으면 OOMKilled, CPU를 넘으면 스로틀링.

requests와 limits의 관계에 따라 QoS 등급이 정해지고, 노드 메모리가 모자랄 때 쫓겨나는 순서가 된다.

| 등급 | 조건 | 쫓겨나는 순서 |
|---|---|---|
| Guaranteed | 모든 컨테이너가 CPU·메모리 requests와 limits를 같게 | 가장 늦게 |
| Burstable | 일부만 설정했거나 둘이 다름 | 중간 |
| BestEffort | 아무것도 설정 안 함 | 가장 먼저 |

실무 원칙:

1. **메모리는 requests와 limits를 같게** 두는 경우가 많다. 메모리는 압축할 수 없어서, 넘치면 죽는다. 예측 가능하게 만든다.
2. **CPU limits는 신중하게.** CPU는 압축 가능한 자원이라 넘쳐도 죽지 않고 느려진다. limits를 너무 낮게 잡으면 평균 사용률이 낮은데도 순간적인 스로틀링으로 지연이 튄다. CPU limits를 두지 않고 requests만 정확히 잡는 팀도 많다.
3. **requests는 실제 사용량으로 정한다.** 너무 크면 노드가 놀고(비용), 너무 작으면 한 노드에 몰려 서로 방해한다. 관측 데이터나 VPA 권장값을 본다.
4. **네임스페이스마다 LimitRange와 ResourceQuota**로 기본값과 총량을 정한다. 아무것도 안 적은 BestEffort 파드가 운영에 들어가는 것을 막는다.

언어 런타임도 확인한다. 예전 JVM이나 일부 런타임은 컨테이너 메모리 한도를 모르고 호스트 메모리 기준으로 힙을 잡아 OOMKilled가 났다. 요즘 버전은 cgroup을 인식하지만, 힙 비율 설정을 확인하는 습관이 필요하다.

## 깊게 6 — 스케줄링

스케줄러는 **거르기**(이 노드에 놓을 수 있나)와 **점수 매기기**(어디가 가장 좋나) 두 단계로 노드를 고른다. 영향을 주는 도구:

- **nodeSelector, 노드 어피니티**: "GPU 노드에만", "이 존에만".
- **파드 어피니티·안티어피니티**: "캐시 파드 옆에", "같은 앱의 복제본은 서로 다른 노드에".
- **테인트와 톨러레이션**: 노드에 "아무나 오지 마"를 붙이고(테인트), 허락받은 파드만 톨러레이션으로 들어간다. GPU 노드, 전용 노드 풀, 시스템 전용 노드에 쓴다. 톨러레이션은 "들어갈 수 있다"일 뿐 "반드시 거기로"가 아니라서, 전용 배치에는 노드 어피니티를 같이 쓴다.
- **토폴로지 분산 제약**: 복제본을 존이나 노드에 고르게 퍼뜨린다. 한 존 장애로 서비스 전체가 죽지 않게 하는 핵심 설정이다.
- **우선순위와 선점**: 자리가 없을 때 중요한 파드가 덜 중요한 파드를 밀어낸다.
- **PodDisruptionBudget**: 노드 업그레이드나 축소처럼 **계획된** 중단 때 동시에 몇 개까지 내려가도 되는지 정한다. 이게 없으면 노드를 비우면서 복제본이 한꺼번에 내려갈 수 있다.

## 깊게 7 — 워크로드 종류

| 종류 | 성격 | 예 |
|---|---|---|
| Deployment | 상태 없는 복제본, 롤링 업데이트 | 웹, API |
| StatefulSet | 고정 이름·순서·전용 볼륨 | DB, 카프카, 주키퍼 |
| DaemonSet | 노드마다 하나 | 로그 수집기, 모니터링 에이전트, CNI |
| Job / CronJob | 끝나는 작업, 주기 작업 | 배치, 마이그레이션, 백업 |

- **Deployment 롤링 업데이트**는 `maxSurge`(추가로 더 띄울 수)와 `maxUnavailable`(동시에 내려도 되는 수)로 속도와 안전을 조절한다. 새 파드가 Ready가 되어야 다음으로 넘어가므로 readiness 프로브가 배포 안전의 열쇠다.
- **StatefulSet**은 파드마다 `이름-0`, `이름-1` 처럼 고정된 이름과 자기 볼륨을 준다. 파드가 다시 떠도 같은 볼륨이 붙는다. 다만 DB 복제나 장애 조치 같은 "데이터의 정합성"은 쿠버네티스가 해 주지 않는다. 운영 DB는 관리형 서비스를 쓰거나, 검증된 오퍼레이터를 쓰는 것이 보통이다.

트래픽 입구는 이렇다.

- **Service**: 파드 집합에 고정 이름과 가상 IP를 준다. ClusterIP(내부), NodePort, LoadBalancer(클라우드 LB 생성).
- **Ingress**: HTTP 경로·호스트 기반 라우팅을 하나의 입구에 모은다. 컨트롤러 구현에 따라 동작이 다르다.
- **Gateway API**: Ingress의 후속 표준. 인프라 담당(Gateway)과 앱 담당(HTTPRoute)의 역할을 나누고, 가중치 라우팅 같은 기능을 표준으로 담았다.

설정은 **ConfigMap**, 비밀은 **Secret**. Secret은 기본적으로 base64 인코딩일 뿐이라 etcd 암호화와 RBAC, 외부 비밀 저장소 연동이 필요하다(03편).

## 깊게 8 — 오토스케일링

세 층이 있다.

| 무엇을 | 도구 | 기준 |
|---|---|---|
| 파드 수 | HPA | CPU·메모리, 사용자 지표(요청 수, 대기열 길이) |
| 파드 크기 | VPA | 실제 사용량으로 requests 조정 |
| 노드 수 | Cluster Autoscaler, Karpenter | Pending 파드, 비어 있는 노드 |

흐름은 이렇게 맞물린다. 트래픽이 늘면 HPA가 파드를 늘리고, 놓을 자리가 없어 Pending이 생기면 노드 오토스케일러가 노드를 추가한다. 트래픽이 줄면 반대로.

- **HPA는 requests 대비 사용률로 계산한다.** requests가 엉터리면 스케일링도 엉터리다.
- **HPA와 VPA를 같은 지표(CPU)로 같이 쓰면 서로 싸운다.** VPA는 권장값만 보는 모드로 쓰거나, HPA는 다른 지표를 쓴다.
- **Cluster Autoscaler**는 미리 정의한 노드 그룹(인스턴스 타입이 정해진)을 늘리고 줄인다.
- **Karpenter**는 노드 그룹 없이, Pending 파드의 요구에 맞는 인스턴스 타입을 그때그때 골라 띄운다. 스팟 인스턴스 활용과 노드 통합(빈 노드를 정리해 비용 절감)에 강하다. 원래 AWS용으로 시작했다.
- **GKE Autopilot**은 노드 관리 자체를 Google에 맡기고 파드 단위로 과금한다. 노드 풀 고민이 사라지는 대신, 특권 파드나 일부 노드 설정에 제약이 있다.
- 노드가 뜨는 데 시간이 걸린다. 갑작스러운 피크에는 여유 용량을 미리 두거나(낮은 우선순위의 자리 표시 파드), 예정된 이벤트 전에 미리 늘린다.

## 깊게 9 — 관리형 쿠버네티스 비교

세 클라우드 모두 컨트롤 플레인(API 서버, etcd)은 클라우드가 운영하고, 사용자는 노드와 워크로드를 다룬다. 차이는 세부에 있다.

| 항목 | EKS | GKE | AKS |
|---|---|---|---|
| 파드 네트워크 기본 | VPC CNI (파드가 VPC IP) | VPC 네이티브 (별칭 IP) | Azure CNI 계열 또는 오버레이 |
| 노드 관리 | 관리형 노드 그룹, Fargate, Karpenter | 노드 풀, Autopilot | 노드 풀, 가상 노드 |
| 업그레이드 | 사용자가 시작 (버전 지원 기간 관리) | 릴리스 채널로 자동 업그레이드 가능 | 자동 업그레이드 채널 |
| 파드 클라우드 권한 | IRSA, Pod Identity | Workload Identity | Entra Workload ID |

운영에서 중요한 차이:

- **업그레이드 철학**: 쿠버네티스는 마이너 버전이 자주 나오고 각 버전의 지원 기간이 정해져 있다. GKE는 릴리스 채널(Rapid, Regular, Stable)로 자동 업그레이드를 기본으로 하고 유지 관리 창과 제외 기간으로 시점을 통제한다. EKS는 사용자가 업그레이드를 계획해서 실행하는 성격이 강하고, 표준 지원이 끝난 버전은 연장 지원 비용이 붙는다. 어느 쪽이든 **업그레이드는 정기 업무**로 계획해야 한다.
- **업그레이드 순서**: 컨트롤 플레인 → 애드온(CNI, CoreDNS, kube-proxy) → 노드. 노드는 새 노드 풀을 만들어 옮기는(블루-그린) 방식이 롤백이 쉽다. 사용 중지된 API를 쓰는 매니페스트가 있는지 먼저 점검한다.
- **IP 소비**: EKS VPC CNI는 파드마다 VPC IP를 쓰므로 서브넷이 빨리 바닥난다. 접두사 위임이나 보조 대역을 계획한다.

## 깊게 10 — 멀티 테넌시

여러 팀이 한 클러스터를 쓰는 경우의 기본선:

1. **네임스페이스를 팀·서비스 단위로.** 이름 충돌을 막고 정책의 단위가 된다.
2. **RBAC**: 팀은 자기 네임스페이스에서만 권한. 클러스터 전체 권한(ClusterRole 바인딩)은 플랫폼 팀만.
3. **NetworkPolicy**: 기본은 모두 통신 가능하다. 네임스페이스마다 "기본 거부"를 깔고 필요한 통신만 연다. CNI가 NetworkPolicy를 지원해야 동작한다.
4. **ResourceQuota와 LimitRange**: 한 팀이 클러스터 자원을 다 먹지 못하게.
5. **Pod Security Standards**: 특권 컨테이너, 호스트 네트워크, 호스트 경로 마운트를 막는다.
6. **정책 엔진**: 승인 제어 단계에서 "레지스트리 제한", "라벨 필수", "다이제스트 필수" 같은 규칙을 강제한다(Kyverno, Gatekeeper, 내장 ValidatingAdmissionPolicy).

네임스페이스는 **약한 격리**다. 같은 노드와 커널을 공유한다. 신뢰 수준이 다른 테넌트(외부 고객 코드)는 노드 풀을 나누거나, 샌드박스 런타임을 쓰거나, 클러스터 자체를 나눈다. "클러스터를 몇 개로 나눌까"는 격리 요구와 운영 비용의 트레이드오프다.

## 장애 대응 예시 — 자주 만나는 다섯 가지

디버깅 기본 순서는 항상 같다.

```
kubectl get pods        상태 보기
kubectl describe pod    이벤트 보기
kubectl logs (--previous) 로그
kubectl get events      클러스터 이벤트
```

`describe` 맨 아래의 **Events**가 대부분 답을 말해 준다.

**1. Pending**
- 증상: 파드가 노드에 배치되지 않는다.
- 원인 후보: requests가 커서 들어갈 노드가 없음, 노드 어피니티·테인트 조건이 안 맞음, PVC가 묶이지 않음(존이 다른 볼륨), 노드 오토스케일러가 최대치.
- 확인: Events의 `FailedScheduling` 메시지가 이유를 말한다("Insufficient memory", "node(s) had untolerated taint").

**2. ImagePullBackOff**
- 원인 후보: 이미지 이름·태그 오타, 레지스트리 인증 실패(권한, 풀 시크릿), 노드가 레지스트리에 닿지 못함(사설 서브넷에 NAT나 엔드포인트 없음), 공용 레지스트리 받기 제한.
- 확인: Events의 pull 에러 메시지, 노드에서 레지스트리 접근 경로.

**3. CrashLoopBackOff**
- 의미: 컨테이너가 시작했다가 죽기를 반복하고, 재시작 간격이 점점 길어진다.
- 원인 후보: 앱 설정 오류(환경 변수, 비밀 없음), 의존 서비스 연결 실패, liveness 프로브가 너무 엄격함, OOMKilled.
- 확인: `kubectl logs --previous` 로 **죽기 직전** 로그를 본다. `describe` 의 Last State에서 종료 이유(OOMKilled, Error)와 종료 코드를 본다.

**4. Evicted / OOMKilled**
- OOMKilled는 컨테이너가 자기 limits를 넘은 것. Evicted는 노드 전체의 메모리·디스크 압박으로 kubelet이 파드를 쫓아낸 것이다.
- 조치: 실제 사용량으로 requests·limits 조정, 메모리 누수 확인, 노드의 디스크(로그, 이미지) 정리, BestEffort 파드 없애기.

**5. DNS 문제**
- 증상: 서비스 이름이 간헐적으로 안 풀리거나, 외부 도메인 조회가 느리다.
- 원인 후보: CoreDNS 파드 부족이나 과부하, 파드의 `ndots:5` 기본 설정 때문에 외부 도메인 하나에 검색 도메인 조회가 여러 번 붙는 문제, conntrack 경합으로 UDP DNS 패킷 유실.
- 조치: CoreDNS 수평 확장, NodeLocal DNSCache 도입, 외부 도메인은 끝에 점을 붙인 완전한 이름 사용이나 ndots 조정.

## 깊게 11 — 서버리스의 트레이드오프

| | AWS Lambda | Cloud Run | Azure Functions / Container Apps |
|---|---|---|---|
| 단위 | 함수 (이미지도 가능) | 컨테이너 | 함수 / 컨테이너 |
| 동시성 | 실행 환경 하나가 한 번에 요청 하나 | 인스턴스 하나가 여러 요청 동시 처리 가능 | 플랜·설정에 따름 |
| 0으로 축소 | 예 | 예 | 플랜에 따라 |

### 콜드 스타트

요청이 왔는데 준비된 실행 환경이 없으면, 새 환경을 만들고(마이크로 VM이나 샌드박스), 코드나 이미지를 받고, 런타임을 띄우고, 초기화 코드를 돌린다. 이 시간이 첫 요청에 붙는다.

줄이는 방법:
1. **미리 데워 둔다**: Lambda 프로비저닝된 동시성, Cloud Run 최소 인스턴스, Functions 프리미엄 플랜의 상시 준비 인스턴스. 대신 켜 둔 만큼 비용이 든다.
2. **초기화를 가볍게**: 패키지·이미지 크기를 줄이고, 무거운 초기화는 지연 로딩한다.
3. **런타임 선택**: 시작이 빠른 런타임을 고르거나, Lambda SnapStart처럼 초기화된 상태를 스냅샷으로 재사용하는 기능을 쓴다.
4. **연결 재사용**: 핸들러 밖에서 DB·HTTP 클라이언트를 만들어 다음 호출에 재사용한다. 다만 서버리스가 갑자기 많이 늘면 DB 연결이 폭발하므로 RDS Proxy 같은 연결 풀을 앞에 둔다.

### 서버리스를 고르지 않는 경우

- 실행 시간 상한을 넘는 긴 작업
- 항상 높은 트래픽이 일정하게 오는 서비스 (켜 둔 서버가 더 쌀 수 있다)
- 지연 시간 요구가 아주 엄격하고 콜드 스타트를 감당할 수 없는 경우
- 특수 네트워크, 로컬 상태, 특정 하드웨어가 필요한 경우

판단 기준은 결국 같다. "운영 부담을 얼마나 맡기고, 그 대가로 어떤 제약을 받아들이는가."

---

## 설계 예시 — 여러 팀이 쓰는 컨테이너 플랫폼

1. **클러스터 구분**: 운영과 비운영을 클러스터로 분리. 운영은 리전당 하나에서 시작하고, 격리 요구가 큰 서비스는 별도 클러스터.
2. **노드 풀**: 시스템 전용(테인트), 일반 워크로드, 특수(GPU, 메모리 큰 노드)로 나누고 여러 존에 걸친다.
3. **팀 온보딩 템플릿**: 네임스페이스 + RBAC + NetworkPolicy 기본 거부 + ResourceQuota + 워크로드 신원을 한 번에 만드는 템플릿.
4. **배포 표준**: 이미지는 사내 레지스트리, 다이제스트 고정, 서명 검증. GitOps로 클러스터 상태를 저장소와 일치. 프로브·리소스·PDB·토폴로지 분산이 없는 매니페스트는 정책으로 거부.
5. **관측**: 로그·지표·추적을 공통 수집기(DaemonSet, OpenTelemetry)로. 팀별 대시보드와 알람 기본 세트.
6. **업그레이드 운영**: 분기별 업그레이드 일정, 비운영에서 먼저, 사용 중지 API 점검, 노드 풀 교체 방식.
7. **비용**: 네임스페이스별 비용 할당(라벨), 요청량 대비 실제 사용량 리포트, 스팟과 노드 통합.

플랫폼 팀의 목표는 "각 팀이 쿠버네티스를 깊게 몰라도 안전하게 배포할 수 있는 길"을 만드는 것이다.

---

## 자주 하는 실수

- liveness 프로브에서 DB를 확인해 연쇄 재시작을 만든다.
- requests 없이 배포해 BestEffort 파드가 가장 먼저 쫓겨난다.
- CPU limits를 너무 낮게 걸어 이유 모를 지연이 생긴다.
- 복제본을 3개 두고도 토폴로지 분산이 없어 한 노드·한 존에 몰린다.
- PodDisruptionBudget 없이 노드 업그레이드를 해 서비스가 한꺼번에 내려간다.
- `latest` 태그로 배포해 어떤 이미지가 도는지 모른다.
- 종료 처리(SIGTERM, preStop)를 하지 않아 배포 때마다 에러가 난다.
- 업그레이드를 미루다 지원이 끝난 버전에 묶인다.
- 파드 IP 소비를 계산하지 않아 서브넷이 바닥난다.

## 면접 질문 10개와 답

**1. VM, 컨테이너, 서버리스를 어떻게 고르는가?**
OS나 커널 제어가 필요하거나 레거시·라이선스 제약이 있으면 VM을 쓴다. 여러 서비스를 같은 방식으로 배포·관측·보안 관리하고 싶고 운영할 인력이 있으면 쿠버네티스 같은 컨테이너 플랫폼이 맞다. 트래픽이 들쭉날쭉하고 요청 단위로 짧게 끝나는 일은 서버리스가 비용과 운영 면에서 유리하다. 결국 운영 부담을 얼마나 맡기고 어떤 제약을 받아들이느냐의 판단이다.

**2. 컨테이너가 VM보다 가벼운 이유는?**
VM은 하이퍼바이저 위에 게스트 커널 전체를 부팅하지만, 컨테이너는 호스트 커널을 공유하는 프로세스다. 네임스페이스로 보이는 범위를 나누고, cgroups로 자원을 제한하고, 오버레이 파일 시스템으로 이미지 레이어를 공유한다. 그래서 시작이 빠르고 밀도가 높다. 대신 커널을 공유하므로 격리가 VM보다 약해서, 신뢰할 수 없는 코드에는 gVisor나 마이크로 VM 같은 추가 격리를 쓴다.

> 日本語: コンテナはホストのカーネルを共有するプロセスで、namespaceとcgroupで分離と制限をしているので軽量です。

**3. kubectl apply 후 파드가 뜨기까지의 흐름은?**
API 서버가 인증·인가·승인 제어를 거쳐 etcd에 저장하고, Deployment와 ReplicaSet 컨트롤러가 파드 객체를 만든다. 스케줄러가 노드를 정하면 그 노드의 kubelet이 CNI로 네트워크, CSI로 볼륨을 붙이고 런타임으로 컨테이너를 띄운다. readiness 프로브를 통과하면 엔드포인트에 등록되어 트래픽을 받는다. 이 단계를 알면 Pending, ContainerCreating, Running 중 어디서 멈췄는지로 원인을 좁힐 수 있다.

**4. 프로브 세 종류의 차이는?**
liveness는 실패하면 컨테이너를 재시작하므로 프로세스 자체가 멈췄는지만 봐야 하고 외부 의존성을 넣으면 안 된다. readiness는 실패하면 트래픽에서만 빠지므로 준비 상태나 일시적 과부하를 표현한다. startup은 시작이 느린 앱이 준비될 때까지 다른 프로브를 보류시켜 시작 중 재시작 반복을 막는다.

**5. requests와 limits는 어떻게 정하는가?**
requests는 스케줄링 기준이라 실제 사용량에 맞춰 정하고, 메모리는 넘치면 죽기 때문에 requests와 limits를 같게 두는 경우가 많다. CPU는 압축 가능한 자원이라 limits를 낮게 잡으면 스로틀링으로 지연이 튀므로 신중하게 정하거나 두지 않기도 한다. 관측 데이터와 VPA 권장값을 보고 조정하며, 네임스페이스마다 기본값과 총량을 정책으로 강제한다.

**6. 파드가 Pending이다. 어디부터 보는가?**
`kubectl describe pod` 의 이벤트에서 FailedScheduling 메시지를 먼저 본다. 자원 부족이면 requests 크기와 노드 여유, 오토스케일러 최대치를 확인하고, 테인트나 어피니티 불일치면 조건을 고친다. PVC가 묶이지 않았다면 스토리지 클래스와 볼륨의 존을 확인한다.

**7. CrashLoopBackOff는 어떻게 디버깅하는가?**
`kubectl logs --previous` 로 죽기 직전 로그를 보고, `describe` 의 Last State에서 종료 이유가 OOMKilled인지 앱 에러인지 확인한다. 설정·비밀 누락, 의존 서비스 연결 실패, 너무 엄격한 liveness 프로브가 흔한 원인이다. 필요하면 같은 이미지를 디버그용으로 띄우거나 임시 디버그 컨테이너를 붙여 환경을 확인한다.

**8. EKS, GKE, AKS의 차이는?**
셋 다 컨트롤 플레인을 관리해 주지만 파드 네트워크 방식, 노드 관리 옵션, 업그레이드 철학이 다르다. EKS는 파드가 VPC IP를 직접 써서 IP 계획이 중요하고 업그레이드를 사용자가 계획하는 성격이 강하다. GKE는 릴리스 채널로 자동 업그레이드가 기본이고 Autopilot으로 노드 관리를 넘길 수 있다. AKS는 Entra ID와 Azure 서비스 연동이 강점이다.

**9. 여러 팀이 한 클러스터를 쓸 때 무엇을 설정하는가?**
팀별 네임스페이스와 RBAC로 권한을 나누고, NetworkPolicy 기본 거부로 통신을 제한하며, ResourceQuota와 LimitRange로 자원 독점을 막는다. Pod Security Standards와 정책 엔진으로 특권 컨테이너나 검증 안 된 이미지를 막는다. 네임스페이스는 약한 격리라서 신뢰 수준이 다른 테넌트는 노드 풀이나 클러스터를 분리한다.

> 日本語: Namespace・RBAC・NetworkPolicy・ResourceQuotaで分離しますが、信頼レベルが違う場合はクラスタを分けます。

**10. 서버리스 콜드 스타트는 왜 생기고 어떻게 줄이는가?**
준비된 실행 환경이 없을 때 새 환경을 만들고 코드를 받아 런타임과 초기화 코드를 돌리는 시간이 첫 요청에 붙기 때문이다. 최소 인스턴스나 프로비저닝된 동시성으로 미리 데워 두고, 패키지를 줄이고 초기화를 가볍게 하며, 스냅샷 기능이나 빠른 런타임을 쓴다. 미리 데우는 만큼 비용이 들어서 지연 요구와 비용 사이에서 정한다.

## 정답

1. 파드 안 컨테이너들이 NET 네임스페이스를 공유하기 때문이다. 같은 IP와 포트 공간을 쓴다.
2. 죽지 않는다. 할당량을 다 쓰면 그 주기 동안 멈추는 스로틀링이 걸려 느려진다. 메모리 한도를 넘으면 OOMKilled로 죽는다.
3. DB가 잠깐 느려지거나 끊기면 모든 파드의 liveness가 실패해 동시에 재시작되고, 재시작 중에 서비스 전체가 멈추는 연쇄 장애가 날 수 있다.
4. 아니다. 톨러레이션은 테인트된 노드에 들어갈 수 있게 할 뿐 그 노드로 가라는 뜻이 아니다. 노드 어피니티(또는 nodeSelector)를 함께 써야 한다.
5. 노드 오토스케일러(Cluster Autoscaler나 Karpenter)가 Pending 파드를 보고 노드를 추가한다. 최대 노드 수나 인스턴스 할당량에 걸렸는지도 확인한다.
