## 질문

브라우저에 `https://example.com` 을 치고 엔터를 누르면, 화면이 뜨기 전까지 무슨 일이 일어날까?

면접 단골 질문이다. 답은 길지만 뼈대는 다섯 단계다.

## 한 장으로 보기

```
[1] 이름 → 주소       DNS        example.com 은 IP가 뭐지?
[2] 길 찾기           라우팅      그 IP로 가려면 어느 게이트웨이로?
[3] 연결 만들기       TCP        3-웨이 핸드셰이크 (SYN → SYN/ACK → ACK)
[4] 암호화 합의       TLS        인증서 확인 + 세션 키 합의
[5] 요청과 응답       HTTP       GET / → 200 OK + HTML
```

그 뒤 브라우저는 HTML을 읽으며 CSS·JS·이미지를 받으려고 [1]~[5]를 다시 돈다. 같은 서버면 이미 맺은 연결을 다시 쓴다.

## 단계별로 조금 더

**[1] DNS.** 브라우저 캐시 → OS 캐시 → 공유기나 회사의 DNS 서버(재귀 리졸버) 순서로 묻는다. 리졸버가 모르면 루트 → `.com` → `example.com` 담당 서버까지 차례로 물어 답을 받아 온다. 받은 답은 TTL 동안 캐시한다. (08편)

**[2] 라우팅.** 목적지 IP가 내 네트워크 안이면 바로 보내고, 밖이면 기본 게이트웨이(공유기)로 보낸다. 같은 네트워크 안에서 실제 전달은 MAC 주소로 하므로, 게이트웨이의 MAC을 ARP로 알아낸다. (04편)

**[3] TCP.** 데이터를 보내기 전에 양쪽이 "보낼 준비 됐다"를 세 번의 패킷으로 확인한다. 여기서 1 RTT(왕복 시간)가 든다. (03편)

**[4] TLS.** 서버가 인증서를 보내고, 브라우저는 그 인증서가 믿을 만한 기관이 서명한 `example.com` 의 것인지 확인한다. 그다음 이번 연결에서만 쓸 대칭키를 합의한다. TLS 1.3 기준 1 RTT. (07편)

**[5] HTTP.** 이제 암호화된 통로로 `GET /` 요청을 보내고 응답을 받는다.

가는 길에 공유기에서 NAT가 내 사설 IP를 공인 IP로 바꾸고(06편), 서버 앞의 로드밸런서가 여러 서버 중 하나를 고른다(09편).

## 직접 확인 (맥 터미널)

```bash
# [1] DNS: example.com 의 IP
dig +short example.com

# [2] 내 기본 게이트웨이
route -n get default | grep gateway

# [2] 목적지까지 거치는 라우터들
traceroute -n example.com

# [3]~[5] 한 번에: 연결, TLS, HTTP 과정을 모두 출력
curl -v https://example.com -o /dev/null

# 단계별 소요 시간
curl -o /dev/null -s -w 'dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} first_byte=%{time_starttransfer}\n' https://example.com
```

마지막 명령의 숫자는 누적 시간이다. `tcp - dns` 가 TCP 연결 시간, `tls - tcp` 가 TLS 시간이다. 먼 리전 서버로 바꿔 보면 RTT가 커질수록 tcp·tls 구간이 같이 늘어나는 게 보인다.

## 클라우드에서는

| 단계 | 클라우드에서 대응하는 것 |
|---|---|
| DNS | Route 53, Cloud DNS. 가중치·장애 조치 레코드로 트래픽 방향을 바꾼다 |
| 라우팅 | VPC 라우팅 테이블, 인터넷 게이트웨이, NAT 게이트웨이 |
| TCP | 로드밸런서의 유휴 타임아웃, 연결 재사용 |
| TLS | 로드밸런서에서 인증서로 종단 (ACM, Certificate Manager) |
| HTTP | L7 로드밸런서의 경로 기반 라우팅 |

장애가 나면 "어느 단계에서 멈췄나"부터 나눈다. 이름이 안 풀리는지(DNS), 연결이 안 되는지(라우팅·방화벽·TCP), 인증서 오류인지(TLS), 서버가 에러를 주는지(HTTP). 이 순서가 그대로 장애 대응 순서다.

## 면접 한 줄 답

> DNSで名前を解決し、TCPで接続を確立、TLSで暗号化の合意をした後、HTTPでリクエストを送ります。障害対応でもこの順番で切り分けます。

DNS로 이름을 풀고, TCP로 연결을 맺고, TLS로 암호화를 합의한 뒤 HTTP로 요청을 보냅니다. 장애 대응도 이 순서로 나눠서 봅니다.
