## 개념과 배경

### 공동 책임 모델

클라우드 보안은 클라우드 회사와 사용자가 나눠 진다. 기본 문장은 이렇다. 클라우드 회사는 **클라우드 자체의 보안**(데이터센터, 하드웨어, 가상화 계층, 관리형 서비스의 내부)을 책임지고, 사용자는 **클라우드 안에 올린 것의 보안**(데이터, 계정과 권한, 네트워크 설정, 운영체제와 애플리케이션)을 책임진다.

경계선은 서비스 종류에 따라 움직인다.

| 영역 | IaaS (VM) | 컨테이너·PaaS | SaaS·서버리스 |
|---|---|---|---|
| 물리·가상화 | 회사 | 회사 | 회사 |
| OS 패치 | 사용자 | 대부분 회사 | 회사 |
| 런타임·앱 코드 | 사용자 | 사용자 | 일부 사용자 |
| 데이터·권한·설정 | 사용자 | 사용자 | 사용자 |

마지막 줄이 핵심이다. 어떤 서비스를 써도 **데이터, 권한, 설정**은 끝까지 사용자 몫이다. 실제 클라우드 사고 대부분이 해킹 기술이 아니라 이 세 가지의 실수(공개된 버킷, 너무 넓은 권한, 유출된 키)에서 나온다. 그래서 클라우드 엔지니어 면접의 보안 질문은 대부분 IAM과 설정 관리로 모인다.

### 인증과 인가

- **인증(Authentication)**: 너는 누구냐. 비밀번호, 액세스 키, 인증서, OIDC 토큰으로 신원을 증명한다.
- **인가(Authorization)**: 그래서 무엇을 해도 되냐. 정책이 "이 주체가 이 자원에 이 행동을 할 수 있다"를 정한다.

클라우드 IAM은 둘 다 하지만, 면접에서 깊게 묻는 쪽은 인가다. "정책이 어떻게 평가되는가"를 설명할 수 있어야 한다.

### IAM의 네 요소

어느 클라우드든 IAM은 같은 문장 구조를 가진다.

```
누가(주체) 무엇에(자원)
무엇을(행동) 어떤 조건에서(조건)
허용 또는 거부
```

- 주체: 사람 사용자, 그룹, 역할, 서비스 계정, 관리 ID
- 자원: 버킷, VM, DB, 키, 프로젝트·구독 전체
- 행동: `s3:GetObject`, `compute.instances.start` 같은 API 단위
- 조건: 출발지 IP, MFA 여부, 태그, 시간, 요청한 VPC 엔드포인트

클라우드마다 이름과 문법이 다를 뿐 이 네 칸을 채우는 방식의 차이다.

## 깊게 1 — AWS 정책 평가

### 정책의 종류

AWS에는 정책이 여러 겹 있다. 겹마다 역할이 다르다.

| 정책 | 붙는 곳 | 하는 일 |
|---|---|---|
| 자격 증명 기반 정책 | 사용자·그룹·역할 | 이 주체가 할 수 있는 일 |
| 리소스 기반 정책 | S3 버킷, KMS 키, SQS 등 | 이 자원에 누가 접근할 수 있나 |
| SCP | Organizations의 OU·계정 | 계정 안 모든 주체의 최대치 |
| 권한 경계 | 사용자·역할 | 그 주체가 가질 수 있는 최대치 |
| 세션 정책 | 역할을 맡을 때 전달 | 그 세션의 최대치 |

여기서 중요한 구분은 **허용을 주는 정책**과 **상한만 정하는 정책**이다. 자격 증명 기반 정책과 리소스 기반 정책은 허용을 준다. SCP, 권한 경계, 세션 정책은 허용을 주지 않는다. "이 이상은 안 된다"는 울타리만 친다. 울타리 안에서 실제 허용은 다른 정책이 줘야 한다.

### 평가 순서

같은 계정 안의 요청이라면 대략 이렇게 판단한다.

```
1. 어디든 명시적 Deny?  → 거부
2. SCP가 허용 범위 밖?  → 거부
3. 리소스 정책이 허용?  → (같은 계정이면)
                          허용 가능
4. 권한 경계 밖?        → 거부
5. 세션 정책 밖?        → 거부
6. 자격 증명 정책 허용? → 허용
7. 아무도 허용 안 함    → 거부 (기본)
```

외워야 할 원칙은 세 개다.

1. **기본은 거부다.** 아무 정책도 허용하지 않으면 거부된다(암묵적 거부).
2. **명시적 Deny가 모든 것을 이긴다.** 어느 정책이든 Deny가 하나라도 걸리면 끝이다.
3. **상한 정책은 교집합이다.** SCP, 권한 경계, 세션 정책을 모두 통과해야 하고, 그 안에서 누군가 허용을 줘야 한다.

같은 계정에서 리소스 기반 정책이 주체를 직접 허용하면 자격 증명 정책 없이도 접근되는 경우가 있다. 반면 **다른 계정**에서 오는 요청은 양쪽 모두 허용해야 한다. 상대 계정의 주체 쪽 정책도 허용하고, 내 자원의 리소스 정책도 허용해야 한다. 면접에서 자주 걸리는 지점이다.

### SCP와 권한 경계의 차이

둘 다 상한이지만 쓰는 사람과 목적이 다르다.

- **SCP**: 조직 관리자가 계정 단위로 건다. "이 계정에서는 아무도 서울·도쿄 외 리전을 못 쓴다", "CloudTrail을 아무도 끄지 못한다", "루트 사용자는 아무것도 못 한다" 같은 조직 규칙이다. 계정 관리자도 벗어날 수 없다. 관리 계정 자체에는 적용되지 않는다는 점도 기억해 둔다.
- **권한 경계**: 개발팀에 "IAM 역할을 직접 만들 권한"을 위임할 때 쓴다. 개발자가 만든 역할은 반드시 특정 권한 경계를 달도록 강제하면, 개발자가 자기보다 더 강한 역할을 만들어 권한을 올리는(권한 상승) 길이 막힌다.

공통 기반 관점에서는 SCP가 **가드레일**, 권한 경계가 **위임의 안전장치**다.

### 계정 간 역할 위임

A 계정의 CI가 B 계정에 배포해야 한다고 하자. 장기 키를 B 계정에 만들지 않고 역할 위임을 쓴다.

```
A의 역할 ──AssumeRole──▶ B의 역할
         (STS 임시 자격 증명)
```

설정은 두 쪽이다.

1. **B 계정 역할의 신뢰 정책**: "A 계정의 이 역할이 나를 맡을 수 있다". 주체를 계정 전체가 아니라 특정 역할 ARN으로 좁힌다.
2. **A 계정 역할의 권한 정책**: "B 계정의 그 역할에 대해 `sts:AssumeRole` 을 할 수 있다".

외부 업체(서드파티 SaaS)에 우리 계정 접근을 줄 때는 **External ID** 조건을 신뢰 정책에 넣는다. 업체가 여러 고객의 역할을 맡는 구조에서, 다른 고객이 우리 역할 ARN을 알아내 업체를 속여 접근하는 문제(혼동된 대리인 문제)를 막는 장치다.

얻는 것: 자격 증명이 짧게 살다 사라진다. 누가 언제 역할을 맡았는지 CloudTrail에 남는다. 키를 돌릴 필요가 없다.

## 깊게 2 — GCP IAM

### 바인딩과 상속

GCP는 정책을 **자원 계층**에 붙인다.

```
조직
 └ 폴더
    └ 프로젝트
       └ 자원 (버킷, VM ...)
```

정책은 "역할을 주체에게 묶는 바인딩"의 목록이다. 위에서 준 권한은 아래로 **상속**된다. 폴더에서 준 편집자 역할은 그 아래 모든 프로젝트에 적용된다. 그래서 상위에서 넓게 주면 위험하고, 아래에서 빼앗을 수 없다(허용 정책은 합집합이다).

역할은 세 종류다.

- **기본 역할**(Owner, Editor, Viewer): 너무 넓다. 운영 환경에서는 쓰지 않는 것이 원칙이다.
- **사전 정의 역할**: 서비스별로 잘게 나뉜 역할. 대부분 여기서 고른다.
- **커스텀 역할**: 필요한 권한만 골라 만든다. 관리 부담이 생긴다.

아래로 빼앗을 수 없는 문제를 보완하는 것이 **거부 정책(IAM Deny)** 이다. 허용과 별개로 평가되고, 거부가 허용을 이긴다. 조직 단위 제약은 **조직 정책**(Organization Policy)으로 건다. 예를 들어 "서비스 계정 키 생성 금지", "외부 IP를 가진 VM 금지", "특정 리전만 허용" 같은 규칙이다. AWS의 SCP와 비슷한 가드레일 역할이다.

### 서비스 계정과 키 문제

서비스 계정은 사람 대신 프로그램이 쓰는 신원이다. 문제는 **서비스 계정 키**(JSON 파일)다.

- 만료가 없다(직접 지우거나 돌려야 한다).
- 파일이라 복사되고, 저장소에 올라가고, 노트북에 남는다.
- 누가 쓰는지 추적이 어렵다.

그래서 권장은 "키를 만들지 말라"다. 대신 쓰는 방법은 이렇다.

| 상황 | 키 대신 |
|---|---|
| GCP 안에서 실행 (VM, GKE, Cloud Run) | 자원에 서비스 계정을 붙인다. 메타데이터 서버가 짧은 토큰을 준다 |
| GKE 파드 | Workload Identity로 쿠버네티스 서비스 계정과 연결 |
| 외부 (CI, 다른 클라우드, 온프레) | Workload Identity Federation |
| 사람이 임시로 | 서비스 계정 가장(impersonation) |

**가장(impersonation)** 은 사람이 키 없이 서비스 계정의 짧은 토큰을 받아 그 권한으로 일하는 방식이다. 사람에게는 "서비스 계정 토큰 생성자" 역할만 주고, 실제 권한은 서비스 계정에 둔다. 누가 가장했는지 감사 로그에 남는다.

## 깊게 3 — Azure RBAC와 Entra ID

Azure는 신원과 자원 권한이 두 층으로 나뉜다.

- **Microsoft Entra ID**(옛 이름 Azure AD): 사용자, 그룹, 앱 등록, 서비스 주체, 관리 ID가 사는 신원 디렉터리. 조건부 액세스(위치·기기·위험도에 따라 MFA 요구)도 여기서 한다.
- **Azure RBAC**: 구독·리소스 그룹·자원에 "역할 할당"을 붙여 권한을 준다.

자원 계층은 관리 그룹 → 구독 → 리소스 그룹 → 자원이고, GCP처럼 위에서 준 역할이 아래로 상속된다. 조직 가드레일은 **Azure Policy**(예: 허용 리전, 공용 IP 금지, 태그 강제)로 건다.

프로그램용 신원은 **관리 ID**(Managed Identity)를 쓴다. VM, App Service, Functions, 컨테이너에 붙이면 Azure가 자격 증명을 만들고 돌린다. 코드에 비밀이 없다. 시스템 할당(자원과 수명이 같음)과 사용자 할당(따로 만들어 여러 자원이 공유)이 있다.

세 클라우드를 한 줄로 비교하면 이렇다.

| 개념 | AWS | GCP | Azure |
|---|---|---|---|
| 프로그램 신원 | IAM 역할 | 서비스 계정 | 관리 ID |
| 조직 가드레일 | SCP | 조직 정책 | Azure Policy |
| 계층 | 조직·OU·계정 | 조직·폴더·프로젝트 | 관리 그룹·구독·RG |

## 깊게 4 — 최소 권한을 실제로 하는 법

"최소 권한"은 말은 쉽고 하기는 어렵다. 처음부터 딱 맞는 권한을 아는 사람은 없기 때문이다. 실무 순서는 이렇다.

1. **넓게 시작하되 기간을 정한다.** 개발 환경에서 넓은 권한으로 시작하고, 운영 전에 줄인다.
2. **실제 사용 기록으로 줄인다.** AWS IAM Access Analyzer는 CloudTrail 기록을 바탕으로 실제 쓴 권한만 담은 정책을 만들어 주고, 쓰지 않은 권한과 외부에 열린 자원을 찾아 준다. GCP는 IAM Recommender가 쓰지 않는 권한을 줄이라고 제안한다.
3. **사람의 상시 권한을 없앤다.** 운영 환경 관리자 권한은 평소에 없고, 필요할 때 승인을 받아 몇 시간만 받는다(Just-in-time access). Azure는 Privileged Identity Management, AWS는 IAM Identity Center의 권한 세트와 임시 승격 도구, GCP는 Privileged Access Manager 같은 기능을 쓴다.
4. **사람은 SSO로.** 개인별 IAM 사용자와 장기 키 대신 회사 IdP와 연동한 SSO로 로그인하고, 역할을 맡는다. 퇴사자 처리도 IdP 한 곳에서 끝난다.
5. **루트·전역 관리자는 봉인한다.** MFA를 걸고, 일상 업무에 쓰지 않고, 쓰면 알람이 울리게 한다.

## 깊게 5 — 워크로드 신원 연합

"장기 키를 없앤다"의 핵심 기술이다. 원리는 하나다. **이미 신원을 증명할 수 있는 시스템이 발급한 토큰을, 클라우드가 믿고 짧은 자격 증명으로 바꿔 준다.**

```
CI가 OIDC 토큰 발급
  (저장소·브랜치 정보 포함)
        │
        ▼
클라우드 STS가 서명 검증
 + 조건 확인 (저장소, 브랜치)
        │
        ▼
1시간짜리 임시 자격 증명
```

GitHub Actions 예시로 보면, AWS는 IAM에 OIDC 공급자를 등록하고 역할의 신뢰 정책에 "이 저장소의 main 브랜치에서 온 토큰만"이라는 조건을 건다. GCP는 Workload Identity Pool과 공급자를 만들고 속성 조건으로 같은 제한을 건다. Azure는 앱 등록이나 사용자 할당 관리 ID에 페더레이션 자격 증명을 추가한다.

**조건을 좁히는 것이 전부다.** 조건 없이 공급자만 등록하면, 같은 CI 서비스를 쓰는 남의 저장소에서 발급한 토큰도 통과할 수 있다. 저장소, 브랜치나 환경, 가능하면 워크플로까지 고정한다.

쿠버네티스 안의 파드도 같은 원리다.

| 클러스터 | 방식 |
|---|---|
| EKS | IRSA(서비스 계정 토큰을 OIDC로 교환) 또는 EKS Pod Identity |
| GKE | Workload Identity Federation for GKE |
| AKS | Microsoft Entra Workload ID |

공통점: 파드마다 다른 클라우드 권한을 준다. 노드 전체에 권한을 붙이는 방식(노드 역할)은 그 노드의 모든 파드가 같은 권한을 갖게 되므로 피한다. 그리고 파드가 노드의 메타데이터 엔드포인트로 노드 자격 증명을 훔쳐 가지 못하게 막는다(AWS는 IMDSv2와 홉 제한, GKE는 메타데이터 서버 대체).

## 깊게 6 — 암호화와 키 관리

### 저장 중·전송 중 암호화

- **전송 중**: TLS. 로드밸런서까지, 그리고 가능하면 서비스 사이와 DB 연결까지. 인증서 검증을 포함해야 의미가 있다.
- **저장 중**: 디스크, 객체 저장소, DB를 암호화한다. 주요 클라우드는 대부분 기본으로 암호화한다. 질문은 "암호화했는가"보다 **"키를 누가 관리하는가"** 다.

### 봉투 암호화

큰 데이터를 KMS에 직접 보내 암호화하지 않는다. 대신 두 겹으로 한다.

```
데이터 ──DEK로 암호화──▶ 암호문
DEK ──KEK(KMS)로 암호화──▶ 암호화된 DEK
저장: 암호문 + 암호화된 DEK
```

- **DEK**(데이터 키): 데이터마다 만드는 대칭키. 로컬에서 빠르게 암호화한다.
- **KEK**(키 암호화 키): KMS 안에만 있고 밖으로 나오지 않는다. DEK를 감싸는 데만 쓴다.

복호화할 때는 암호화된 DEK를 KMS에 보내 풀고, 풀린 DEK로 데이터를 푼다. 얻는 것은 세 가지다.

1. 큰 데이터가 KMS를 오가지 않아 빠르고 싸다.
2. 진짜 열쇠(KEK)는 KMS 밖으로 나오지 않는다. 접근은 IAM으로 통제되고 모든 사용이 감사 로그에 남는다.
3. **키 교체가 가볍다.** KMS 키를 교체하면 새 버전으로 새 DEK를 감싸고, 옛 버전은 옛 데이터를 풀기 위해 남겨 둔다. 데이터 전체를 다시 암호화할 필요가 없다.

### 키의 종류

| 종류 | 관리 | 고를 때 |
|---|---|---|
| 클라우드 관리 키 | 클라우드가 전부 | 기본. 대부분 충분 |
| 고객 관리 키 (CMK) | 우리가 정책·교체·비활성화 | 접근 통제와 감사, 키 폐기로 데이터 무력화가 필요할 때 |
| 외부·HSM 키 | 전용 하드웨어, 외부 보관 | 규제상 키를 직접 통제해야 할 때 |

고객 관리 키의 가장 큰 의미는 **키 정책으로 접근을 한 번 더 막을 수 있다**는 점이다. 버킷 권한이 실수로 열려도, 키 사용 권한이 없으면 데이터를 풀 수 없다. 반대로 키를 지우면 그 키로 암호화한 데이터는 영원히 못 푼다. 그래서 KMS는 키 삭제에 대기 기간을 둔다.

HSM은 키가 하드웨어 밖으로 나가지 않음을 보장하는 장비다. 관리형 KMS도 내부적으로 HSM을 쓰며, 전용 HSM(CloudHSM, Cloud HSM, Azure Dedicated/Managed HSM)은 단일 테넌트 통제가 필요할 때 쓴다.

## 깊게 7 — 비밀값 관리

DB 비밀번호, API 키, 인증서 같은 비밀값은 코드나 이미지, 환경 변수 파일에 넣지 않는다. 비밀 관리 서비스에 두고 실행할 때 가져온다.

| 클라우드 | 서비스 |
|---|---|
| AWS | Secrets Manager (설정값은 Parameter Store) |
| GCP | Secret Manager |
| Azure | Key Vault |

좋은 운영의 조건:

1. **읽는 권한을 워크로드 신원에만.** 앞의 워크로드 신원 연합과 묶인다. 비밀에 접근하는 열쇠가 또 다른 비밀이면 문제가 반복된다.
2. **자동 교체.** Secrets Manager는 Lambda를 이용해 DB 비밀번호를 주기적으로 바꾸는 기능이 있다. 교체 중에도 서비스가 끊기지 않도록, 앱이 새 값을 다시 읽거나 두 개의 사용자를 번갈아 쓰는 방식을 설계한다.
3. **버전과 감사.** 누가 언제 읽었는지 남는다. 사고 때 "이 비밀을 읽은 주체"를 찾을 수 있어야 한다.
4. **쿠버네티스에서는** Secret 객체가 기본적으로 base64일 뿐 암호화가 아니다. etcd 암호화를 켜고, 가능하면 외부 비밀 저장소와 연동(Secrets Store CSI 드라이버, External Secrets)한다.

가장 좋은 비밀은 **없는 비밀**이다. DB도 IAM 인증(RDS IAM 인증, Cloud SQL IAM 인증, Entra 인증)을 쓰면 비밀번호 자체가 사라진다.

## 깊게 8 — 네트워크 보안 계층과 제로 트러스트

네트워크 보안은 여러 겹으로 쌓는다. 한 겹이 뚫려도 다음 겹이 막는다(심층 방어).

| 계층 | 도구 | 막는 것 |
|---|---|---|
| 경계 | WAF, DDoS 보호 | SQL 주입, 봇, 대량 트래픽 |
| 서브넷 | NACL (AWS) | 서브넷 단위 거친 차단 |
| 인스턴스 | 보안 그룹, 방화벽 규칙, NSG | 포트·출발지 단위 허용 |
| 서비스 접근 | 프라이빗 엔드포인트 | 관리형 서비스를 인터넷 없이 |
| 앱 | 인증·인가, mTLS | 신원 기반 접근 |

몇 가지 깊이 있는 포인트:

- **보안 그룹은 상태 저장, NACL은 상태 비저장이다.** 보안 그룹은 들어온 요청의 응답이 자동으로 허용되지만, NACL은 응답 방향(임시 포트 범위)도 따로 열어야 한다.
- **보안 그룹은 다른 보안 그룹을 출발지로 지정할 수 있다.** IP 대신 "웹 서버 그룹에서 오는 것만 DB 그룹에 허용"처럼 역할 기반으로 규칙을 만들면 IP가 바뀌어도 규칙이 유지된다. GCP는 네트워크 태그나 서비스 계정을 대상으로 방화벽을 건다.
- **프라이빗 엔드포인트**(AWS PrivateLink·VPC 엔드포인트, GCP Private Service Connect·Private Google Access, Azure Private Endpoint)로 S3·KMS·DB 같은 관리형 서비스를 VPC 안 주소로 부른다. 인터넷 경로가 사라지고, 엔드포인트 정책이나 VPC Service Controls로 "이 네트워크에서만 이 자원에 접근"을 걸 수 있다. 데이터 유출 방지의 중요한 장치다.
- **WAF와 DDoS 보호**는 로드밸런서·CDN 앞에서 동작한다(AWS WAF·Shield, Cloud Armor, Azure WAF·DDoS Protection).

**제로 트러스트**는 "회사 네트워크 안이면 믿는다"를 버리는 것이다. 모든 요청을 신원, 기기 상태, 문맥으로 매번 확인한다. 실무 예:

- 관리 화면이나 내부 도구에 VPN 대신 **신원 인식 프록시**(GCP IAP, AWS Verified Access, Entra 애플리케이션 프록시)를 둔다. 로그인과 권한 확인을 통과한 사람만 들어간다.
- 서버 접속에 SSH 포트를 인터넷에 열지 않고, AWS Systems Manager Session Manager, GCP IAP TCP 포워딩, Azure Bastion으로 접속한다. 모든 세션이 기록된다.
- 서비스 사이 통신은 mTLS로 서로의 신원을 확인한다.

## 깊게 9 — 탐지와 대응

막는 것만큼 **알아채는 것**이 중요하다.

1. **감사 로그를 켜고 지킨다.** AWS CloudTrail(조직 전체, 별도 로그 계정에 보관), GCP Cloud Audit Logs(관리 활동은 기본, 데이터 접근은 켜야 함), Azure Activity Log와 Entra 로그인 로그. 로그 저장소는 지우거나 고칠 수 없게(객체 잠금, 보존 정책) 별도 계정·프로젝트에 둔다. 공격자가 가장 먼저 지우려는 것이 로그다.
2. **위협 탐지 서비스.** Amazon GuardDuty, Security Command Center, Microsoft Defender for Cloud가 비정상 API 호출, 알려진 악성 IP와의 통신, 자격 증명 오용을 찾아 준다.
3. **설정 점검.** AWS Config·Security Hub, SCC, Defender의 권장 사항으로 "공개된 버킷", "MFA 없는 관리자" 같은 설정 위반을 지속적으로 찾는다.
4. **SIEM으로 모은다.** 여러 클라우드와 IdP 로그를 한곳(Microsoft Sentinel, Google Security Operations, 또는 별도 SIEM)에 모아 상관 분석과 알람을 한다.

### 장애 대응 예시: 액세스 키가 공개 저장소에 올라갔다

면접 단골이다. 순서가 중요하다.

```
1 막기   → 키 비활성화
2 범위   → 그 키로 한 일 조사
3 정리   → 만든 것 제거·복구
4 원인   → 왜 키가 있었나
5 재발   → 키 자체를 없애기
```

1. **즉시 키를 비활성화한다.** 삭제보다 비활성화가 먼저다(조사용으로 남기고, 필요하면 다시 켤 수 있다). 대체 키가 필요한 워크로드는 새 키로 바꾸는데, 이때도 가능하면 임시 자격 증명 방식으로 옮긴다. 이미 발급된 임시 세션이 있으면 그 역할의 세션도 무효화한다(AWS는 역할에 "이 시각 이전 세션 거부" 정책을 붙이는 기능이 있다).
2. **그 키로 무슨 일이 있었는지 본다.** CloudTrail에서 해당 액세스 키 ID로 검색한다. 새 IAM 사용자·키 생성, 권한 변경, 낯선 리전의 VM 생성(채굴), 데이터 다운로드, 로그 비활성화 시도를 찾는다.
3. **공격자가 남긴 것을 정리한다.** 새로 생긴 사용자·역할·키, 백도어 정책, 낯선 리전 자원을 지운다. 데이터 유출이 의심되면 영향 범위를 정하고 보고 절차를 시작한다.
4. **저장소에서 지우는 것으로 끝나지 않는다.** git 기록과 포크, 캐시에 남는다. 그래서 1번이 먼저다.
5. **재발 방지.** 장기 키를 없애고 SSO·역할·워크로드 신원 연합으로 바꾼다. 커밋 전 비밀 탐지(pre-commit 훅, 저장소의 비밀 스캔)를 켠다. SCP로 IAM 사용자 키 생성을 막는 것도 방법이다.

## 깊게 10 — 공급망 보안과 규정 준수

### 공급망

우리 코드보다 **우리가 가져다 쓰는 것**(베이스 이미지, 라이브러리, CI 액션)이 공격 경로가 되는 경우가 늘었다.

- **취약점 스캔**: 레지스트리(ECR, Artifact Registry, ACR)와 CI에서 이미지와 의존성을 스캔한다. 심각도 기준을 정해 배포를 막는다.
- **SBOM**: 이미지 안에 무엇이 들어 있는지 목록을 만들어 둔다. 새 취약점이 발표되면 "우리 이미지 중 어디에 영향이 있는가"를 바로 찾을 수 있다.
- **서명과 검증**: CI에서 만든 이미지에 서명하고(Sigstore cosign, Notation), 클러스터는 서명된 이미지만 실행하도록 정책을 건다(GKE Binary Authorization, 쿠버네티스 승인 정책 도구).
- **이미지 고정**: 태그(`latest`)가 아니라 다이제스트(`@sha256:...`)로 배포해 같은 이름의 다른 이미지가 들어오지 못하게 한다.
- **CI 권한 최소화**: CI가 운영 환경 관리자 권한을 갖지 않게 하고, 외부 액션은 커밋 해시로 고정한다.

### 규정 준수

금융·통신처럼 규제가 있는 업계는 "안전하다"를 **증명**해야 한다. 클라우드 회사는 자기 책임 영역의 인증(ISO 27001, SOC 2 등) 보고서를 제공하고, 우리는 우리 영역의 통제를 증명한다. 엔지니어 관점에서 중요한 것은 **증명 가능한 구조**다.

- 모든 설정을 IaC로 두고 변경은 리뷰를 거친다(누가 왜 바꿨는지 남는다).
- 가드레일(SCP, 조직 정책, Azure Policy)로 위반 자체를 막는다.
- 지속적인 설정 점검으로 위반을 찾고 기록한다.
- 감사 로그를 변경 불가능하게 보관한다.

## 설계 예시 — 공통 기반의 보안 기본선

여러 팀이 쓰는 클라우드 공통 기반(랜딩 존)을 만든다고 하자. 보안 기본선을 이 순서로 깐다.

1. **계정·프로젝트 구조**: 환경(운영·스테이징·개발)과 팀을 계정·프로젝트·구독 단위로 나눈다. 계정 경계가 가장 강한 격리이고, 사고의 폭발 반경을 줄인다. 보안 도구 계정과 로그 보관 계정은 따로 둔다.
2. **신원**: 회사 IdP와 SSO 연동. 사람은 역할을 맡아 일하고 장기 키가 없다. 운영 관리자 권한은 승인 기반 임시 부여.
3. **가드레일**: 허용 리전 제한, 감사 로그 끄기 금지, 공개 버킷 차단, 서비스 계정 키 생성 금지, 공용 IP 제한을 조직 단위로 건다.
4. **워크로드 신원**: CI는 OIDC 연합, 쿠버네티스 파드는 워크로드 신원. 비밀은 비밀 저장소에.
5. **네트워크**: 허브-스포크 구조로 출입구를 중앙에 모은다. 관리형 서비스는 프라이빗 엔드포인트로. 관리 접속은 신원 인식 프록시나 세션 매니저로.
6. **암호화**: 기본 암호화에 더해, 민감 데이터는 고객 관리 키. 키 사용 권한을 데이터 권한과 분리한다.
7. **탐지**: 감사 로그를 로그 계정에 변경 불가로 모으고, 위협 탐지와 설정 점검을 전 계정에 자동 적용, 알람을 SIEM과 당번 체계에 연결한다.
8. **템플릿화**: 새 팀이 계정을 요청하면 이 모든 것이 자동으로 깔린 상태로 나오게 한다(AWS Control Tower와 Account Factory, GCP의 랜딩 존 청사진, Azure 랜딩 존). 팀은 가드레일 안에서 자유롭게 일한다.

"보안팀이 매번 검토하는 구조"가 아니라 "**안전한 것이 기본값인 구조**"를 만드는 것이 공통 기반 엔지니어의 일이다.

## 자주 하는 실수

- 개발 편의를 위해 `*:*`(전체 권한)를 주고 줄이는 일을 잊는다.
- OIDC 연합을 설정하면서 저장소·브랜치 조건을 빼먹는다.
- 서비스 계정 키를 "임시로" 만들고 몇 년 동안 쓴다.
- 쿠버네티스 Secret을 암호화된 저장소라고 착각한다.
- 로그를 같은 계정에 두어, 침입자가 로그부터 지운다.
- 키 유출 시 저장소에서 파일만 지우고 키를 비활성화하지 않는다.
- 노드 역할에 넓은 권한을 붙여 모든 파드가 그 권한을 공유한다.
- 보안 그룹에 `0.0.0.0/0` 으로 SSH나 DB 포트를 연다.
- 고객 관리 키를 쓰면서 키 정책과 삭제 대기 기간을 이해하지 못해, 키를 잘못 비활성화해 서비스를 멈춘다.

## 면접 질문 10개와 답

**1. 공동 책임 모델을 설명해 보라.**
클라우드 회사는 데이터센터와 하드웨어, 가상화 계층 같은 클라우드 자체의 보안을 책임지고, 사용자는 그 위에 올린 데이터와 권한, 설정, 애플리케이션을 책임진다. 경계는 서비스 종류에 따라 움직여서, VM이면 OS 패치까지 사용자 몫이고 서버리스로 갈수록 클라우드 쪽이 넓어진다. 하지만 어떤 서비스든 데이터와 권한, 설정은 끝까지 사용자 책임이다. 실제 사고 대부분이 이 영역의 실수라서, 클라우드 엔지니어의 보안 업무는 IAM과 설정 관리가 중심이다.

> 日本語: クラウド事業者はクラウド自体のセキュリティを、利用者はクラウド上のデータ・権限・設定を担当します。

**2. AWS에서 요청이 허용되는지 어떻게 판단하는가?**
기본은 거부이고, 어느 정책이든 명시적 Deny가 있으면 바로 거부된다. 그다음 SCP, 권한 경계, 세션 정책 같은 상한 정책을 모두 통과해야 하고, 그 범위 안에서 자격 증명 기반 정책이나 리소스 기반 정책이 허용을 줘야 최종 허용된다. 다른 계정에서 오는 요청은 호출하는 쪽과 자원 쪽 정책이 모두 허용해야 한다. 상한 정책은 허용을 주지 않고 울타리만 친다는 점이 핵심이다.

**3. SCP와 권한 경계는 어떻게 다른가?**
둘 다 허용을 주지 않는 상한이지만, SCP는 조직 관리자가 계정 단위로 거는 가드레일이고 계정 관리자도 벗어날 수 없다. 권한 경계는 특정 사용자나 역할에 붙는 상한으로, 개발팀에 역할 생성 권한을 위임하면서 권한 상승을 막을 때 쓴다. 예를 들어 "만드는 역할은 반드시 이 경계를 달아야 한다"는 조건을 걸면 개발자가 자기보다 강한 역할을 만들 수 없다.

**4. 다른 계정의 자원에 접근하게 하려면?**
장기 키 대신 역할 위임을 쓴다. 대상 계정의 역할 신뢰 정책에 호출하는 쪽의 특정 역할을 주체로 허용하고, 호출하는 쪽 역할에는 그 역할에 대한 AssumeRole 권한을 준다. 그러면 STS가 짧은 임시 자격 증명을 발급하고 모든 위임이 감사 로그에 남는다. 외부 업체라면 External ID 조건을 넣어 혼동된 대리인 문제를 막는다.

**5. GCP 서비스 계정 키를 피하라는 이유는?**
키 파일은 만료가 없고 복사되기 쉬워 유출되면 오래 악용된다. GCP 안에서는 자원에 서비스 계정을 붙여 메타데이터 서버에서 짧은 토큰을 받고, GKE는 Workload Identity, 외부 CI나 다른 클라우드는 Workload Identity Federation을 쓴다. 사람은 서비스 계정 가장으로 짧은 토큰을 받는다. 조직 정책으로 키 생성 자체를 막아 두는 것이 좋다.

> 日本語: サービスアカウントキーは有効期限がなく漏洩リスクが高いので、Workload Identity連携で短期トークンを使います。

**6. CI에 장기 키 없이 배포 권한을 주는 방법은?**
CI가 발급하는 OIDC 토큰을 클라우드가 신뢰하도록 공급자를 등록하고, 토큰을 짧은 자격 증명으로 교환한다. 가장 중요한 것은 신뢰 조건을 저장소와 브랜치나 환경까지 좁히는 것이다. 조건이 없으면 같은 CI 서비스를 쓰는 다른 저장소의 토큰도 통과할 수 있다. 결과적으로 돌려야 할 키가 사라지고 배포 기록이 감사 로그에 남는다.

**7. 봉투 암호화는 무엇이고 왜 쓰는가?**
데이터는 로컬에서 만든 데이터 키로 암호화하고, 그 데이터 키만 KMS의 키 암호화 키로 감싸서 함께 저장하는 방식이다. 큰 데이터가 KMS를 오가지 않아 빠르고, 진짜 키는 KMS 밖으로 나오지 않으며 사용 기록이 남는다. 키를 교체해도 데이터 전체를 다시 암호화할 필요 없이 새 버전으로 새 데이터 키를 감싸면 된다.

**8. 고객 관리 키는 언제 쓰는가?**
기본 암호화로 충분한 경우가 많지만, 키 정책으로 데이터 접근을 한 번 더 통제하고 싶을 때, 키 사용을 감사해야 할 때, 키를 폐기해 데이터를 무력화할 수 있어야 할 때 쓴다. 버킷 권한이 실수로 열려도 키 권한이 없으면 복호화할 수 없다는 이중 통제가 장점이다. 대신 키 정책 실수나 비활성화가 장애로 이어질 수 있어 운영 책임이 커진다.

**9. 액세스 키가 유출되었다. 무엇을 하겠는가?**
먼저 키를 비활성화하고, 그 키로 맡은 세션이 있으면 무효화한다. 그다음 감사 로그에서 그 키로 한 행동을 찾아 새 사용자나 키 생성, 권한 변경, 낯선 리전 자원 생성, 데이터 접근을 확인하고 정리한다. 저장소에서 파일을 지우는 것만으로는 기록과 포크에 남기 때문에 비활성화가 우선이다. 마지막으로 장기 키를 없애고 역할과 워크로드 신원 연합으로 바꾸며 커밋 전 비밀 탐지를 켜서 재발을 막는다.

> 日本語: まずキーを無効化し、監査ログで影響範囲を調査してから、長期キーをなくす仕組みに変えます。

**10. 공통 기반을 설계할 때 보안을 어떻게 나누는가?**
계정·프로젝트 경계로 격리하고, SSO와 임시 권한으로 사람의 신원을 관리하며, 조직 단위 가드레일로 위반을 원천 차단한다. 워크로드는 연합 신원과 비밀 저장소를 쓰고, 네트워크는 허브-스포크와 프라이빗 엔드포인트로 출입을 모은다. 감사 로그는 별도 계정에 변경 불가로 모으고 위협 탐지와 설정 점검을 자동 적용한다. 그리고 이 모든 것을 템플릿화해 새 계정이 안전한 기본값으로 나오게 한다.

## 정답

1. 아니다. SCP는 상한일 뿐 허용을 주지 않는다. 사용자의 자격 증명 기반 정책(또는 리소스 기반 정책)이 따로 허용해야 한다.
2. 양쪽 모두다. 호출하는 계정의 주체 정책이 그 버킷 읽기를 허용하고, 버킷의 리소스 정책도 그 주체를 허용해야 한다.
3. 같은 노드의 모든 파드가 같은 권한을 공유한다. 한 파드가 뚫리면 다른 워크로드의 권한까지 쓸 수 있다. 워크로드 신원으로 파드마다 권한을 나눈다.
4. 아니다. 새 버전 키로 새 데이터 키를 감싸고, 옛 버전은 기존 데이터 키를 풀기 위해 남는다.
5. NACL이다. 상태 비저장이라 응답이 돌아오는 임시 포트 범위를 따로 열어야 한다. 보안 그룹은 상태 저장이라 응답이 자동 허용된다.
