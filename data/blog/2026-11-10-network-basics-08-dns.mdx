## 질문

DNS 레코드를 새 서버 주소로 바꿨다. 그런데 일부 사용자는 한 시간째 옛 서버로 간다. 또 어떤 사용자는 새로 만든 이름이 "없는 도메인"이라고 나온다. 둘 다 왜 그럴까?

답은 둘 다 **캐시**다. 하나는 "있는 답"의 캐시, 하나는 "없다는 답"의 캐시. 이 글은 DNS가 어떻게 답을 찾고, 어디에 얼마나 기억하는지부터 시작해서, 운영하며 자주 밟는 함정까지 간다.

## 1. 왜 이런 구조가 됐나

인터넷 초기에는 모든 컴퓨터의 이름과 주소를 적은 파일(HOSTS.TXT) 하나를 한 곳에서 관리하고, 모두가 그 파일을 주기적으로 내려받았다. 지금도 맥과 리눅스에 남아 있는 `/etc/hosts` 가 그 흔적이다.

컴퓨터가 늘자 이 방식은 무너졌다. 파일은 커지고, 갱신은 느리고, 한 곳이 모든 이름을 책임졌다. 그래서 1980년대에 나온 DNS는 세 가지 원칙으로 설계됐다.

- **계층으로 나눈다.** 이름을 점으로 끊어 트리로 만든다.
- **책임을 위임한다.** 각 층은 바로 아래층의 담당자만 알면 된다.
- **기억해 둔다.** 한 번 물어본 답은 정해진 시간 동안 캐시한다.

이 세 가지가 DNS가 전 세계 규모로 돌아가는 이유이자, 운영에서 겪는 문제 대부분의 원인이다.

## 2. 이름의 트리와 위임

`www.example.com.` 을 오른쪽부터 읽으면 트리의 경로다. 맨 끝의 점은 **루트**다(평소엔 생략한다).

```
.             루트
└ com.        TLD
  └ example.  도메인
    └ www     호스트
```

- 루트는 `com`, `jp`, `kr` 같은 TLD의 담당 서버만 안다.
- `com` 담당 서버는 `example.com` 의 담당 서버만 안다.
- `example.com` 담당 서버가 `www.example.com` 의 실제 주소를 안다.

"아래층 담당자를 알려 주는 것"을 **위임**이라고 한다. 위임받아 한 담당자가 책임지는 범위를 **영역**(zone)이라고 한다. 도메인을 사면 등록기관을 통해 `com` 서버에 "example.com의 담당은 이 서버들"이라는 위임 정보(NS 레코드)가 올라간다.

## 3. 세 종류의 등장인물

| 역할 | 하는 일 | 예 |
|---|---|---|
| 스텁 리졸버 | 앱 대신 리졸버에 묻는 OS 부품 | 맥·리눅스 내장 |
| 재귀 리졸버 | 끝까지 물어서 답을 가져오고 캐시 | 통신사 DNS, 8.8.8.8, VPC 리졸버 |
| 권한 서버 | 자기 영역의 정답을 가짐 | Route 53, Cloud DNS 영역 |

앱이 "이 이름의 주소는?"이라고 물으면, OS의 스텁 리졸버가 설정된 재귀 리졸버(집에서는 공유기, 회사에서는 사내 DNS)에 묻는다. 재귀 리졸버가 실제 탐색을 맡는다. 권한 서버는 남에게 묻지 않고 자기 영역의 답만 한다.

중간에 **포워더**가 끼기도 한다. 사내 DNS가 직접 탐색하지 않고 다른 리졸버에게 "대신 물어 줘"라고 넘기는 구성이다.

## 4. 조회 한 번을 끝까지 따라가기

캐시가 하나도 없다고 가정하고, 재귀 리졸버가 `www.example.com` 의 A 레코드를 찾는 과정이다.

**1단계: 루트에게.** 리졸버는 루트 서버들의 주소를 처음부터 알고 있다(루트 힌트 파일). 루트에게 묻는다.

```
리졸버 → 루트
  www.example.com A?
루트 → 리졸버
  모름. com은 이 서버들에게.
  (com의 NS + 그 IP)
```

**2단계: com 서버에게.**

```
리졸버 → com 서버
  www.example.com A?
com → 리졸버
  모름. example.com은
  ns1.example.com에게.
  (NS + 글루 IP)
```

**3단계: example.com 서버에게.**

```
리졸버 → ns1.example.com
  www.example.com A?
ns1 → 리졸버
  93.184.215.14
  TTL 300
```

리졸버는 이 답과 중간에 받은 위임 정보(com 담당, example.com 담당)를 **각자의 TTL 동안 전부 캐시**한다. 다음에 누가 `mail.example.com` 을 물으면 루트와 com을 건너뛰고 바로 3단계로 간다.

### 글루 레코드: 닭과 달걀 풀기

2단계에서 이상한 점이 있다. example.com의 담당 서버 이름이 `ns1.example.com` 이다. 그런데 `ns1.example.com` 의 주소를 알려면 example.com 담당 서버에 물어야 한다. 끝없는 순환이다.

그래서 위임할 때 상위(com 서버)가 담당 서버의 **IP까지 같이** 준다. 이 덤으로 주는 주소를 **글루 레코드**라고 한다. 담당 서버 이름이 자기 영역 안에 있을 때만 필요하다.

## 5. 레코드 종류

| 레코드 | 뜻 |
|---|---|
| A / AAAA | 이름 → IPv4 / IPv6 |
| CNAME | 이름 → 다른 이름 (별명) |
| NS | 이 영역의 권한 서버 |
| SOA | 영역의 기본 정보 |
| MX | 메일 받는 서버 |
| TXT | 자유 텍스트 (소유 확인, SPF 등) |
| CAA | 인증서 발급 허용 CA |
| SRV | 서비스의 호스트와 포트 |
| PTR | IP → 이름 (역방향) |

몇 가지는 더 알아 둘 만하다.

**SOA.** 영역마다 하나 있는 "영역 설명서"다. 대표 권한 서버, 관리자 연락처, 일련번호(바뀔 때마다 증가), 보조 서버가 동기화할 주기, 그리고 **부정 응답 캐시 시간**(6절)이 들어 있다.

**CNAME 규칙.** CNAME이 있는 이름에는 다른 레코드를 둘 수 없다. 그래서 영역 꼭대기(`example.com` 자체, apex)에는 CNAME을 못 쓴다. 꼭대기에는 SOA와 NS가 반드시 있기 때문이다. 클라우드는 이 제약을 피하려고 꼭대기에서도 로드밸런서 같은 자원을 가리킬 수 있는 자체 레코드(Route 53 Alias 등)를 준다. CNAME과 달리 리졸버 입장에서는 그냥 A 레코드로 보인다.

**CAA.** "우리 도메인의 인증서는 이 CA만 발급할 수 있다"를 선언한다. CA는 발급 전에 이 레코드를 확인해야 한다. 07편의 인증서 투명성과 함께 엉뚱한 발급을 막는 장치다.

**SRV.** `_서비스._프로토콜.이름` 형식으로 "이 서비스는 어느 호스트의 몇 번 포트에 있다"를 우선순위·가중치와 함께 알려 준다. 쿠버네티스의 Service 이름, 일부 메일·디렉터리 서비스가 쓴다.

## 6. TTL과 캐시, 그리고 부정 캐시

### 캐시는 여러 겹이다

```
앱 / 브라우저 캐시
  ↓
OS 캐시
  ↓
재귀 리졸버 캐시
  ↓
권한 서버 (원본)
```

각 층은 받은 답을 **TTL 초 동안** 기억한다. TTL은 권한 서버의 운영자, 즉 우리가 레코드마다 정한다.

- TTL이 길면: 조회가 빠르고 권한 서버 부담이 적다. 대신 바꿔도 늦게 반영된다.
- TTL이 짧으면: 빨리 반영된다. 대신 조회가 늘고, 권한 서버나 리졸버가 잠깐 아플 때 바로 영향이 온다.

처음 질문의 "한 시간째 옛 서버" 는 TTL이 3600이었다는 뜻이다.

### "없다"는 답도 캐시한다

없는 이름을 물으면 권한 서버는 **NXDOMAIN**(그런 이름 없음)이라고 답한다. 리졸버는 이 "없음"도 캐시한다. 이게 **부정 캐시**다. 캐시 시간은 그 영역의 SOA에 적힌 값으로 정해진다(SOA 레코드 자체의 TTL과 SOA의 마지막 칸 중 작은 값).

여기서 처음 질문의 두 번째 증상이 나온다.

1. 새 서비스 `api.example.com` 을 띄우기 전에, 누가(또는 배포 스크립트가) 그 이름을 먼저 조회했다.
2. 리졸버가 NXDOMAIN을 캐시했다.
3. 그 뒤에 레코드를 만들었다.
4. 부정 캐시가 끝날 때까지, 그 리졸버를 쓰는 사람에게는 계속 "없는 도메인"이다.

대응: 레코드를 **먼저 만들고** 그다음에 조회한다. 그리고 SOA의 부정 캐시 시간을 너무 길게 두지 않는다.

## 7. 전송: UDP, TCP, EDNS

DNS 조회는 기본적으로 **UDP 53번**을 쓴다. 질문 하나, 답 하나라서 TCP의 연결 비용(03편)이 아깝기 때문이다.

- 원래 UDP 응답은 512바이트로 제한됐다.
- **EDNS**라는 확장으로 "나는 더 큰 UDP 응답도 받을 수 있다"를 알려서 그 제한을 늘렸다.
- 그래도 응답이 너무 크면 서버는 잘린 응답에 "잘렸음" 표시(TC 비트)를 붙인다. 클라이언트는 **TCP 53번**으로 다시 묻는다.
- 영역 전체를 다른 서버로 복사하는 존 전송도 TCP를 쓴다.

함정: 방화벽에서 "DNS는 UDP 53만 열면 된다"고 TCP 53을 막으면, 평소에는 멀쩡하다가 **응답이 큰 경우에만** 실패한다. 레코드가 많은 이름이나 DNSSEC 서명이 붙은 응답이 그렇다. 02편의 "큰 것만 멈추는" 장애와 같은 모양이다.

## 8. 애니캐스트: 같은 주소, 여러 장소

루트 서버는 이름이 a부터 m까지 13개뿐이지만, 실제 서버는 전 세계 수많은 곳에 있다. 8.8.8.8이나 1.1.1.1도 마찬가지다. 비결은 **애니캐스트**다.

- 여러 장소의 서버가 **같은 IP 주소**를 인터넷에 광고한다.
- 인터넷의 라우팅(BGP)이 각 사용자를 **네트워크상 가장 가까운** 장소로 보낸다.
- 한 장소가 죽으면 그 광고가 사라지고, 트래픽은 자동으로 다음으로 가까운 곳으로 간다.

DNS가 애니캐스트와 잘 맞는 이유는 UDP 질문 하나, 답 하나로 끝나기 때문이다. 중간에 경로가 바뀌어도 잃을 연결 상태가 없다. 같은 원리를 CDN과 글로벌 로드밸런서(09편)도 쓴다.

## 9. DNS를 지키는 두 가지: DNSSEC과 DoH·DoT

DNS는 원래 평문이고, 답이 진짜인지 확인하는 장치가 없었다. 문제는 두 갈래다.

**위조된 답(캐시 오염).** 공격자가 리졸버에 가짜 답을 먼저 밀어 넣으면, 그 리졸버를 쓰는 모두가 가짜 주소로 간다. 이걸 막는 게 **DNSSEC**이다.
- 권한 서버가 레코드에 서명(RRSIG)을 붙이고, 서명 검사용 공개키(DNSKEY)를 공개한다.
- 상위 영역이 하위 영역 키의 지문(DS 레코드)을 자기 쪽에 둔다.
- 이렇게 루트까지 서명이 이어지는 **신뢰 사슬**이 생긴다. 07편 인증서 체인과 같은 구조다.
- DNSSEC은 **암호화가 아니다.** 답이 진짜인지만 보장하고, 누가 무엇을 물었는지는 그대로 보인다.
- 운영 부담이 크다. 키 교체를 잘못하면 서명 검증이 실패해서 도메인 전체가 "없는 것"이 된다.

**엿보기.** 내가 어떤 사이트에 가는지가 DNS 질문으로 다 드러난다. 이걸 막는 게 리졸버까지의 구간을 암호화하는 **DoT**(TLS 위 DNS, 853번 포트)와 **DoH**(HTTPS 위 DNS, 443번 포트)다. 브라우저와 OS가 점점 기본으로 켜고 있다.

정리하면 DNSSEC은 "답이 진짜인가", DoH·DoT는 "남이 엿보나"를 푼다. 서로 다른 문제다.

## 10. 사설 DNS와 하이브리드

**사설 영역.** VPC 안에서만 보이는 영역을 만들어 `db.internal` 같은 이름을 쓴다. 서버 IP가 바뀌어도 레코드만 고치면 앱 설정은 그대로다. AWS의 Private Hosted Zone, GCP Cloud DNS의 비공개 영역이 여기 해당한다.

**스플릿 호라이즌.** 같은 이름에 대해 안에서 물으면 사설 IP, 밖에서 물으면 공인 IP를 답하는 구성이다. 내부 트래픽이 인터넷을 돌아 나가지 않게 한다. 대신 "어디서 물었느냐에 따라 답이 다르다"는 점을 잊으면 디버깅이 헷갈린다.

**하이브리드 전달.** 회사 데이터센터와 클라우드 VPC가 연결돼 있으면, 서로의 사설 이름을 풀어야 한다.

```
온프레 → 클라우드 이름
  온프레 DNS 조건부 전달
  → 클라우드 인바운드
    엔드포인트

클라우드 → 온프레 이름
  아웃바운드 엔드포인트
  + 전달 규칙
  → 온프레 DNS
```

AWS는 Route 53 Resolver의 인바운드·아웃바운드 엔드포인트, GCP는 Cloud DNS의 전달 영역과 인바운드 서버 정책으로 이걸 만든다. 대역(05편)과 라우팅(04편)이 먼저 맞아야 DNS 전달도 동작한다.

## 11. 쿠버네티스의 DNS와 ndots 함정

쿠버네티스 안에서는 **CoreDNS**가 리졸버 역할을 한다. Service를 만들면 `서비스.네임스페이스.svc.cluster.local` 이 그 Service의 ClusterIP로 풀린다. 같은 네임스페이스면 `서비스` 이름만으로도 된다.

어떻게 짧은 이름이 될까? 파드의 `/etc/resolv.conf` 에 **검색 도메인**이 들어 있기 때문이다.

```
search ns.svc.cluster.local
       svc.cluster.local
       cluster.local
options ndots:5
```

`ndots:5` 는 "이름에 점이 5개 미만이면, 검색 도메인을 하나씩 붙여서 먼저 시도해 보라"는 뜻이다.

함정은 **외부 이름**이다. 파드가 `api.example.com`(점 2개)을 물으면:

```
api.example.com.ns.svc.cluster.local
api.example.com.svc.cluster.local
api.example.com.cluster.local
api.example.com   ← 여기서 성공
```

실패할 질문을 먼저 여러 번 하고 나서야 진짜 이름을 묻는다. IPv4·IPv6 질문을 따로 하면 그 두 배다. 외부 API를 많이 부르는 서비스에서는 DNS 질의가 몇 배로 늘고, CoreDNS가 바빠지고, 지연이 붙는다.

대응:
- 외부 이름 끝에 점을 붙여 완전한 이름(`api.example.com.`)으로 쓴다. 검색 도메인을 건너뛴다.
- 해당 파드의 `ndots` 를 낮춘다(dnsConfig).
- 노드마다 DNS 캐시를 두는 NodeLocal DNSCache를 쓴다.

## 12. 자주 막히는 장애 사례

**1. 바꿨는데 옛 서버로 간다**
- 원인: TTL 동안의 캐시. 또는 TTL을 무시하고 오래 캐시하는 클라이언트(일부 JVM 설정, 연결 풀이 주소를 한 번만 푸는 라이브러리).
- 해결: 13절의 전환 절차. 옛 서버는 트래픽이 0이 될 때까지 남긴다.

**2. 새로 만든 이름이 "없다"고 나온다**
- 원인: 부정 캐시(6절).
- 해결: 레코드를 먼저 만들고 조회한다. 급하면 해당 리졸버의 캐시를 비운다.

**3. 새 호스팅 영역에 레코드를 넣었는데 아무 변화가 없다**
- 원인: 위임 불일치. 등록기관에 등록된 NS는 여전히 옛 DNS 서비스를 가리키는데, 새 서비스에 영역을 만들고 거기에만 레코드를 넣었다.
- 해결: `dig NS 도메인 @상위서버` 로 실제 위임을 확인하고, 등록기관의 NS를 새 영역의 NS로 바꾼다. NS 변경 자체도 TTL이 길어서 넉넉히 기다린다.

**4. 큰 응답만 실패한다**
- 원인: TCP 53 차단, 또는 큰 UDP 조각이 중간에서 버려짐(7절).
- 해결: TCP 53 허용, EDNS 버퍼 크기 조정.

**5. 모든 게 한꺼번에 느리거나 죽는다**
- 원인: 리졸버 장애. DNS가 죽으면 서버는 멀쩡해도 모든 서비스가 죽은 것처럼 보인다. 쿠버네티스에서는 CoreDNS 과부하(11절)가 흔하다.
- 해결: 리졸버 이중화, 노드 로컬 캐시, DNS 질의 수와 실패율 모니터링.

## 13. DNS로 서버를 옮기는 절차

1. **미리 TTL을 낮춘다.** 전환 하루~이틀 전, 레코드 TTL을 60초 정도로 낮춘다. 그리고 **이전 TTL만큼** 기다린다. 이전 TTL이 하루였다면 하루를 기다려야 모든 캐시가 새 TTL을 갖게 된다.
2. **새 서버를 준비하고 직접 확인한다.** 호스트 파일이나 `curl --resolve` 로 새 주소에 붙어 본다.
3. **레코드를 바꾼다.** 1~2분 안에 대부분의 트래픽이 넘어온다.
4. **옛 서버를 관찰한다.** 들어오는 요청이 0에 가까워질 때까지 끄지 않는다. 늦게 오는 클라이언트를 위해서다.
5. **TTL을 원래대로 올린다.**

**DNS 장애 조치의 한계.** 헬스체크와 묶어서 "주 서버가 죽으면 보조 주소를 답한다"를 자동으로 할 수 있다. 하지만 헬스체크가 장애를 감지하는 시간 + TTL + 클라이언트 캐시가 더해져서, 실제 전환에는 대개 분 단위가 걸린다. 초 단위 전환이 필요하면 DNS가 아니라 로드밸런서나 애니캐스트(09편)로 해야 한다.

## 14. 클라우드에서는

- **Route 53 라우팅 정책**: 단순, 가중치(일부만 새 버전으로), 지연 시간 기반(가장 가까운 리전), 장애 조치(헬스체크 연동), 지리 기반.
- **사설 영역**: VPC에 붙여서 그 안에서만 보이게. 여러 VPC에 같은 영역을 붙일 수 있다.
- **하이브리드**: Route 53 Resolver 엔드포인트, Cloud DNS 전달 영역·피어링 영역.
- **VPC 기본 리졸버**: AWS는 VPC 대역의 두 번째 주소(+2)에, GCP는 메타데이터 서버 주소에 리졸버가 있다. 인스턴스는 기본으로 이걸 쓴다.
- **쿠버네티스**: CoreDNS, NodeLocal DNSCache, 외부 DNS 레코드를 자동으로 만들어 주는 external-dns.



```bash
# TCP로 묻기, CAA 보기
```

```bash
# 맥 DNS 캐시 비우기
sudo dscacheutil -flushcache
sudo killall -HUP mDNSResponder
```

같은 질문을 두 번 하면 두 번째 답의 TTL이 줄어 있다. 캐시에서 나온 답이라는 뜻이다.

## 면접 한 줄 답

> DNSはリゾルバがルートから順に権威サーバーに問い合わせて名前を解決し、TTLの間キャッシュします。切り替えの前にTTLを短くしておき、古いサーバーはトラフィックがなくなるまで残します。

DNS는 리졸버가 루트부터 차례로 권한 서버에 물어 이름을 풀고 TTL 동안 캐시합니다. 전환 전에 TTL을 줄여 두고, 옛 서버는 트래픽이 없어질 때까지 남겨 둡니다.

### 꼬리질문

**Q. 새로 만든 레코드가 일부 사용자에게만 안 보이는 이유는?**
레코드를 만들기 전에 누가 조회해서 리졸버가 NXDOMAIN을 캐시했을 수 있습니다. SOA에 정해진 부정 캐시 시간 동안은 계속 "없음"으로 보입니다.

**Q. DNSSEC을 쓰면 DNS가 암호화되나요?**
아닙니다. DNSSEC은 답이 위조되지 않았는지를 서명으로 보장할 뿐이고, 질의 내용은 보입니다. 암호화는 DoH나 DoT가 합니다.

**Q. DNS 장애 조치로 무중단 전환이 되나요?**
헬스체크 감지 시간과 TTL, 클라이언트 캐시 때문에 보통 분 단위가 걸립니다. 초 단위가 필요하면 로드밸런서나 애니캐스트로 전환합니다.

## 정답

1. 담당 서버의 이름이 그 영역 안에 있을 때(`example.com` 의 NS가 `ns1.example.com`). 그 이름을 풀려면 그 서버에 물어야 하는 순환을 끊기 위해, 상위 영역이 IP를 같이 준다.
2. CNAME이 있는 이름에는 다른 레코드를 둘 수 없는데, 꼭대기에는 SOA와 NS가 반드시 있어야 하기 때문이다. 클라우드는 Alias 같은 자체 레코드로 해결한다.
3. 레코드를 만들기 전에 조회해서 NXDOMAIN이 캐시되면, 만든 뒤에도 한동안 "없음"으로 보인다. 레코드를 먼저 만들고 조회하며, SOA의 부정 캐시 시간을 너무 길게 두지 않는다.
4. 응답이 커서 UDP로 다 못 보내 TCP로 다시 물어야 할 때. 레코드가 많거나 DNSSEC 서명이 붙은 응답에서만 실패한다.
5. `ndots:5` 와 검색 도메인 때문에, 점이 5개 미만인 이름은 검색 도메인을 붙인 이름부터 차례로 시도한다. 이름 끝에 점을 붙이거나, ndots를 낮추거나, 노드 로컬 DNS 캐시를 쓴다.
