## 질문

이벤트 때문에 트래픽이 10배로 뛴다. 서버를 어떻게 늘리고, 요청은 누가 나눠 줄까?

## 스케일 업과 스케일 아웃

| | 스케일 업 | 스케일 아웃 |
|---|---|---|
| 방법 | 서버 한 대를 더 크게 | 같은 서버를 여러 대로 |
| 장점 | 앱을 안 바꿔도 된다 | 한계가 거의 없고, 한 대가 죽어도 버틴다 |
| 단점 | 한계가 있고, 그 한 대가 단일 장애점 | 앱이 상태를 안 가져야 한다 (세션을 밖에) |

스케일 아웃을 하면 "요청을 여러 대에 나눠 주는" 장치가 필요하다. 그게 **로드밸런서**다.

## L4와 L7

| | L4 로드밸런서 | L7 로드밸런서 |
|---|---|---|
| 보는 것 | IP, 포트 | HTTP 경로, 헤더, 쿠키 |
| 할 수 있는 것 | 연결 단위로 분배 | 요청 단위로 분배, `/api` 는 A로 `/img` 는 B로 |
| TLS | 그대로 통과 가능 | 보통 여기서 종단 |
| 속도 | 빠르다 | 내용을 열어 보는 만큼 비용 |
| 예 | AWS NLB, GCP 네트워크 LB | AWS ALB, GCP 애플리케이션 LB, Envoy, nginx |

HTTP 서비스면 대개 L7, DB나 TCP 프로토콜이면 L4다.

## 분배 방식

- **라운드 로빈:** 차례대로. 서버 성능이 같고 요청 무게가 비슷할 때.
- **최소 연결:** 지금 연결이 가장 적은 서버로. 요청마다 처리 시간이 크게 다를 때.
- **가중치:** 서버마다 비율을 정한다. 새 버전에 10%만 보내는 카나리 배포에 쓴다.
- **해시(IP·쿠키):** 같은 사용자를 같은 서버로(스티키 세션). 편하지만 한 서버에 쏠릴 수 있어서, 세션을 Redis 같은 외부 저장소로 빼는 게 낫다.

## 장애를 만드는 세 가지 설정

**1. 헬스체크.** 로드밸런서는 주기적으로 서버에 물어보고, 대답 없는 서버는 빼고 보낸다. 헬스체크 경로가 DB까지 확인하면, DB가 잠깐 느려질 때 **모든 서버가 동시에 빠져** 전체 장애가 된다. 헬스체크는 "이 프로세스가 요청을 받을 수 있나"만 가볍게 보는 게 보통이다.

**2. 타임아웃의 순서.** 앞단이 뒷단보다 짧으면, 뒷단은 일을 끝냈는데 앞단은 이미 포기하고 에러(504)를 준다. 바깥에서 안쪽으로 갈수록 타임아웃을 조금씩 짧게 잡는 게 원칙이다. 앱의 keep-alive는 로드밸런서의 유휴 타임아웃보다 길게(03편).

**3. 재시도.** 실패한 요청을 다른 서버로 다시 보내면 성공률이 오른다. 하지만 결제 같은 쓰기 요청을 두 번 보내면 두 번 처리될 수 있다. 쓰기 요청은 **멱등 키**(같은 키의 요청은 한 번만 처리)를 붙이거나 재시도하지 않는다. 그리고 모두가 동시에 재시도하면 회복 중인 서버를 다시 쓰러뜨리므로, 간격을 점점 늘리고(지수 백오프) 무작위 지연을 섞는다.

## 트래픽이 몰릴 때 앞에서부터 줄이기

서버를 늘리기 전에, 서버까지 오는 요청 자체를 줄이는 게 싸다.

1. **CDN·캐시:** 이미지, 정적 파일, 자주 같은 응답은 서버까지 안 오게.
2. **속도 제한(rate limit):** 한 사용자·IP가 보내는 양을 제한.
3. **대기열:** 바로 처리 안 해도 되는 일(메일 발송, 이미지 변환)은 큐에 넣고 천천히.
4. **오토스케일링:** 그다음에 서버 수를 자동으로 늘리고 줄인다. 늘어나는 데 몇 분 걸리므로 예정된 이벤트는 미리 늘려 둔다.
5. **DB가 마지막 병목:** 읽기 복제본, 연결 풀, 캐시로 DB까지 가는 요청을 줄인다.

## 직접 확인 (맥 터미널)

```bash
# 로드밸런서 뒤의 서버가 여러 대면, 여러 번 물을 때마다 다른 IP가 나오기도 한다
for i in 1 2 3; do dig +short www.amazon.com | tail -1; done

# 응답 헤더에서 어떤 프록시·서버가 처리했는지 보기
curl -sI https://example.com | grep -iE 'server|via|x-cache|age'

# 간단한 부하 (Apache Bench가 있다면): 100개 요청, 동시 10개
ab -n 100 -c 10 https://example.com/
```

남의 서비스에 부하를 거는 건 하면 안 된다. `ab` 는 내 로컬 서버(`python3 -m http.server`)에 대고 연습한다.

## 클라우드에서는

- 로드밸런서 자체도 여러 AZ에 걸쳐 둔다. 뒤의 서버도 AZ마다 나눠 둬야 한 AZ 장애를 버틴다.
- 오토스케일링 기준은 CPU만 보지 말고 요청 수나 대기열 길이처럼 실제 부하를 반영하는 지표로.
- 배포할 때는 로드밸런서에서 빠지는 서버가 처리 중이던 요청을 마저 끝내도록 연결 드레이닝(등록 해제 지연)을 건다. 이게 없으면 배포 때마다 일부 요청이 끊긴다.
- 로드밸런서 하나가 단일 장애점이 되지 않도록, 리전 단위 장애까지 대비하려면 DNS나 글로벌 로드밸런서로 다른 리전에 넘기는 구성을 둔다.
