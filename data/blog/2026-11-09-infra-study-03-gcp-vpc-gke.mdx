## AWS와 가장 다른 점

| | AWS | GCP |
|---|---|---|
| VPC 범위 | 리전 | **전역** |
| 서브넷 범위 | 가용 영역(AZ) | **리전** |
| 밖으로 나가는 NAT | 서브넷에 두는 NAT Gateway | **Cloud Router에 붙는 Cloud NAT** (관리형, 서버 없음) |
| 방화벽 | 인스턴스의 보안 그룹 | **VPC 단위 방화벽 규칙**, 네트워크 태그·서비스 계정으로 대상 지정 |
| 프로젝트·계정 | 계정 | 프로젝트 (결제는 결제 계정에 연결) |

GCP는 VPC가 전역이라 서울과 도쿄 서브넷이 같은 VPC 안에서 바로 통신한다. AWS라면 VPC 피어링이나 Transit Gateway가 필요한 일이다.

## 방화벽 규칙

GCP 방화벽 규칙은 VPC에 걸고, 대상을 **네트워크 태그**나 **서비스 계정**으로 고른다.

```
허용: tcp:22 / 출발 35.235.240.0/20 (IAP) / 대상 태그 ssh-allowed
```

`35.235.240.0/20`은 IAP(Identity-Aware Proxy) TCP 전달 대역이다. VM에 공인 SSH 포트를 열지 않고도 `gcloud compute ssh --tunnel-through-iap`로 접속할 수 있다. 공인 22번 포트를 닫아 두는 좋은 기본값이다.

## Cloud NAT

사설 IP만 가진 VM·GKE 노드가 밖으로 나가려면 Cloud NAT가 필요하다. 출발 IP를 **고정 IP로 예약**해 두면, 외부 시스템 허용 목록에 넣을 값이 안정된다. 자동 할당으로 두면 IP가 바뀔 수 있다.

## GKE의 주소: VPC 네이티브

GKE는 서브넷에 **보조 범위(secondary range)** 두 개를 둔다.

| 범위 | 쓰임 |
|---|---|
| 기본 범위 | 노드 IP |
| 보조 범위 1 | 파드 IP |
| 보조 범위 2 | 서비스(ClusterIP) IP |

파드 IP가 VPC에서 라우팅되므로 같은 VPC의 VM이 파드에 직접 닿는다. 설계할 때 세 범위가 다른 네트워크(온프레미스, 다른 클라우드)와 겹치지 않게 미리 나눠 둔다. 나중에 바꾸기 어렵다.

## API를 먼저 켜야 한다

GCP는 서비스마다 API를 프로젝트에서 켜야 쓸 수 있다(`container.googleapis.com`, `compute.googleapis.com` 등). Terraform으로 클러스터를 만들 때 API가 꺼져 있으면 실패한다. API 활성화를 별도 리소스(`google_project_service`)로 두고 의존 관계를 건다.

## 릴리스 채널과 유지보수

GKE는 릴리스 채널(Rapid, Regular, Stable)에 따라 **자동으로 업그레이드**된다. 편하지만 중요한 일정과 겹치면 위험하다.

- **유지보수 창:** 업그레이드가 일어나도 되는 시간대를 지정한다.
- **유지보수 제외:** 특정 기간 업그레이드를 막는다. 시연·이벤트 기간에 건다.
- 단, **노드 자동 복구**는 제외 기간에도 동작한다. 노드가 비정상이면 새로 만든다. "아무것도 안 바뀐다"고 기대하면 안 된다.

## 노드 풀을 0으로 줄이기

비용을 줄이려고 노드 풀을 0으로 줄일 때는 순서가 있다.

1. 자동 확장(autoscaling)을 먼저 끄거나 최소값을 0으로 둔다. 안 그러면 최소값으로 다시 올라온다.
2. `gcloud container clusters resize … --num-nodes 0`
3. 관리형 인스턴스 그룹(MIG)의 목표 크기가 실제로 0인지 확인한다.

PersistentVolume 디스크는 남는다. 다시 늘리면 파드가 같은 디스크에 붙는다.

## 체크리스트

- [ ] GCP 방화벽을 태그·서비스 계정 기준으로 설명할 수 있다
- [ ] Cloud NAT 출발 IP를 고정했다
- [ ] 노드·파드·서비스 대역이 다른 네트워크와 겹치지 않는다
- [ ] 릴리스 채널과 유지보수 제외의 한계(자동 복구)를 안다
