지난 정보처리기사 실기에서 기억나는 문제는 **스텁·드라이버, 응집도, 결합도, 테스트**였다. 실제 출제 경험과 반복 출제 영역이 겹치므로 다음 시험에서는 이 영역을 반드시 득점해야 한다.

> 이 글에서 말하는 5점 후보는 실제 배점을 보장하는 표현이 아니라, 한 문항이 출제되면 반드시 맞히겠다는 개인 득점 목표다.

## 1. 5점 후보 우선순위

| 순위 | 영역            | 합격 기준                           |
| ---- | --------------- | ----------------------------------- |
| 1    | 스텁·드라이버   | 하향식·상향식 문장만 보고 즉시 구분 |
| 2    | 결합도          | 6종류의 식별 키워드 구분            |
| 3    | 응집도          | 7종류의 식별 키워드 구분            |
| 4    | 테스트 커버리지 | 문장·결정·조건·조건/결정 구분       |
| 5    | 디자인 패턴     | 대표 패턴의 한 줄 정의 구분         |

## 2. 스텁과 드라이버

| 구분      | 스텁(Stub)                   | 드라이버(Driver)                     |
| --------- | ---------------------------- | ------------------------------------ |
| 통합 방향 | 하향식                       | 상향식                               |
| 대체 대상 | 아직 구현되지 않은 하위 모듈 | 아직 구현되지 않은 상위 모듈         |
| 역할      | 호출되면 단순 결과 반환      | 하위 모듈 호출, 입력 전달, 결과 확인 |

```text
하향식 → 하위 모듈 대체 → 스텁
상향식 → 상위 모듈 대체 → 드라이버
```

암기:

```text
하스상드
하향식은 스텁, 상향식은 드라이버
```

### 문제 식별법

```text
“하위 모듈을 대신해 단순 결과를 반환” → 스텁
“상위 모듈을 대신해 하위 모듈을 호출” → 드라이버
```

## 3. 결합도

결합도는 모듈 사이의 의존 정도다. **낮을수록 좋은 설계**다.

### 강함 → 약함

```text
내용 → 공통 → 외부 → 제어 → 스탬프 → 자료
```

암기:

```text
내공외제스자
```

| 결합도        | 식별 키워드                                       |
| ------------- | ------------------------------------------------- |
| 내용 결합도   | 다른 모듈 내부의 변수·기능을 직접 참조하거나 변경 |
| 공통 결합도   | 여러 모듈이 전역 데이터 영역을 공유               |
| 외부 결합도   | 외부 장치, 프로토콜, 파일 형식을 함께 사용        |
| 제어 결합도   | 플래그나 제어 요소를 전달하여 상대 흐름을 결정    |
| 스탬프 결합도 | 배열, 객체, 구조체, 레코드 전체를 전달            |
| 자료 결합도   | 필요한 단순 데이터만 매개변수로 전달              |

### 바로 맞히는 키워드

```text
내부 직접 접근 = 내용
전역 변수 = 공통
장치·프로토콜·파일 = 외부
제어 플래그 = 제어
구조체·배열·객체 = 스탬프
필요한 값만 전달 = 자료
```

## 4. 응집도

응집도는 모듈 내부 구성 요소의 관련성이다. **높을수록 좋은 설계**다.

### 강함 → 약함

```text
기능 → 순차 → 교환 → 절차 → 시간 → 논리 → 우연
```

암기:

```text
기순교절시논우
```

| 응집도               | 식별 키워드                                |
| -------------------- | ------------------------------------------ |
| 기능적 응집도        | 모든 요소가 하나의 명확한 기능 수행        |
| 순차적 응집도        | 앞 활동의 출력이 다음 활동의 입력          |
| 교환적·통신적 응집도 | 여러 활동이 동일한 입력과 출력 데이터 사용 |
| 절차적 응집도        | 관련 기능을 정해진 순서대로 수행           |
| 시간적 응집도        | 초기화·종료처럼 같은 시점에 실행되는 기능  |
| 논리적 응집도        | 유사 기능 중 제어값에 따라 하나를 선택     |
| 우연적 응집도        | 관련 없는 기능을 임의로 모음               |

### 헷갈리는 세 가지

```text
출력이 다음 입력 → 순차적
같은 데이터를 사용 → 교환적
단순히 정해진 순서 → 절차적
```

## 5. 결합도와 응집도 비교

```text
결합도: 모듈과 모듈 사이 → 낮게
응집도: 모듈 내부 → 높게
```

좋은 모듈 설계는 **낮은 결합도와 높은 응집도**를 가진다.

## 6. 테스트 기본 원리

| 원리                 | 의미                                                    |
| -------------------- | ------------------------------------------------------- |
| 완벽한 테스트 불가능 | 모든 입력과 실행 경로를 전부 시험할 수 없음             |
| 결함 집중            | 소수 모듈에서 대부분의 결함 발견                        |
| 파레토 법칙          | 약 20% 코드에서 약 80% 결함 발견                        |
| 살충제 패러독스      | 같은 테스트를 반복하면 새 결함 발견이 어려워짐          |
| 정황 의존            | 시스템 특성과 환경에 따라 테스트 방법이 달라짐          |
| 오류-부재의 궤변     | 결함이 없어도 사용자 요구를 만족하지 못하면 품질이 낮음 |
| 조기 테스트          | 개발 초기에 테스트할수록 수정 비용 감소                 |

```text
동일 테스트 반복 → 살충제 패러독스
일부 모듈에 결함 집중 → 결함 집중·파레토
결함 0이지만 요구 미충족 → 오류-부재의 궤변
```

## 7. 정적 테스트와 동적 테스트

| 구분          | 정적 테스트                  | 동적 테스트          |
| ------------- | ---------------------------- | -------------------- |
| 프로그램 실행 | 실행하지 않음                | 실행함               |
| 대상          | 명세서, 설계서, 소스 코드    | 실행 가능한 프로그램 |
| 예            | 동료검토, 워크스루, 인스펙션 | 화이트박스, 블랙박스 |

### 리뷰 유형

| 유형                  | 특징                                               |
| --------------------- | -------------------------------------------------- |
| 동료검토(Peer Review) | 동료가 산출물을 검토                               |
| 워크스루(Walkthrough) | 작성자가 설명하며 검토, 비교적 비공식적            |
| 인스펙션(Inspection)  | 훈련된 검토자가 절차와 체크리스트에 따라 공식 검토 |

## 8. 화이트박스 테스트

프로그램 내부 구조, 제어 흐름, 조건과 경로를 기준으로 테스트한다.

| 기법             | 핵심                                            |
| ---------------- | ----------------------------------------------- |
| 기초 경로 검사   | 제어 흐름 그래프와 순환 복잡도로 독립 경로 검사 |
| 조건 검사        | 논리 조건 검사                                  |
| 루프 검사        | 반복문의 시작·종료·반복 횟수 검사               |
| 데이터 흐름 검사 | 변수 정의와 사용 위치 검사                      |

## 9. 테스트 커버리지

| 커버리지              | 만족 조건                                    |
| --------------------- | -------------------------------------------- |
| 문장 커버리지         | 모든 실행문을 한 번 이상 실행                |
| 결정·분기 커버리지    | 전체 결정식의 참과 거짓을 모두 실행          |
| 조건 커버리지         | 각 개별 조건의 참과 거짓을 모두 실행         |
| 조건/결정 커버리지    | 개별 조건과 전체 결정 결과 모두 참·거짓 실행 |
| 변경 조건/결정(MC/DC) | 각 조건이 결정 결과에 독립적으로 영향        |
| 다중 조건 커버리지    | 개별 조건의 가능한 모든 조합 실행            |

### 예제

```c
if (A || B) {
    execute();
}
```

- 문장 커버리지: `execute()`가 한 번 실행되면 만족
- 결정 커버리지: `A || B` 전체 결과가 참·거짓을 모두 가져야 함
- 조건 커버리지: A와 B 각각이 참·거짓을 모두 가져야 함

```text
실행문 = 문장
전체 판단 결과 = 결정·분기
판단문 안의 개별식 = 조건
```

## 10. 블랙박스 테스트

내부 코드를 보지 않고 요구사항과 입출력 명세를 기준으로 테스트한다.

| 기법             | 핵심                                              |
| ---------------- | ------------------------------------------------- |
| 동등 분할        | 입력 영역을 유효·무효 그룹으로 나누어 대표값 선택 |
| 경곗값 분석      | 경계값과 경계 바로 전·후를 검사                   |
| 결정 테이블      | 조건과 행동의 조합을 표로 검사                    |
| 상태 전이        | 이벤트에 따른 상태 변화 검사                      |
| 원인-효과 그래프 | 입력 조건과 출력 결과 관계를 그래프로 분석        |
| 오류 추정        | 경험을 바탕으로 오류 가능성이 높은 부분 검사      |

```text
나이 허용 범위 20~60
경곗값 후보: 19, 20, 21, 59, 60, 61
```

## 11. 테스트 단계

| 단계          | 대상                            |
| ------------- | ------------------------------- |
| 단위 테스트   | 함수, 클래스, 모듈 등 최소 단위 |
| 통합 테스트   | 모듈 사이 인터페이스와 상호작용 |
| 시스템 테스트 | 완성된 전체 시스템              |
| 인수 테스트   | 사용자 요구 충족 여부           |

### 인수 테스트 유형

| 유형        | 의미                                        |
| ----------- | ------------------------------------------- |
| 알파 테스트 | 개발자 환경에서 사용자가 테스트             |
| 베타 테스트 | 실제 사용자 환경에서 제한된 사용자가 테스트 |

## 12. 통합 테스트 전략

| 전략     | 방식                        | 더미 모듈       |
| -------- | --------------------------- | --------------- |
| 하향식   | 최상위 모듈부터 아래로 통합 | 스텁            |
| 상향식   | 최하위 모듈부터 위로 통합   | 드라이버        |
| 빅뱅     | 모든 모듈을 한 번에 통합    | 일반적으로 없음 |
| 샌드위치 | 하향식과 상향식을 함께 진행 | 스텁과 드라이버 |

## 13. 테스트 오라클

테스트 결과가 올바른지 판단하기 위해 기대 결과를 제공하는 장치 또는 기준이다.

| 오라클             | 핵심                                   |
| ------------------ | -------------------------------------- |
| 참 오라클          | 모든 입력에 정확한 결과 제공           |
| 샘플링 오라클      | 특정 입력에만 결과 제공                |
| 추정 오라클        | 일부 입력은 정확한 결과, 나머지는 추정 |
| 일관성 검사 오라클 | 이전 실행 결과와 현재 결과 비교        |

## 14. 요구사항

| 구분              | 의미                                       |
| ----------------- | ------------------------------------------ |
| 기능적 요구사항   | 시스템이 수행해야 할 기능과 입출력         |
| 비기능적 요구사항 | 성능, 보안, 신뢰성, 자원, 운영, 품질, 제약 |

### 요구사항 개발 순서

```text
도출 → 분석 → 명세 → 확인
```

| 단계 | 주요 활동                                   |
| ---- | ------------------------------------------- |
| 도출 | 인터뷰, 설문, 브레인스토밍 등으로 요구 수집 |
| 분석 | 충돌, 범위, 우선순위 분석과 모델링          |
| 명세 | 요구사항을 명확하고 검증 가능하게 문서화    |
| 확인 | 검토, 프로토타이핑, 테스트 케이스로 검증    |

## 15. UML 관계

| 관계   | 표기·의미                                      |
| ------ | ---------------------------------------------- |
| 연관   | 실선, 객체 사이의 구조적 관계                  |
| 의존   | 점선 화살표, 한 요소의 변경이 다른 요소에 영향 |
| 일반화 | 빈 삼각형 실선, 상속 관계                      |
| 실체화 | 빈 삼각형 점선, 인터페이스 구현                |
| 집약   | 빈 마름모, 약한 전체-부분 관계                 |
| 합성   | 채운 마름모, 강한 전체-부분·생명주기 공유      |

```text
부분이 독립적으로 존재 가능 → 집약
전체가 사라지면 부분도 함께 소멸 → 합성
```

## 16. 대표 디자인 패턴

### 생성 패턴

| 패턴             | 한 줄 정의                            |
| ---------------- | ------------------------------------- |
| Singleton        | 인스턴스를 하나만 생성                |
| Factory Method   | 객체 생성을 하위 클래스에 위임        |
| Abstract Factory | 관련 객체군을 구체 클래스 없이 생성   |
| Builder          | 복잡한 객체의 생성 과정과 표현을 분리 |
| Prototype        | 기존 객체를 복제하여 새 객체 생성     |

### 구조 패턴

| 패턴      | 한 줄 정의                               |
| --------- | ---------------------------------------- |
| Adapter   | 호환되지 않는 인터페이스를 변환          |
| Bridge    | 기능 계층과 구현 계층을 분리             |
| Composite | 단일·복합 객체를 트리로 동일 취급        |
| Decorator | 객체를 감싸 기능을 동적으로 추가         |
| Facade    | 복잡한 하위 시스템에 단순 통합 창구 제공 |
| Flyweight | 객체를 공유하여 메모리 절약              |
| Proxy     | 대리 객체가 실제 객체 접근을 제어        |

### 행위 패턴

| 패턴            | 한 줄 정의                             |
| --------------- | -------------------------------------- |
| Observer        | 상태 변화를 의존 객체에 통지           |
| Strategy        | 알고리즘을 캡슐화하여 교체             |
| Iterator        | 내부 구조를 노출하지 않고 순회         |
| Command         | 요청을 객체로 캡슐화                   |
| State           | 상태에 따라 객체 행동 변경             |
| Template Method | 알고리즘 골격은 상위, 세부 구현은 하위 |

```text
인터페이스 변환 = Adapter
기능과 구현 분리 = Bridge
접근 대리 = Proxy
기능을 감싸 추가 = Decorator
상태 변경 통지 = Observer
알고리즘 교체 = Strategy
```

## 17. 형상 관리

소프트웨어 생명주기 동안 발생하는 산출물의 변경을 체계적으로 통제하고 무결성을 유지하는 활동이다.

```text
형상 식별 → 버전 제어 → 변경 제어 → 형상 감사 → 상태 보고
```

| 용어        | 의미                            |
| ----------- | ------------------------------- |
| 체크아웃    | 저장소에서 작업 사본 가져오기   |
| 체크인·커밋 | 변경사항을 저장소에 반영        |
| 브랜치      | 독립적인 개발 흐름 생성         |
| 병합        | 서로 다른 개발 흐름의 변경 통합 |

## 18. 최종 5점 암기 카드

```text
하향식=스텁, 상향식=드라이버
결합도는 낮게, 응집도는 높게
결합도: 내공외제스자
응집도: 기순교절시논우
문장=실행문
결정=전체 참·거짓
조건=개별 조건 참·거짓
동등 분할=대표 그룹
경곗값=경계 전·경계·경계 후
Adapter=인터페이스 변환
Bridge=기능과 구현 분리
Observer=상태 변화 통지
Strategy=알고리즘 교체
기능 요구=무엇을 수행하는가
비기능 요구=성능·보안·품질·제약
```

시험에서는 긴 설명을 전부 읽기 전에 `하향식`, `전역`, `구조체 전체`, `다음 입력`, `개별 조건`, `경계`, `인터페이스 변환` 같은 식별어에 먼저 밑줄을 긋는다. 식별어와 정답을 한 쌍으로 기억하면 단답형 풀이 시간이 크게 줄어든다.
