## 이 글에서 답할 면접 질문

- AWS의 이 서비스는 GCP와 Azure에서 무엇에 해당하는가?
- 세 클라우드의 IAM은 어떻게 다른가? 같은 "역할"이라는 말이 같은 뜻인가?
- AWS VPC와 GCP VPC의 가장 큰 차이는?
- 회사가 멀티 클라우드를 해야 하는가? 하지 말아야 할 때는?
- "벤더 종속을 피한다"는 건 구체적으로 무엇을 피한다는 뜻인가?
- 여러 클라우드에서 같은 앱을 돌리려면 무엇을 표준화하고 무엇을 각 클라우드에 맡기는가?
- 온프레와 클라우드, 클라우드와 클라우드는 어떻게 연결하고, 서로를 어떻게 인증하는가?

## 개념과 배경

### 멀티 클라우드라는 말의 세 가지 뜻

면접에서 "멀티 클라우드 경험"을 물을 때, 실제로는 세 가지 다른 상황을 가리킬 수 있다. 먼저 어느 쪽인지 정리해야 답이 흐트러지지 않는다.

1. **업무별로 다른 클라우드**: 주력 서비스는 AWS, 데이터 분석은 GCP, 사내 업무는 Azure. 가장 흔한 형태다. 한 앱이 여러 클라우드에 걸치지는 않는다.
2. **같은 앱을 여러 클라우드에**: 한 클라우드가 통째로 장애가 나도 다른 클라우드에서 서비스를 이어 간다. 가장 어렵고 비싸다.
3. **하이브리드**: 온프레 데이터센터와 클라우드를 함께 쓴다. 대기업과 통신사처럼 기존 설비가 큰 회사에서 현실적인 형태다.

"멀티 클라우드를 한다"고 할 때 대부분의 회사는 1번 또는 3번이다. 2번은 규제, 대형 고객 요구, 전략적 협상력 같은 분명한 이유가 있을 때만 한다. 이 구분을 먼저 말하면 "유행어로 멀티 클라우드를 말하는 사람"과 구별된다.

### 서비스 대응표

먼저 지도부터 그린다. 이름은 다르지만 대응하는 서비스다. 다만 **대응한다는 것이 같다는 뜻은 아니다**. 차이는 다음 절에서 다룬다.

| 영역 | AWS | GCP | Azure |
|---|---|---|---|
| 가상 머신 | EC2 | Compute Engine | Virtual Machines |
| 관리형 쿠버네티스 | EKS | GKE | AKS |
| 서버리스 컨테이너 | App Runner, Fargate | Cloud Run | Container Apps |
| 함수 | Lambda | Cloud Run functions | Azure Functions |
| 가상 네트워크 | VPC | VPC | VNet |
| 오브젝트 스토리지 | S3 | Cloud Storage | Blob Storage |
| 관리형 RDB | RDS, Aurora | Cloud SQL, AlloyDB | Azure SQL, Database for PostgreSQL |
| 전역 RDB | Aurora DSQL 등 | Spanner | Cosmos DB(다중 모델) |
| NoSQL 키-값 | DynamoDB | Firestore, Bigtable | Cosmos DB |
| 데이터 웨어하우스 | Redshift | BigQuery | Synapse, Fabric |
| 메시지 큐·이벤트 | SQS, SNS, EventBridge | Pub/Sub | Service Bus, Event Grid |
| DNS | Route 53 | Cloud DNS | Azure DNS |
| CDN | CloudFront | Cloud CDN | Front Door |
| 키 관리 | KMS | Cloud KMS | Key Vault |
| 비밀값 | Secrets Manager | Secret Manager | Key Vault |
| 모니터링·로그 | CloudWatch | Cloud Monitoring·Logging | Azure Monitor |
| IaC(자체) | CloudFormation | Infrastructure Manager | ARM·Bicep |

이 표는 외우는 것보다 **"새 클라우드를 만나면 이 행들을 채워 보는" 습관**이 중요하다. 면접에서 모르는 서비스를 물으면 "그건 AWS의 무엇에 해당하는 서비스로 이해하고 있습니다"라고 연결하면 된다.

## 깊게 1: 이름은 같아도 다른 것 — IAM

세 클라우드 모두 "역할", "정책", "권한"이라는 단어를 쓰지만 모델이 다르다. 이 차이를 설명할 수 있느냐가 멀티 클라우드 면접의 핵심이다.

### AWS: 정책 문서를 주체나 자원에 붙인다

- 권한은 **JSON 정책 문서**로 쓴다. "어떤 Action을 어떤 Resource에 어떤 Condition에서 Allow/Deny".
- 정책을 **주체**(사용자, 그룹, 역할)에 붙이거나(신원 기반 정책), **자원**(S3 버킷, KMS 키 등)에 붙인다(자원 기반 정책).
- **역할**(role)은 "누군가가 잠시 빌려 쓰는 신원"이다. 역할에는 두 정책이 있다. 이 역할로 무엇을 할 수 있는지(권한 정책)와 누가 이 역할을 빌릴 수 있는지(신뢰 정책).
- 평가 규칙: 명시적 Deny가 하나라도 있으면 거부, 없으면 Allow가 있어야 허용. 여기에 SCP, 권한 경계, 세션 정책이 상한선으로 겹친다.

### GCP: 계층의 자원에 "누가 어떤 역할"을 묶는다

- 권한은 **역할**(role, 권한 묶음)과 **주체**(principal)를 자원에 **바인딩**하는 방식이다. "이 프로젝트에서 이 그룹은 `roles/compute.viewer`".
- 바인딩은 조직·폴더·프로젝트·개별 자원 어디에나 할 수 있고 **아래로 상속**된다. 위에서 준 권한을 아래에서 뺄 수는 없다(거부 정책이라는 별도 기능은 있다).
- GCP의 "역할"은 AWS의 "역할"과 전혀 다르다. AWS의 역할은 빌려 쓰는 신원이고, GCP의 역할은 권한 목록이다. AWS의 역할에 가장 가까운 GCP 개념은 **서비스 계정**이다.

### Azure: 범위에 역할 할당

- **RBAC 역할 할당** = 주체 + 역할 정의 + 범위. 범위는 관리 그룹, 구독, 리소스 그룹, 개별 자원.
- 신원은 **Entra ID**에 있다. 사람, 그룹, 서비스 주체(앱 등록), **관리 ID**(Azure 자원에 붙는 신원).
- Entra ID 자체의 역할(디렉터리 관리)과 Azure 자원의 RBAC 역할은 별개의 체계다. 헷갈리기 쉽다.

| 질문 | AWS | GCP | Azure |
|---|---|---|---|
| 권한 단위 | 정책 문서 | 역할(권한 묶음) | 역할 정의 |
| 어디에 붙나 | 주체 또는 자원 | 계층의 자원에 바인딩 | 범위에 할당 |
| 프로그램 신원 | IAM 역할 | 서비스 계정 | 관리 ID, 서비스 주체 |
| 상한선 | SCP, 권한 경계 | 조직 정책, 거부 정책 | Azure Policy, 거부 할당 |

### 면접에서 쓰는 비교 한 줄

"AWS는 정책 문서를 주체나 자원에 붙이는 모델이고, GCP는 계층 구조의 자원에 주체와 역할을 바인딩해서 상속시키는 모델이며, Azure는 Entra ID의 주체에 범위를 지정해 역할을 할당하는 모델입니다. 그래서 같은 '역할'이라는 단어도 AWS에서는 빌려 쓰는 신원, GCP와 Azure에서는 권한 묶음을 뜻합니다."

## 깊게 2: 네트워크의 범위와 방화벽

### VPC는 리전 단위인가, 전역인가

| 항목 | AWS | GCP | Azure |
|---|---|---|---|
| VPC·VNet 범위 | 리전 | **전역** | 리전 |
| 서브넷 범위 | 가용 영역(AZ) | 리전 | 리전 |
| 리전 간 연결 | 피어링·TGW 필요 | 같은 VPC면 기본 연결 | 피어링 필요 |

- **AWS**: VPC는 리전 하나에 속하고, 서브넷은 AZ 하나에 속한다. 그래서 고가용성 설계는 "AZ마다 서브넷을 하나씩" 만드는 것에서 시작한다.
- **GCP**: VPC 하나가 전 세계 리전에 걸칠 수 있고, 서브넷은 리전 단위(그 리전의 모든 존에 걸침)다. 서울 서브넷과 도쿄 서브넷이 같은 VPC 안에 있으면 따로 연결하지 않아도 사설 IP로 통신한다.
- **Azure**: VNet은 리전 단위, 서브넷도 리전 단위(존을 가로지른다).

이 차이가 설계에 미치는 영향은 크다. GCP에서는 "전 세계를 VPC 하나로" 설계할 수 있지만, AWS에서는 리전마다 VPC를 만들고 연결해야 한다. 반대로 AWS의 서브넷이 AZ에 묶여 있다는 건, 서브넷만 보고도 어느 AZ인지 알 수 있다는 장점이기도 하다.

### 방화벽: 상태 저장, 붙는 위치

| 항목 | AWS | GCP | Azure |
|---|---|---|---|
| 주된 도구 | 보안 그룹 | VPC 방화벽 규칙·정책 | NSG |
| 붙는 곳 | 네트워크 인터페이스 | VPC (태그·서비스 계정으로 대상 지정) | 서브넷 또는 NIC |
| 상태 저장 | 예 | 예 | 예 |
| 거부 규칙 | 없음(허용만) | 있음(우선순위) | 있음(우선순위) |
| 서브넷 단위 무상태 | NACL | — | — |

- AWS 보안 그룹은 **허용만** 쓸 수 있고, 다른 보안 그룹을 출발지로 지정할 수 있다("웹 서버 그룹에서 오는 것만 허용"). 거부가 필요하면 서브넷 단위의 무상태 NACL을 쓴다.
- GCP 방화벽 규칙은 VPC에 걸고, **네트워크 태그나 서비스 계정**으로 대상 VM을 고른다. 우선순위 숫자로 허용·거부를 섞는다. 계층형 방화벽 정책으로 조직·폴더 단위 규칙도 걸 수 있다.
- Azure NSG는 서브넷이나 NIC에 붙이고 우선순위로 허용·거부를 섞는다. 애플리케이션 보안 그룹(ASG)으로 "역할 이름"을 대상으로 쓸 수 있다.

같은 "포트 443만 열어라"도 클라우드마다 규칙을 거는 위치와 대상 지정 방법이 다르다. 멀티 클라우드에서 보안 정책을 통일하려면 "무엇을 허용할지"는 공통으로 정하고, "어떻게 거는지"는 클라우드별 모듈로 구현한다.

### 로드밸런서

| 종류 | AWS | GCP | Azure |
|---|---|---|---|
| L7 (HTTP) | ALB | 애플리케이션 LB | Application Gateway, Front Door |
| L4 (TCP/UDP) | NLB | 네트워크 LB | Azure Load Balancer |
| 전역 | Global Accelerator, CloudFront | 전역 외부 애플리케이션 LB | Front Door |

GCP의 전역 외부 애플리케이션 로드밸런서는 **애니캐스트 IP 하나**로 전 세계 사용자를 가장 가까운 리전에 보낸다. AWS에서 같은 효과를 내려면 리전별 ALB 앞에 Global Accelerator나 CloudFront, 또는 Route 53 지연 기반 라우팅을 조합한다. "같은 기능을 어떤 조합으로 만드는가"를 아는 것이 멀티 클라우드 설계 능력이다.

## 깊게 3: 왜 멀티 클라우드를 하나, 그리고 하지 말아야 할 때

### 타당한 이유

- **업무 적합성**: 분석은 BigQuery, 사내 시스템은 Microsoft 생태계처럼 각 클라우드의 강점이 다르다.
- **인수합병**: 다른 클라우드를 쓰던 회사를 합치면 자연스럽게 멀티가 된다.
- **규제·고객 요구**: 특정 산업이나 고객이 특정 클라우드, 특정 리전, 이중 공급자를 요구한다.
- **협상력**: 한 공급자에 완전히 묶이지 않으면 가격·조건 협상에서 유리하다.
- **극단적 가용성 요구**: 한 클라우드 전체 장애도 견뎌야 하는 서비스.

### 하지 말아야 할 때

- **가용성을 이유로 무조건 하려 할 때**: 대부분의 장애는 리전 하나, 서비스 하나 단위다. 같은 클라우드 안에서 멀티 AZ·멀티 리전으로 충분한 경우가 많고, 비용은 훨씬 싸다.
- **팀이 한 클라우드도 아직 깊게 못 다룰 때**: 두 클라우드를 얕게 다루면 두 배로 위험하다.
- **데이터가 크고 자주 오갈 때**: 클라우드 사이 데이터 전송 비용과 지연이 이점을 다 먹는다.

면접에서는 "멀티 클라우드는 목적이 아니라 수단"이라는 태도를 보여 주는 것이 좋다. 그리고 비용을 말한다. 사람(두 클라우드 전문성), 도구(관측·보안 도구 이중화), 데이터 전송, 최소 공통분모 설계로 잃는 기능.

## 깊게 4: 종속은 여러 층에 있다

"벤더 종속을 피한다"를 구체적으로 말할 수 있어야 한다. 종속은 한 층이 아니다.

| 층 | 무엇에 묶이나 | 옮기기 난이도 |
|---|---|---|
| 컴퓨트 | VM 이미지, 인스턴스 타입 | 낮음 (컨테이너로 풀림) |
| 관리형 서비스 | DynamoDB, BigQuery, Lambda 이벤트 | 높음 |
| 데이터 | 데이터의 양과 위치 | 매우 높음 (데이터 중력) |
| IAM·보안 | 정책 모델, 신원 | 높음 |
| 네트워크 | 구조, 전용선, IP | 중간~높음 |
| 사람·도구 | 기술, 운영 절차, 대시보드 | 높음 |

- **데이터 중력**: 데이터가 쌓이면 그 데이터를 쓰는 서비스가 데이터 옆으로 모인다. 수백 TB를 옮기는 데는 전송 비용과 시간, 정합성 검증이 든다. 실질적으로 가장 강한 종속이다.
- **관리형 서비스**: 고유한 API와 동작(트랜잭션 모델, 일관성, 이벤트 형식)에 앱 코드가 맞춰진다. 바꾸려면 코드를 고쳐야 한다.
- **사람과 도구**: 운영 절차, 알림 규칙, 장애 대응 매뉴얼이 한 클라우드의 콘솔과 지표 이름에 맞춰져 있다.

종속을 완전히 없애는 건 불가능하고, 바람직하지도 않다. 관리형 서비스를 쓰는 이유가 바로 그 고유 기능 때문이기 때문이다. 그래서 질문은 "종속을 피할까"가 아니라 **"어느 층의 종속을 받아들이고, 어느 층은 빠져나올 길을 남길까"**다.

## 깊게 5: 이식성 전략

### 컨테이너와 쿠버네티스

앱을 컨테이너로 만들면 실행 환경이 이미지에 들어가서 "어디서 돌리나"의 차이가 크게 줄어든다. 쿠버네티스는 배포·확장·서비스 디스커버리의 공통 언어를 준다. EKS, GKE, AKS가 모두 같은 쿠버네티스 API를 제공한다.

하지만 쿠버네티스가 모든 차이를 숨겨 주지는 않는다.

- **로드밸런서·인그레스**: 어노테이션과 컨트롤러가 클라우드마다 다르다.
- **스토리지 클래스**: 디스크 종류와 동작이 다르다.
- **파드의 클라우드 권한**: EKS의 IRSA·Pod Identity, GKE의 Workload Identity Federation for GKE, AKS의 Workload ID. 원리는 비슷하지만 설정이 다르다.
- **네트워크(CNI)**: 파드가 VPC IP를 직접 받는 방식인지, 오버레이인지에 따라 IP 계획과 방화벽 규칙이 달라진다.

그래서 "쿠버네티스를 쓰면 이식성이 생긴다"보다 "**앱 계층의 이식성이 생기고, 클러스터 계층의 차이는 클라우드별 설정으로 흡수한다**"가 정확한 답이다.

### Terraform과 클라우드별 모듈

Terraform은 여러 클라우드를 같은 도구, 같은 워크플로(plan → 리뷰 → apply)로 다루게 해 준다. 하지만 **코드는 클라우드마다 다르다**. `aws_vpc`와 `google_compute_network`는 다른 자원이다.

좋은 구조는 이렇다.

```
modules/
  network/aws
  network/gcp
  network/azure
  cluster/aws ...
envs/
  prod-aws  → network/aws 사용
  prod-gcp  → network/gcp 사용
```

- 모듈의 **입력과 출력 모양을 맞춘다**. "이름, 대역, 리전을 받아 서브넷 ID 목록을 내보낸다." 안은 클라우드마다 다르게 구현한다.
- 위 계층(환경 구성)은 같은 모양의 입력으로 어느 클라우드든 조립한다.

### 추상화 층의 함정: 최소 공통분모

모든 클라우드를 하나의 API로 감싸는 추상화 층을 만들면 이식성은 높아진다. 대가는 **세 클라우드가 모두 가진 기능만 쓸 수 있다**는 것이다. BigQuery의 강점도, DynamoDB의 강점도 못 쓴다. 이걸 최소 공통분모 문제라고 부른다.

현실적인 원칙은 다음과 같다.

- **차별화되지 않는 부분은 표준화한다**: 컨테이너, 배포 파이프라인, 설정 주입, 로그 형식, 메트릭 이름, 인증 방식.
- **차별화되는 부분은 그 클라우드의 강점을 쓴다**: 분석, 전역 DB, 특수 하드웨어. 대신 그 부분을 **경계가 분명한 모듈**로 두어, 바꿀 때 영향 범위를 좁힌다.
- **데이터 형식은 열린 형식으로**: Parquet, CSV, 표준 SQL 덤프. 저장소를 바꿔도 데이터를 꺼낼 수 있다.

### 12-Factor 설정

앱이 클라우드를 모르게 하는 가장 쉬운 방법은 **환경에 따라 달라지는 모든 것을 설정으로 빼는 것**이다. DB 주소, 버킷 이름, 큐 주소를 환경 변수나 설정 서비스로 주입하면, 같은 이미지가 어느 클라우드에서든 돈다. 비밀값은 각 클라우드의 비밀 관리자에서 읽되, 읽는 방법을 앱 바깥(CSI 드라이버, 사이드카, 초기화 단계)으로 빼면 앱 코드는 그대로다.

## 깊게 6: 하이브리드 연결과 클라우드 간 신원

### 연결 방식

| 방식 | AWS | GCP | Azure |
|---|---|---|---|
| 인터넷 위 암호화 터널 | Site-to-Site VPN | Cloud VPN (HA VPN) | VPN Gateway |
| 전용선 | Direct Connect | Cloud Interconnect | ExpressRoute |
| 클라우드 간 전용 연결 | 파트너·교차 연결 서비스 | Cross-Cloud Interconnect | 파트너 연결 |

- **VPN**: 빠르게 만들 수 있고 싸다. 인터넷을 지나므로 대역폭과 지연이 일정하지 않다. 전용선의 백업으로도 쓴다.
- **전용선**: 대역폭과 지연이 안정적이고, 대용량 전송 비용 구조가 유리한 경우가 많다. 개통에 시간이 걸리고, 한 회선은 단일 장애점이라 **두 위치에 이중**으로 둔다.
- 경로 교환은 대개 **BGP**로 한다. 각 클라우드의 라우터(AWS VGW·TGW, GCP Cloud Router, Azure 게이트웨이)와 온프레 라우터가 BGP로 대역을 주고받는다.
- IP 대역이 겹치면 연결 자체가 막힌다. 랜딩 존의 IP 계획이 여기서 효과를 낸다.

### 클라우드 간 신원: 키를 주고받지 않는다

A 클라우드의 프로그램이 B 클라우드의 API를 불러야 할 때, B의 장기 키를 A에 저장하는 것이 가장 쉽고 가장 위험하다. 대신 **워크로드 신원 연합**을 쓴다.

```
A의 워크로드
 │ A가 발급한 토큰(OIDC)
 ▼
B의 STS·연합 설정
 │ 발급자·대상·주체 검증
 ▼
B의 임시 자격 증명
```

| 받는 쪽 | 연합 기능 |
|---|---|
| AWS | IAM OIDC 공급자 + `AssumeRoleWithWebIdentity` |
| GCP | Workload Identity Federation (풀·공급자) |
| Azure | 앱 등록·관리 ID의 페더레이션 자격 증명 |

신뢰 조건을 좁히는 것이 핵심이다. "그 발급자가 준 토큰이면 누구든"이 아니라, 특정 주체(특정 서비스 계정, 특정 저장소의 특정 브랜치)만 허용한다. 이 조건이 넓으면 연합 자체가 구멍이 된다.

## 깊게 7: 데이터 전송 비용

클라우드는 대체로 **들어오는 데이터는 무료이거나 싸고, 나가는 데이터는 비싸다**. 그리고 같은 클라우드 안에서도 AZ 사이, 리전 사이 전송에 비용이 붙는 경우가 많다. 정확한 요금은 클라우드, 리전, 양, 계약마다 다르므로 설계할 때 그 시점의 요금표로 계산한다.

설계에 주는 영향:

- **데이터를 쓰는 곳 옆에 데이터를 둔다**. 분석을 다른 클라우드에서 한다면 원본 전체를 매번 옮기지 말고, 필요한 요약·증분만 옮긴다.
- **멀티 클라우드 액티브-액티브**는 동기화 트래픽이 계속 클라우드 사이를 오간다. 비용 모델에 반드시 넣는다.
- **CDN과 캐시**로 사용자에게 나가는 트래픽을 줄인다.
- **같은 리전의 관리형 서비스는 프라이빗 엔드포인트**로 붙여, NAT 처리 비용과 경로를 줄인다.

면접에서 아키텍처를 그릴 때 화살표마다 "이 선으로 하루 얼마나 흐르나, 그건 같은 AZ인가, 리전 간인가, 클라우드 간인가"를 말하면, 비용까지 생각하는 엔지니어로 보인다.

## 깊게 8: 멀티 클라우드 운영

### 관측

클라우드마다 모니터링 도구가 다르다. 각자 쓰면 장애 때 대시보드 세 개를 오간다.

- **수집은 표준으로**: OpenTelemetry로 메트릭·로그·트레이스를 같은 형식으로 낸다.
- **보는 곳은 하나로**: 공통 관측 백엔드(오픈소스 스택이나 상용 SaaS) 한 곳에서 본다.
- 클라우드 고유 지표(관리형 DB, 로드밸런서)는 각 클라우드에서 가져와 같은 곳으로 모은다.
- **이름 규칙**을 통일한다. 서비스 이름, 환경, 리전 라벨이 같아야 한 쿼리로 비교할 수 있다.

### 정책과 보안

- "무엇을 허용하나"는 한 문서로(예: 운영 환경 공개 IP 금지, 암호화 필수), "어떻게 강제하나"는 SCP, 조직 정책, Azure Policy로 각각.
- 쿠버네티스 계층의 정책은 클라우드와 무관하게 같은 도구(OPA Gatekeeper, Kyverno 같은 승인 정책)로 통일할 수 있다.
- 보안 발견 사항을 클라우드별 도구에서 한 곳(SIEM, CSPM 도구)으로 모은다.

### 사람

가장 과소평가되는 비용이다. 두 클라우드를 운영하려면 두 클라우드를 깊게 아는 사람이 당직에 있어야 한다. 그래서 흔한 구조는 "주력 클라우드는 모든 팀이, 보조 클라우드는 플랫폼 팀이 기반을 표준화해서 서비스 팀은 골든 패스로만 쓰게" 하는 것이다.

## 설계 예시: 가상의 통신 회사의 이중 클라우드 구성

가상의 통신 회사가 고객용 "요금 조회" 서비스를 두 클라우드에서 돌리기로 했다. 이유는 대형 법인 고객이 "한 공급자 장애로 서비스가 멈추면 안 된다"는 조건을 계약에 넣었기 때문이다. 주 클라우드는 AWS, 대기는 GCP다.

### 1단계: 무엇을 이중으로 할지 정한다

모든 것을 이중으로 하면 비용이 두 배를 넘는다. 먼저 등급을 나눈다.

- 요금 조회 API와 읽기 데이터: 이중화 대상.
- 요금 계산 배치: 주 클라우드에만. 장애 때는 몇 시간 늦어도 된다.
- 분석: 원래부터 GCP.

### 2단계: 표준화할 것

- 앱은 컨테이너 이미지 하나. 양쪽 쿠버네티스(EKS, GKE)에 같은 매니페스트를 배포하고, 클라우드별 차이(인그레스, 스토리지 클래스, 파드 권한)는 오버레이로 분리한다.
- 설정은 환경 변수로 주입한다. 비밀값은 각 클라우드의 비밀 관리자에서 CSI 드라이버로 마운트한다.
- 관측은 OpenTelemetry로 내보내 한 백엔드에서 본다.
- Terraform 모듈은 `network`, `cluster`, `database`를 클라우드별로 만들고 입출력 모양을 맞춘다.

### 3단계: 데이터

```
[AWS] PostgreSQL(주)
   │ 논리 복제
   ▼ (전용선 또는 VPN)
[GCP] PostgreSQL(읽기 대기)
```

- 쓰기는 주 클라우드에서만 한다. 대기 쪽은 읽기 전용 복제본으로 둔다.
- 복제는 클라우드 간 연결 위로 하고, TLS에서 인증서 검증까지 켠다.
- 복제는 백업이 아니다. 각 클라우드에 독립된 백업을 따로 둔다.

### 4단계: 트래픽 전환

- 앞단은 DNS 장애 조치 또는 클라우드 중립 CDN·프록시로 두 클라우드를 묶는다.
- 주 클라우드 헬스체크가 실패하면 대기로 읽기 트래픽을 보낸다. 쓰기 전환(대기 승격)은 데이터 정합성 확인 절차를 거쳐 사람이 결정한다.
- TTL과 클라이언트 캐시 때문에 DNS 전환은 즉시가 아니라는 점을 계약 조건(RTO)에 반영한다.

### 5단계: 신원과 연결

- AWS의 배포 파이프라인이 GCP에 배포할 때, GCP 키를 저장하지 않고 워크로드 신원 연합으로 임시 권한을 받는다. 신뢰 조건은 특정 파이프라인 역할로만 좁힌다.
- 클라우드 간 연결은 처음엔 HA VPN으로, 복제 트래픽이 커지면 전용 연결을 검토한다.

### 6단계: 검증

- 분기마다 실제로 대기 클라우드로 전환해 본다. 전환 시간, 데이터 차이, 놓친 설정을 기록한다.
- 클라우드 간 전송 비용을 매달 확인한다.

이 예시의 핵심 메시지는 "**전부가 아니라 필요한 것만 이중화하고, 표준화할 층과 클라우드 고유 기능을 쓸 층을 나눈다**"이다.

## 자주 하는 실수

1. **"멀티 클라우드면 가용성이 올라간다"고 단정한다.** 전환을 시험하지 않은 대기 환경은 장애 때 동작하지 않는다. 복잡성 자체가 장애 원인이 되기도 한다.
2. **AWS의 역할과 GCP의 역할을 같은 것으로 설명한다.** 하나는 빌려 쓰는 신원, 하나는 권한 묶음이다.
3. **GCP VPC를 리전 단위로 설계한다.** 전역 VPC의 장점을 못 쓰고, 불필요한 VPC와 피어링이 생긴다.
4. **최소 공통분모로 모든 걸 감싼다.** 각 클라우드의 강점을 다 버리고, 추상화 층 자체가 유지보수 부담이 된다.
5. **데이터 전송 비용을 설계 마지막에 계산한다.** 화살표 하나가 월 비용을 지배할 수 있다.
6. **클라우드 간 인증에 장기 키를 쓴다.** 워크로드 신원 연합으로 바꾼다.
7. **IP 대역 계획 없이 연결부터 한다.** 겹친 대역은 VPN이 연결된 뒤에야 발견된다.
8. **관측을 클라우드별로 둔다.** 장애 때 원인 찾는 시간이 길어진다.

## 면접 질문 10개와 답

**Q1. 멀티 클라우드를 해야 하는가?**

목적에 따라 다릅니다. 업무별로 강점이 다른 클라우드를 쓰는 것, 인수합병, 규제나 고객 요구가 있다면 타당합니다. 단순히 가용성을 위해서라면 같은 클라우드 안의 멀티 AZ·멀티 리전이 대부분 더 싸고 확실합니다. 멀티 클라우드는 사람, 도구, 데이터 전송 비용이 들기 때문에 이유가 분명할 때만 합니다.

> 日本語: マルチクラウドは目的ではなく手段で、理由が明確なときにだけ採用します。

**Q2. AWS, GCP, Azure의 IAM 차이를 설명해 달라.**

AWS는 JSON 정책 문서를 주체나 자원에 붙이는 모델이고, 역할은 빌려 쓰는 신원입니다. GCP는 조직 계층의 자원에 주체와 역할을 바인딩하고 아래로 상속시키며, 역할은 권한 묶음입니다. Azure는 Entra ID의 주체에 역할 정의를 범위를 지정해 할당합니다. 프로그램 신원은 각각 IAM 역할, 서비스 계정, 관리 ID가 대응합니다.

**Q3. AWS VPC와 GCP VPC의 차이는?**

AWS VPC는 리전 단위이고 서브넷은 AZ 단위입니다. GCP VPC는 전역이고 서브넷은 리전 단위라서, 같은 VPC 안이라면 다른 리전끼리도 따로 연결 없이 사설 IP로 통신합니다. 그래서 GCP는 VPC 하나로 여러 리전을 설계할 수 있고, AWS는 리전마다 VPC를 만들어 연결합니다.

> 日本語: AWSのVPCはリージョン単位ですが、GCPのVPCはグローバルで、サブネットがリージョン単位です。

**Q4. 보안 그룹과 GCP 방화벽 규칙의 차이는?**

AWS 보안 그룹은 네트워크 인터페이스에 붙는 상태 저장 방화벽이고 허용 규칙만 있습니다. 다른 보안 그룹을 출발지로 지정할 수 있습니다. GCP 방화벽 규칙은 VPC에 걸고 네트워크 태그나 서비스 계정으로 대상을 고르며, 우선순위로 허용과 거부를 섞습니다. 거부가 필요한 경우 AWS는 서브넷 단위 NACL을 따로 씁니다.

**Q5. 벤더 종속은 어디에 있는가?**

컴퓨트, 관리형 서비스, 데이터, IAM, 네트워크, 사람과 도구의 여러 층에 있습니다. 컴퓨트는 컨테이너로 비교적 쉽게 풀리지만, 데이터 중력과 관리형 서비스의 고유 API가 가장 강한 종속입니다. 그래서 종속을 없애기보다, 어느 층의 종속을 받아들이고 어느 층에 빠져나올 길을 남길지 결정합니다.

**Q6. 쿠버네티스를 쓰면 이식성이 해결되는가?**

앱 계층의 이식성은 크게 좋아집니다. 하지만 인그레스와 로드밸런서, 스토리지 클래스, 파드의 클라우드 권한, CNI는 클라우드마다 다릅니다. 그래서 매니페스트의 공통 부분과 클라우드별 오버레이를 나누고, 클러스터 자체는 클라우드별 Terraform 모듈로 만듭니다.

**Q7. 최소 공통분모 문제란?**

모든 클라우드를 하나의 추상화로 감싸면 세 곳이 모두 가진 기능만 쓸 수 있게 되는 문제입니다. 각 클라우드의 강점을 버리게 되고 추상화 층 자체가 부담이 됩니다. 그래서 차별화되지 않는 부분은 표준화하고, 차별화되는 기능은 경계가 분명한 모듈로 두고 그 클라우드의 강점을 씁니다.

**Q8. 클라우드 A의 서비스가 클라우드 B의 API를 호출할 때 인증은?**

B의 장기 키를 A에 저장하지 않고 워크로드 신원 연합을 씁니다. A가 발급한 OIDC 토큰을 B가 검증해서 임시 자격 증명으로 바꿔 줍니다. 이때 발급자, 대상, 주체 조건을 특정 워크로드로 좁혀야 연합 자체가 구멍이 되지 않습니다.

> 日本語: 長期キーを保存せず、ワークロードIDフェデレーションで一時的な認証情報を受け取ります。

**Q9. 온프레와 클라우드는 어떻게 연결하는가?**

빠르게 시작할 때는 IPsec VPN, 안정적인 대역폭과 지연이 필요하면 Direct Connect, Cloud Interconnect, ExpressRoute 같은 전용선을 씁니다. 전용선은 서로 다른 위치에 이중으로 두고 VPN을 백업으로 둡니다. 경로는 BGP로 교환하고, 연결 전에 IP 대역이 겹치지 않게 계획합니다.

**Q10. 멀티 클라우드 환경의 관측은 어떻게 하는가?**

수집 형식을 OpenTelemetry로 통일하고, 보는 곳은 한 백엔드로 모읍니다. 클라우드 고유 지표도 같은 곳으로 가져오고, 서비스·환경·리전 라벨 이름을 통일해 한 쿼리로 비교할 수 있게 합니다. 장애 때 대시보드 여러 개를 오가지 않는 것이 목표입니다.

1. 서비스 계정이 AWS의 IAM 역할(프로그램이 쓰는 신원)에 가장 가깝다. GCP의 "역할"은 권한의 묶음이다.
2. 아무것도 필요 없다. GCP VPC는 전역이라 같은 VPC의 서브넷끼리는 리전이 달라도 기본으로 라우팅된다. 방화벽 규칙만 허용하면 된다.
