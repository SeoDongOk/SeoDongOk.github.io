Docker와 가상머신(VM)은 모두 애플리케이션을 격리된 환경에서 실행하는 기술이다. 하지만 **격리를 만드는 계층**이 다르다. VM은 하드웨어를 가상화해 각 가상머신이 독립된 운영체제와 커널을 실행하고, 컨테이너는 호스트 커널을 공유하면서 프로세스가 바라보는 시스템 환경을 격리한다.

이 차이를 이해하면 Docker가 왜 가볍고 빠른지, 이미지에 적힌 `ubuntu`나 `debian`이 무엇을 뜻하는지, 그리고 컨테이너가 VM을 완전히 대체하지 않는 이유까지 한 번에 설명할 수 있다.

## Docker가 해결하려던 문제

애플리케이션을 실행하려면 코드 외에도 런타임, 시스템 라이브러리, 패키지 버전, 환경 설정이 필요하다. 개발자의 노트북에서는 정상인데 테스트 서버에서는 실패하는 문제도 대부분 이런 환경 차이에서 발생한다.

VM은 애플리케이션마다 독립적인 운영체제를 제공해 강한 격리를 만들 수 있지만, 단일 애플리케이션을 격리하기 위해 운영체제 전체를 부팅하는 것은 비용이 크다. 메모리와 디스크 사용량이 늘고, 시작과 종료에도 상대적으로 많은 시간이 필요하다.

컨테이너는 애플리케이션과 실행에 필요한 파일을 이미지로 묶고, 호스트의 커널은 공유한다. 그 결과 다음과 같은 장점을 얻는다.

- **환경 일관성**: 동일한 이미지로 개발·테스트·운영 환경의 차이를 줄인다.
- **빠른 시작과 종료**: 새로운 운영체제를 부팅하지 않고 격리된 프로세스를 실행한다.
- **높은 밀도**: 같은 서버에서 일반적으로 더 많은 워크로드를 실행할 수 있다.
- **의존성 격리**: 프로젝트별 런타임과 라이브러리 충돌을 줄인다.
- **배포 단위 표준화**: 이미지 자체를 테스트하고 레지스트리를 통해 배포할 수 있다.

다만 컨테이너 기술 자체가 Docker와 함께 처음 생긴 것은 아니다. Linux에는 이미 프로세스 격리와 리소스 제어 기능이 존재했다. Docker의 중요한 역할은 이러한 기능을 이미지 빌드, 레지스트리 배포, 컨테이너 실행이라는 일관된 개발 경험으로 묶은 것이다.

## VM과 Docker 컨테이너 구조 비교

구조를 단순화하면 다음과 같다.

```text
VM

Application A        Application B
Libraries            Libraries
Guest OS             Guest OS
Guest Kernel         Guest Kernel
────────────── Hypervisor ──────────────
Host OS / Hardware
```

```text
Container

Application A        Application B
Libraries            Libraries
Container A          Container B
──────────── Container Runtime ─────────
Shared Host Kernel
Host OS / Hardware
```

| 구분         | VM                   | Docker 컨테이너                |
| ------------ | -------------------- | ------------------------------ |
| 격리 계층    | 가상 하드웨어        | 운영체제의 프로세스 환경       |
| 운영체제     | VM마다 Guest OS 실행 | 호스트 커널 공유               |
| 커널         | VM마다 독립된 커널   | 같은 호스트의 커널 사용        |
| 시작 방식    | Guest OS 부팅        | 격리된 프로세스 시작           |
| 리소스 사용  | 일반적으로 더 큼     | 일반적으로 더 작음             |
| 격리 경계    | 하이퍼바이저와 VM    | 공유 커널과 컨테이너 보안 설정 |
| 다른 OS 커널 | 실행 가능            | 그대로 실행할 수 없음          |

여기서 “Docker가 빠르다”는 말은 애플리케이션의 연산 자체가 무조건 빨라진다는 뜻이 아니다. 별도의 Guest OS를 부팅하지 않으므로 **환경을 생성하고 애플리케이션을 시작하는 오버헤드가 작다**는 의미에 가깝다.

## 핵심은 OS보다 커널이다

운영체제를 단순화하면 두 영역으로 나눠 볼 수 있다.

1. **커널 공간**: 프로세스, 메모리, 네트워크, 파일시스템, 장치 등을 관리한다.
2. **사용자 공간(User Space)**: 셸, 시스템 라이브러리, 패키지 관리자, 각종 실행 파일이 존재한다.

VM에는 사용자 공간뿐 아니라 독립된 커널도 들어간다. 반면 Linux 컨테이너 이미지에는 애플리케이션이 사용할 사용자 공간의 파일과 설정은 들어가지만, 실행 중 사용할 Linux 커널은 들어가지 않는다.

따라서 Ubuntu 호스트에서 Debian 이미지를 실행해도 컨테이너가 사용하는 커널은 호스트의 Linux 커널이다.

```bash
docker run --rm debian:bookworm uname -a
```

이 명령에서 컨테이너 내부의 `uname`은 Debian 사용자 공간에서 실행되지만, 출력되는 커널 정보는 컨테이너 전용 Debian 커널이 아니라 호스트가 제공한 커널 정보다.

그래서 Docker 이미지 이름에 있는 `ubuntu`, `debian`, `alpine`을 “완전한 운영체제”라고 이해하면 혼란이 생긴다. 더 정확하게는 **해당 배포판의 사용자 공간 파일과 패키지 생태계를 기반으로 만든 이미지**다.

## macOS와 Windows에서는 어떻게 실행될까

Linux 컨테이너는 Linux 커널 기능에 의존한다. macOS는 Linux 커널이 아니므로 macOS용 Docker Desktop에서 Linux 컨테이너를 직접 실행할 수 없다. Docker Desktop이 관리하는 경량 Linux VM을 먼저 실행하고, 그 VM의 Linux 커널 위에서 컨테이너를 구동한다.

```text
macOS
└─ Docker Desktop의 Linux VM
   └─ Linux Kernel
      ├─ Container A
      └─ Container B
```

Windows에서 Linux 컨테이너를 실행할 때도 Linux 커널을 제공하는 가상화 계층이 필요하다. 반대로 Windows 컨테이너는 Windows 커널과의 호환성이 필요하다.

즉, “컨테이너는 호스트 커널을 공유한다”는 설명은 맞지만, Docker Desktop에서는 **사용자가 직접 사용하는 macOS나 Windows가 아니라 Docker가 관리하는 VM의 커널**을 공유할 수 있다는 점까지 함께 기억해야 한다.

## 컨테이너를 만드는 네 가지 핵심 요소

### 1. Namespaces: 보이는 범위를 나눈다

Namespaces는 프로세스마다 시스템을 서로 다르게 보이게 만든다.

- PID Namespace: 컨테이너별 프로세스 목록 격리
- Network Namespace: 네트워크 인터페이스, IP, 라우팅 테이블 격리
- Mount Namespace: 파일시스템 마운트 지점 격리
- UTS Namespace: 호스트 이름과 도메인 이름 격리
- IPC Namespace: 프로세스 간 통신 자원 격리
- User Namespace: 컨테이너 사용자와 호스트 사용자 ID 분리

컨테이너 안에서 PID 1로 보이는 프로세스도 호스트 입장에서는 일반 프로세스 중 하나다. 다만 Namespace 때문에 컨테이너 내부에서는 자신에게 허용된 프로세스와 네트워크만 보인다.

### 2. Cgroups: 사용할 수 있는 양을 제한한다

Cgroups(Control Groups)는 프로세스 그룹의 리소스 사용량을 측정하고 제한한다.

```bash
docker run --memory=512m --cpus=1.0 my-app
```

위 컨테이너는 메모리와 CPU 사용 범위를 제한받는다. Namespaces가 “무엇을 볼 수 있는가”를 다룬다면, Cgroups는 “얼마나 사용할 수 있는가”를 다룬다고 이해하면 쉽다.

### 3. Image: 실행 환경을 담은 불변 템플릿

이미지는 애플리케이션 코드, 런타임, 라이브러리, 설정과 기본 실행 명령을 포함하는 표준화된 패키지다. 여러 읽기 전용 레이어로 구성되며, 이미지를 변경하려면 기존 이미지를 직접 수정하는 것이 아니라 새로운 이미지를 빌드한다.

```text
Dockerfile ── docker build ──> Image
Image      ── docker run   ──> Container
```

### 4. Container: 이미지로 시작한 격리된 프로세스

컨테이너는 이미지의 실행 인스턴스다. 실행할 때 이미지 위에 얇은 쓰기 가능 레이어가 추가된다. 컨테이너 내부에서 생성한 파일은 기본적으로 이 레이어에 저장되므로 컨테이너를 삭제하면 함께 사라질 수 있다.

DB 데이터나 업로드 파일처럼 보존해야 하는 데이터는 볼륨이나 외부 스토리지에 저장해 컨테이너의 생명주기와 분리해야 한다.

## 동일한 이미지가 모든 차이를 없애는 것은 아니다

Docker 이미지는 재현성을 크게 높여 주지만 환경 차이를 완전히 제거하지는 않는다.

- CPU 아키텍처가 `amd64`인지 `arm64`인지 확인해야 한다.
- 호스트 또는 VM의 커널 기능과 버전에 영향을 받을 수 있다.
- 환경 변수, Secret, 네트워크, 볼륨은 이미지 외부 설정이다.
- 외부 DB와 API 같은 의존 서비스의 상태는 이미지로 고정되지 않는다.
- 잘못된 권한이나 특권 컨테이너 설정은 격리를 약화할 수 있다.

따라서 “어디서나 동일하게 실행된다”는 말은 **호환되는 컨테이너 런타임과 올바른 외부 설정이 준비됐을 때 실행 환경의 차이를 크게 줄인다**는 뜻으로 이해하는 것이 정확하다.

## VM과 컨테이너는 경쟁 관계가 아니다

컨테이너는 VM을 완전히 대체하는 기술이 아니다. 실제 클라우드 환경에서는 VM 위에 컨테이너 런타임을 설치하고 여러 컨테이너를 실행하는 구성이 흔하다.

### VM이 더 적합한 경우

- 서로 다른 운영체제나 커널이 필요할 때
- 커널 수준의 더 강한 격리 경계가 필요할 때
- 레거시 애플리케이션이 완전한 OS 환경을 전제로 할 때
- VM 단위의 보안·컴플라이언스 정책을 적용해야 할 때

### 컨테이너가 더 적합한 경우

- 짧은 시간에 애플리케이션을 배포하고 확장해야 할 때
- 개발·CI·운영 환경을 이미지로 통일하고 싶을 때
- 마이크로서비스별 의존성을 분리해야 할 때
- 동일한 인프라에서 여러 워크로드를 효율적으로 운영할 때

VM이 인프라와 커널의 격리를 담당하고, 컨테이너가 애플리케이션의 배포와 실행 단위를 담당하도록 함께 사용할 수도 있다.

## 흔히 혼동하는 표현 정리

| 흔한 표현                          | 더 정확한 설명                                                                    |
| ---------------------------------- | --------------------------------------------------------------------------------- |
| 컨테이너마다 OS가 있다             | 배포판의 사용자 공간 파일은 있지만 별도 커널은 없다                               |
| 컨테이너는 작은 VM이다             | 격리된 프로세스이며 VM과 격리 계층이 다르다                                       |
| 이미지는 실행 중인 서버다          | 이미지는 템플릿이고 컨테이너가 실행 인스턴스다                                    |
| Docker가 컨테이너 기술을 발명했다  | 기존 Linux 격리 기술을 사용하기 쉬운 플랫폼과 배포 방식으로 표준화했다            |
| Docker를 쓰면 어디서나 무조건 같다 | 호환되는 커널·아키텍처·외부 설정이 필요하다                                       |
| 컨테이너는 VM보다 항상 안전하다    | VM이 일반적으로 더 강한 격리 경계를 제공하며 컨테이너 보안은 설정에 크게 좌우된다 |

## 최종 정리

Docker와 VM의 차이는 다음 문장으로 압축할 수 있다.

> VM은 하드웨어를 가상화해 독립적인 운영체제와 커널을 실행하고, Docker 컨테이너는 호스트 커널을 공유하면서 프로세스가 바라보는 실행 환경과 리소스를 격리한다.

Docker의 가벼움은 “운영체제가 아예 없다”에서 오는 것이 아니라 **컨테이너마다 별도의 커널을 부팅하지 않는 구조**에서 나온다. Namespaces가 프로세스의 시야를 나누고, Cgroups가 리소스를 제한하며, 이미지는 실행 환경을 일관된 패키지로 제공한다.

이 기본 구조를 이해한 다음에는 Dockerfile 레이어, 볼륨, 네트워크, Compose와 이미지 최적화로 확장하면 된다. 실습 순서는 [DevOps with Docker 핵심 정리](/blog/2026-10-26-devops-with-docker-mooc-softbank-crash-course)에서 이어서 확인할 수 있다.
