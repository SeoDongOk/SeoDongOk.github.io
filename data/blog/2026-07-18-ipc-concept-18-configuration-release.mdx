## 시험 직전 빈출도

> **우선순위 B · ★★★☆☆**
>
> 형상관리·릴리스는 반복 이력은 있으나 최근 핵심군보다 회차 편차가 큰 보조 득점 영역이다.

- **최소 암기:** 형상 식별·통제·감사·상태보고, 체크인/체크아웃, 베이스라인, 릴리스 노트
- **5점 후보:** 형상관리 4절차=식별→통제→감사→기록(상태보고)
- **판정 기준:** 별점은 Q-Net의 공식 출제 확률이 아니다. 2020년 1회~2026년 1회 복원 목록과 2026 시나공 핵심요약의 실기 출제 이력 표기를 개념군 단위로 교차해 정한 **시험 전날 상대 우선순위**다.

형상 관리는 소프트웨어 생명주기 동안 산출물의 변경을 통제하고 무결성을 유지하는 활동이다. 단순히 Git을 사용하는 것보다 넓은 관리 개념이다.

## 1. 형상 항목

형상 관리 대상으로 식별하고 통제할 필요가 있는 산출물이다.

```text
요구사항 명세서
설계 문서
소스 코드
테스트 케이스와 결과
빌드·배포 스크립트
사용자 문서
라이브러리와 환경 설정
```

## 2. 형상 관리 목적

```text
변경사항 통제
버전과 기준선 관리
산출물 무결성 유지
변경 이력과 책임 추적
정확한 버전의 재현과 배포
```

## 3. 형상 관리 절차

| 활동      | 의미                                   |
| --------- | -------------------------------------- |
| 형상 식별 | 관리할 항목과 이름·버전·기준선 정의    |
| 버전 제어 | 형상 항목의 여러 버전 관리             |
| 형상 통제 | 변경 요청을 검토·승인하고 반영         |
| 형상 감사 | 변경이 승인 내용과 기준에 맞는지 확인  |
| 상태 보고 | 형상 항목과 변경 진행 상태를 기록·보고 |

```text
무엇을 관리할지 = 식별
변경 승인·반영 = 통제
올바르게 반영됐는지 = 감사
현재 상태 기록 = 상태 보고
```

## 4. 기준선

공식 검토와 승인을 거쳐 이후 변경이 통제되는 확정 상태다.

```text
요구사항 기준선
설계 기준선
제품 기준선
```

기준선 이후의 변경은 정식 변경 절차를 거쳐야 한다.

## 5. 버전 관리 방식

| 방식                 | 특징                                      |
| -------------------- | ----------------------------------------- |
| 공유 폴더 방식       | 단순 파일 공유, 충돌과 이력 관리가 어려움 |
| 클라이언트-서버 방식 | 중앙 저장소에서 버전 관리                 |
| 분산 저장소 방식     | 각 개발자가 전체 저장소와 이력을 보유     |

## 6. 버전 관리 용어

| 용어            | 의미                                  |
| --------------- | ------------------------------------- |
| Repository      | 형상 항목과 변경 이력을 저장하는 공간 |
| Checkout·Clone  | 저장소의 작업 사본 가져오기           |
| Commit·Check-in | 변경사항을 저장소에 기록              |
| Update·Pull     | 저장소의 최신 변경을 작업 공간에 반영 |
| Push            | 로컬 변경을 원격 저장소에 전송        |
| Branch          | 독립적인 개발 흐름 생성               |
| Merge           | 서로 다른 변경 흐름 통합              |
| Tag             | 특정 버전에 고정된 이름 부여          |

## 7. 변경 관리 절차

```text
변경 요청 등록
→ 영향 분석
→ 변경 승인·거절
→ 구현
→ 테스트
→ 형상 감사
→ 기준선·문서 갱신
```

변경 통제 위원회(CCB)는 주요 변경 요청의 승인 여부와 우선순위를 결정한다.

## 8. 빌드와 배포

| 용어   | 의미                                    |
| ------ | --------------------------------------- |
| 빌드   | 소스와 자원을 실행 가능한 산출물로 변환 |
| 배포   | 빌드 산출물을 목표 환경에 설치·적용     |
| 릴리스 | 사용자에게 제공하기로 승인된 제품 버전  |

## 9. 배포 전략

| 전략      | 의미                                     |
| --------- | ---------------------------------------- |
| 롤링      | 인스턴스를 순차적으로 새 버전으로 교체   |
| 블루-그린 | 구·신 환경을 병렬 구성하고 트래픽 전환   |
| 카나리    | 일부 사용자·인스턴스에 먼저 배포 후 확대 |
| 빅뱅      | 전체 환경을 한 번에 교체                 |

```text
두 환경 전환 = 블루-그린
소수에게 먼저 = 카나리
순차 교체 = 롤링
```

## 10. 릴리스 노트

개발 과정의 릴리스 정보를 최종 사용자와 관련 조직에 공유하는 문서다.

### 주요 항목

```text
헤더: 문서명, 제품명, 버전, 날짜
개요와 목적
변경·개선 내용
수정한 문제
알려진 문제
영향도
설치·업그레이드·복구 방법
지원 정보와 연락처
```

## 11. Semantic Versioning

```text
MAJOR.MINOR.PATCH
```

| 항목  | 증가 조건               |
| ----- | ----------------------- |
| MAJOR | 호환되지 않는 변경      |
| MINOR | 하위 호환되는 기능 추가 |
| PATCH | 하위 호환되는 버그 수정 |

## 12. CI와 CD

| 용어            | 의미                                                      |
| --------------- | --------------------------------------------------------- |
| 지속적 통합(CI) | 변경을 자주 통합하고 자동 빌드·테스트                     |
| 지속적 전달     | 언제든 배포 가능한 상태까지 자동화, 운영 배포는 승인 가능 |
| 지속적 배포     | 검증 통과 변경을 운영 환경까지 자동 배포                  |

## 13. 시험 직전 암기

```text
관리 대상 정의 = 형상 식별
변경 승인·반영 = 형상 통제
승인대로 반영됐는지 = 형상 감사
현재 변경 상태 = 상태 보고
승인된 확정 상태 = 기준선
변경 승인 조직 = CCB
두 환경 전환 = 블루-그린
일부에 먼저 배포 = 카나리
MAJOR = 호환 깨짐
MINOR = 호환 기능 추가
PATCH = 호환 버그 수정
```
